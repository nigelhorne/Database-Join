  205: =head1 DESCRIPTION
  206: 
  207: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  208: single logical, read-only view.  Each component database is queried
  209: independently through its own C<Database::Abstraction> interface.  The results
  210: are combined using a shared key column (C<join_column>).
  211: In effect, this means that you can view data from more than one database using
  212: an intuitive, non-SQL interface.
  213: 
  214: Every storage format that C<Database::Abstraction> supports works as a
  215: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  216: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  217: within the same join.
  218: 
  219: The module exposes the same read-only API as C<Database::Abstraction>:
  220: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  221: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  222: shortcut.  Callers do not need to know how many underlying databases are
  223: involved.
  224: 
  225: Think of it as a virtual database table that is assembled on demand from
  226: several real tables, one per component database.
  227: 
  228: B<Join backends>
  229: 
  230: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  231: combined source row count.  For small datasets (up to C<max_array_rows>,
  232: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  233: automatically spills source rows into a temporary SQLite database and executes
  234: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  235: size instead of three.  You can also force either path unconditionally with
  236: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  237: 
  238: =head2 Join semantics
  239: 
  240: The C<join_type> parameter controls what happens when a particular key value
  241: exists in some component databases but not all:
  242: 
  243: =over 4
  244: 
  245: =item C<left> (the default)
  246: 
  247: All rows from the I<primary> (first) database are returned.  Columns from
  248: subsequent databases are included where a matching row is found, and simply
  249: absent from the hashref where there is no match.  If you are familiar with
  250: SQL, this is a LEFT OUTER JOIN on the first table.
  251: 
  252: =item C<inner>
  253: 
  254: Only rows whose join-column value is present in I<every> component database
  255: are returned.  This is equivalent to a SQL INNER JOIN.
  256: 
  257: =item C<outer>
  258: 
  259: Every join-column value found in I<any> component database is returned.
  260: Columns from databases that do not have that key value are absent from the
  261: merged row.  This is a FULL OUTER JOIN.
  262: 
  263: =back
  264: 
  265: B<Important override rule:> whenever you pass a query criterion for a column
  266: that belongs to a secondary database, that database automatically acts as an
  267: inner-join partner for that query only -- regardless of C<join_type>.  This
  268: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  269: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  270: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  271: as a WHERE clause would exclude them).
  272: 
  273: =head2 Column ownership and routing
  274: 
  275: At construction time, C<Database::Join> calls C<columns()> on each component
  276: database and builds an internal index that maps every column name to the
  277: database that owns it.
  278: 
  279: When you pass criteria to a query method, each key-value pair is automatically
  280: routed to the right database.  You never need to say which database a column
  281: belongs to.
  282: 
  283: The C<join_column> is special: criteria on it are broadcast to I<all>
  284: databases so that each database fetches only the relevant rows before the
  285: in-memory merge.
  286: 
  287: When the same non-join column name exists in more than one database, the
  288: I<last> database in the C<databases> array wins by default: its value
  289: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  290: preserve both values under distinct names instead.
  291: 
  292: =head1 LIMITATIONS
  293: 
  294: =over 4
  295: 
  296: =item Memory usage (array backend)
  297: 
  298: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  299: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  300: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  301: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  302: 
  303: =item SQLite backend uses a persistent cache file
  304: 
  305: When the SQLite path is active, a single C<.db> file with a randomly generated
  306: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  307: first time a query runs on a given C<Database::Join> object.  Source data is
  308: spilled into that file once; subsequent queries against the same object reuse
  309: the file without re-fetching the source data.
  310: 
  311: The cache is automatically invalidated and rebuilt whenever any source
  312: database's C<updated()> timestamp changes (indicating new data), or when
  313: C<add_database()> is called.
  314: 
  315: The file is deleted when the C<Database::Join> object is destroyed (typically
  316: when it goes out of scope).  At any given moment no more than one such file
  317: exists per object.  The directory must be writable and have enough free space
  318: for the full source data (once, not per-query).
  319: 
  320: =item No chained builder or raw SQL
  321: 
  322: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  323: or C<fetchrow_hashref> instead.
  324: 
  325: =item Single-column equi-join only
  326: 
  327: Joining on more than one column simultaneously, or on expressions, is not
  328: supported.  When the join key has different names in different databases,
  329: use C<join_map> to declare each database's local column name.
  330: 
  331: =item Sort order
  332: 
  333: Results are sorted ascending by C<join_column> by default.  Pass
  334: C<< order_by => 'colname' >> (or C<< order_by => ['colname', 'DESC'] >>)
  335: to any query method to override this.  The array path uses string comparison
  336: (C<cmp>); for accurate numeric ordering on large datasets use the SQLite
  337: backend, which sorts natively by type.
  338: 
  339: =item count() fetches all rows
  340: 
  341: C<count()> executes the full join and counts the resulting rows in Perl.  It
  342: does not push a C<COUNT(*)> query down to the databases.
  343: 
  344: =back

  346: =head1 COMMON PITFALLS
  347: 
  348: =over 4
  349: 
  350: =item The join_column must exist in every component database
  351: 
  352: If even one database is missing the join key column, C<new()> (or
  353: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  354: column has a different local name in some databases.
  355: 
  356: =item Criteria on a removed column are silently dropped
  357: 
  358: If you call C<remove_column('tier')> and later query
  359: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  360: C<carp> warning) and all rows are returned.  Always pass criteria before
  361: removing columns, or restructure your code to avoid this.
  362: 
  363: =item You cannot remove the join column
  364: 
  365: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  366: is required for the merge to work.
  367: 
  368: =item Left join does not guarantee all columns are populated
  369: 
  370: Under a LEFT join, rows from the primary database that have no matching row
  371: in a secondary database will be returned with I<no keys> from that secondary
  372: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  373: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  374: than just C<$row->{score}> when the secondary match is optional.
  375: 
  376: =item Filters act as inner-join partners
  377: 
  378: Any database that has a C<filters> entry is promoted to an inner-join partner,
  379: regardless of C<join_type>.  A row whose join-key value does not appear in
  380: the filtered database's result is removed from the merged output entirely, not
  381: merely missing its secondary columns.  This is intentional but can be
  382: surprising if you expected LEFT join semantics.
  383: 
  384: =item Criteria-merging replaces scalar filters
  385: 
  386: When both a base filter and a query criterion target the same column, and both
  387: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  388: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  389: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  390: the base filter is ignored for that query.
  391: 
  392: =item AUTOLOAD sees the full merged join when filters or join_map are active
  393: 
  394: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  395: (C<< $join->columnname(...) >>) runs the full join query rather than
  396: delegating directly to the owning database.  This is necessary for correctness
  397: but means the result respects all active filters and join-key translations,
  398: which may differ from what the owning database would return on its own.
  399: 
  400: =item Duplicate column names: last database wins (unless collision_prefix is set)
  401: 
  402: When two component databases each have a column called C<notes>, the second
  403: database's value silently overwrites the first in every merged row.  Use
  404: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  405: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  406: (or C<remove_column>) to drop the unwanted duplicate entirely.
  407: 
  408: =item Mutating the filters hashref after construction has no effect
  409: 
  410: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  411: passed to C<add_database>) at the moment of construction.  The original hashref
  412: you passed in is never stored.  If you later modify it -- for example, to
  413: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  414: Construct a new C<Database::Join> object, or use a component
  415: C<Database::Abstraction> that supports dynamic filter modification.
  416: 
  417: =item auto mode may always use the array path for some DAs
  418: 
  419: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  420: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  421: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  422: from C<Database::Abstraction> is treated as uncountable, because the parent
  423: class C<count()> expects a key argument and behaves differently from a
  424: "return total row count" function.  In that case C<Database::Join>
  425: conservatively uses the array path for the whole query, even if the dataset is
  426: large.  To opt in to the SQLite path for such a DA, either add your own
  427: C<count()> override that returns the total row count, implement C<dbi_source()>,
  428: or use C<backend =E<gt> 'sqlite'> unconditionally.
  429: 
  430: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  431: 
  432: When a component database implements C<dbi_source()>, C<Database::Join> always
  433: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  434: for columns in that database>.  The criteria are translated into parameterised
  435: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  436: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  437: force a spill; that restriction has been removed.)
  438: 
  439: =item Broadcast join-column criterion does not force secondaries into inner-join
  440: 
  441: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  442: C<Database::Join> broadcasts it to all component databases so each DA can
  443: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  444: incorrectly counted as "having criteria" for secondary databases, causing
  445: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  446: join-column criterion was present.  The fix: only non-join-column criteria
  447: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  448: a secondary to inner-join status.  The broadcast itself is now a transparent
  449: key-range selector that does not affect join semantics.
  450: 
  451: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  452: 
  453: C<LIKE>, C<NOT LIKE>, C<IN>, and C<NOT IN> are fully supported on the SQLite
  454: backend.  C<LIKE>/C<NOT LIKE> take a scalar pattern; C<IN>/C<NOT IN> take an
  455: arrayref of values.  All are injection-safe because values are passed as bind
  456: parameters, never interpolated.
  457: 
  458:     # LIKE
  459:     my $rows = $join->selectall_arrayref(name => { LIKE => 'A%' });
  460: 
  461:     # IN
  462:     my $rows = $join->selectall_arrayref(tier => { IN => ['gold', 'silver'] });
  463: 
  464:     # NOT IN
  465:     my $rows = $join->selectall_arrayref(tier => { 'NOT IN' => ['bronze'] });
  466: 
  467: C<IN> with an empty arrayref matches no rows (SQL semantics: C<IN ()> is
  468: always false).  C<NOT IN> with an empty arrayref matches all rows (no
  469: constraint added).
  470: 
  471: C<IS NULL> and C<IS NOT NULL> are supported on the SQLite backend using an
  472: explicit operator hashref:
  473: 
  474:     my $rows = $join->selectall_arrayref(score => { 'IS NULL'     => undef });
  475:     my $rows = $join->selectall_arrayref(score => { 'IS NOT NULL' => 1    });
  476: 
  477: The hashref value is ignored; only the key selects the operator.  A bare
  478: C<undef> criterion value (C<< score => undef >>) also generates C<IS NULL>
  479: on the SQLite path.  Note: on the in-memory array path, the component DA
  480: may treat an C<undef> criterion value as C<< no filter >> rather than
  481: C<IS NULL>, so use the explicit hashref form for consistent behaviour
  482: across backends.
  483: 
  484: Any operator not in the supported set is skipped on the SQLite path with a
  485: C<carp> warning.  The array path forwards all operators to the component DA
  486: unchanged, which may or may not honour them.
  487: 
  488: =item Temp file directory must be writable and have free space
  489: 
  490: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  491: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).

  811: =head2 join_map - joining on differently-named columns
  812: 
  813: By default every component database must have a column whose name matches
  814: C<join_column>.  If a database uses a different local name for the join key,
  815: declare the mapping with C<join_map>.
  816: 
  817: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  818: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  819: B<value> is the name that B<that particular database> uses for the join key.
  820: 
  821: Databases not listed in C<join_map> are assumed to already have a column
  822: named C<join_column> and need no entry.
  823: 
  824: Throughout the merged view the join key is I<always> referred to by the name
  825: given in C<join_column>.  The local alias is never exposed in returned rows,
  826: in C<columns()>, or in C<schema()>.

  874: =head2 filters - permanent per-database row filters
  875: 
  876: C<filters> lets you restrict a component database to a subset of its rows
  877: permanently, without repeating the criterion on every query call.
  878: 
  879: Think of it as telling the join: "whenever you query this database, always
  880: add these extra conditions".  Callers never need to specify the restriction
  881: themselves and can never accidentally omit it.
  882: 
  883: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  884: database in the C<databases> array (same numbering as C<join_map>).  Each
  885: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  886: accepts.
  887: 
  888: B<Key-set semantics>
  889: 
  890: A filtered database always acts as an inner-join partner, regardless of the
  891: C<join_type> setting.  Any join-key value that does not pass the filter is
  892: excluded from the merged output entirely -- not just missing its secondary
  893: columns.  This ensures the filter genuinely restricts the view rather than
  894: simply hiding a few fields.
  895: 
  896: B<Criteria merging>
  897: 
  898: When a query call also passes a criterion for a column that already has a base
  899: filter, the two constraints are combined:
  900: 
  901: =over 4
  902: 
  903: =item *

  908: 
  909: =item *
  910: 
  911: When either value is a plain scalar, or the operators conflict, the
  912: query-time criterion wins and the base filter for that column is ignored for
  913: that one call.

  915: =back

  939: =head2 collision_prefix - preserve colliding columns from secondary databases
  940: 
  941: By default, when a column name appears in more than one database the I<last>
  942: database wins: its value silently overwrites earlier ones in merged rows.
  943: This loses data and makes the origin invisible.
  944: 
  945: C<collision_prefix> changes this for secondary databases you designate.
  946: When a secondary database at index N has a column that already exists in the
  947: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  948: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  949: visible: the original column keeps its name (from the earlier database), and
  950: the collision gets the prefixed name.
  951: 
  952: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  953: a secondary database in the C<databases> array (same numbering as C<join_map>).
  954: Each B<value> is the prefix string to prepend.  An index-0 entry is
  955: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  956: preserves the previous last-wins behaviour and changes nothing.
  957: 
  958: Non-colliding columns from a secondary database are always added as-is with
  959: no prefix, whether or not C<collision_prefix> is configured.
  960: 
  961: B<Example -- sales table and products table, both with a "product" column>

  963:     # $sales    columns: id, product, amount, date
  964:     # $products columns: sku, product, price, category

  966: 
  967:     my $join = Database::Join->new(
  968:         databases        => [$sales, $products],

  997: =head2 backend - SQLite join backend for large datasets
  998: 
  999: C<Database::Join> can merge component databases in two different ways,
 1000: controlled by the C<backend> constructor parameter.
 1001: 
 1002: =over 4
 1003: 
 1004: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
 1005: 
 1006: All matching rows are fetched from every component database into Perl hashes
 1007: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
 1008: is roughly three times the combined source data size (one copy per database
 1009: plus one merged copy).
 1010: 
 1011: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1012: 
 1013: C<Database::Join> creates a temporary SQLite database file, spills source
 1014: rows into it (one table per component database), then executes a single SQL
 1015: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1016: source data size.
 1017: 
 1018: The temporary file is created once and reused across multiple query calls on
 1019: the same object (the cache).  Only query-time criteria vary per call; they
 1020: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1021: automatically rebuilt when any source database's C<updated()> timestamp
 1022: changes.  The file is deleted when the object is destroyed (goes out of
 1023: scope).  See I<Temporary file: name, location, and lifetime> below for
 1024: details.
 1025: 
 1026: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
 1027: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
 1028: 
 1029: =item C<backend =E<gt> 'auto'> (default)
 1030: 
 1031: C<Database::Join> counts the total rows from all component databases cheaply
 1032: -- without fetching them -- and then decides:
 1033: 
 1034: =over 4
 1035: 
 1036: =item *
 1037: 
 1038: If the combined count is less than or equal to C<max_array_rows> (default
 1039: 10,000), use the array path.
 1040: 
 1041: =item *
 1042: 
 1043: If the combined count exceeds C<max_array_rows>, use the SQLite path.
 1044: 
 1045: =back
 1046: 
 1047: For counting to work without fetching, each component database must either
 1048: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
 1049: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
 1050: method in its own package -- not just inherit one from a parent class.  If
 1051: neither is available for a particular database, C<Database::Join> plays it
 1052: safe and uses the array path for the whole query without fetching any rows.
 1053: 
 1054: =back
 1055: 
 1056: B<Choosing max_array_rows>
 1057: 
 1058: The default of 10,000 is a reasonable starting point.  Adjust it to match
 1059: your hardware and typical row width.  For wide rows (many columns or long
 1060: strings) you may want a lower threshold; for narrow rows you can raise it.
 1061: 
 1062: B<Temporary file: name, location, and lifetime>
 1063: 
 1064: When the SQLite path is active, a single temporary SQLite database file acts
 1065: as the join cache for the life of the C<Database::Join> object.
 1066: 
 1067: B<Name>: the filename is randomly generated by C<File::Temp>, for example:
 1068: 
 1069:     /tmp/Cj8xK7mP2Q.db
 1070: 
 1071: The random portion (ten characters) is chosen automatically to avoid
 1072: collisions.  Only the directory is under your control; you cannot specify
 1073: the filename itself.
 1074: 
 1075: B<Location>: controlled by the C<tmpdir> constructor parameter.
 1076: If C<tmpdir> is not specified, C<File::Spec-E<gt>tmpdir()> is used (usually
 1077: C</tmp> on Unix, or the value of the C<TEMP> or C<TMP> environment variable
 1078: on Windows).
 1079: 
 1080: B<Lifetime: one file per object, deleted when the object is destroyed>: the
 1081: file is created on the first query call that uses the SQLite path and kept
 1082: alive until the C<Database::Join> object is destroyed (i.e. when it goes out
 1083: of scope or is explicitly C<undef>-d).  At most one file exists per object at
 1084: any given moment.  Calling C<selectall_arrayref()> ten times on the same
 1085: object creates and uses I<one> file, not ten.
 1086: 
 1087: B<Cache invalidation>: the cache is automatically rebuilt (the old file is
 1088: replaced with a new one) when any source database's C<updated()> return value
 1089: changes, or when C<add_database()> is called.  Base-filter criteria
 1090: (C<filters> constructor parameter) are applied once at build time for spilled
 1091: sources; query-time criteria are applied per-call as SQL C<WHERE> clauses.
 1092: 
 1093: To use a different directory -- for example a RAM-backed filesystem or a
 1094: faster local disk:
 1095: 
 1096:     my $join = Database::Join->new(
 1097:         databases      => [ $db1, $db2 ],
 1098:         join_column    => 'entry',
 1099:         backend        => 'sqlite',
 1100:         tmpdir         => '/dev/shm',     # Linux RAM disk
 1101:     );
 1102: 
 1103: B<Parallel secondary fetches (C<parallel> constructor parameter)>
 1104: 
 1105: By default, component databases are queried sequentially â€” the primary first,
 1106: then each secondary in order.  When the component databases are network- or
 1107: disk-backed and have non-trivial per-query latency, the sequential fetch means
 1108: total latency is the I<sum> of all per-DA latencies.
 1109: 
 1110: Setting C<< parallel => 1 >> in the constructor enables concurrent fetching
 1111: of secondary databases using Perl C<threads>.  With C<parallel => 1> and
 1112: two or more secondary databases (C<n E<gt> 2> total), secondary fetches run in
 1113: parallel after the primary fetch completes; total latency drops to
 1114: I<max(secondary latencies)> instead of I<sum(secondary latencies)>.
 1115: 
 1116:     my $join = Database::Join->new(
 1117:         databases   => [ $customers, $loyalty, $scores ],   # 3 DAs â€” 2 secondaries

 1120:     );
 1121: 
 1122: Requirements and caveats:
 1123: 
 1124: =over 4
 1125: 
 1126: =item *
 1127: 
 1128: The C<threads> module must be available.  Most distributions ship it, but it
 1129: requires a Perl binary compiled with C<-Dusethreads>.  When threads are
 1130: unavailable, a C<carp> warning is emitted and fetching falls back to
 1131: sequential; the result is identical, only slower.
 1132: 
 1133: =item *
 1134: 
 1135: Parallel fetching is only active when the join has three or more total
 1136: databases (C<n E<gt> 2>).  With two databases (one secondary), the thread
 1137: creation overhead exceeds the benefit of concurrency; sequential is used
 1138: regardless of C<parallel>.
 1139: 
 1140: =item *
 1141: 
 1142: Component databases must be safe to call from Perl threads.  In-memory
 1143: databases (CSV, JSON, TSV after slurp) are safe.  DBI-backed databases
 1144: whose handles were created in the same thread may not be safe â€” consult your
 1145: DBD driver's thread documentation.  The array backend is recommended for
 1146: DBI-backed sources; the SQLite backend performs its join in a single SQL
 1147: statement and does not use parallel fetching.
 1148: 
 1149: =item *
 1150: 
 1151: C<parallel => 1> applies to the array backend only.  The SQLite backend
 1152: performs a single SQL JOIN after spilling source data, so per-DA parallelism
 1153: is irrelevant.
 1154: 
 1155: =back
 1156: 
 1157: B<Zero-copy ATTACH (C<dbi_source()> interface)>
 1158: 
 1159: Normally, when the SQLite path is active, rows from each component database
 1160: are fetched one by one and inserted into the temporary SQLite file.  This is
 1161: efficient but does involve INSERT overhead.
 1162: 
 1163: If a component database is itself SQLite-backed and implements a
 1164: C<dbi_source()> method, C<Database::Join> can skip the row-by-row copy
 1165: entirely and instead use C<ATTACH DATABASE> to link the source file directly
 1166: to the temporary join connection.  This is the zero-copy path and is
 1167: significantly faster for large SQLite sources.
 1168: 
 1169: The C<dbi_source()> method must return a hashref with two keys:
 1170: 
 1171: =over 4
 1172: 
 1173: =item C<dbh>
 1174: 
 1175: A connected C<DBD::SQLite> database handle (C<DBI> connection object).
 1176: 
 1177: =item C<table>
 1178: 
 1179: The name of the table in that database that holds the source rows.
 1180: 
 1181: =back
 1182: 
 1183: Example implementation:
 1184: 
 1185:     package My::SQLiteDatabase;
 1186:     use parent 'Database::Abstraction';
 1187: 
 1188:     sub dbi_source {
 1189:         my ($self) = @_;

 1191:             dbh   => $self->{_dbh},      # connected DBD::SQLite handle
 1192:             table => $self->{_table},    # table name in that database
 1193:         };
 1194:     }
 1195: 
 1196:     1;
 1197: 
 1198: The zero-copy ATTACH path is only used when there are no query-time criteria
 1199: for that database in the current call.  When criteria exist, the database is
 1200: queried via C<selectall_arrayref> as usual and the resulting rows are inserted
 1201: into the temporary file.
 1202: 
 1203: B<Result identity>
 1204: 
 1205: Both the array path and the SQLite path produce identical results for any
 1206: given query.  You can switch between them freely without changing callers.
 1207: The C<collision_prefix> column renaming, C<join_map> key translation, and all
 1208: three join types (left, inner, outer) work identically on both paths.

 3580: =head1 SECURITY CONSIDERATIONS
 3581: 
 3582: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3583: generates SQL strings, never opens files, and never calls C<system()>,
 3584: C<exec()>, or C<eval()>.  The security properties described below are
 3585: architectural guarantees, not run-time checks.
 3586: 
 3587: =head2 What Database::Join guarantees
 3588: 
 3589: =over 4
 3590: 
 3591: =item Criteria partition isolation
 3592: 
 3593: Every criterion you pass to a query method is routed to I<exactly one>
 3594: component database (the one that owns that column), or to I<all> databases
 3595: when the criterion is on the join key column.  A hostile value in a criterion
 3596: for column C<name> (owned by database A) will never reach database B.
 3597: 
 3598: =item Unknown columns are rejected before reaching any database
 3599: 
 3600: If a criterion column name is not present in any component database (or has
 3601: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3602: and silently drops the criterion.  No database receives the hostile key.
 3603: 
 3604: =item AUTOLOAD only accepts word-character column names
 3605: 
 3606: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3607: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3608: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3609: C<_>) are additionally blocked with an explicit C<croak>.
 3610: 
 3611: =item No value sanitisation (by design)
 3612: 
 3613: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3614: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3615: responsibility of the underlying C<Database::Abstraction> objects (which use
 3616: parameterised queries).  Preventing XSS or header injection is the
 3617: responsibility of the CGI or web layer that renders the output.
 3618: 
 3619: =item Taint-mode compatible (array path)
 3620: 
 3621: The array merge path contains no C<system()>, C<exec()>, backtick,
 3622: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3623: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3624: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3625: an I<untainted> capture, so the column name used for dispatch is clean under
 3626: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3627: objects; those objects are responsible for handling tainted values at the SQL
 3628: parameterisation layer.
 3629: 
 3630: =item SQLite backend: column names are quoted, values are parametrised
 3631: 
 3632: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3633: All column and table names are double-quoted (SQL identifier quoting) before
 3634: being embedded in statement strings.  All row values are passed to SQLite
 3635: exclusively through DBI prepared statement placeholders -- never by string
 3636: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3637: into the temporary database.
 3638: 
 3639: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3640: unpredictable filename.  No C<system()> or shell command is used to create or
 3641: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3642: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3643: in the generated SQL come from C<columns()>, which is produced by
 3644: C<Database::Abstraction> at construction time -- they are not derived from
 3645: caller-supplied criteria values.
 3646: 
 3647: =item Operator hashref broadcast copy
 3648: 
 3649: When the same join-key criterion (an operator hashref such as
 3650: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3651: database receives its own I<shallow copy> of the hashref.  A component database
 3652: that mutates the hashref's contents at the top level cannot affect what
 3653: subsequent databases receive.
 3654: 
 3655: =item collision_prefix value type guard
 3656: 
 3657: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3658: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3659: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3660: column name, C<columns()> listing, and merged row returned to the caller.  The
 3661: guard fires before any column name is constructed.
 3662: 
 3663: =item Filter deep-copy isolation
 3664: 
 3665: The C<filters> constructor parameter and the C<filter> option of
 3666: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3667: original hashrefs are never stored; post-construction mutation of those
 3668: hashrefs cannot widen or bypass the configured row-security constraints.
 3669: 
 3670: =back
