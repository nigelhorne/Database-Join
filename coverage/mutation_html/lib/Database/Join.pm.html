  173: =head1 DESCRIPTION
  174: 
  175: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  176: single logical, read-only view.  Each component database is queried
  177: independently through its own C<Database::Abstraction> interface.  The results
  178: are combined using a shared key column (C<join_column>).
  179: In effect, this means that you can view data from more than one database using
  180: an intuitive, non-SQL interface.
  181: 
  182: The module exposes the same read-only API as C<Database::Abstraction>:
  183: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  184: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  185: shortcut.  Callers do not need to know how many underlying databases are
  186: involved.
  187: 
  188: Think of it as a virtual database table that is assembled on demand from
  189: several real tables, one per component database.
  190: 
  191: B<Join backends>
  192: 
  193: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  194: combined source row count.  For small datasets (up to C<max_array_rows>,
  195: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  196: automatically spills source rows into a temporary SQLite database and executes
  197: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  198: size instead of three.  You can also force either path unconditionally with
  199: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  200: 
  201: =head2 Join semantics
  202: 
  203: The C<join_type> parameter controls what happens when a particular key value
  204: exists in some component databases but not all:
  205: 
  206: =over 4
  207: 
  208: =item C<left> (the default)
  209: 
  210: All rows from the I<primary> (first) database are returned.  Columns from
  211: subsequent databases are included where a matching row is found, and simply
  212: absent from the hashref where there is no match.  If you are familiar with
  213: SQL, this is a LEFT OUTER JOIN on the first table.
  214: 
  215: =item C<inner>
  216: 
  217: Only rows whose join-column value is present in I<every> component database
  218: are returned.  This is equivalent to a SQL INNER JOIN.
  219: 
  220: =item C<outer>
  221: 
  222: Every join-column value found in I<any> component database is returned.
  223: Columns from databases that do not have that key value are absent from the
  224: merged row.  This is a FULL OUTER JOIN.
  225: 
  226: =back
  227: 
  228: B<Important override rule:> whenever you pass a query criterion for a column
  229: that belongs to a secondary database, that database automatically acts as an
  230: inner-join partner for that query only -- regardless of C<join_type>.  This
  231: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  232: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  233: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  234: as a WHERE clause would exclude them).
  235: 
  236: =head2 Column ownership and routing
  237: 
  238: At construction time, C<Database::Join> calls C<columns()> on each component
  239: database and builds an internal index that maps every column name to the
  240: database that owns it.
  241: 
  242: When you pass criteria to a query method, each key-value pair is automatically
  243: routed to the right database.  You never need to say which database a column
  244: belongs to.
  245: 
  246: The C<join_column> is special: criteria on it are broadcast to I<all>
  247: databases so that each database fetches only the relevant rows before the
  248: in-memory merge.
  249: 
  250: When the same non-join column name exists in more than one database, the
  251: I<last> database in the C<databases> array wins by default: its value
  252: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  253: preserve both values under distinct names instead.
  254: 
  255: =head1 LIMITATIONS
  256: 
  257: =over 4
  258: 
  259: =item Memory usage (array backend)
  260: 
  261: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  262: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  263: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  264: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  265: 
  266: =item SQLite backend uses a persistent cache file
  267: 
  268: When the SQLite path is active, a single C<.db> file with a randomly generated
  269: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  270: first time a query runs on a given C<Database::Join> object.  Source data is
  271: spilled into that file once; subsequent queries against the same object reuse
  272: the file without re-fetching the source data.
  273: 
  274: The cache is automatically invalidated and rebuilt whenever any source
  275: database's C<updated()> timestamp changes (indicating new data), or when
  276: C<add_database()> is called.
  277: 
  278: The file is deleted when the C<Database::Join> object is destroyed (typically
  279: when it goes out of scope).  At any given moment no more than one such file
  280: exists per object.  The directory must be writable and have enough free space
  281: for the full source data (once, not per-query).
  282: 
  283: =item No chained builder or raw SQL
  284: 
  285: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  286: or C<fetchrow_hashref> instead.
  287: 
  288: =item Single-column equi-join only
  289: 
  290: Joining on more than one column simultaneously, or on expressions, is not
  291: supported.  When the join key has different names in different databases,
  292: use C<join_map> to declare each database's local column name.
  293: 
  294: =item Sort order
  295: 
  296: Results are sorted by the C<join_column> value only.  Caller-specified
  297: C<ORDER BY> is not propagated to the component databases.
  298: 
  299: =item count() fetches all rows
  300: 
  301: C<count()> executes the full join and counts the resulting rows in Perl.  It
  302: does not push a C<COUNT(*)> query down to the databases.
  303: 
  304: =back

  306: =head1 COMMON PITFALLS
  307: 
  308: =over 4
  309: 
  310: =item The join_column must exist in every component database
  311: 
  312: If even one database is missing the join key column, C<new()> (or
  313: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  314: column has a different local name in some databases.
  315: 
  316: =item Criteria on a removed column are silently dropped
  317: 
  318: If you call C<remove_column('tier')> and later query
  319: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  320: C<carp> warning) and all rows are returned.  Always pass criteria before
  321: removing columns, or restructure your code to avoid this.
  322: 
  323: =item You cannot remove the join column
  324: 
  325: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  326: is required for the merge to work.
  327: 
  328: =item Left join does not guarantee all columns are populated
  329: 
  330: Under a LEFT join, rows from the primary database that have no matching row
  331: in a secondary database will be returned with I<no keys> from that secondary
  332: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  333: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  334: than just C<$row->{score}> when the secondary match is optional.
  335: 
  336: =item Filters act as inner-join partners
  337: 
  338: Any database that has a C<filters> entry is promoted to an inner-join partner,
  339: regardless of C<join_type>.  A row whose join-key value does not appear in
  340: the filtered database's result is removed from the merged output entirely, not
  341: merely missing its secondary columns.  This is intentional but can be
  342: surprising if you expected LEFT join semantics.
  343: 
  344: =item Criteria-merging replaces scalar filters
  345: 
  346: When both a base filter and a query criterion target the same column, and both
  347: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  348: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  349: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  350: the base filter is ignored for that query.
  351: 
  352: =item AUTOLOAD sees the full merged join when filters or join_map are active
  353: 
  354: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  355: (C<< $join->columnname(...) >>) runs the full join query rather than
  356: delegating directly to the owning database.  This is necessary for correctness
  357: but means the result respects all active filters and join-key translations,
  358: which may differ from what the owning database would return on its own.
  359: 
  360: =item Duplicate column names: last database wins (unless collision_prefix is set)
  361: 
  362: When two component databases each have a column called C<notes>, the second
  363: database's value silently overwrites the first in every merged row.  Use
  364: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  365: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  366: (or C<remove_column>) to drop the unwanted duplicate entirely.
  367: 
  368: =item Mutating the filters hashref after construction has no effect
  369: 
  370: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  371: passed to C<add_database>) at the moment of construction.  The original hashref
  372: you passed in is never stored.  If you later modify it -- for example, to
  373: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  374: Construct a new C<Database::Join> object, or use a component
  375: C<Database::Abstraction> that supports dynamic filter modification.
  376: 
  377: =item auto mode may always use the array path for some DAs
  378: 
  379: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  380: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  381: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  382: from C<Database::Abstraction> is treated as uncountable, because the parent
  383: class C<count()> expects a key argument and behaves differently from a
  384: "return total row count" function.  In that case C<Database::Join>
  385: conservatively uses the array path for the whole query, even if the dataset is
  386: large.  To opt in to the SQLite path for such a DA, either add your own
  387: C<count()> override that returns the total row count, implement C<dbi_source()>,
  388: or use C<backend =E<gt> 'sqlite'> unconditionally.
  389: 
  390: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  391: 
  392: When a component database implements C<dbi_source()>, C<Database::Join> always
  393: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  394: for columns in that database>.  The criteria are translated into parameterised
  395: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  396: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  397: force a spill; that restriction has been removed.)
  398: 
  399: =item Temp file directory must be writable and have free space
  400: 
  401: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  402: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  403: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  404: only the directory is under your control.  The file is created on the first
  405: query and kept alive until the object is destroyed; it is not re-created on
  406: every query call.  If the directory is not writable, or the filesystem is full,
  407: the call will C<croak> with C<error_sqlite_connect>.  Check permissions and
  408: free space if you see that error.
  409: 
  410: =back

  433: =head3 DESCRIPTION
  434: 
  435: Constructs and returns a new C<Database::Join> object.
  436: 
  437: Each element of C<databases> must be an already-instantiated subclass of
  438: C<Database::Abstraction>.  The constructor calls C<columns()> on every
  439: database to build an internal column-routing table and verifies that
  440: C<join_column> (or its local alias from C<join_map>) is present in each one.
  441: 
  442: Columns listed in C<remove_columns> are hidden immediately: they do not appear
  443: in C<columns()>, C<schema()>, or any returned row hashref.  This is equivalent
  444: to calling C<remove_column> once per name after construction.
  445: 
  446: =head3 API SPECIFICATION
  447: 
  448: =head4 Input
  449: 
  450:     databases      => { type => 'arrayref', required => 1 }
  451:                       # One or more Database::Abstraction subclass objects.
  452:                       #
  453:                       # DOMAIN -- EP valid:   non-empty arrayref of blessed DA subclasses.
  454:                       # DOMAIN -- EP invalid: scalar, hashref, or absent => croak.
  455:                       # DOMAIN -- BVA size:   minimum 1 element; no documented upper bound.
  456:                       # DOMAIN -- BVA elem:   each element must pass isa('Database::Abstraction').
  457: 
  458:     join_column    => { type => 'string',   optional => 1, default => 'entry' }
  459:                       # The column name shared by all databases (the join key).
  460:                       #
  461:                       # DOMAIN -- EP valid:   any non-empty string present in every component DA.
  462:                       # DOMAIN -- EP invalid: column absent from any DA => croak join_col_missing.
  463:                       # DOMAIN -- BVA:        empty string '' is treated as a column name and
  464:                       #                       will croak if (as expected) it is absent from every DA.
  465:                       # DOMAIN -- NOTE:       matching is case-sensitive and exact.
  466: 
  467:     join_type      => { type => 'string',   optional => 1, default => 'left',
  468:                         enum => ['inner', 'left', 'outer'] }
  469:                       # Controls which keys appear in the result when not all
  470:                       # databases share the same key values.
  471:                       #
  472:                       # DOMAIN -- EP valid:   exactly 'inner', 'left', or 'outer'.
  473:                       # DOMAIN -- EP invalid: any other string including 'INNER', 'LEFT',
  474:                       #                       'OUTER' (enum check is case-sensitive), 'cross',
  475:                       #                       or '' => croak from validate_strict.
  476: 
  477:     join_map       => { type => 'hashref',  optional => 1 }
  478:                       # Zero-based database index => local column name.
  479:                       # See the join_map section for full details.
  480:                       #
  481:                       # DOMAIN -- EP valid:   hashref values must be plain strings.
  482:                       # DOMAIN -- EP invalid: reference value (hashref, arrayref, coderef, etc.)
  483:                       #                       => croak; the guard prevents heap-address leakage.
  484:                       # DOMAIN -- BVA:        out-of-range keys (beyond the databases array) are
  485:                       #                       silently ignored.
  486: 
  487:     filters        => { type => 'hashref',  optional => 1 }
  488:                       # Zero-based database index => criteria hashref.
  489:                       # Permanent row restrictions on individual databases.
  490:                       # See the filters section for full details.
  491: 
  492:     collision_prefix => { type => 'hashref', optional => 1 }
  493:                       # Zero-based database index (>0) => prefix string.
  494:                       # When a secondary database has a column that collides
  495:                       # with a column already present in the merged view, the
  496:                       # secondary column is published as "$prefix.$col" instead
  497:                       # of silently overwriting the earlier value.
  498:                       # Index 0 entries are silently ignored.
  499:                       # Omitting this parameter preserves the original
  500:                       # last-database-wins behaviour.
  501:                       # See the collision_prefix section for full details.

  704: =head2 join_map - joining on differently-named columns
  705: 
  706: By default every component database must have a column whose name matches
  707: C<join_column>.  If a database uses a different local name for the join key,
  708: declare the mapping with C<join_map>.
  709: 
  710: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  711: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  712: B<value> is the name that B<that particular database> uses for the join key.
  713: 
  714: Databases not listed in C<join_map> are assumed to already have a column
  715: named C<join_column> and need no entry.
  716: 
  717: Throughout the merged view the join key is I<always> referred to by the name
  718: given in C<join_column>.  The local alias is never exposed in returned rows,
  719: in C<columns()>, or in C<schema()>.
  720: 
  721: B<When do you need join_map?>
  722: 
  723: You need C<join_map> when you have two tables like:
  724: 
  725:     cities table  : entry (the city name) | statecode
  726:     stnames table : entry (the state code) | state
  727: 
  728: Here you want to join cities.statecode to stnames.entry.  You choose
  729: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  730: that same concept C<entry>, so you declare:
  731: 
  732:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  733: 
  734: B<Example>
  735: 
  736:     #                        index 0     index 1
  737:     my @databases = (       $cities,    $stnames  );
  738:     #  join key column:    'statecode'  'entry'
  739:     #  join_column:        'statecode' (chosen canonical name)
  740:     #  stnames differs, so declare the alias:
  741: 
  742:     my $join = Database::Join->new(
  743:         databases   => \@databases,
  744:         join_column => 'statecode',
  745:         join_map    => { 1 => 'entry' },
  746:     );

  752:     my $row = $join->fetchrow_hashref(statecode => 'CA');

  755: 
  756: If you build the join incrementally with C<add_database>, pass
  757: C<join_column> directly to that call instead of using C<join_map>:
  758: 
  759:     my $join = Database::Join->new(

  767: =head2 filters - permanent per-database row filters
  768: 
  769: C<filters> lets you restrict a component database to a subset of its rows
  770: permanently, without repeating the criterion on every query call.
  771: 
  772: Think of it as telling the join: "whenever you query this database, always
  773: add these extra conditions".  Callers never need to specify the restriction
  774: themselves and can never accidentally omit it.
  775: 
  776: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  777: database in the C<databases> array (same numbering as C<join_map>).  Each
  778: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  779: accepts.
  780: 
  781: B<Key-set semantics>
  782: 
  783: A filtered database always acts as an inner-join partner, regardless of the
  784: C<join_type> setting.  Any join-key value that does not pass the filter is
  785: excluded from the merged output entirely -- not just missing its secondary
  786: columns.  This ensures the filter genuinely restricts the view rather than
  787: simply hiding a few fields.
  788: 
  789: B<Criteria merging>
  790: 
  791: When a query call also passes a criterion for a column that already has a base
  792: filter, the two constraints are combined:
  793: 
  794: =over 4
  795: 
  796: =item *
  797: 
  798: When both the base filter value and the query criterion are operator hashrefs
  799: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  800: merged: I<both> constraints apply simultaneously (AND semantics).
  801: 
  802: =item *
  803: 
  804: When either value is a plain scalar, or the operators conflict, the
  805: query-time criterion wins and the base filter for that column is ignored for
  806: that one call.
  807: 
  808: =back
  809: 
  810: B<Example -- only show orders placed more than 60 days ago>
  811: 
  812:     my $join = Database::Join->new(

  832: =head2 collision_prefix - preserve colliding columns from secondary databases
  833: 
  834: By default, when a column name appears in more than one database the I<last>
  835: database wins: its value silently overwrites earlier ones in merged rows.
  836: This loses data and makes the origin invisible.
  837: 
  838: C<collision_prefix> changes this for secondary databases you designate.
  839: When a secondary database at index N has a column that already exists in the
  840: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  841: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  842: visible: the original column keeps its name (from the earlier database), and
  843: the collision gets the prefixed name.
  844: 
  845: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  846: a secondary database in the C<databases> array (same numbering as C<join_map>).
  847: Each B<value> is the prefix string to prepend.  An index-0 entry is
  848: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  849: preserves the previous last-wins behaviour and changes nothing.
  850: 
  851: Non-colliding columns from a secondary database are always added as-is with
  852: no prefix, whether or not C<collision_prefix> is configured.
  853: 
  854: B<Example -- sales table and products table, both with a "product" column>
  855: 
  856:     # $sales    columns: id, product, amount, date
  857:     # $products columns: sku, product, price, category
  858:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  859: 
  860:     my $join = Database::Join->new(
  861:         databases        => [$sales, $products],
  862:         join_column      => 'product',
  863:         join_map         => { 1 => 'sku' },
  864:         collision_prefix => { 1 => 'products' },
  865:     );
  866: 
  867:     $join->columns;
  868:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  869:     #                                                               ^-- prefixed collision
  870: 
  871:     my $row = $join->fetchrow_hashref(product => 'widget');
  872:     # $row->{product}            -- value from $sales
  873:     # $row->{'products.product'} -- value from $products (different row, same column name)
  874:     # $row->{price}              -- from $products, no collision, kept as-is
  875: 
  876: B<Querying on a prefixed column>
  877: 
  878: Use the full published name as the criterion key:
  879: 
  880:     my $rows = $join->selectall_arrayref('products.product' => 'widget');
  881:     # Internally routes as: product => 'widget' to $products

  884: 
  885: C<remove_column> operates on published names.  To suppress a prefixed
  886: collision column entirely, pass the prefixed name:
  887: 
  888:     $join->remove_column('products.product');

  890: =head2 backend - SQLite join backend for large datasets
  891: 
  892: C<Database::Join> can merge component databases in two different ways,
  893: controlled by the C<backend> constructor parameter.
  894: 
  895: =over 4
  896: 
  897: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  898: 
  899: All matching rows are fetched from every component database into Perl hashes
  900: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
  901: is roughly three times the combined source data size (one copy per database
  902: plus one merged copy).
  903: 
  904: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
  905: 
  906: C<Database::Join> creates a temporary SQLite database file, spills source
  907: rows into it (one table per component database), then executes a single SQL
  908: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
  909: source data size.
  910: 
  911: The temporary file is created once and reused across multiple query calls on
  912: the same object (the cache).  Only query-time criteria vary per call; they
  913: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
  914: automatically rebuilt when any source database's C<updated()> timestamp
  915: changes.  The file is deleted when the object is destroyed (goes out of
  916: scope).  See I<Temporary file: name, location, and lifetime> below for
  917: details.
  918: 
  919: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
  920: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
  921: 
  922: =item C<backend =E<gt> 'auto'> (default)
  923: 
  924: C<Database::Join> counts the total rows from all component databases cheaply
  925: -- without fetching them -- and then decides:
  926: 
  927: =over 4
  928: 
  929: =item *
  930: 
  931: If the combined count is less than or equal to C<max_array_rows> (default
  932: 10,000), use the array path.
  933: 
  934: =item *
  935: 
  936: If the combined count exceeds C<max_array_rows>, use the SQLite path.
  937: 
  938: =back
  939: 
  940: For counting to work without fetching, each component database must either
  941: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
  942: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
  943: method in its own package -- not just inherit one from a parent class.  If
  944: neither is available for a particular database, C<Database::Join> plays it
  945: safe and uses the array path for the whole query without fetching any rows.
  946: 
  947: =back

 2933: =item Criteria partition isolation
 2934: 
 2935: Every criterion you pass to a query method is routed to I<exactly one>
 2936: component database (the one that owns that column), or to I<all> databases
 2937: when the criterion is on the join key column.  A hostile value in a criterion
 2938: for column C<name> (owned by database A) will never reach database B.
 2939: 
 2940: =item Unknown columns are rejected before reaching any database
 2941: 
 2942: If a criterion column name is not present in any component database (or has
 2943: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 2944: and silently drops the criterion.  No database receives the hostile key.
 2945: 
 2946: =item AUTOLOAD only accepts word-character column names
 2947: 
 2948: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 2949: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 2950: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 2951: C<_>) are additionally blocked with an explicit C<croak>.
 2952: 
 2953: =item No value sanitisation (by design)
 2954: 
 2955: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 2956: I<values> in criteria hashrefs.  Preventing SQL injection is the
 2957: responsibility of the underlying C<Database::Abstraction> objects (which use
 2958: parameterised queries).  Preventing XSS or header injection is the
 2959: responsibility of the CGI or web layer that renders the output.
 2960: 
 2961: =item Taint-mode compatible (array path)
 2962: 
 2963: The array merge path contains no C<system()>, C<exec()>, backtick,
 2964: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 2965: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 2966: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 2967: an I<untainted> capture, so the column name used for dispatch is clean under
 2968: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 2969: objects; those objects are responsible for handling tainted values at the SQL
 2970: parameterisation layer.
 2971: 
 2972: =item SQLite backend: column names are quoted, values are parametrised
 2973: 
 2974: When the SQLite path is active, C<Database::Join> generates SQL internally.
 2975: All column and table names are double-quoted (SQL identifier quoting) before
 2976: being embedded in statement strings.  All row values are passed to SQLite
 2977: exclusively through DBI prepared statement placeholders -- never by string
 2978: interpolation.  A hostile value in a source row therefore cannot inject SQL
 2979: into the temporary database.
 2980: 
 2981: The temporary SQLite file is created by C<File::Temp> using a securely random,
 2982: unpredictable filename.  No C<system()> or shell command is used to create or
 2983: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 2984: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 2985: in the generated SQL come from C<columns()>, which is produced by
 2986: C<Database::Abstraction> at construction time -- they are not derived from
 2987: caller-supplied criteria values.
 2988: 
 2989: =item Operator hashref broadcast copy
 2990: 
 2991: When the same join-key criterion (an operator hashref such as
 2992: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 2993: database receives its own I<shallow copy> of the hashref.  A component database
 2994: that mutates the hashref's contents at the top level cannot affect what
 2995: subsequent databases receive.
 2996: 
 2997: =item collision_prefix value type guard
 2998: 
 2999: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3000: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3001: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3002: column name, C<columns()> listing, and merged row returned to the caller.  The
 3003: guard fires before any column name is constructed.
 3004: 
 3005: =item Filter deep-copy isolation
 3006: 
 3007: The C<filters> constructor parameter and the C<filter> option of
 3008: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3009: original hashrefs are never stored; post-construction mutation of those
 3010: hashrefs cannot widen or bypass the configured row-security constraints.
 3011: 
 3012: =back

 3015: 
 3016: =over 4
 3017: 
 3018: =item Sanitise values before building criteria
 3019: 
 3020: DJ passes criterion values verbatim to component databases.  If your
 3021: application accepts user-supplied filter values (e.g. from a CGI query
 3022: string), those values I<must> be validated or sanitised by your application
 3023: before being passed to DJ.
 3024: 
 3025: =item Restrict which columns the caller can filter on
 3026: 
 3027: Any column in C<columns()> can be used as a filter criterion.  If a column
 3028: should not be filterable by end users (e.g. an internal status flag), hide it
 3029: with C<remove_column> so that queries on it are silently dropped.
 3030: 
 3031: =item Do not expose the joined view directly to user-supplied criteria
 3032: 
 3033: DJ is not a firewall.  It faithfully routes user input to component databases.
 3034: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 3035: columns and validates their values.

 3331: =head1 STATE DIAGRAM
 3332: 
 3333: C<Database::Join> objects follow three independent finite state machines (FSMs).
 3334: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 3335: triggers that cause transitions (arrows), and important side-effects.
 3336: 
 3337: =head2 FSM 1: Object Lifecycle
 3338: 
 3339: Governs the structural state of a C<Database::Join> instance.
 3340: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 3341: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 3342: are not shown because they do not change state.
 3343: 
 3344:     [pre-creation]
 3345:          |
 3346:          | new( databases => [...], join_column => '...' )
 3347:          |   Side-effect: _col_db routing table built;
 3348:          |                _autoload_pk cached from dbs[0]{id}
 3349:          v
 3350:     [CONSTRUCTED] <-----------------------------------------+
 3351:          |    |                                              |
 3352:          |    +--------------------------------------------+ |
 3353:          |    (query methods: no structural change)         | |
 3354:          |                                                  | |
 3355:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 3356:          |                                      |    |        |
 3357:          |   Side-effect: col removed from       |    |        |
 3358:          |   _col_db; _col_cache and             +----+        |
 3359:          |   _schema_cache cleared.              (idempotent;  |
 3360:          |   Join column cannot be removed.)      chainable)   |
 3361:          |                                                     |
 3362:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 3363:                                                 |    |
 3364:              Side-effect: new columns added;    |    | add_database( db )
 3365:              _col_db extended; SQLite cache     |    | (chainable; each
 3366:              invalidated (if any).              +----+  extends the view)
 3367: 
 3368:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 3369:     Both transitions are legal on any valid object, in any order.
 3370: 
 3371:     Illegal triggers (always croak; object state is not changed):
 3372: 
 3373:       Trigger                              Error
 3374:       -----------------------------------  ---------------------------------
 3375:       new( databases => [] )               error_no_databases
 3376:       remove_column( join_column )         error_remove_join_column
 3377:       add_database( non-reference )        error_invalid_database
 3378:       new() with join_col absent from DB   error_join_col_absent
