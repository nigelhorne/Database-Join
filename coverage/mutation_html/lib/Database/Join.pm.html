  141: =head1 DESCRIPTION
  142: 
  143: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  144: single logical, read-only view.  Each component database is queried
  145: independently through its own C<Database::Abstraction> interface.  The results
  146: are combined in Perl memory using a shared key column (C<join_column>).
  147: 
  148: The module exposes the same read-only API as C<Database::Abstraction>:
  149: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  150: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  151: shortcut.  Callers do not need to know how many underlying databases are
  152: involved.
  153: 
  154: Think of it as a virtual database table that is assembled on demand from
  155: several real tables, one per component database.
  156: 
  157: =head2 Join semantics
  158: 
  159: The C<join_type> parameter controls what happens when a particular key value
  160: exists in some component databases but not all:
  161: 
  162: =over 4
  163: 
  164: =item C<left> (the default)
  165: 
  166: All rows from the I<primary> (first) database are returned.  Columns from
  167: subsequent databases are included where a matching row is found, and simply
  168: absent from the hashref where there is no match.  If you are familiar with
  169: SQL, this is a LEFT OUTER JOIN on the first table.
  170: 
  171: =item C<inner>
  172: 
  173: Only rows whose join-column value is present in I<every> component database
  174: are returned.  This is equivalent to a SQL INNER JOIN.
  175: 
  176: =item C<outer>
  177: 
  178: Every join-column value found in I<any> component database is returned.
  179: Columns from databases that do not have that key value are absent from the
  180: merged row.  This is a FULL OUTER JOIN.
  181: 
  182: =back
  183: 
  184: B<Important override rule:> whenever you pass a query criterion for a column
  185: that belongs to a secondary database, that database automatically acts as an
  186: inner-join partner for that query only -- regardless of C<join_type>.  This
  187: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  188: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  189: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  190: as a WHERE clause would exclude them).
  191: 
  192: =head2 Column ownership and routing
  193: 
  194: At construction time, C<Database::Join> calls C<columns()> on each component
  195: database and builds an internal index that maps every column name to the
  196: database that owns it.
  197: 
  198: When you pass criteria to a query method, each key-value pair is automatically
  199: routed to the right database.  You never need to say which database a column
  200: belongs to.
  201: 
  202: The C<join_column> is special: criteria on it are broadcast to I<all>
  203: databases so that each database fetches only the relevant rows before the
  204: in-memory merge.
  205: 
  206: When the same non-join column name exists in more than one database, the
  207: I<last> database in the C<databases> array wins: its value overwrites earlier
  208: ones in merged rows.
  209: 
  210: =head1 LIMITATIONS
  211: 
  212: =over 4
  213: 
  214: =item In-memory join only
  215: 
  216: All matching rows from every component database are fetched into memory before
  217: the merge.  This is not suitable for very large result sets.
  218: 
  219: =item No chained builder or raw SQL
  220: 
  221: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  222: or C<fetchrow_hashref> instead.
  223: 
  224: =item Single-column equi-join only
  225: 
  226: Joining on more than one column simultaneously, or on expressions, is not
  227: supported.  When the join key has different names in different databases,
  228: use C<join_map> to declare each database's local column name.
  229: 
  230: =item Sort order
  231: 
  232: Results are sorted by the C<join_column> value only.  Caller-specified
  233: C<ORDER BY> is not propagated to the component databases.
  234: 
  235: =item count() fetches all rows
  236: 
  237: C<count()> executes the full join and counts the resulting rows in Perl.  It
  238: does not push a C<COUNT(*)> query down to the databases.
  239: 
  240: =back
  241: 
  242: =head1 COMMON PITFALLS
  243: 
  244: =over 4
  245: 
  246: =item The join_column must exist in every component database
  247: 
  248: If even one database is missing the join key column, C<new()> (or
  249: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  250: column has a different local name in some databases.
  251: 
  252: =item Criteria on a removed column are silently dropped
  253: 
  254: If you call C<remove_column('tier')> and later query
  255: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  256: C<carp> warning) and all rows are returned.  Always pass criteria before
  257: removing columns, or restructure your code to avoid this.
  258: 
  259: =item You cannot remove the join column
  260: 
  261: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  262: is required for the merge to work.
  263: 
  264: =item Left join does not guarantee all columns are populated
  265: 
  266: Under a LEFT join, rows from the primary database that have no matching row
  267: in a secondary database will be returned with I<no keys> from that secondary
  268: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  269: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  270: than just C<$row->{score}> when the secondary match is optional.
  271: 
  272: =item Filters act as inner-join partners
  273: 
  274: Any database that has a C<filters> entry is promoted to an inner-join partner,
  275: regardless of C<join_type>.  A row whose join-key value does not appear in
  276: the filtered database's result is removed from the merged output entirely, not
  277: merely missing its secondary columns.  This is intentional but can be
  278: surprising if you expected LEFT join semantics.
  279: 
  280: =item Criteria-merging replaces scalar filters
  281: 
  282: When both a base filter and a query criterion target the same column, and both
  283: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  284: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  285: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  286: the base filter is ignored for that query.
  287: 
  288: =item AUTOLOAD sees the full merged join when filters or join_map are active
  289: 
  290: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  291: (C<< $join->columnname(...) >>) runs the full join query rather than
  292: delegating directly to the owning database.  This is necessary for correctness
  293: but means the result respects all active filters and join-key translations,
  294: which may differ from what the owning database would return on its own.
  295: 
  296: =item Duplicate column names: last database wins
  297: 
  298: When two component databases each have a column called C<notes>, the second
  299: database's value silently overwrites the first in every merged row.  Use
  300: C<remove_columns> (or C<remove_column>) to drop the unwanted duplicate.
  301: 
  302: =back

  304: =head1 SECURITY CONSIDERATIONS
  305: 
  306: C<Database::Join> is a pure in-memory routing and merge layer.  It never
  307: generates SQL strings, never opens files, and never calls C<system()>,
  308: C<exec()>, or C<eval()>.  The security properties described below are
  309: architectural guarantees, not run-time checks.
  310: 
  311: =head2 What Database::Join guarantees
  312: 
  313: =over 4
  314: 
  315: =item Criteria partition isolation
  316: 
  317: Every criterion you pass to a query method is routed to I<exactly one>
  318: component database (the one that owns that column), or to I<all> databases
  319: when the criterion is on the join key column.  A hostile value in a criterion
  320: for column C<name> (owned by database A) will never reach database B.
  321: 
  322: =item Unknown columns are rejected before reaching any database
  323: 
  324: If a criterion column name is not present in any component database (or has
  325: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
  326: and silently drops the criterion.  No database receives the hostile key.
  327: 
  328: =item AUTOLOAD only accepts word-character column names
  329: 
  330: Perl's method dispatch extracts the column name via C<\w+>, which matches only
  331: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
  332: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
  333: C<_>) are additionally blocked with an explicit C<croak>.
  334: 
  335: =item No value sanitisation (by design)
  336: 
  337: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
  338: I<values> in criteria hashrefs.  Preventing SQL injection is the
  339: responsibility of the underlying C<Database::Abstraction> objects (which use
  340: parameterised queries).  Preventing XSS or header injection is the
  341: responsibility of the CGI or web layer that renders the output.
  342: 
  343: =item Operator hashref aliasing
  344: 
  345: When the same join-key criterion (an operator hashref such as
  346: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, all of
  347: them receive a reference to the I<same> hashref.  A malicious component
  348: database that mutates the hashref's contents could affect what subsequent
  349: databases receive.  Component databases are assumed to be trusted.
  350: 
  351: =back
  352: 
  353: =head2 What the caller is responsible for
  354: 
  355: =over 4
  356: 
  357: =item Sanitise values before building criteria
  358: 
  359: DJ passes criterion values verbatim to component databases.  If your
  360: application accepts user-supplied filter values (e.g. from a CGI query
  361: string), those values I<must> be validated or sanitised by your application
  362: before being passed to DJ.
  363: 
  364: =item Restrict which columns the caller can filter on
  365: 
  366: Any column in C<columns()> can be used as a filter criterion.  If a column
  367: should not be filterable by end users (e.g. an internal status flag), hide it
  368: with C<remove_column> so that queries on it are silently dropped.
  369: 
  370: =item Do not expose the joined view directly to user-supplied criteria
  371: 
  372: DJ is not a firewall.  It faithfully routes user input to component databases.
  373: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
  374: columns and validates their values.
  375: 
  376: =back

  619: =head2 filters - permanent per-database row filters
  620: 
  621: C<filters> lets you restrict a component database to a subset of its rows
  622: permanently, without repeating the criterion on every query call.
  623: 
  624: Think of it as telling the join: "whenever you query this database, always
  625: add these extra conditions".  Callers never need to specify the restriction
  626: themselves and can never accidentally omit it.
  627: 
  628: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  629: database in the C<databases> array (same numbering as C<join_map>).  Each
  630: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  631: accepts.
  632: 
  633: B<Key-set semantics>
  634: 
  635: A filtered database always acts as an inner-join partner, regardless of the
  636: C<join_type> setting.  Any join-key value that does not pass the filter is
  637: excluded from the merged output entirely -- not just missing its secondary
  638: columns.  This ensures the filter genuinely restricts the view rather than
  639: simply hiding a few fields.
  640: 
  641: B<Criteria merging>
  642: 
  643: When a query call also passes a criterion for a column that already has a base
  644: filter, the two constraints are combined:

  646: =over 4
  647: 
  648: =item *

  654: =item *

  656: When either value is a plain scalar, or the operators conflict, the

  660: =back

  662: B<Example -- only show orders placed more than 60 days ago>
  663:
