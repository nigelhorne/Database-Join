  196: =head1 DESCRIPTION
  197: 
  198: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  199: single logical, read-only view.  Each component database is queried
  200: independently through its own C<Database::Abstraction> interface.  The results
  201: are combined using a shared key column (C<join_column>).
  202: In effect, this means that you can view data from more than one database using
  203: an intuitive, non-SQL interface.
  204: 
  205: Every storage format that C<Database::Abstraction> supports works as a
  206: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  207: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  208: within the same join.
  209: 
  210: The module exposes the same read-only API as C<Database::Abstraction>:
  211: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  212: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  213: shortcut.  Callers do not need to know how many underlying databases are
  214: involved.
  215: 
  216: Think of it as a virtual database table that is assembled on demand from
  217: several real tables, one per component database.
  218: 
  219: B<Join backends>
  220: 
  221: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  222: combined source row count.  For small datasets (up to C<max_array_rows>,
  223: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  224: automatically spills source rows into a temporary SQLite database and executes
  225: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  226: size instead of three.  You can also force either path unconditionally with
  227: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  228: 
  229: =head2 Join semantics
  230: 
  231: The C<join_type> parameter controls what happens when a particular key value
  232: exists in some component databases but not all:
  233: 
  234: =over 4
  235: 
  236: =item C<left> (the default)
  237: 
  238: All rows from the I<primary> (first) database are returned.  Columns from
  239: subsequent databases are included where a matching row is found, and simply
  240: absent from the hashref where there is no match.  If you are familiar with
  241: SQL, this is a LEFT OUTER JOIN on the first table.
  242: 
  243: =item C<inner>
  244: 
  245: Only rows whose join-column value is present in I<every> component database
  246: are returned.  This is equivalent to a SQL INNER JOIN.
  247: 
  248: =item C<outer>
  249: 
  250: Every join-column value found in I<any> component database is returned.
  251: Columns from databases that do not have that key value are absent from the
  252: merged row.  This is a FULL OUTER JOIN.
  253: 
  254: =back
  255: 
  256: B<Important override rule:> whenever you pass a query criterion for a column
  257: that belongs to a secondary database, that database automatically acts as an
  258: inner-join partner for that query only -- regardless of C<join_type>.  This
  259: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  260: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  261: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  262: as a WHERE clause would exclude them).
  263: 
  264: =head2 Column ownership and routing
  265: 
  266: At construction time, C<Database::Join> calls C<columns()> on each component
  267: database and builds an internal index that maps every column name to the
  268: database that owns it.
  269: 
  270: When you pass criteria to a query method, each key-value pair is automatically
  271: routed to the right database.  You never need to say which database a column
  272: belongs to.
  273: 
  274: The C<join_column> is special: criteria on it are broadcast to I<all>
  275: databases so that each database fetches only the relevant rows before the
  276: in-memory merge.
  277: 
  278: When the same non-join column name exists in more than one database, the
  279: I<last> database in the C<databases> array wins by default: its value
  280: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  281: preserve both values under distinct names instead.
  282: 
  283: =head1 LIMITATIONS
  284: 
  285: =over 4
  286: 
  287: =item Memory usage (array backend)
  288: 
  289: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  290: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  291: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  292: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  293: 
  294: =item SQLite backend uses a persistent cache file
  295: 
  296: When the SQLite path is active, a single C<.db> file with a randomly generated
  297: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  298: first time a query runs on a given C<Database::Join> object.  Source data is
  299: spilled into that file once; subsequent queries against the same object reuse
  300: the file without re-fetching the source data.
  301: 
  302: The cache is automatically invalidated and rebuilt whenever any source
  303: database's C<updated()> timestamp changes (indicating new data), or when
  304: C<add_database()> is called.
  305: 
  306: The file is deleted when the C<Database::Join> object is destroyed (typically
  307: when it goes out of scope).  At any given moment no more than one such file
  308: exists per object.  The directory must be writable and have enough free space
  309: for the full source data (once, not per-query).
  310: 
  311: =item No chained builder or raw SQL
  312: 
  313: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  314: or C<fetchrow_hashref> instead.
  315: 
  316: =item Single-column equi-join only
  317: 
  318: Joining on more than one column simultaneously, or on expressions, is not
  319: supported.  When the join key has different names in different databases,
  320: use C<join_map> to declare each database's local column name.
  321: 
  322: =item Sort order
  323: 
  324: Results are sorted ascending by C<join_column> by default.  Pass
  325: C<< sort_by => 'colname' >> (or C<< sort_by => ['colname', 'DESC'] >>)
  326: to any query method to override this.  The array path uses string comparison
  327: (C<cmp>); for accurate numeric ordering on large datasets use the SQLite
  328: backend, which sorts natively by type.
  329: 
  330: =item count() on the array backend fetches all rows
  331: 
  332: On the array backend, C<count()> executes the full in-memory join and counts
  333: the resulting rows in Perl; no C<COUNT(*)> is pushed to the component
  334: databases.  On the SQLite backend, C<count()> executes a C<SELECT COUNT(*)>
  335: SQL query against the cached join tables, avoiding a full row transfer.
  336: 
  337: =back

  339: =head1 COMMON PITFALLS
  340: 
  341: =over 4
  342: 
  343: =item The join_column must exist in every component database
  344: 
  345: If even one database is missing the join key column, C<new()> (or
  346: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  347: column has a different local name in some databases.
  348: 
  349: =item Criteria on a removed column are silently dropped
  350: 
  351: If you call C<remove_column('tier')> and later query
  352: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  353: C<carp> warning) and all rows are returned.  Always pass criteria before
  354: removing columns, or restructure your code to avoid this.
  355: 
  356: =item You cannot remove the join column
  357: 
  358: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  359: is required for the merge to work.
  360: 
  361: =item Left join does not guarantee all columns are populated
  362: 
  363: Under a LEFT join, rows from the primary database that have no matching row
  364: in a secondary database will be returned with I<no keys> from that secondary
  365: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  366: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  367: than just C<$row->{score}> when the secondary match is optional.
  368: 
  369: =item Filters act as inner-join partners
  370: 
  371: Any database that has a C<filters> entry is promoted to an inner-join partner,
  372: regardless of C<join_type>.  A row whose join-key value does not appear in
  373: the filtered database's result is removed from the merged output entirely, not
  374: merely missing its secondary columns.  This is intentional but can be
  375: surprising if you expected LEFT join semantics.
  376: 
  377: =item Criteria-merging replaces scalar filters
  378: 
  379: When both a base filter and a query criterion target the same column, and both
  380: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  381: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  382: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  383: the base filter is ignored for that query.
  384: 
  385: =item AUTOLOAD sees the full merged join when filters or join_map are active
  386: 
  387: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  388: (C<< $join->columnname(...) >>) runs the full join query rather than
  389: delegating directly to the owning database.  This is necessary for correctness
  390: but means the result respects all active filters and join-key translations,
  391: which may differ from what the owning database would return on its own.
  392: 
  393: =item Duplicate column names: last database wins (unless collision_prefix is set)
  394: 
  395: When two component databases each have a column called C<notes>, the second
  396: database's value silently overwrites the first in every merged row.  Use
  397: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  398: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  399: (or C<remove_column>) to drop the unwanted duplicate entirely.
  400: 
  401: =item Mutating the filters hashref after construction has no effect
  402: 
  403: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  404: passed to C<add_database>) at the moment of construction.  The original hashref
  405: you passed in is never stored.  If you later modify it -- for example, to
  406: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  407: Construct a new C<Database::Join> object, or use a component
  408: C<Database::Abstraction> that supports dynamic filter modification.
  409: 
  410: =item auto mode may always use the array path for some DAs
  411: 
  412: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  413: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  414: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  415: from C<Database::Abstraction> is treated as uncountable, because the parent
  416: class C<count()> expects a key argument and behaves differently from a
  417: "return total row count" function.  In that case C<Database::Join>
  418: conservatively uses the array path for the whole query, even if the dataset is
  419: large.  To opt in to the SQLite path for such a DA, either add your own
  420: C<count()> override that returns the total row count, implement C<dbi_source()>,
  421: or use C<backend =E<gt> 'sqlite'> unconditionally.
  422: 
  423: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  424: 
  425: When a component database implements C<dbi_source()>, C<Database::Join> always
  426: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  427: for columns in that database>.  The criteria are translated into parameterised
  428: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  429: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  430: force a spill; that restriction has been removed.)
  431: 
  432: =item Broadcast join-column criterion does not force secondaries into inner-join
  433: 
  434: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  435: C<Database::Join> broadcasts it to all component databases so each DA can
  436: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  437: incorrectly counted as "having criteria" for secondary databases, causing
  438: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  439: join-column criterion was present.  The fix: only non-join-column criteria
  440: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  441: a secondary to inner-join status.  The broadcast itself is now a transparent
  442: key-range selector that does not affect join semantics.
  443: 
  444: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  445: 
  446: C<LIKE>, C<NOT LIKE>, C<IN>, and C<NOT IN> are fully supported on the SQLite
  447: backend.  C<LIKE>/C<NOT LIKE> take a scalar pattern; C<IN>/C<NOT IN> take an
  448: arrayref of values.  All are injection-safe because values are passed as bind
  449: parameters, never interpolated.
  450: 
  451:     # LIKE
  452:     my $rows = $join->selectall_arrayref(name => { LIKE => 'A%' });
  453: 
  454:     # IN
  455:     my $rows = $join->selectall_arrayref(tier => { IN => ['gold', 'silver'] });
  456: 
  457:     # NOT IN
  458:     my $rows = $join->selectall_arrayref(tier => { 'NOT IN' => ['bronze'] });
  459: 
  460: C<IN> with an empty arrayref matches no rows (SQL semantics: C<IN ()> is
  461: always false).  C<NOT IN> with an empty arrayref matches all rows (no
  462: constraint added).
  463: 
  464: C<IS NULL> and C<IS NOT NULL> are supported on the SQLite backend using an
  465: explicit operator hashref:
  466: 
  467:     my $rows = $join->selectall_arrayref(score => { 'IS NULL'     => undef });
  468:     my $rows = $join->selectall_arrayref(score => { 'IS NOT NULL' => 1    });
  469: 
  470: The hashref value is ignored; only the key selects the operator.  A bare
  471: C<undef> criterion value (C<< score => undef >>) also generates C<IS NULL>
  472: on the SQLite path.  Note: on the in-memory array path, the component DA
  473: may treat an C<undef> criterion value as C<< no filter >> rather than
  474: C<IS NULL>, so use the explicit hashref form for consistent behaviour
  475: across backends.
  476: 
  477: Any operator not in the supported set is skipped on the SQLite path with a
  478: C<carp> warning.  The array path forwards all operators to the component DA
  479: unchanged, which may or may not honour them.
  480: 
  481: =item Temp file directory must be writable and have free space
  482: 
  483: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  484: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  485: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  486: only the directory is under your control.  The file is created on the first
  487: query and kept alive until the object is destroyed; it is not re-created on
  488: every query call.  If the directory is not writable, or the filesystem is full,
  489: the call will C<croak> with C<error_sqlite_connect>.  Check permissions and
  490: free space if you see that error.
  491: 
  492: =item C<join =E<gt>> criteria are not supported
  493: 
  494: C<Database::Abstraction> accepts a C<join =E<gt> { table =E<gt> ..., on =E<gt> ... }>
  495: key in its criteria hashrefs to express an SQL JOIN within a single table.
  496: C<Database::Join> cannot route this to a component DA meaningfully: the merged
  497: view has no concept of a single underlying table.  Passing C<join =E<gt>> to any
  498: query method will C<croak> with C<error_join_criterion>.
  499: 
  500: B<Fix:> Model the joined table as a separate C<Database::Abstraction> object and
  501: add it to the C<databases =E<gt> []> list.  Use C<join_column> or C<join_map> to
  502: specify the shared key.

  816: =head2 join_map - joining on differently-named columns
  817: 
  818: By default every component database must have a column whose name matches
  819: C<join_column>.  If a database uses a different local name for the join key,
  820: declare the mapping with C<join_map>.
  821: 
  822: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  823: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  824: B<value> is the name that B<that particular database> uses for the join key.
  825: 
  826: Databases not listed in C<join_map> are assumed to already have a column
  827: named C<join_column> and need no entry.
  828: 
  829: Throughout the merged view the join key is I<always> referred to by the name
  830: given in C<join_column>.  The local alias is never exposed in returned rows,
  831: in C<columns()>, or in C<schema()>.

  833: B<When do you need join_map?>
  834: 
  835: You need C<join_map> when you have two tables like:
  836: 
  837:     cities table  : entry (the city name) | statecode
  838:     stnames table : entry (the state code) | state

  841: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  842: that same concept C<entry>, so you declare:

  844:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'

  879: =head2 filters - permanent per-database row filters
  880: 
  881: C<filters> lets you restrict a component database to a subset of its rows
  882: permanently, without repeating the criterion on every query call.
  883: 
  884: Think of it as telling the join: "whenever you query this database, always
  885: add these extra conditions".  Callers never need to specify the restriction
  886: themselves and can never accidentally omit it.
  887: 
  888: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  889: database in the C<databases> array (same numbering as C<join_map>).  Each
  890: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  891: accepts.
  892: 
  893: B<Key-set semantics>
  894: 
  895: A filtered database always acts as an inner-join partner, regardless of the
  896: C<join_type> setting.  Any join-key value that does not pass the filter is
  897: excluded from the merged output entirely -- not just missing its secondary
  898: columns.  This ensures the filter genuinely restricts the view rather than
  899: simply hiding a few fields.
  900: 
  901: B<Criteria merging>
  902: 
  903: When a query call also passes a criterion for a column that already has a base
  904: filter, the two constraints are combined:
  905: 
  906: =over 4
  907: 
  908: =item *
  909: 
  910: When both the base filter value and the query criterion are operator hashrefs
  911: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  912: merged: I<both> constraints apply simultaneously (AND semantics).
  913: 
  914: =item *
  915: 
  916: When either value is a plain scalar, or the operators conflict, the
  917: query-time criterion wins and the base filter for that column is ignored for
  918: that one call.
  919: 
  920: =back

  923: 
  924:     my $join = Database::Join->new(

  944: =head2 collision_prefix - preserve colliding columns from secondary databases
  945: 
  946: By default, when a column name appears in more than one database the I<last>
  947: database wins: its value silently overwrites earlier ones in merged rows.
  948: This loses data and makes the origin invisible.
  949: 
  950: C<collision_prefix> changes this for secondary databases you designate.
  951: When a secondary database at index N has a column that already exists in the
  952: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  953: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  954: visible: the original column keeps its name (from the earlier database), and
  955: the collision gets the prefixed name.
  956: 
  957: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  958: a secondary database in the C<databases> array (same numbering as C<join_map>).
  959: Each B<value> is the prefix string to prepend.  An index-0 entry is
  960: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  961: preserves the previous last-wins behaviour and changes nothing.
  962: 
  963: Non-colliding columns from a secondary database are always added as-is with
  964: no prefix, whether or not C<collision_prefix> is configured.

  966: B<Example -- sales table and products table, both with a "product" column>
  967: 
  968:     # $sales    columns: id, product, amount, date

  970:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  971: 
  972:     my $join = Database::Join->new(
  973:         databases        => [$sales, $products],
  974:         join_column      => 'product',
  975:         join_map         => { 1 => 'sku' },
  976:         collision_prefix => { 1 => 'products' },
  977:     );
  978: 
  979:     $join->columns;
  980:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  981:     #                                                               ^-- prefixed collision
  982: 
  983:     my $row = $join->fetchrow_hashref(product => 'widget');
  984:     # $row->{product}            -- value from $sales
  985:     # $row->{'products.product'} -- value from $products (different row, same column name)
  986:     # $row->{price}              -- from $products, no collision, kept as-is

  988: B<Querying on a prefixed column>
  989: 
  990: Use the full published name as the criterion key:
  991: 
  992:     my $rows = $join->selectall_arrayref('products.product' => 'widget');
  993:     # Internally routes as: product => 'widget' to $products

  995: B<Interaction with remove_column>
  996: 
  997: C<remove_column> operates on published names.  To suppress a prefixed
  998: collision column entirely, pass the prefixed name:
  999: 
 1000:     $join->remove_column('products.product');

 1002: =head2 backend - SQLite join backend for large datasets
 1003: 
 1004: C<Database::Join> can merge component databases in two different ways,
 1005: controlled by the C<backend> constructor parameter.
 1006: 
 1007: =over 4
 1008: 
 1009: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
 1010: 
 1011: All matching rows are fetched from every component database into Perl hashes
 1012: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
 1013: is roughly three times the combined source data size (one copy per database
 1014: plus one merged copy).
 1015: 
 1016: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1017: 
 1018: C<Database::Join> creates a temporary SQLite database file, spills source
 1019: rows into it (one table per component database), then executes a single SQL
 1020: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1021: source data size.
 1022: 
 1023: The temporary file is created once and reused across multiple query calls on
 1024: the same object (the cache).  Only query-time criteria vary per call; they
 1025: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1026: automatically rebuilt when any source database's C<updated()> timestamp
 1027: changes.  The file is deleted when the object is destroyed (goes out of
 1028: scope).  See I<Temporary file: name, location, and lifetime> below for
 1029: details.
 1030: 
 1031: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
 1032: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
 1033: 
 1034: =item C<backend =E<gt> 'auto'> (default)
 1035: 
 1036: C<Database::Join> counts the total rows from all component databases cheaply
 1037: -- without fetching them -- and then decides:
 1038: 
 1039: =over 4
 1040: 
 1041: =item *
 1042: 
 1043: If the combined count is less than or equal to C<max_array_rows> (default
 1044: 10,000), use the array path.
 1045: 
 1046: =item *
 1047: 
 1048: If the combined count exceeds C<max_array_rows>, use the SQLite path.
 1049: 
 1050: =back
 1051: 
 1052: For counting to work without fetching, each component database must either
 1053: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
 1054: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
 1055: method in its own package -- not just inherit one from a parent class.  If
 1056: neither is available for a particular database, C<Database::Join> plays it
 1057: safe and uses the array path for the whole query without fetching any rows.
 1058: 
 1059: =back
 1060: 
 1061: B<Choosing max_array_rows>
 1062: 
 1063: The default of 10,000 is a reasonable starting point.  Adjust it to match
 1064: your hardware and typical row width.  For wide rows (many columns or long
 1065: strings) you may want a lower threshold; for narrow rows you can raise it.
 1066: 
 1067: B<Temporary file: name, location, and lifetime>
 1068: 
 1069: When the SQLite path is active, a single temporary SQLite database file acts
 1070: as the join cache for the life of the C<Database::Join> object.
 1071: 
 1072: B<Name>: the filename is randomly generated by C<File::Temp>, for example:
 1073: 
 1074:     /tmp/Cj8xK7mP2Q.db
 1075: 
 1076: The random portion (ten characters) is chosen automatically to avoid
 1077: collisions.  Only the directory is under your control; you cannot specify
 1078: the filename itself.
 1079: 
 1080: B<Location>: controlled by the C<tmpdir> constructor parameter.
 1081: If C<tmpdir> is not specified, C<File::Spec-E<gt>tmpdir()> is used (usually
 1082: C</tmp> on Unix, or the value of the C<TEMP> or C<TMP> environment variable
 1083: on Windows).
 1084: 
 1085: B<Lifetime: one file per object, deleted when the object is destroyed>: the
 1086: file is created on the first query call that uses the SQLite path and kept
 1087: alive until the C<Database::Join> object is destroyed (i.e. when it goes out
 1088: of scope or is explicitly C<undef>-d).  At most one file exists per object at
 1089: any given moment.  Calling C<selectall_arrayref()> ten times on the same
 1090: object creates and uses I<one> file, not ten.
 1091: 
 1092: B<Cache invalidation>: the cache is automatically rebuilt (the old file is
 1093: replaced with a new one) when any source database's C<updated()> return value
 1094: changes, or when C<add_database()> is called.  Base-filter criteria
 1095: (C<filters> constructor parameter) are applied once at build time for spilled
 1096: sources; query-time criteria are applied per-call as SQL C<WHERE> clauses.
 1097: 
 1098: To use a different directory -- for example a RAM-backed filesystem or a
 1099: faster local disk:
 1100: 
 1101:     my $join = Database::Join->new(
 1102:         databases      => [ $db1, $db2 ],
 1103:         join_column    => 'entry',
 1104:         backend        => 'sqlite',
 1105:         tmpdir         => '/dev/shm',     # Linux RAM disk
 1106:     );
 1107: 
 1108: B<Parallel secondary fetches (C<parallel> constructor parameter)>
 1109: 
 1110: By default, component databases are queried sequentially - the primary first,
 1111: then each secondary in order.  When the component databases are network- or
 1112: disk-backed and have non-trivial per-query latency, the sequential fetch means
 1113: total latency is the I<sum> of all per-DA latencies.
 1114: 
 1115: Setting C<< parallel => 1 >> in the constructor enables concurrent fetching
 1116: of secondary databases using Perl C<threads>.  With C<parallel => 1> and
 1117: two or more secondary databases (C<n E<gt> 2> total), secondary fetches run in
 1118: parallel after the primary fetch completes; total latency drops to
 1119: I<max(secondary latencies)> instead of I<sum(secondary latencies)>.
 1120: 
 1121:     my $join = Database::Join->new(
 1122:         databases   => [ $customers, $loyalty, $scores ],   # 3 DAs - 2 secondaries
 1123:         join_column => 'entry',
 1124:         parallel    => 1,    # loyalty and scores fetched concurrently
 1125:     );
 1126: 
 1127: Requirements and caveats:
 1128: 
 1129: =over 4
 1130: 
 1131: =item *
 1132: 
 1133: The C<threads> module must be available.  Most distributions ship it, but it
 1134: requires a Perl binary compiled with C<-Dusethreads>.  When threads are
 1135: unavailable, a C<carp> warning is emitted and fetching falls back to
 1136: sequential; the result is identical, only slower.
 1137: 
 1138: =item *
 1139: 
 1140: Parallel fetching is only active when the join has three or more total
 1141: databases (C<n E<gt> 2>).  With two databases (one secondary), the thread
 1142: creation overhead exceeds the benefit of concurrency; sequential is used
 1143: regardless of C<parallel>.
 1144: 
 1145: =item *
 1146: 
 1147: Component databases must be safe to call from Perl threads.  In-memory
 1148: databases (CSV, JSON, TSV after slurp) are safe.  DBI-backed databases
 1149: whose handles were created in the same thread may not be safe - consult your
 1150: DBD driver's thread documentation.  The array backend is recommended for
 1151: DBI-backed sources; the SQLite backend performs its join in a single SQL
 1152: statement and does not use parallel fetching.
 1153: 
 1154: =item *
 1155: 
 1156: C<parallel => 1> applies to the array backend only.  The SQLite backend
 1157: performs a single SQL JOIN after spilling source data, so per-DA parallelism
 1158: is irrelevant.
 1159: 
 1160: =back
 1161: 
 1162: B<Zero-copy ATTACH (C<dbi_source()> interface)>
 1163: 
 1164: Normally, when the SQLite path is active, rows from each component database
 1165: are fetched one by one and inserted into the temporary SQLite file.  This is
 1166: efficient but does involve INSERT overhead.
 1167: 
 1168: If a component database is itself SQLite-backed and implements a
 1169: C<dbi_source()> method, C<Database::Join> can skip the row-by-row copy
 1170: entirely and instead use C<ATTACH DATABASE> to link the source file directly
 1171: to the temporary join connection.  This is the zero-copy path and is
 1172: significantly faster for large SQLite sources.
 1173: 
 1174: The C<dbi_source()> method must return a hashref with two keys:
 1175: 
 1176: =over 4
 1177: 
 1178: =item C<dbh>
 1179: 
 1180: A connected C<DBD::SQLite> database handle (C<DBI> connection object).
 1181: 
 1182: =item C<table>
 1183: 
 1184: The name of the table in that database that holds the source rows.
 1185: 
 1186: =back
 1187: 
 1188: Example implementation:
 1189: 
 1190:     package My::SQLiteDatabase;
 1191:     use parent 'Database::Abstraction';
 1192: 
 1193:     sub dbi_source {
 1194:         my ($self) = @_;
 1195:         return {
 1196:             dbh   => $self->{_dbh},      # connected DBD::SQLite handle
 1197:             table => $self->{_table},    # table name in that database
 1198:         };
 1199:     }
 1200: 
 1201:     1;
 1202: 
 1203: The zero-copy ATTACH path is always used when a component database implements
 1204: C<dbi_source()>.  Query-time criteria are applied as parameterised SQL
 1205: C<WHERE> clauses against the ATTACHed source table, so no row-level copy is
 1206: needed even when the current call includes column filters.  (Prior to 0.005.0
 1207: any query-time criteria forced a spill; that restriction was removed in
 1208: 0.005.0.)
 1209: 
 1210: B<Result identity>
 1211: 
 1212: Both the array path and the SQLite path produce identical results for any
 1213: given query.  You can switch between them freely without changing callers.
 1214: The C<collision_prefix> column renaming, C<join_map> key translation, and all
 1215: three join types (left, inner, outer) work identically on both paths.

 3869: =head1 SECURITY CONSIDERATIONS
 3870: 
 3871: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3872: generates SQL strings, never opens files, and never calls C<system()>,
 3873: C<exec()>, or C<eval()>.  The security properties described below are
 3874: architectural guarantees, not run-time checks.
 3875: 
 3876: =head2 What Database::Join guarantees
 3877: 
 3878: =over 4
 3879: 
 3880: =item Criteria partition isolation
 3881: 
 3882: Every criterion you pass to a query method is routed to I<exactly one>
 3883: component database (the one that owns that column), or to I<all> databases
 3884: when the criterion is on the join key column.  A hostile value in a criterion
 3885: for column C<name> (owned by database A) will never reach database B.
 3886: 
 3887: =item Unknown columns are rejected before reaching any database
 3888: 
 3889: If a criterion column name is not present in any component database (or has
 3890: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3891: and silently drops the criterion.  No database receives the hostile key.
 3892: 
 3893: =item AUTOLOAD only accepts word-character column names
 3894: 
 3895: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3896: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3897: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3898: C<_>) are additionally blocked with an explicit C<croak>.
 3899: 
 3900: =item No value sanitisation (by design)
 3901: 
 3902: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3903: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3904: responsibility of the underlying C<Database::Abstraction> objects (which use
 3905: parameterised queries).  Preventing XSS or header injection is the
 3906: responsibility of the CGI or web layer that renders the output.
 3907: 
 3908: =item Taint-mode compatible (array path)
 3909: 
 3910: The array merge path contains no C<system()>, C<exec()>, backtick,
 3911: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3912: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3913: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3914: an I<untainted> capture, so the column name used for dispatch is clean under
 3915: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3916: objects; those objects are responsible for handling tainted values at the SQL
 3917: parameterisation layer.
 3918: 
 3919: =item SQLite backend: column names are quoted, values are parametrised
 3920: 
 3921: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3922: All column and table names are double-quoted (SQL identifier quoting) before
 3923: being embedded in statement strings.  All row values are passed to SQLite
 3924: exclusively through DBI prepared statement placeholders -- never by string
 3925: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3926: into the temporary database.
 3927: 
 3928: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3929: unpredictable filename.  No C<system()> or shell command is used to create or
 3930: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3931: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3932: in the generated SQL come from C<columns()>, which is produced by
 3933: C<Database::Abstraction> at construction time -- they are not derived from
 3934: caller-supplied criteria values.
 3935: 
 3936: =item Operator hashref broadcast copy
 3937: 
 3938: When the same join-key criterion (an operator hashref such as
 3939: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3940: database receives its own I<shallow copy> of the hashref.  A component database
 3941: that mutates the hashref's contents at the top level cannot affect what
 3942: subsequent databases receive.
 3943: 
 3944: =item collision_prefix value type guard
 3945: 
 3946: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3947: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3948: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3949: column name, C<columns()> listing, and merged row returned to the caller.  The
 3950: guard fires before any column name is constructed.
 3951: 
 3952: =item Filter deep-copy isolation
 3953: 
 3954: The C<filters> constructor parameter and the C<filter> option of
 3955: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3956: original hashrefs are never stored; post-construction mutation of those
 3957: hashrefs cannot widen or bypass the configured row-security constraints.
 3958: 
 3959: =back
 3960: 
 3961: =head2 What the caller is responsible for
 3962: 
 3963: =over 4
 3964: 
 3965: =item Sanitise values before building criteria
 3966: 
 3967: DJ passes criterion values verbatim to component databases.  If your
 3968: application accepts user-supplied filter values (e.g. from a CGI query
 3969: string), those values I<must> be validated or sanitised by your application
 3970: before being passed to DJ.
 3971: 
 3972: =item Restrict which columns the caller can filter on
 3973: 
 3974: Any column in C<columns()> can be used as a filter criterion.  If a column
 3975: should not be filterable by end users (e.g. an internal status flag), hide it
 3976: with C<remove_column> so that queries on it are silently dropped.
 3977: 
 3978: =item Do not expose the joined view directly to user-supplied criteria
 3979: 
 3980: DJ is not a firewall.  It faithfully routes user input to component databases.
 3981: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 3982: columns and validates their values.
 3983: 
 3984: =back

 4278: =head1 STATE DIAGRAM
 4279: 
 4280: C<Database::Join> objects follow three independent finite state machines (FSMs).
 4281: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 4282: triggers that cause transitions (arrows), and important side-effects.
 4283: 
 4284: =head2 FSM 1: Object Lifecycle
 4285: 
 4286: Governs the structural state of a C<Database::Join> instance.
 4287: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 4288: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 4289: are not shown because they do not change state.
 4290: 
 4291:     [pre-creation]
 4292:          |
 4293:          | new( databases => [...], join_column => '...' )
 4294:          |   Side-effect: _col_db routing table built;
 4295:          |                _autoload_pk cached from dbs[0]{id}
 4296:          v
 4297:     [CONSTRUCTED] <-----------------------------------------+
 4298:          |    |                                              |
 4299:          |    +--------------------------------------------+ |
 4300:          |    (query methods: no structural change)         | |
 4301:          |                                                  | |
 4302:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 4303:          |                                      |    |        |
 4304:          |   Side-effect: col removed from       |    |        |
 4305:          |   _col_db; _col_cache and             +----+        |
 4306:          |   _schema_cache cleared.              (idempotent;  |
 4307:          |   Join column cannot be removed.)      chainable)   |
 4308:          |                                                     |
 4309:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 4310:                                                 |    |
 4311:              Side-effect: new columns added;    |    | add_database( db )
 4312:              _col_db extended; SQLite cache     |    | (chainable; each
 4313:              invalidated (if any).              +----+  extends the view)
 4314: 
 4315:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 4316:     Both transitions are legal on any valid object, in any order.
 4317: 
 4318:     Illegal triggers (always croak; object state is not changed):
 4319: 
 4320:       Trigger                              Error
 4321:       -----------------------------------  ---------------------------------
 4322:       new( databases => [] )               error_no_databases
 4323:       remove_column( join_column )         error_remove_join_column
