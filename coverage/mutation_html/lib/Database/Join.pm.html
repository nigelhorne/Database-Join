  213: =head1 DESCRIPTION
  214: 
  215: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  216: single logical, read-only view.  Each component database is queried
  217: independently through its own C<Database::Abstraction> interface.  The results
  218: are combined using a shared key column (C<join_column>).
  219: In effect, this means that you can view data from more than one database using
  220: an intuitive, non-SQL interface.
  221: 
  222: Every storage format that C<Database::Abstraction> supports works as a
  223: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  224: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  225: within the same join.
  226: 
  227: The module exposes the same read-only API as C<Database::Abstraction>:
  228: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  229: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  230: shortcut.  Callers do not need to know how many underlying databases are
  231: involved.
  232: 
  233: Think of it as a virtual database table that is assembled on demand from
  234: several real tables, one per component database.
  235: 
  236: B<Join backends>
  237: 
  238: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  239: combined source row count.  For small datasets (up to C<max_array_rows>,
  240: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  241: automatically spills source rows into a temporary SQLite database and executes
  242: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  243: size instead of three.  You can also force either path unconditionally with
  244: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  245: 
  246: =head2 Join semantics
  247: 
  248: The C<join_type> parameter controls what happens when a particular key value
  249: exists in some component databases but not all:
  250: 
  251: =over 4
  252: 
  253: =item C<left> (the default)
  254: 
  255: All rows from the I<primary> (first) database are returned.  Columns from
  256: subsequent databases are included where a matching row is found, and simply
  257: absent from the hashref where there is no match.  If you are familiar with
  258: SQL, this is a LEFT OUTER JOIN on the first table.
  259: 
  260: =item C<inner>
  261: 
  262: Only rows whose join-column value is present in I<every> component database
  263: are returned.  This is equivalent to a SQL INNER JOIN.
  264: 
  265: =item C<outer>
  266: 
  267: Every join-column value found in I<any> component database is returned.
  268: Columns from databases that do not have that key value are absent from the
  269: merged row.  This is a FULL OUTER JOIN.
  270: 
  271: =back
  272: 
  273: B<Important override rule:> whenever you pass a query criterion for a column
  274: that belongs to a secondary database, that database automatically acts as an
  275: inner-join partner for that query only -- regardless of C<join_type>.  This
  276: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  277: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  278: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  279: as a WHERE clause would exclude them).
  280: 
  281: =head2 Column ownership and routing
  282: 
  283: At construction time, C<Database::Join> calls C<columns()> on each component
  284: database and builds an internal index that maps every column name to the
  285: database that owns it.
  286: 
  287: When you pass criteria to a query method, each key-value pair is automatically
  288: routed to the right database.  You never need to say which database a column
  289: belongs to.
  290: 
  291: The C<join_column> is special: criteria on it are broadcast to I<all>
  292: databases so that each database fetches only the relevant rows before the
  293: in-memory merge.
  294: 
  295: When the same non-join column name exists in more than one database, the
  296: I<last> database in the C<databases> array wins by default: its value
  297: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  298: preserve both values under distinct names instead.
  299: 
  300: =head1 LIMITATIONS
  301: 
  302: =over 4
  303: 
  304: =item Memory usage (array backend)
  305: 
  306: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  307: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  308: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  309: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  310: 
  311: =item SQLite backend uses a persistent cache file
  312: 
  313: When the SQLite path is active, a single C<.db> file with a randomly generated
  314: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  315: first time a query runs on a given C<Database::Join> object.  Source data is
  316: spilled into that file once; subsequent queries against the same object reuse
  317: the file without re-fetching the source data.
  318: 
  319: The cache is automatically invalidated and rebuilt whenever any source
  320: database's C<updated()> timestamp changes (indicating new data), or when
  321: C<add_database()> is called.
  322: 
  323: The file is deleted when the C<Database::Join> object is destroyed (typically
  324: when it goes out of scope).  At any given moment no more than one such file
  325: exists per object.  The directory must be writable and have enough free space
  326: for the full source data (once, not per-query).
  327: 
  328: =item No chained builder or raw SQL
  329: 
  330: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  331: or C<fetchrow_hashref> instead.
  332: 
  333: =item Single-column equi-join only
  334: 
  335: Joining on more than one column simultaneously, or on expressions, is not
  336: supported.  When the join key has different names in different databases,
  337: use C<join_map> to declare each database's local column name.
  338: 
  339: =item Sort order
  340: 
  341: Results are sorted ascending by C<join_column> by default.  Pass
  342: C<< sort_by => 'colname' >> (or C<< sort_by => ['colname', 'DESC'] >>)
  343: to any query method to override this.  The array path uses string comparison
  344: (C<cmp>); for accurate numeric ordering on large datasets use the SQLite
  345: backend, which sorts natively by type.
  346: 
  347: =item count() on the array backend fetches all rows
  348: 
  349: On the array backend, C<count()> executes the full in-memory join and counts
  350: the resulting rows in Perl; no C<COUNT(*)> is pushed to the component
  351: databases.  On the SQLite backend, C<count()> executes a C<SELECT COUNT(*)>
  352: SQL query against the cached join tables, avoiding a full row transfer.
  353: 
  354: =back

  356: =head1 COMMON PITFALLS
  357: 
  358: =over 4
  359: 
  360: =item The join_column must exist in every component database
  361: 
  362: If even one database is missing the join key column, C<new()> (or
  363: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  364: column has a different local name in some databases.
  365: 
  366: =item Criteria on a removed column are silently dropped
  367: 
  368: If you call C<remove_column('tier')> and later query
  369: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  370: C<carp> warning) and all rows are returned.  Always pass criteria before
  371: removing columns, or restructure your code to avoid this.
  372: 
  373: =item You cannot remove the join column
  374: 
  375: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  376: is required for the merge to work.
  377: 
  378: =item Left join does not guarantee all columns are populated
  379: 
  380: Under a LEFT join, rows from the primary database that have no matching row
  381: in a secondary database will be returned with I<no keys> from that secondary
  382: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  383: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  384: than just C<$row->{score}> when the secondary match is optional.
  385: 
  386: =item Filters act as inner-join partners
  387: 
  388: Any database that has a C<filters> entry is promoted to an inner-join partner,
  389: regardless of C<join_type>.  A row whose join-key value does not appear in
  390: the filtered database's result is removed from the merged output entirely, not
  391: merely missing its secondary columns.  This is intentional but can be
  392: surprising if you expected LEFT join semantics.
  393: 
  394: =item Criteria-merging replaces scalar filters
  395: 
  396: When both a base filter and a query criterion target the same column, and both
  397: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  398: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  399: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  400: the base filter is ignored for that query.
  401: 
  402: =item AUTOLOAD sees the full merged join when filters or join_map are active
  403: 
  404: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  405: (C<< $join->columnname(...) >>) runs the full join query rather than
  406: delegating directly to the owning database.  This is necessary for correctness
  407: but means the result respects all active filters and join-key translations,
  408: which may differ from what the owning database would return on its own.
  409: 
  410: =item Duplicate column names: last database wins (unless collision_prefix is set)
  411: 
  412: When two component databases each have a column called C<notes>, the second
  413: database's value silently overwrites the first in every merged row.  Use
  414: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  415: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  416: (or C<remove_column>) to drop the unwanted duplicate entirely.
  417: 
  418: =item Mutating the filters hashref after construction has no effect
  419: 
  420: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  421: passed to C<add_database>) at the moment of construction.  The original hashref
  422: you passed in is never stored.  If you later modify it -- for example, to
  423: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  424: Construct a new C<Database::Join> object, or use a component
  425: C<Database::Abstraction> that supports dynamic filter modification.
  426: 
  427: =item auto mode may always use the array path for some DAs
  428: 
  429: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  430: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  431: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  432: from C<Database::Abstraction> is treated as uncountable, because the parent
  433: class C<count()> expects a key argument and behaves differently from a
  434: "return total row count" function.  In that case C<Database::Join>
  435: conservatively uses the array path for the whole query, even if the dataset is
  436: large.  To opt in to the SQLite path for such a DA, either add your own
  437: C<count()> override that returns the total row count, implement C<dbi_source()>,
  438: or use C<backend =E<gt> 'sqlite'> unconditionally.
  439: 
  440: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  441: 
  442: When a component database implements C<dbi_source()>, C<Database::Join> always
  443: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  444: for columns in that database>.  The criteria are translated into parameterised
  445: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  446: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  447: force a spill; that restriction has been removed.)
  448: 
  449: =item Broadcast join-column criterion does not force secondaries into inner-join
  450: 
  451: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  452: C<Database::Join> broadcasts it to all component databases so each DA can
  453: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  454: incorrectly counted as "having criteria" for secondary databases, causing
  455: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  456: join-column criterion was present.  The fix: only non-join-column criteria
  457: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  458: a secondary to inner-join status.  The broadcast itself is now a transparent
  459: key-range selector that does not affect join semantics.
  460: 
  461: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  462: 
  463: C<LIKE>, C<NOT LIKE>, C<IN>, and C<NOT IN> are fully supported on the SQLite
  464: backend.  C<LIKE>/C<NOT LIKE> take a scalar pattern; C<IN>/C<NOT IN> take an
  465: arrayref of values.  All are injection-safe because values are passed as bind
  466: parameters, never interpolated.
  467: 
  468:     # LIKE
  469:     my $rows = $join->selectall_arrayref(name => { LIKE => 'A%' });
  470: 
  471:     # IN

  474:     # NOT IN
  475:     my $rows = $join->selectall_arrayref(tier => { 'NOT IN' => ['bronze'] });

  477: C<IN> with an empty arrayref matches no rows (SQL semantics: C<IN ()> is
  478: always false).  C<NOT IN> with an empty arrayref matches all rows (no
  479: constraint added).
  480: 
  481: C<IS NULL> and C<IS NOT NULL> are supported on the SQLite backend using an
  482: explicit operator hashref:
  483: 
  484:     my $rows = $join->selectall_arrayref(score => { 'IS NULL'     => undef });
  485:     my $rows = $join->selectall_arrayref(score => { 'IS NOT NULL' => 1    });

  487: The hashref value is ignored; only the key selects the operator.  A bare
  488: C<undef> criterion value (C<< score => undef >>) also generates C<IS NULL>
  489: on the SQLite path.  Note: on the in-memory array path, the component DA
  490: may treat an C<undef> criterion value as C<< no filter >> rather than
  491: C<IS NULL>, so use the explicit hashref form for consistent behaviour
  492: across backends.
  493: 
  494: Any operator not in the supported set is skipped on the SQLite path with a
  495: C<carp> warning.  The array path forwards all operators to the component DA
  496: unchanged, which may or may not honour them.
  497: 
  498: =item Temp file directory must be writable and have free space
  499: 
  500: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  501: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  502: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  503: only the directory is under your control.  The file is created on the first
  504: query and kept alive until the object is destroyed; it is not re-created on
  505: every query call.  If the directory is not writable, or the filesystem is full,
  506: the call will C<croak> with C<error_sqlite_connect>.  Check permissions and
  507: free space if you see that error.
  508: 
  509: =item C<join =E<gt>> criteria are not supported
  510: 
  511: C<Database::Abstraction> accepts a C<join =E<gt> { table =E<gt> ..., on =E<gt> ... }>
  512: key in its criteria hashrefs to express an SQL JOIN within a single table.
  513: C<Database::Join> cannot route this to a component DA meaningfully: the merged
  514: view has no concept of a single underlying table.  Passing C<join =E<gt>> to any
  515: query method will C<croak> with C<error_join_criterion>.
  516: 
  517: B<Fix:> Model the joined table as a separate C<Database::Abstraction> object and
  518: add it to the C<databases =E<gt> []> list.  Use C<join_column> or C<join_map> to
  519: specify the shared key.

  879: =head2 join_map - joining on differently-named columns
  880: 
  881: By default every component database must have a column whose name matches
  882: C<join_column>.  If a database uses a different local name for the join key,
  883: declare the mapping with C<join_map>.

  885: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  886: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  887: B<value> is the name that B<that particular database> uses for the join key.

  889: Databases not listed in C<join_map> are assumed to already have a column
  890: named C<join_column> and need no entry.

  893: given in C<join_column>.  The local alias is never exposed in returned rows,

  932: C<join_column> directly to that call instead of using C<join_map>:
  933: 
  934:     my $join = Database::Join->new(
  935:         databases   => [ $cities ],
  936:         join_column => 'statecode',
  937:     );
  938:     $join->add_database($stnames, join_column => 'entry');
  939: 
  940: This is exactly equivalent to the C<join_map> form above.
  941: 
  942: =head2 filters - permanent per-database row filters
  943: 
  944: C<filters> lets you restrict a component database to a subset of its rows
  945: permanently, without repeating the criterion on every query call.
  946: 
  947: Think of it as telling the join: "whenever you query this database, always
  948: add these extra conditions".  Callers never need to specify the restriction
  949: themselves and can never accidentally omit it.
  950: 
  951: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  952: database in the C<databases> array (same numbering as C<join_map>).  Each
  953: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  954: accepts.
  955: 
  956: B<Key-set semantics>
  957: 
  958: A filtered database always acts as an inner-join partner, regardless of the
  959: C<join_type> setting.  Any join-key value that does not pass the filter is
  960: excluded from the merged output entirely -- not just missing its secondary
  961: columns.  This ensures the filter genuinely restricts the view rather than
  962: simply hiding a few fields.
  963: 
  964: B<Criteria merging>
  965: 
  966: When a query call also passes a criterion for a column that already has a base
  967: filter, the two constraints are combined:
  968: 
  969: =over 4
  970: 
  971: =item *
  972: 
  973: When both the base filter value and the query criterion are operator hashrefs
  974: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  975: merged: I<both> constraints apply simultaneously (AND semantics).
  976: 
  977: =item *
  978: 
  979: When either value is a plain scalar, or the operators conflict, the
  980: query-time criterion wins and the base filter for that column is ignored for
  981: that one call.
  982: 
  983: =back
  984: 
  985: B<Example -- only show orders placed more than 60 days ago>
  986: 
  987:     my $join = Database::Join->new(
  988:         databases   => [ $customers, $orders ],
  989:         join_column => 'entry',
  990:         filters     => { 1 => { age_days => { '>' => 60 } } },
  991:     );
  992: 
  993:     # Every query automatically sees only old orders
  994:     my $rows = $join->selectall_arrayref();
  995: 
  996:     # Additional criteria layer on top -- gold tier AND old order
  997:     my $vip  = $join->selectall_arrayref(tier => 'gold');
  998: 
  999:     # Range intersection: age_days > 60 AND age_days < 365
 1000:     my $mid  = $join->selectall_arrayref(age_days => { '<' => 365 });
 1001: 
 1002: When using C<add_database>, pass C<filter> (singular) to set the base
 1003: criteria for the new database:
 1004: 
 1005:     $join->add_database($orders, filter => { age_days => { '>' => 60 } });
 1006: 
 1007: =head2 base_criteria - permanent view-level row filters by column name
 1008: 
 1009: C<base_criteria> is a convenience alternative to C<filters> for callers who
 1010: know the column names they want to restrict but prefer not to track database
 1011: indices.
 1012: 
 1013:     my $join = Database::Join->new(
 1014:         databases     => [ $customers, $orders ],
 1015:         join_column   => 'entry',
 1016:         base_criteria => { active => 1, deleted_at => undef },
 1017:     );
 1018: 
 1019:     # Every query automatically sees only active, non-deleted rows.
 1020:     my $rows = $join->selectall_arrayref();
 1021: 
 1022: At construction time C<base_criteria> is partitioned by column ownership
 1023: using the same routing logic as C<selectall_arrayref>.  Each criterion is
 1024: sent to the database that owns that column and stored as a permanent base
 1025: filter (equivalent to the corresponding C<filters> entry).
 1026: 
 1027: B<Unknown columns> emit a C<warn_unknown_column> carp and are silently
 1028: dropped, just as they would be in a query call.
 1029: 
 1030: B<Key-set semantics> are identical to C<filters>: any database that receives
 1031: a C<base_criteria> slice acts as an inner-join partner regardless of
 1032: C<join_type>.
 1033: 
 1034: B<Precedence>: when a column appears in both C<base_criteria> and C<filters>,
 1035: the C<filters> entry wins on plain-scalar conflicts; operator-hashref values
 1036: are combined with AND semantics.
 1037: 
 1038: B<Use cases>
 1039: 
 1040: =over 4
 1041: 
 1042: =item *
 1043: 
 1044: Row-level security: C<< base_criteria => { tenant_id => $tid } >>
 1045: 
 1046: =item *
 1047: 
 1048: Soft-delete filtering: C<< base_criteria => { deleted_at => undef } >>
 1049: 
 1050: =item *
 1051: 
 1052: Status gates: C<< base_criteria => { active => 1 } >>
 1053: 
 1054: =back

 1056: =head2 collision_prefix - preserve colliding columns from secondary databases
 1057: 
 1058: By default, when a column name appears in more than one database the I<last>
 1059: database wins: its value silently overwrites earlier ones in merged rows.
 1060: This loses data and makes the origin invisible.
 1061: 
 1062: C<collision_prefix> changes this for secondary databases you designate.
 1063: When a secondary database at index N has a column that already exists in the
 1064: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
 1065: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
 1066: visible: the original column keeps its name (from the earlier database), and
 1067: the collision gets the prefixed name.
 1068: 
 1069: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
 1070: a secondary database in the C<databases> array (same numbering as C<join_map>).
 1071: Each B<value> is the prefix string to prepend.  An index-0 entry is
 1072: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
 1073: preserves the previous last-wins behaviour and changes nothing.
 1074: 
 1075: Non-colliding columns from a secondary database are always added as-is with
 1076: no prefix, whether or not C<collision_prefix> is configured.
 1077: 
 1078: B<Example -- sales table and products table, both with a "product" column>
 1079: 
 1080:     # $sales    columns: id, product, amount, date
 1081:     # $products columns: sku, product, price, category
 1082:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
 1083: 
 1084:     my $join = Database::Join->new(
 1085:         databases        => [$sales, $products],
 1086:         join_column      => 'product',
 1087:         join_map         => { 1 => 'sku' },
 1088:         collision_prefix => { 1 => 'products' },
 1089:     );
 1090: 
 1091:     $join->columns;
 1092:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
 1093:     #                                                               ^-- prefixed collision
 1094: 
 1095:     my $row = $join->fetchrow_hashref(product => 'widget');
 1096:     # $row->{product}            -- value from $sales
 1097:     # $row->{'products.product'} -- value from $products (different row, same column name)
 1098:     # $row->{price}              -- from $products, no collision, kept as-is
 1099: 
 1100: B<Querying on a prefixed column>
 1101: 
 1102: Use the full published name as the criterion key:
 1103: 
 1104:     my $rows = $join->selectall_arrayref('products.product' => 'widget');
 1105:     # Internally routes as: product => 'widget' to $products
 1106: 
 1107: B<Interaction with remove_column>
 1108: 
 1109: C<remove_column> operates on published names.  To suppress a prefixed
 1110: collision column entirely, pass the prefixed name:
 1111: 
 1112:     $join->remove_column('products.product');

 1114: =head2 backend - SQLite join backend for large datasets
 1115: 
 1116: C<Database::Join> can merge component databases in two different ways,
 1117: controlled by the C<backend> constructor parameter.
 1118: 
 1119: =over 4
 1120: 
 1121: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
 1122: 
 1123: All matching rows are fetched from every component database into Perl hashes
 1124: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
 1125: is roughly three times the combined source data size (one copy per database
 1126: plus one merged copy).
 1127: 
 1128: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1129: 
 1130: C<Database::Join> creates a temporary SQLite database file, spills source
 1131: rows into it (one table per component database), then executes a single SQL
 1132: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1133: source data size.
 1134: 
 1135: The temporary file is created once and reused across multiple query calls on
 1136: the same object (the cache).  Only query-time criteria vary per call; they
 1137: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1138: automatically rebuilt when any source database's C<updated()> timestamp
 1139: changes.  The file is deleted when the object is destroyed (goes out of
 1140: scope).  See I<Temporary file: name, location, and lifetime> below for
 1141: details.
 1142: 
 1143: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
 1144: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
 1145: 
 1146: =item C<backend =E<gt> 'auto'> (default)
 1147: 
 1148: C<Database::Join> counts the total rows from all component databases cheaply
 1149: -- without fetching them -- and then decides:
 1150: 
 1151: =over 4
 1152: 
 1153: =item *
 1154: 
 1155: If the combined count is less than or equal to C<max_array_rows> (default
 1156: 10,000), use the array path.
 1157: 
 1158: =item *
 1159: 
 1160: If the combined count exceeds C<max_array_rows>, use the SQLite path.
 1161: 
 1162: =back
 1163: 
 1164: For counting to work without fetching, each component database must either
 1165: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
 1166: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
 1167: method in its own package -- not just inherit one from a parent class.  If
 1168: neither is available for a particular database, C<Database::Join> plays it
 1169: safe and uses the array path for the whole query without fetching any rows.
 1170: 
 1171: =back
 1172: 
 1173: B<Choosing max_array_rows>
 1174: 
 1175: The default of 10,000 is a reasonable starting point.  Adjust it to match
 1176: your hardware and typical row width.  For wide rows (many columns or long
 1177: strings) you may want a lower threshold; for narrow rows you can raise it.
 1178: 
 1179: B<Temporary file: name, location, and lifetime>
 1180: 
 1181: When the SQLite path is active, a single temporary SQLite database file acts
 1182: as the join cache for the life of the C<Database::Join> object.
 1183: 
 1184: B<Name>: the filename is randomly generated by C<File::Temp>, for example:
 1185: 
 1186:     /tmp/Cj8xK7mP2Q.db
 1187: 
 1188: The random portion (ten characters) is chosen automatically to avoid
 1189: collisions.  Only the directory is under your control; you cannot specify
 1190: the filename itself.
 1191: 
 1192: B<Location>: controlled by the C<tmpdir> constructor parameter.
 1193: If C<tmpdir> is not specified, C<File::Spec-E<gt>tmpdir()> is used (usually
 1194: C</tmp> on Unix, or the value of the C<TEMP> or C<TMP> environment variable
 1195: on Windows).
 1196: 
 1197: B<Lifetime: one file per object, deleted when the object is destroyed>: the
 1198: file is created on the first query call that uses the SQLite path and kept
 1199: alive until the C<Database::Join> object is destroyed (i.e. when it goes out
 1200: of scope or is explicitly C<undef>-d).  At most one file exists per object at
 1201: any given moment.  Calling C<selectall_arrayref()> ten times on the same
 1202: object creates and uses I<one> file, not ten.
 1203: 
 1204: B<Cache invalidation>: the cache is automatically rebuilt (the old file is
 1205: replaced with a new one) when any source database's C<updated()> return value
 1206: changes, or when C<add_database()> is called.  Base-filter criteria
 1207: (C<filters> constructor parameter) are applied once at build time for spilled
 1208: sources; query-time criteria are applied per-call as SQL C<WHERE> clauses.
 1209: 
 1210: To use a different directory -- for example a RAM-backed filesystem or a
 1211: faster local disk:
 1212: 
 1213:     my $join = Database::Join->new(
 1214:         databases      => [ $db1, $db2 ],
 1215:         join_column    => 'entry',
 1216:         backend        => 'sqlite',
 1217:         tmpdir         => '/dev/shm',     # Linux RAM disk
 1218:     );
 1219: 
 1220: B<Parallel secondary fetches (C<parallel> constructor parameter)>
 1221: 
 1222: By default, component databases are queried sequentially - the primary first,
 1223: then each secondary in order.  When the component databases are network- or
 1224: disk-backed and have non-trivial per-query latency, the sequential fetch means
 1225: total latency is the I<sum> of all per-DA latencies.
 1226: 
 1227: Setting C<< parallel => 1 >> in the constructor enables concurrent fetching
 1228: of secondary databases using Perl C<threads>.  With C<parallel => 1> and
 1229: two or more secondary databases (C<n E<gt> 2> total), secondary fetches run in
 1230: parallel after the primary fetch completes; total latency drops to
 1231: I<max(secondary latencies)> instead of I<sum(secondary latencies)>.
 1232: 
 1233:     my $join = Database::Join->new(
 1234:         databases   => [ $customers, $loyalty, $scores ],   # 3 DAs - 2 secondaries
 1235:         join_column => 'entry',
 1236:         parallel    => 1,    # loyalty and scores fetched concurrently
 1237:     );
 1238: 
 1239: Requirements and caveats:
 1240: 
 1241: =over 4
 1242: 
 1243: =item *
 1244: 
 1245: The C<threads> module must be available.  Most distributions ship it, but it
 1246: requires a Perl binary compiled with C<-Dusethreads>.  When threads are
 1247: unavailable, a C<carp> warning is emitted and fetching falls back to
 1248: sequential; the result is identical, only slower.
 1249: 
 1250: =item *
 1251: 
 1252: Parallel fetching is only active when the join has three or more total
 1253: databases (C<n E<gt> 2>).  With two databases (one secondary), the thread
 1254: creation overhead exceeds the benefit of concurrency; sequential is used
 1255: regardless of C<parallel>.
 1256: 
 1257: =item *
 1258: 
 1259: Component databases must be safe to call from Perl threads.  In-memory
 1260: databases (CSV, JSON, TSV after slurp) are safe.  DBI-backed databases
 1261: whose handles were created in the same thread may not be safe - consult your
 1262: DBD driver's thread documentation.  The array backend is recommended for
 1263: DBI-backed sources; the SQLite backend performs its join in a single SQL
 1264: statement and does not use parallel fetching.
 1265: 
 1266: =item *
 1267: 
 1268: C<parallel => 1> applies to the array backend only.  The SQLite backend
 1269: performs a single SQL JOIN after spilling source data, so per-DA parallelism
 1270: is irrelevant.
 1271: 
 1272: =back
 1273: 
 1274: B<Zero-copy ATTACH (C<dbi_source()> interface)>
 1275: 
 1276: Normally, when the SQLite path is active, rows from each component database
 1277: are fetched one by one and inserted into the temporary SQLite file.  This is
 1278: efficient but does involve INSERT overhead.
 1279: 
 1280: If a component database is itself SQLite-backed and implements a
 1281: C<dbi_source()> method, C<Database::Join> can skip the row-by-row copy
 1282: entirely and instead use C<ATTACH DATABASE> to link the source file directly
 1283: to the temporary join connection.  This is the zero-copy path and is
 1284: significantly faster for large SQLite sources.
 1285: 
 1286: The C<dbi_source()> method must return a hashref with two keys:
 1287: 
 1288: =over 4
 1289: 
 1290: =item C<dbh>
 1291: 
 1292: A connected C<DBD::SQLite> database handle (C<DBI> connection object).
 1293: 
 1294: =item C<table>
 1295: 
 1296: The name of the table in that database that holds the source rows.
 1297: 
 1298: =back
 1299: 
 1300: Example implementation:
 1301: 
 1302:     package My::SQLiteDatabase;
 1303:     use parent 'Database::Abstraction';
 1304: 
 1305:     sub dbi_source {
 1306:         my ($self) = @_;
 1307:         return {
 1308:             dbh   => $self->{_dbh},      # connected DBD::SQLite handle
 1309:             table => $self->{_table},    # table name in that database
 1310:         };
 1311:     }
 1312: 
 1313:     1;
 1314: 
 1315: The zero-copy ATTACH path is always used when a component database implements
 1316: C<dbi_source()>.  Query-time criteria are applied as parameterised SQL
 1317: C<WHERE> clauses against the ATTACHed source table, so no row-level copy is
 1318: needed even when the current call includes column filters.  (Prior to 0.005.0
 1319: any query-time criteria forced a spill; that restriction was removed in
 1320: 0.005.0.)
 1321: 
 1322: B<Result identity>
 1323: 
 1324: Both the array path and the SQLite path produce identical results for any
 1325: given query.  You can switch between them freely without changing callers.
 1326: The C<collision_prefix> column renaming, C<join_map> key translation, and all
 1327: three join types (left, inner, outer) work identically on both paths.

 1329: =head2 selectall_arrayref
 1330: 
 1331: =head3 SYNOPSIS
 1332: 
 1333:     my $rows = $join->selectall_arrayref();
 1334:     my $rows = $join->selectall_arrayref(tier  => 'gold');
 1335:     my $rows = $join->selectall_arrayref(score => { '>' => 80 });
 1336:     my $rows = $join->selectall_arrayref('C001');  # positional: entry => 'C001'
 1337:     my $rows = $join->selectall_arrayref(sort_by => 'name');
 1338:     my $rows = $join->selectall_arrayref(tier => 'gold', sort_by => ['score', 'DESC']);
 1339:     my $rows = $join->selectall_arrayref(limit => 10);
 1340:     my $rows = $join->selectall_arrayref(limit => 10, offset => 20);
 1341:     my $rows = $join->selectall_arrayref(tier => 'gold', sort_by => 'name', limit => 5);
 1342: 
 1343: =head3 DESCRIPTION
 1344: 
 1345: Returns an arrayref of hashrefs representing the merged view of all component
 1346: databases, optionally filtered by the given criteria.
 1347: 
 1348: Criteria for columns that live in different databases are routed
 1349: automatically: each database is queried with only the criteria that apply to
 1350: its own columns.  The results are combined in memory using C<join_column>.
 1351: 
 1352: Accepts the same criteria syntax as C<Database::Abstraction::selectall_arrayref>.
 1353: A single plain scalar argument is interpreted as the C<join_column> value
 1354: (equivalent to C<< entry => 'C001' >> when C<join_column> is C<'entry'>).
 1355: 
 1356: =head3 API SPECIFICATION
 1357: 
 1358: =head4 Input
 1359: 
 1360:     Calling conventions (in order of precedence):
 1361:       1. No arguments             -- returns all rows
 1362:       2. One plain scalar         -- shorthand for join_column => $scalar
 1363:       3. Key-value pairs or
 1364:          a criteria hashref       -- routed per-database
 1365: 
 1366:     Values may be:
 1367:       Plain scalar                -- exact match
 1368:       Hashref of operators        -- e.g. { '>' => 80 }
 1369: 
 1370:     Optional parameters (mixed in with any of the above):
 1371:       sort_by => 'colname'            -- sort ascending by that column
 1372:       sort_by => ['colname', 'DESC']  -- sort descending
 1373:       sort_by => ['colname', 'ASC']   -- sort ascending (explicit)
 1374:       limit    => N                    -- return at most N rows (positive integer)
 1375:       offset   => M                   -- skip the first M rows (non-negative integer)
 1376: 
 1377:     The column named in sort_by must be present in the merged view (i.e. it
 1378:     must appear in columns()).  An unknown column or an invalid direction emits
 1379:     a carp warning and falls back to the default join_column ascending sort.
 1380: 
 1381:     limit and offset are applied after ordering.  offset without limit skips
 1382:     rows but returns all remaining rows.  limit without offset starts from
 1383:     the first qualifying row.  An invalid limit or offset emits a carp warning
 1384:     and the parameter is ignored (treated as absent).
 1385: 
 1386:     DOMAIN -- sort_by:
 1387:       EP absent:          result sorted by join_column ASC (default).
 1388:       EP string:          any column name in columns(); sorts ASC by that column.
 1389:       EP ['col','ASC']:   explicit ascending; equivalent to the string form.
 1390:       EP ['col','DESC']:  descending sort by the named column.
 1391:       EP ['col']:         single-element arrayref; direction defaults to ASC.
 1392:       EP []:              empty arrayref; column is undef -> carp + join_col ASC fallback.
 1393:       EP invalid column:  column not in columns() -> carp + join_col ASC fallback.
 1394:       EP invalid dir:     direction not 'ASC' or 'DESC' -> carp + ASC used.
 1395:       Sort is lexicographic (cmp); use backend=>'sqlite' for numeric ORDER BY.
 1396: 
 1397:     DOMAIN -- limit:
 1398:       EP absent:          no truncation; all qualifying rows are returned.
 1399:       EP 0:               not a positive integer -> carp + ignored (all rows returned).
 1400:       BVA min valid = 1:  exactly 1 row returned.
 1401:       BVA at count:       limit == total rows -> all rows returned (no truncation).
 1402:       BVA above count:    limit > total rows -> all rows returned.
 1403:       EP invalid:         negative integer, float string, or non-numeric string
 1404:                           => carp + ignored (all rows returned).
 1405:       Valid domain:       integers in [1, INF); matched by /^\d+\z/a with value >= 1.
 1406: 
 1407:     DOMAIN -- offset:
 1408:       EP absent:          no rows skipped; result starts from row 0.
 1409:       BVA min valid = 0:  no rows skipped (zero is a valid non-negative integer).
 1410:       BVA offset=1:       first row skipped; result starts from row 1.
 1411:       BVA offset=N-1:     N-1 rows skipped; only the last row returned.
 1412:       BVA offset=N:       all N rows skipped; empty result returned.
 1413:       BVA offset>N:       all rows skipped; empty result returned.
 1414:       EP invalid:         negative integer, float string, or non-numeric string
 1415:                           => carp + ignored (no rows skipped).
 1416:       Valid domain:       integers in [0, INF); matched by /^\d+\z/a.
 1417: 
 1418: =head4 Output
 1419: 
 1420:     Arrayref of hashrefs; one hashref per qualifying merged row.
 1421:     Sorted ascending by join_column by default; caller-controlled via sort_by.
 1422:     At most C<limit> rows when limit is given; the first C<offset> rows are
 1423:     skipped when offset is given.
 1424:     Returns a reference to an empty array when no rows match.
 1425: 
 1426: =head3 EXAMPLE
 1427: 
 1428:     # All rows from both databases
 1429:     my $all = $join->selectall_arrayref();
 1430: 
 1431:     # Only rows where the 'tier' column (from the loyalty database)
 1432:     # equals 'gold' -- the criterion is routed to the right database
 1433:     my $vip = $join->selectall_arrayref(tier => 'gold');
 1434: 
 1435:     # Operator hashref: score > 80
 1436:     my $high = $join->selectall_arrayref(score => { '>' => 80 });
 1437: 
 1438:     # Access each merged row
 1439:     for my $row (@{$vip}) {
 1440:         printf "%-10s tier=%-8s score=%d\n",
 1441:             $row->{entry}, $row->{tier}, $row->{score} // 0;
 1442:     }

 4698: =head1 ENCODING
 4699: 
 4700: All text that passes through C<Database::Join> at the Perl layer (column names,
 4701: criteria values, merged row values) is treated as opaque strings.
 4702: C<Database::Join> does not inspect, encode, or transform string content.
 4703: 
 4704: =over 4
 4705: 
 4706: =item Column names
 4707: 
 4708: Column names are plain ASCII strings as returned by C<Database::Abstraction::columns()>.
 4709: Non-ASCII column names are accepted but not tested; behaviour depends on the
 4710: underlying DA and database driver.
 4711: 
 4712: =item Criteria values and row data
 4713: 
 4714: Values are passed verbatim between callers and component DAs.  Full UTF-8 is
 4715: safe as long as the underlying C<Database::Abstraction> objects and their
 4716: database drivers handle UTF-8 correctly.  C<Database::Join> neither encodes
 4717: nor decodes any value.
 4718: 
 4719: =item SQLite backend
 4720: 
 4721: When the SQLite path is active, values are inserted into the temporary SQLite
 4722: database via DBI placeholders (never string interpolation), so binary-safe
 4723: round-tripping depends on C<DBD::SQLite>'s character encoding settings.
 4724: By default C<DBD::SQLite> operates in UTF-8 mode, which is correct for text
 4725: data.  Binary blobs are not explicitly tested.
 4726: 
 4727: =item i18n messages
 4728: 
 4729: All internal error and warning messages route through the C<i18n> object
 4730: (if one is supplied) via a C<translate($key, @args)> call.  The translation
 4731: dictionary controls the final encoding of those strings.

 4963: =head1 SECURITY CONSIDERATIONS
 4964: 
 4965: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 4966: generates SQL strings, never opens files, and never calls C<system()>,
 4967: C<exec()>, or C<eval()>.  The security properties described below are
 4968: architectural guarantees, not run-time checks.
 4969: 
 4970: =head2 What Database::Join guarantees
 4971: 
 4972: =over 4
 4973: 
 4974: =item Criteria partition isolation
 4975: 
 4976: Every criterion you pass to a query method is routed to I<exactly one>
 4977: component database (the one that owns that column), or to I<all> databases
 4978: when the criterion is on the join key column.  A hostile value in a criterion
 4979: for column C<name> (owned by database A) will never reach database B.
 4980: 
 4981: =item Unknown columns are rejected before reaching any database
 4982: 
 4983: If a criterion column name is not present in any component database (or has
 4984: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 4985: and silently drops the criterion.  No database receives the hostile key.
 4986: 
 4987: =item AUTOLOAD only accepts word-character column names
 4988: 
 4989: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 4990: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 4991: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 4992: C<_>) are additionally blocked with an explicit C<croak>.
 4993: 
 4994: =item No value sanitisation (by design)
 4995: 
 4996: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 4997: I<values> in criteria hashrefs.  Preventing SQL injection is the
 4998: responsibility of the underlying C<Database::Abstraction> objects (which use
 4999: parameterised queries).  Preventing XSS or header injection is the
 5000: responsibility of the CGI or web layer that renders the output.
 5001: 
 5002: =item Taint-mode compatible (array path)
 5003: 
 5004: The array merge path contains no C<system()>, C<exec()>, backtick,
 5005: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 5006: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 5007: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 5008: an I<untainted> capture, so the column name used for dispatch is clean under
 5009: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 5010: objects; those objects are responsible for handling tainted values at the SQL
 5011: parameterisation layer.
 5012: 
 5013: =item SQLite backend: column names are quoted, values are parametrised
 5014: 
 5015: When the SQLite path is active, C<Database::Join> generates SQL internally.
 5016: All column and table names are double-quoted (SQL identifier quoting) before
 5017: being embedded in statement strings.  All row values are passed to SQLite
 5018: exclusively through DBI prepared statement placeholders -- never by string
 5019: interpolation.  A hostile value in a source row therefore cannot inject SQL
 5020: into the temporary database.
 5021: 
 5022: The temporary SQLite file is created by C<File::Temp> using a securely random,
 5023: unpredictable filename.  No C<system()> or shell command is used to create or
 5024: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 5025: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 5026: in the generated SQL come from C<columns()>, which is produced by
 5027: C<Database::Abstraction> at construction time -- they are not derived from
 5028: caller-supplied criteria values.
 5029: 
 5030: =item Operator hashref broadcast copy
 5031: 
 5032: When the same join-key criterion (an operator hashref such as
 5033: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 5034: database receives its own I<shallow copy> of the hashref.  A component database
 5035: that mutates the hashref's contents at the top level cannot affect what
 5036: subsequent databases receive.
 5037: 
 5038: =item collision_prefix value type guard
 5039: 
 5040: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 5041: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 5042: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 5043: column name, C<columns()> listing, and merged row returned to the caller.  The
 5044: guard fires before any column name is constructed.
 5045: 
 5046: =item Filter deep-copy isolation
 5047: 
 5048: The C<filters> constructor parameter and the C<filter> option of
 5049: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 5050: original hashrefs are never stored; post-construction mutation of those
 5051: hashrefs cannot widen or bypass the configured row-security constraints.
 5052: 
 5053: =back
 5054: 
 5055: =head2 What the caller is responsible for
 5056: 
 5057: =over 4
 5058: 
 5059: =item Sanitise values before building criteria
 5060: 
 5061: DJ passes criterion values verbatim to component databases.  If your
 5062: application accepts user-supplied filter values (e.g. from a CGI query
 5063: string), those values I<must> be validated or sanitised by your application
 5064: before being passed to DJ.
 5065: 
 5066: =item Restrict which columns the caller can filter on
 5067: 
 5068: Any column in C<columns()> can be used as a filter criterion.  If a column
 5069: should not be filterable by end users (e.g. an internal status flag), hide it
 5070: with C<remove_column> so that queries on it are silently dropped.
 5071: 
 5072: =item Do not expose the joined view directly to user-supplied criteria
 5073: 
 5074: DJ is not a firewall.  It faithfully routes user input to component databases.
 5075: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 5076: columns and validates their values.
 5077: 
 5078: =back

 5410: Governs the structural state of a C<Database::Join> instance.
 5411: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 5412: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 5413: are not shown because they do not change state.
 5414: 
 5415:     [pre-creation]
 5416:          |
 5417:          | new( databases => [...], join_column => '...' )
 5418:          |   Side-effect: _col_db routing table built;
 5419:          |                _autoload_pk cached from dbs[0]{id}
 5420:          v
 5421:     [CONSTRUCTED] <-----------------------------------------+
 5422:          |    |                                              |
 5423:          |    +--------------------------------------------+ |
 5424:          |    (query methods: no structural change)         | |
 5425:          |                                                  | |
 5426:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 5427:          |                                      |    |        |
 5428:          |   Side-effect: col removed from       |    |        |
 5429:          |   _col_db; _col_cache and             +----+        |
 5430:          |   _schema_cache cleared.              (idempotent;  |
 5431:          |   Join column cannot be removed.)      chainable)   |
 5432:          |                                                     |
 5433:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 5434:                                                 |    |
 5435:              Side-effect: new columns added;    |    | add_database( db )
 5436:              _col_db extended; SQLite cache     |    | (chainable; each
 5437:              invalidated (if any).              +----+  extends the view)
 5438: 
 5439:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 5440:     Both transitions are legal on any valid object, in any order.
 5441: 
 5442:     Illegal triggers (always croak; object state is not changed):
 5443: 
 5444:       Trigger                              Error
 5445:       -----------------------------------  ---------------------------------
 5446:       new( databases => [] )               error_no_databases
 5447:       remove_column( join_column )         error_remove_join_column
 5448:       add_database( non-reference )        error_invalid_database
 5449:       new() with join_col absent from DB   error_join_col_absent

 5451: =head2 FSM 2: SQLite Cache Lifecycle
 5452: 
 5453: Governs the temporary SQLite cache used by the C<backend='sqlite'> and
 5454: C<backend='auto'> join paths.  The cache does not exist until the first
 5455: query on the SQLite path.
 5456: 
 5457:     [ABSENT] <----- add_database( db )
 5458:        |                  |
 5459:        |  (no temp file)  | Side-effect: old DBI handle disconnected;
 5460:        |                  |   _sqlite_cache deleted.
 5461:        |                  |
 5462:        |                  +<-------------------------------------------+
 5463:        |                                                               |
 5464:        | first query on SQLite path                                    |
 5465:        | Side-effect: File::Temp db created in tmpdir;                 |
 5466:        |   DBI connected; sources ATTACHed or spilled;                 |
 5467:        |   _sqlite_cache = { dbh, tmpfile, n, updated, ... }           |
 5468:        v                                                               |
 5469:     [FRESH] <--+                                                       |
 5470:        |        |                                                      |
 5471:        |        | subsequent queries                                   |
 5472:        |        | (cache reused; refaddr of _sqlite_cache unchanged)   |
 5473:        +--------+                                                      |
 5474:        |                                                               |
 5475:        | updated() timestamp of any source DA changes                  |
 5476:        | -- OR -- source row count changes                             |
 5477:        | Side-effect: none yet (_cache_fresh returns false)            |
 5478:        v                                                               |
 5479:     [STALE]                                                            |
 5480:        |                                                               |
 5481:        | next query                                                    |
 5482:        | Side-effect: old DBI handle disconnected; old temp file       |
 5483:        |   unlinked; new temp file built from current source data.     |
 5484:        +---------------------------------------------------------------+
 5485:        (transitions to FRESH)
 5486: 
 5487:     On object DESTROY:
 5488:       FRESH/STALE:  DBI handle disconnected; File::Temp object released
 5489:                     (temp file unlinked by File::Temp DESTROY).
 5490:       ABSENT:       No temp file exists; no-op.

 5492: =head2 FSM 3: Column Visibility (per column)
 5493: 
 5494: Each column in the logical view independently follows a two-state machine.
 5495: Transition from VISIBLE to REMOVED is one-way: C<add_database> never
 5496: restores a column that is in C<_removed_cols>.
 5497: 
 5498:     [VISIBLE] <-- initial state for every column at construction
 5499:          |    |
 5500:          |    | query / columns() / schema()
 5501:          |    | (column present in results; no state change)
 5502:          +----+
 5503:          |
 5504:          | remove_column( col )
 5505:          | Side-effect: col deleted from _col_db;
 5506:          |   _col_cache and _schema_cache cleared.
 5507:          v
 5508:     [REMOVED] <---+
 5509:          |         |
 5510:          |         | remove_column( col ) again
 5511:          |         | (idempotent; no error; no second side-effect)
 5512:          +---------+
 5513: 
 5514:     One-way invariant:
 5515:       If col is in _removed_cols, then add_database( db_that_has_col )
 5516:       does NOT re-add it.  Formal: col_db' = col_db âŠ• { c | c in
