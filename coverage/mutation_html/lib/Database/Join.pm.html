  193: =head1 DESCRIPTION
  194: 
  195: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  196: single logical, read-only view.  Each component database is queried
  197: independently through its own C<Database::Abstraction> interface.  The results
  198: are combined using a shared key column (C<join_column>).
  199: In effect, this means that you can view data from more than one database using
  200: an intuitive, non-SQL interface.
  201: 
  202: Every storage format that C<Database::Abstraction> supports works as a
  203: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  204: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  205: within the same join.
  206: 
  207: The module exposes the same read-only API as C<Database::Abstraction>:
  208: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  209: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  210: shortcut.  Callers do not need to know how many underlying databases are
  211: involved.
  212: 
  213: Think of it as a virtual database table that is assembled on demand from
  214: several real tables, one per component database.
  215: 
  216: B<Join backends>
  217: 
  218: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  219: combined source row count.  For small datasets (up to C<max_array_rows>,
  220: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  221: automatically spills source rows into a temporary SQLite database and executes
  222: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  223: size instead of three.  You can also force either path unconditionally with
  224: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  225: 
  226: =head2 Join semantics
  227: 
  228: The C<join_type> parameter controls what happens when a particular key value
  229: exists in some component databases but not all:
  230: 
  231: =over 4
  232: 
  233: =item C<left> (the default)
  234: 
  235: All rows from the I<primary> (first) database are returned.  Columns from
  236: subsequent databases are included where a matching row is found, and simply
  237: absent from the hashref where there is no match.  If you are familiar with
  238: SQL, this is a LEFT OUTER JOIN on the first table.
  239: 
  240: =item C<inner>
  241: 
  242: Only rows whose join-column value is present in I<every> component database
  243: are returned.  This is equivalent to a SQL INNER JOIN.
  244: 
  245: =item C<outer>
  246: 
  247: Every join-column value found in I<any> component database is returned.
  248: Columns from databases that do not have that key value are absent from the
  249: merged row.  This is a FULL OUTER JOIN.
  250: 
  251: =back
  252: 
  253: B<Important override rule:> whenever you pass a query criterion for a column
  254: that belongs to a secondary database, that database automatically acts as an
  255: inner-join partner for that query only -- regardless of C<join_type>.  This
  256: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  257: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  258: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  259: as a WHERE clause would exclude them).
  260: 
  261: =head2 Column ownership and routing
  262: 
  263: At construction time, C<Database::Join> calls C<columns()> on each component
  264: database and builds an internal index that maps every column name to the
  265: database that owns it.
  266: 
  267: When you pass criteria to a query method, each key-value pair is automatically
  268: routed to the right database.  You never need to say which database a column
  269: belongs to.
  270: 
  271: The C<join_column> is special: criteria on it are broadcast to I<all>
  272: databases so that each database fetches only the relevant rows before the
  273: in-memory merge.
  274: 
  275: When the same non-join column name exists in more than one database, the
  276: I<last> database in the C<databases> array wins by default: its value
  277: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  278: preserve both values under distinct names instead.
  279: 
  280: =head1 LIMITATIONS
  281: 
  282: =over 4
  283: 
  284: =item Memory usage (array backend)
  285: 
  286: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  287: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  288: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  289: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  290: 
  291: =item SQLite backend uses a persistent cache file
  292: 
  293: When the SQLite path is active, a single C<.db> file with a randomly generated
  294: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  295: first time a query runs on a given C<Database::Join> object.  Source data is
  296: spilled into that file once; subsequent queries against the same object reuse
  297: the file without re-fetching the source data.
  298: 
  299: The cache is automatically invalidated and rebuilt whenever any source
  300: database's C<updated()> timestamp changes (indicating new data), or when
  301: C<add_database()> is called.
  302: 
  303: The file is deleted when the C<Database::Join> object is destroyed (typically
  304: when it goes out of scope).  At any given moment no more than one such file
  305: exists per object.  The directory must be writable and have enough free space
  306: for the full source data (once, not per-query).
  307: 
  308: =item No chained builder or raw SQL
  309: 
  310: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  311: or C<fetchrow_hashref> instead.
  312: 
  313: =item Single-column equi-join only
  314: 
  315: Joining on more than one column simultaneously, or on expressions, is not
  316: supported.  When the join key has different names in different databases,
  317: use C<join_map> to declare each database's local column name.
  318: 
  319: =item Sort order
  320: 
  321: Results are sorted ascending by C<join_column> by default.  Pass
  322: C<< order_by => 'colname' >> (or C<< order_by => ['colname', 'DESC'] >>)
  323: to any query method to override this.  The array path uses string comparison
  324: (C<cmp>); for accurate numeric ordering on large datasets use the SQLite
  325: backend, which sorts natively by type.
  326: 
  327: =item count() fetches all rows
  328: 
  329: C<count()> executes the full join and counts the resulting rows in Perl.  It
  330: does not push a C<COUNT(*)> query down to the databases.
  331: 
  332: =back

  334: =head1 COMMON PITFALLS
  335: 
  336: =over 4
  337: 
  338: =item The join_column must exist in every component database
  339: 
  340: If even one database is missing the join key column, C<new()> (or
  341: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  342: column has a different local name in some databases.
  343: 
  344: =item Criteria on a removed column are silently dropped
  345: 
  346: If you call C<remove_column('tier')> and later query
  347: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  348: C<carp> warning) and all rows are returned.  Always pass criteria before
  349: removing columns, or restructure your code to avoid this.
  350: 
  351: =item You cannot remove the join column
  352: 
  353: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  354: is required for the merge to work.
  355: 
  356: =item Left join does not guarantee all columns are populated
  357: 
  358: Under a LEFT join, rows from the primary database that have no matching row
  359: in a secondary database will be returned with I<no keys> from that secondary
  360: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  361: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  362: than just C<$row->{score}> when the secondary match is optional.
  363: 
  364: =item Filters act as inner-join partners
  365: 
  366: Any database that has a C<filters> entry is promoted to an inner-join partner,
  367: regardless of C<join_type>.  A row whose join-key value does not appear in
  368: the filtered database's result is removed from the merged output entirely, not
  369: merely missing its secondary columns.  This is intentional but can be
  370: surprising if you expected LEFT join semantics.
  371: 
  372: =item Criteria-merging replaces scalar filters
  373: 
  374: When both a base filter and a query criterion target the same column, and both
  375: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  376: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  377: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  378: the base filter is ignored for that query.
  379: 
  380: =item AUTOLOAD sees the full merged join when filters or join_map are active
  381: 
  382: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  383: (C<< $join->columnname(...) >>) runs the full join query rather than
  384: delegating directly to the owning database.  This is necessary for correctness
  385: but means the result respects all active filters and join-key translations,
  386: which may differ from what the owning database would return on its own.
  387: 
  388: =item Duplicate column names: last database wins (unless collision_prefix is set)
  389: 
  390: When two component databases each have a column called C<notes>, the second
  391: database's value silently overwrites the first in every merged row.  Use
  392: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  393: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  394: (or C<remove_column>) to drop the unwanted duplicate entirely.
  395: 
  396: =item Mutating the filters hashref after construction has no effect
  397: 
  398: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  399: passed to C<add_database>) at the moment of construction.  The original hashref
  400: you passed in is never stored.  If you later modify it -- for example, to
  401: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  402: Construct a new C<Database::Join> object, or use a component
  403: C<Database::Abstraction> that supports dynamic filter modification.
  404: 
  405: =item auto mode may always use the array path for some DAs
  406: 
  407: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  408: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  409: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  410: from C<Database::Abstraction> is treated as uncountable, because the parent
  411: class C<count()> expects a key argument and behaves differently from a
  412: "return total row count" function.  In that case C<Database::Join>
  413: conservatively uses the array path for the whole query, even if the dataset is
  414: large.  To opt in to the SQLite path for such a DA, either add your own
  415: C<count()> override that returns the total row count, implement C<dbi_source()>,
  416: or use C<backend =E<gt> 'sqlite'> unconditionally.
  417: 
  418: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  419: 
  420: When a component database implements C<dbi_source()>, C<Database::Join> always
  421: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  422: for columns in that database>.  The criteria are translated into parameterised
  423: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  424: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  425: force a spill; that restriction has been removed.)
  426: 
  427: =item Broadcast join-column criterion does not force secondaries into inner-join
  428: 
  429: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  430: C<Database::Join> broadcasts it to all component databases so each DA can
  431: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  432: incorrectly counted as "having criteria" for secondary databases, causing
  433: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  434: join-column criterion was present.  The fix: only non-join-column criteria
  435: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  436: a secondary to inner-join status.  The broadcast itself is now a transparent
  437: key-range selector that does not affect join semantics.
  438: 
  439: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  440: 
  441: C<LIKE>, C<NOT LIKE>, C<IN>, and C<NOT IN> are fully supported on the SQLite
  442: backend.  C<LIKE>/C<NOT LIKE> take a scalar pattern; C<IN>/C<NOT IN> take an
  443: arrayref of values.  All are injection-safe because values are passed as bind
  444: parameters, never interpolated.
  445: 
  446:     # LIKE
  447:     my $rows = $join->selectall_arrayref(name => { LIKE => 'A%' });
  448: 
  449:     # IN
  450:     my $rows = $join->selectall_arrayref(tier => { IN => ['gold', 'silver'] });
  451: 
  452:     # NOT IN
  453:     my $rows = $join->selectall_arrayref(tier => { 'NOT IN' => ['bronze'] });
  454: 
  455: C<IN> with an empty arrayref matches no rows (SQL semantics: C<IN ()> is
  456: always false).  C<NOT IN> with an empty arrayref matches all rows (no
  457: constraint added).
  458: 
  459: C<IS NULL> and C<IS NOT NULL> are supported on the SQLite backend using an
  460: explicit operator hashref:
  461: 
  462:     my $rows = $join->selectall_arrayref(score => { 'IS NULL'     => undef });
  463:     my $rows = $join->selectall_arrayref(score => { 'IS NOT NULL' => 1    });
  464: 
  465: The hashref value is ignored; only the key selects the operator.  A bare
  466: C<undef> criterion value (C<< score => undef >>) also generates C<IS NULL>
  467: on the SQLite path.  Note: on the in-memory array path, the component DA
  468: may treat an C<undef> criterion value as C<< no filter >> rather than
  469: C<IS NULL>, so use the explicit hashref form for consistent behaviour
  470: across backends.
  471: 
  472: Any operator not in the supported set is skipped on the SQLite path with a
  473: C<carp> warning.  The array path forwards all operators to the component DA
  474: unchanged, which may or may not honour them.
  475: 
  476: =item Temp file directory must be writable and have free space
  477: 
  478: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  479: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  480: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  481: only the directory is under your control.  The file is created on the first
  482: query and kept alive until the object is destroyed; it is not re-created on
  483: every query call.  If the directory is not writable, or the filesystem is full,
  484: the call will C<croak> with C<error_sqlite_connect>.  Check permissions and
  485: free space if you see that error.
  486: 
  487: =back

  799: =head2 join_map - joining on differently-named columns
  800: 
  801: By default every component database must have a column whose name matches
  802: C<join_column>.  If a database uses a different local name for the join key,
  803: declare the mapping with C<join_map>.
  804: 
  805: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  806: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  807: B<value> is the name that B<that particular database> uses for the join key.
  808: 
  809: Databases not listed in C<join_map> are assumed to already have a column
  810: named C<join_column> and need no entry.
  811: 
  812: Throughout the merged view the join key is I<always> referred to by the name
  813: given in C<join_column>.  The local alias is never exposed in returned rows,
  814: in C<columns()>, or in C<schema()>.
  815: 
  816: B<When do you need join_map?>
  817: 
  818: You need C<join_map> when you have two tables like:
  819: 
  820:     cities table  : entry (the city name) | statecode
  821:     stnames table : entry (the state code) | state
  822: 
  823: Here you want to join cities.statecode to stnames.entry.  You choose
  824: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  825: that same concept C<entry>, so you declare:
  826: 
  827:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  828: 
  829: B<Example>
  830: 
  831:     #                        index 0     index 1
  832:     my @databases = (       $cities,    $stnames  );
  833:     #  join key column:    'statecode'  'entry'
  834:     #  join_column:        'statecode' (chosen canonical name)
  835:     #  stnames differs, so declare the alias:
  836: 
  837:     my $join = Database::Join->new(

  862: =head2 filters - permanent per-database row filters
  863: 
  864: C<filters> lets you restrict a component database to a subset of its rows
  865: permanently, without repeating the criterion on every query call.
  866: 
  867: Think of it as telling the join: "whenever you query this database, always
  868: add these extra conditions".  Callers never need to specify the restriction
  869: themselves and can never accidentally omit it.
  870: 
  871: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  872: database in the C<databases> array (same numbering as C<join_map>).  Each
  873: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  874: accepts.
  875: 
  876: B<Key-set semantics>
  877: 
  878: A filtered database always acts as an inner-join partner, regardless of the
  879: C<join_type> setting.  Any join-key value that does not pass the filter is
  880: excluded from the merged output entirely -- not just missing its secondary
  881: columns.  This ensures the filter genuinely restricts the view rather than
  882: simply hiding a few fields.
  883: 
  884: B<Criteria merging>
  885: 
  886: When a query call also passes a criterion for a column that already has a base
  887: filter, the two constraints are combined:
  888: 
  889: =over 4
  890: 
  891: =item *
  892: 
  893: When both the base filter value and the query criterion are operator hashrefs
  894: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  895: merged: I<both> constraints apply simultaneously (AND semantics).
  896: 
  897: =item *
  898: 
  899: When either value is a plain scalar, or the operators conflict, the
  900: query-time criterion wins and the base filter for that column is ignored for
  901: that one call.
  902: 
  903: =back
  904:

  906: 
  907:     my $join = Database::Join->new(

  927: =head2 collision_prefix - preserve colliding columns from secondary databases
  928: 
  929: By default, when a column name appears in more than one database the I<last>
  930: database wins: its value silently overwrites earlier ones in merged rows.
  931: This loses data and makes the origin invisible.
  932: 
  933: C<collision_prefix> changes this for secondary databases you designate.
  934: When a secondary database at index N has a column that already exists in the
  935: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  936: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  937: visible: the original column keeps its name (from the earlier database), and
  938: the collision gets the prefixed name.
  939: 
  940: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  941: a secondary database in the C<databases> array (same numbering as C<join_map>).
  942: Each B<value> is the prefix string to prepend.  An index-0 entry is
  943: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  944: preserves the previous last-wins behaviour and changes nothing.
  945: 
  946: Non-colliding columns from a secondary database are always added as-is with
  947: no prefix, whether or not C<collision_prefix> is configured.
  948: 
  949: B<Example -- sales table and products table, both with a "product" column>

  951:     # $sales    columns: id, product, amount, date
  952:     # $products columns: sku, product, price, category
  953:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  954: 
  955:     my $join = Database::Join->new(
  956:         databases        => [$sales, $products],
  957:         join_column      => 'product',
  958:         join_map         => { 1 => 'sku' },
  959:         collision_prefix => { 1 => 'products' },
  960:     );
  961: 
  962:     $join->columns;
  963:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  964:     #                                                               ^-- prefixed collision
  965: 
  966:     my $row = $join->fetchrow_hashref(product => 'widget');
  967:     # $row->{product}            -- value from $sales
  968:     # $row->{'products.product'} -- value from $products (different row, same column name)
  969:     # $row->{price}              -- from $products, no collision, kept as-is
  970:

  985: =head2 backend - SQLite join backend for large datasets
  986: 
  987: C<Database::Join> can merge component databases in two different ways,
  988: controlled by the C<backend> constructor parameter.
  989: 
  990: =over 4
  991: 
  992: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  993: 
  994: All matching rows are fetched from every component database into Perl hashes
  995: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
  996: is roughly three times the combined source data size (one copy per database
  997: plus one merged copy).
  998: 
  999: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1000: 
 1001: C<Database::Join> creates a temporary SQLite database file, spills source
 1002: rows into it (one table per component database), then executes a single SQL
 1003: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1004: source data size.
 1005: 
 1006: The temporary file is created once and reused across multiple query calls on
 1007: the same object (the cache).  Only query-time criteria vary per call; they
 1008: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1009: automatically rebuilt when any source database's C<updated()> timestamp
 1010: changes.  The file is deleted when the object is destroyed (goes out of
 1011: scope).  See I<Temporary file: name, location, and lifetime> below for
 1012: details.

 1014: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in

 1032:

 1038: method in its own package -- not just inherit one from a parent class.  If

 1040: safe and uses the array path for the whole query without fetching any rows.

 3568: =head1 SECURITY CONSIDERATIONS
 3569: 
 3570: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3571: generates SQL strings, never opens files, and never calls C<system()>,
 3572: C<exec()>, or C<eval()>.  The security properties described below are
 3573: architectural guarantees, not run-time checks.
 3574: 
 3575: =head2 What Database::Join guarantees
 3576: 
 3577: =over 4
 3578: 
 3579: =item Criteria partition isolation
 3580: 
 3581: Every criterion you pass to a query method is routed to I<exactly one>
 3582: component database (the one that owns that column), or to I<all> databases
 3583: when the criterion is on the join key column.  A hostile value in a criterion
 3584: for column C<name> (owned by database A) will never reach database B.
 3585: 
 3586: =item Unknown columns are rejected before reaching any database
 3587: 
 3588: If a criterion column name is not present in any component database (or has
 3589: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3590: and silently drops the criterion.  No database receives the hostile key.
 3591: 
 3592: =item AUTOLOAD only accepts word-character column names
 3593: 
 3594: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3595: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3596: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3597: C<_>) are additionally blocked with an explicit C<croak>.
 3598: 
 3599: =item No value sanitisation (by design)
 3600: 
 3601: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3602: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3603: responsibility of the underlying C<Database::Abstraction> objects (which use
 3604: parameterised queries).  Preventing XSS or header injection is the
 3605: responsibility of the CGI or web layer that renders the output.
 3606: 
 3607: =item Taint-mode compatible (array path)
 3608: 
 3609: The array merge path contains no C<system()>, C<exec()>, backtick,
 3610: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3611: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3612: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3613: an I<untainted> capture, so the column name used for dispatch is clean under
 3614: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3615: objects; those objects are responsible for handling tainted values at the SQL
 3616: parameterisation layer.
 3617: 
 3618: =item SQLite backend: column names are quoted, values are parametrised
 3619: 
 3620: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3621: All column and table names are double-quoted (SQL identifier quoting) before
 3622: being embedded in statement strings.  All row values are passed to SQLite
 3623: exclusively through DBI prepared statement placeholders -- never by string
 3624: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3625: into the temporary database.
 3626: 
 3627: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3628: unpredictable filename.  No C<system()> or shell command is used to create or
 3629: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3630: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3631: in the generated SQL come from C<columns()>, which is produced by
 3632: C<Database::Abstraction> at construction time -- they are not derived from
 3633: caller-supplied criteria values.
 3634: 
 3635: =item Operator hashref broadcast copy
 3636: 
 3637: When the same join-key criterion (an operator hashref such as
 3638: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3639: database receives its own I<shallow copy> of the hashref.  A component database
 3640: that mutates the hashref's contents at the top level cannot affect what
 3641: subsequent databases receive.
 3642: 
 3643: =item collision_prefix value type guard
 3644: 
 3645: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3646: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3647: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3648: column name, C<columns()> listing, and merged row returned to the caller.  The
 3649: guard fires before any column name is constructed.
 3650: 
 3651: =item Filter deep-copy isolation
 3652: 
 3653: The C<filters> constructor parameter and the C<filter> option of
 3654: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3655: original hashrefs are never stored; post-construction mutation of those
 3656: hashrefs cannot widen or bypass the configured row-security constraints.
 3657: 
 3658: =back
