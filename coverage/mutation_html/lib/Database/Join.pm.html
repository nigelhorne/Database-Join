  219: =head1 DESCRIPTION
  220: 
  221: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  222: single logical, read-only view.  Each component database is queried
  223: independently through its own C<Database::Abstraction> interface.  The results
  224: are combined using a shared key column (C<join_column>).
  225: In effect, this means that you can view data from more than one database using
  226: an intuitive, non-SQL interface.
  227: 
  228: Every storage format that C<Database::Abstraction> supports works as a
  229: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  230: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  231: within the same join.
  232: 
  233: The module exposes the same read-only API as C<Database::Abstraction>:
  234: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  235: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  236: shortcut.  Callers do not need to know how many underlying databases are
  237: involved.
  238: 
  239: Think of it as a virtual database table that is assembled on demand from
  240: several real tables, one per component database.
  241: 
  242: B<Join backends>
  243: 
  244: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  245: combined source row count.  For small datasets (up to C<max_array_rows>,
  246: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  247: automatically spills source rows into a temporary SQLite database and executes
  248: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  249: size instead of three.  You can also force either path unconditionally with
  250: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  251: 
  252: =head2 Join semantics
  253: 
  254: The C<join_type> parameter controls what happens when a particular key value
  255: exists in some component databases but not all:
  256: 
  257: =over 4
  258: 
  259: =item C<left> (the default)
  260: 
  261: All rows from the I<primary> (first) database are returned.  Columns from
  262: subsequent databases are included where a matching row is found, and simply
  263: absent from the hashref where there is no match.  If you are familiar with
  264: SQL, this is a LEFT OUTER JOIN on the first table.
  265: 
  266: =item C<inner>
  267: 
  268: Only rows whose join-column value is present in I<every> component database
  269: are returned.  This is equivalent to a SQL INNER JOIN.
  270: 
  271: =item C<outer>
  272: 
  273: Every join-column value found in I<any> component database is returned.
  274: Columns from databases that do not have that key value are absent from the
  275: merged row.  This is a FULL OUTER JOIN.
  276: 
  277: =back
  278: 
  279: B<Important override rule:> whenever you pass a query criterion for a column
  280: that belongs to a secondary database, that database automatically acts as an
  281: inner-join partner for that query only -- regardless of C<join_type>.  This
  282: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  283: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  284: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  285: as a WHERE clause would exclude them).
  286: 
  287: =head2 Column ownership and routing
  288: 
  289: At construction time, C<Database::Join> calls C<columns()> on each component
  290: database and builds an internal index that maps every column name to the
  291: database that owns it.
  292: 
  293: When you pass criteria to a query method, each key-value pair is automatically
  294: routed to the right database.  You never need to say which database a column
  295: belongs to.
  296: 
  297: The C<join_column> is special: criteria on it are broadcast to I<all>
  298: databases so that each database fetches only the relevant rows before the
  299: in-memory merge.
  300: 
  301: When the same non-join column name exists in more than one database, the
  302: I<last> database in the C<databases> array wins by default: its value
  303: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  304: preserve both values under distinct names instead.
  305: 
  306: =head1 LIMITATIONS
  307: 
  308: =over 4
  309: 
  310: =item Memory usage (array backend)
  311: 
  312: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  313: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  314: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  315: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  316: 
  317: =item SQLite backend uses a persistent cache file
  318: 
  319: When the SQLite path is active, a single C<.db> file with a randomly generated
  320: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  321: first time a query runs on a given C<Database::Join> object.  Source data is
  322: spilled into that file once; subsequent queries against the same object reuse
  323: the file without re-fetching the source data.
  324: 
  325: The cache is automatically invalidated and rebuilt whenever any source
  326: database's C<updated()> timestamp changes (indicating new data), or when
  327: C<add_database()> is called.
  328: 
  329: The file is deleted when the C<Database::Join> object is destroyed (typically
  330: when it goes out of scope).  At any given moment no more than one such file
  331: exists per object.  The directory must be writable and have enough free space
  332: for the full source data (once, not per-query).
  333: 
  334: =item No chained builder or raw SQL
  335: 
  336: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  337: or C<fetchrow_hashref> instead.
  338: 
  339: =item Single-column equi-join only
  340: 
  341: Joining on more than one column simultaneously, or on expressions, is not
  342: supported.  When the join key has different names in different databases,
  343: use C<join_map> to declare each database's local column name.
  344: 
  345: =item Sort order
  346: 
  347: Results are sorted by the C<join_column> value only.  Caller-specified
  348: C<ORDER BY> is not propagated to the component databases.
  349: 
  350: =item count() fetches all rows
  351: 
  352: C<count()> executes the full join and counts the resulting rows in Perl.  It
  353: does not push a C<COUNT(*)> query down to the databases.
  354: 
  355: =back

  357: =head1 COMMON PITFALLS
  358: 
  359: =over 4
  360: 
  361: =item The join_column must exist in every component database
  362: 
  363: If even one database is missing the join key column, C<new()> (or
  364: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  365: column has a different local name in some databases.
  366: 
  367: =item Criteria on a removed column are silently dropped
  368: 
  369: If you call C<remove_column('tier')> and later query
  370: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  371: C<carp> warning) and all rows are returned.  Always pass criteria before
  372: removing columns, or restructure your code to avoid this.
  373: 
  374: =item You cannot remove the join column
  375: 
  376: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  377: is required for the merge to work.
  378: 
  379: =item Left join does not guarantee all columns are populated
  380: 
  381: Under a LEFT join, rows from the primary database that have no matching row
  382: in a secondary database will be returned with I<no keys> from that secondary
  383: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  384: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  385: than just C<$row->{score}> when the secondary match is optional.
  386: 
  387: =item Filters act as inner-join partners
  388: 
  389: Any database that has a C<filters> entry is promoted to an inner-join partner,
  390: regardless of C<join_type>.  A row whose join-key value does not appear in
  391: the filtered database's result is removed from the merged output entirely, not
  392: merely missing its secondary columns.  This is intentional but can be
  393: surprising if you expected LEFT join semantics.
  394: 
  395: =item Criteria-merging replaces scalar filters
  396: 
  397: When both a base filter and a query criterion target the same column, and both
  398: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  399: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  400: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  401: the base filter is ignored for that query.
  402: 
  403: =item AUTOLOAD sees the full merged join when filters or join_map are active
  404: 
  405: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  406: (C<< $join->columnname(...) >>) runs the full join query rather than
  407: delegating directly to the owning database.  This is necessary for correctness
  408: but means the result respects all active filters and join-key translations,
  409: which may differ from what the owning database would return on its own.
  410: 
  411: =item Duplicate column names: last database wins (unless collision_prefix is set)
  412: 
  413: When two component databases each have a column called C<notes>, the second
  414: database's value silently overwrites the first in every merged row.  Use
  415: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  416: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  417: (or C<remove_column>) to drop the unwanted duplicate entirely.
  418: 
  419: =item Mutating the filters hashref after construction has no effect
  420: 
  421: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  422: passed to C<add_database>) at the moment of construction.  The original hashref
  423: you passed in is never stored.  If you later modify it -- for example, to
  424: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  425: Construct a new C<Database::Join> object, or use a component
  426: C<Database::Abstraction> that supports dynamic filter modification.
  427: 
  428: =item auto mode may always use the array path for some DAs
  429: 
  430: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  431: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  432: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  433: from C<Database::Abstraction> is treated as uncountable, because the parent
  434: class C<count()> expects a key argument and behaves differently from a
  435: "return total row count" function.  In that case C<Database::Join>
  436: conservatively uses the array path for the whole query, even if the dataset is
  437: large.  To opt in to the SQLite path for such a DA, either add your own
  438: C<count()> override that returns the total row count, implement C<dbi_source()>,
  439: or use C<backend =E<gt> 'sqlite'> unconditionally.
  440: 
  441: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  442: 
  443: When a component database implements C<dbi_source()>, C<Database::Join> always
  444: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  445: for columns in that database>.  The criteria are translated into parameterised
  446: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  447: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  448: force a spill; that restriction has been removed.)
  449: 
  450: =item Broadcast join-column criterion does not force secondaries into inner-join
  451: 
  452: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  453: C<Database::Join> broadcasts it to all component databases so each DA can
  454: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  455: incorrectly counted as "having criteria" for secondary databases, causing
  456: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  457: join-column criterion was present.  The fix: only non-join-column criteria
  458: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  459: a secondary to inner-join status.  The broadcast itself is now a transparent
  460: key-range selector that does not affect join semantics.
  461: 
  462: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  463: 
  464: C<LIKE>, C<NOT LIKE>, C<IN>, and C<NOT IN> are fully supported on the SQLite
  465: backend.  C<LIKE>/C<NOT LIKE> take a scalar pattern; C<IN>/C<NOT IN> take an
  466: arrayref of values.  All are injection-safe because values are passed as bind
  467: parameters, never interpolated.
  468: 
  469:     # LIKE
  470:     my $rows = $join->selectall_arrayref(name => { LIKE => 'A%' });
  471: 
  472:     # IN
  473:     my $rows = $join->selectall_arrayref(tier => { IN => ['gold', 'silver'] });
  474: 
  475:     # NOT IN
  476:     my $rows = $join->selectall_arrayref(tier => { 'NOT IN' => ['bronze'] });
  477: 
  478: C<IN> with an empty arrayref matches no rows (SQL semantics: C<IN ()> is
  479: always false).  C<NOT IN> with an empty arrayref matches all rows (no
  480: constraint added).
  481: 
  482: C<IS NULL> and C<IS NOT NULL> are supported on the SQLite backend using an
  483: explicit operator hashref:
  484: 
  485:     my $rows = $join->selectall_arrayref(score => { 'IS NULL'     => undef });
  486:     my $rows = $join->selectall_arrayref(score => { 'IS NOT NULL' => 1    });
  487: 
  488: The hashref value is ignored; only the key selects the operator.  A bare
  489: C<undef> criterion value (C<< score => undef >>) also generates C<IS NULL>
  490: on the SQLite path.  Note: on the in-memory array path, the component DA
  491: may treat an C<undef> criterion value as C<< no filter >> rather than
  492: C<IS NULL>, so use the explicit hashref form for consistent behaviour

  804: =head2 join_map - joining on differently-named columns
  805: 
  806: By default every component database must have a column whose name matches
  807: C<join_column>.  If a database uses a different local name for the join key,
  808: declare the mapping with C<join_map>.
  809: 
  810: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  811: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  812: B<value> is the name that B<that particular database> uses for the join key.
  813: 
  814: Databases not listed in C<join_map> are assumed to already have a column
  815: named C<join_column> and need no entry.
  816: 
  817: Throughout the merged view the join key is I<always> referred to by the name
  818: given in C<join_column>.  The local alias is never exposed in returned rows,
  819: in C<columns()>, or in C<schema()>.
  820: 
  821: B<When do you need join_map?>
  822: 
  823: You need C<join_map> when you have two tables like:
  824: 
  825:     cities table  : entry (the city name) | statecode
  826:     stnames table : entry (the state code) | state
  827: 
  828: Here you want to join cities.statecode to stnames.entry.  You choose
  829: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  830: that same concept C<entry>, so you declare:
  831: 
  832:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  833: 
  834: B<Example>
  835: 
  836:     #                        index 0     index 1
  837:     my @databases = (       $cities,    $stnames  );
  838:     #  join key column:    'statecode'  'entry'
  839:     #  join_column:        'statecode' (chosen canonical name)
  840:     #  stnames differs, so declare the alias:
  841: 
  842:     my $join = Database::Join->new(
  843:         databases   => \@databases,
  844:         join_column => 'statecode',
  845:         join_map    => { 1 => 'entry' },

  867: =head2 filters - permanent per-database row filters
  868: 
  869: C<filters> lets you restrict a component database to a subset of its rows
  870: permanently, without repeating the criterion on every query call.
  871: 
  872: Think of it as telling the join: "whenever you query this database, always
  873: add these extra conditions".  Callers never need to specify the restriction
  874: themselves and can never accidentally omit it.
  875: 
  876: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  877: database in the C<databases> array (same numbering as C<join_map>).  Each
  878: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  879: accepts.
  880: 
  881: B<Key-set semantics>
  882: 
  883: A filtered database always acts as an inner-join partner, regardless of the
  884: C<join_type> setting.  Any join-key value that does not pass the filter is
  885: excluded from the merged output entirely -- not just missing its secondary
  886: columns.  This ensures the filter genuinely restricts the view rather than
  887: simply hiding a few fields.
  888: 
  889: B<Criteria merging>
  890: 
  891: When a query call also passes a criterion for a column that already has a base
  892: filter, the two constraints are combined:
  893: 
  894: =over 4
  895: 
  896: =item *
  897: 
  898: When both the base filter value and the query criterion are operator hashrefs
  899: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  900: merged: I<both> constraints apply simultaneously (AND semantics).
  901: 
  902: =item *
  903: 
  904: When either value is a plain scalar, or the operators conflict, the
  905: query-time criterion wins and the base filter for that column is ignored for
  906: that one call.
  907: 
  908: =back
  909:

  911: 
  912:     my $join = Database::Join->new(

  932: =head2 collision_prefix - preserve colliding columns from secondary databases
  933: 
  934: By default, when a column name appears in more than one database the I<last>
  935: database wins: its value silently overwrites earlier ones in merged rows.
  936: This loses data and makes the origin invisible.
  937: 
  938: C<collision_prefix> changes this for secondary databases you designate.
  939: When a secondary database at index N has a column that already exists in the
  940: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  941: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  942: visible: the original column keeps its name (from the earlier database), and
  943: the collision gets the prefixed name.
  944: 
  945: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  946: a secondary database in the C<databases> array (same numbering as C<join_map>).
  947: Each B<value> is the prefix string to prepend.  An index-0 entry is
  948: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  949: preserves the previous last-wins behaviour and changes nothing.
  950: 
  951: Non-colliding columns from a secondary database are always added as-is with
  952: no prefix, whether or not C<collision_prefix> is configured.
  953: 
  954: B<Example -- sales table and products table, both with a "product" column>
  955: 
  956:     # $sales    columns: id, product, amount, date
  957:     # $products columns: sku, product, price, category
  958:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  959: 
  960:     my $join = Database::Join->new(
  961:         databases        => [$sales, $products],
  962:         join_column      => 'product',
  963:         join_map         => { 1 => 'sku' },
  964:         collision_prefix => { 1 => 'products' },
  965:     );
  966: 
  967:     $join->columns;
  968:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  969:     #                                                               ^-- prefixed collision
  970: 
  971:     my $row = $join->fetchrow_hashref(product => 'widget');
  972:     # $row->{product}            -- value from $sales
  973:     # $row->{'products.product'} -- value from $products (different row, same column name)
  974:     # $row->{price}              -- from $products, no collision, kept as-is

  990: =head2 backend - SQLite join backend for large datasets
  991: 
  992: C<Database::Join> can merge component databases in two different ways,
  993: controlled by the C<backend> constructor parameter.
  994: 
  995: =over 4
  996: 
  997: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  998: 
  999: All matching rows are fetched from every component database into Perl hashes
 1000: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
 1001: is roughly three times the combined source data size (one copy per database
 1002: plus one merged copy).
 1003: 
 1004: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1005: 
 1006: C<Database::Join> creates a temporary SQLite database file, spills source
 1007: rows into it (one table per component database), then executes a single SQL
 1008: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1009: source data size.
 1010: 
 1011: The temporary file is created once and reused across multiple query calls on
 1012: the same object (the cache).  Only query-time criteria vary per call; they
 1013: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1014: automatically rebuilt when any source database's C<updated()> timestamp
 1015: changes.  The file is deleted when the object is destroyed (goes out of
 1016: scope).  See I<Temporary file: name, location, and lifetime> below for
 1017: details.
 1018: 
 1019: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
 1020: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
 1021: 
 1022: =item C<backend =E<gt> 'auto'> (default)
 1023: 
 1024: C<Database::Join> counts the total rows from all component databases cheaply
 1025: -- without fetching them -- and then decides:

 1028: 
 1029: =item *
 1030: 
 1031: If the combined count is less than or equal to C<max_array_rows> (default
 1032: 10,000), use the array path.
 1033: 
 1034: =item *
 1035:

 1043: method in its own package -- not just inherit one from a parent class.  If

 3164: =head1 SECURITY CONSIDERATIONS
 3165: 
 3166: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3167: generates SQL strings, never opens files, and never calls C<system()>,
 3168: C<exec()>, or C<eval()>.  The security properties described below are
 3169: architectural guarantees, not run-time checks.
 3170: 
 3171: =head2 What Database::Join guarantees
 3172: 
 3173: =over 4
 3174: 
 3175: =item Criteria partition isolation
 3176: 
 3177: Every criterion you pass to a query method is routed to I<exactly one>
 3178: component database (the one that owns that column), or to I<all> databases
 3179: when the criterion is on the join key column.  A hostile value in a criterion
 3180: for column C<name> (owned by database A) will never reach database B.
 3181: 
 3182: =item Unknown columns are rejected before reaching any database
 3183: 
 3184: If a criterion column name is not present in any component database (or has
 3185: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3186: and silently drops the criterion.  No database receives the hostile key.
 3187: 
 3188: =item AUTOLOAD only accepts word-character column names
 3189: 
 3190: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3191: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3192: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3193: C<_>) are additionally blocked with an explicit C<croak>.
 3194: 
 3195: =item No value sanitisation (by design)
 3196: 
 3197: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3198: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3199: responsibility of the underlying C<Database::Abstraction> objects (which use
 3200: parameterised queries).  Preventing XSS or header injection is the
 3201: responsibility of the CGI or web layer that renders the output.
 3202: 
 3203: =item Taint-mode compatible (array path)
 3204: 
 3205: The array merge path contains no C<system()>, C<exec()>, backtick,
 3206: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3207: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3208: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3209: an I<untainted> capture, so the column name used for dispatch is clean under
 3210: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3211: objects; those objects are responsible for handling tainted values at the SQL
 3212: parameterisation layer.
 3213: 
 3214: =item SQLite backend: column names are quoted, values are parametrised
 3215: 
 3216: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3217: All column and table names are double-quoted (SQL identifier quoting) before
 3218: being embedded in statement strings.  All row values are passed to SQLite
 3219: exclusively through DBI prepared statement placeholders -- never by string
 3220: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3221: into the temporary database.
 3222: 
 3223: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3224: unpredictable filename.  No C<system()> or shell command is used to create or
 3225: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3226: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3227: in the generated SQL come from C<columns()>, which is produced by
 3228: C<Database::Abstraction> at construction time -- they are not derived from
 3229: caller-supplied criteria values.
 3230: 
 3231: =item Operator hashref broadcast copy
 3232: 
 3233: When the same join-key criterion (an operator hashref such as
 3234: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3235: database receives its own I<shallow copy> of the hashref.  A component database
 3236: that mutates the hashref's contents at the top level cannot affect what
 3237: subsequent databases receive.
 3238: 
 3239: =item collision_prefix value type guard
 3240: 
 3241: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3242: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3243: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3244: column name, C<columns()> listing, and merged row returned to the caller.  The
 3245: guard fires before any column name is constructed.
 3246: 
 3247: =item Filter deep-copy isolation
 3248: 
 3249: The C<filters> constructor parameter and the C<filter> option of
 3250: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3251: original hashrefs are never stored; post-construction mutation of those
 3252: hashrefs cannot widen or bypass the configured row-security constraints.
 3253: 
 3254: =back

 3664: 
 3665: Each column in the logical view independently follows a two-state machine.

 3676:          | Side-effect: col deleted from _col_db;
