  169: =head1 DESCRIPTION
  170: 
  171: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  172: single logical, read-only view.  Each component database is queried
  173: independently through its own C<Database::Abstraction> interface.  The results
  174: are combined using a shared key column (C<join_column>).
  175: In effect, this means that you can view data from more than one database using
  176: an intuitive, non-SQL interface.
  177: 
  178: The module exposes the same read-only API as C<Database::Abstraction>:
  179: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  180: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  181: shortcut.  Callers do not need to know how many underlying databases are
  182: involved.
  183: 
  184: Think of it as a virtual database table that is assembled on demand from
  185: several real tables, one per component database.
  186: 
  187: B<Join backends>
  188: 
  189: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  190: combined source row count.  For small datasets (up to C<max_array_rows>,
  191: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  192: automatically spills source rows into a temporary SQLite database and executes
  193: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  194: size instead of three.  You can also force either path unconditionally with
  195: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  196: 
  197: =head2 Join semantics
  198: 
  199: The C<join_type> parameter controls what happens when a particular key value
  200: exists in some component databases but not all:
  201: 
  202: =over 4
  203: 
  204: =item C<left> (the default)
  205: 
  206: All rows from the I<primary> (first) database are returned.  Columns from
  207: subsequent databases are included where a matching row is found, and simply
  208: absent from the hashref where there is no match.  If you are familiar with
  209: SQL, this is a LEFT OUTER JOIN on the first table.
  210: 
  211: =item C<inner>
  212: 
  213: Only rows whose join-column value is present in I<every> component database
  214: are returned.  This is equivalent to a SQL INNER JOIN.
  215: 
  216: =item C<outer>
  217: 
  218: Every join-column value found in I<any> component database is returned.
  219: Columns from databases that do not have that key value are absent from the
  220: merged row.  This is a FULL OUTER JOIN.
  221: 
  222: =back
  223: 
  224: B<Important override rule:> whenever you pass a query criterion for a column
  225: that belongs to a secondary database, that database automatically acts as an
  226: inner-join partner for that query only -- regardless of C<join_type>.  This
  227: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  228: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  229: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  230: as a WHERE clause would exclude them).
  231: 
  232: =head2 Column ownership and routing
  233: 
  234: At construction time, C<Database::Join> calls C<columns()> on each component
  235: database and builds an internal index that maps every column name to the
  236: database that owns it.
  237: 
  238: When you pass criteria to a query method, each key-value pair is automatically
  239: routed to the right database.  You never need to say which database a column
  240: belongs to.
  241: 
  242: The C<join_column> is special: criteria on it are broadcast to I<all>
  243: databases so that each database fetches only the relevant rows before the
  244: in-memory merge.
  245: 
  246: When the same non-join column name exists in more than one database, the
  247: I<last> database in the C<databases> array wins by default: its value
  248: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  249: preserve both values under distinct names instead.
  250: 
  251: =head1 LIMITATIONS
  252: 
  253: =over 4
  254: 
  255: =item Memory usage (array backend)
  256: 
  257: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  258: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  259: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  260: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  261: 
  262: =item SQLite backend writes a temporary file per query call
  263: 
  264: When the SQLite path is active, a new C<.db> file with a randomly generated
  265: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> at
  266: the I<start> of each call to C<selectall_arrayref()>, C<selectall_array()>,
  267: C<fetchrow_hashref()>, or C<count()>.  The file is deleted at the I<end> of
  268: that same call, before the method returns -- even if an exception is raised.
  269: The file never persists between calls or after the method returns.
  270: 
  271: If you make ten query calls on the same object, ten temporary files are created
  272: and deleted one at a time, each lasting only for the duration of its own call.
  273: At any given moment no more than one such file exists per C<Database::Join>
  274: object.  The directory must be writable and have enough free space for one such
  275: file.
  276: 
  277: =item No chained builder or raw SQL
  278: 
  279: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  280: or C<fetchrow_hashref> instead.
  281: 
  282: =item Single-column equi-join only
  283: 
  284: Joining on more than one column simultaneously, or on expressions, is not
  285: supported.  When the join key has different names in different databases,
  286: use C<join_map> to declare each database's local column name.
  287: 
  288: =item Sort order
  289: 
  290: Results are sorted by the C<join_column> value only.  Caller-specified
  291: C<ORDER BY> is not propagated to the component databases.
  292: 
  293: =item count() fetches all rows
  294: 
  295: C<count()> executes the full join and counts the resulting rows in Perl.  It
  296: does not push a C<COUNT(*)> query down to the databases.
  297: 
  298: =back

  300: =head1 COMMON PITFALLS
  301: 
  302: =over 4
  303: 
  304: =item The join_column must exist in every component database
  305: 
  306: If even one database is missing the join key column, C<new()> (or
  307: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  308: column has a different local name in some databases.
  309: 
  310: =item Criteria on a removed column are silently dropped
  311: 
  312: If you call C<remove_column('tier')> and later query
  313: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  314: C<carp> warning) and all rows are returned.  Always pass criteria before
  315: removing columns, or restructure your code to avoid this.
  316: 
  317: =item You cannot remove the join column
  318: 
  319: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  320: is required for the merge to work.
  321: 
  322: =item Left join does not guarantee all columns are populated
  323: 
  324: Under a LEFT join, rows from the primary database that have no matching row
  325: in a secondary database will be returned with I<no keys> from that secondary
  326: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  327: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  328: than just C<$row->{score}> when the secondary match is optional.
  329: 
  330: =item Filters act as inner-join partners
  331: 
  332: Any database that has a C<filters> entry is promoted to an inner-join partner,
  333: regardless of C<join_type>.  A row whose join-key value does not appear in
  334: the filtered database's result is removed from the merged output entirely, not
  335: merely missing its secondary columns.  This is intentional but can be
  336: surprising if you expected LEFT join semantics.
  337: 
  338: =item Criteria-merging replaces scalar filters
  339: 
  340: When both a base filter and a query criterion target the same column, and both
  341: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  342: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  343: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  344: the base filter is ignored for that query.
  345: 
  346: =item AUTOLOAD sees the full merged join when filters or join_map are active
  347: 
  348: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  349: (C<< $join->columnname(...) >>) runs the full join query rather than
  350: delegating directly to the owning database.  This is necessary for correctness
  351: but means the result respects all active filters and join-key translations,
  352: which may differ from what the owning database would return on its own.
  353: 
  354: =item Duplicate column names: last database wins (unless collision_prefix is set)
  355: 
  356: When two component databases each have a column called C<notes>, the second
  357: database's value silently overwrites the first in every merged row.  Use
  358: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  359: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  360: (or C<remove_column>) to drop the unwanted duplicate entirely.
  361: 
  362: =item Mutating the filters hashref after construction has no effect
  363: 
  364: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  365: passed to C<add_database>) at the moment of construction.  The original hashref
  366: you passed in is never stored.  If you later modify it -- for example, to
  367: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  368: Construct a new C<Database::Join> object, or use a component
  369: C<Database::Abstraction> that supports dynamic filter modification.
  370: 
  371: =item auto mode may always use the array path for some DAs
  372: 
  373: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  374: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  375: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  376: from C<Database::Abstraction> is treated as uncountable, because the parent
  377: class C<count()> expects a key argument and behaves differently from a
  378: "return total row count" function.  In that case C<Database::Join>
  379: conservatively uses the array path for the whole query, even if the dataset is
  380: large.  To opt in to the SQLite path for such a DA, either add your own
  381: C<count()> override that returns the total row count, implement C<dbi_source()>,
  382: or use C<backend =E<gt> 'sqlite'> unconditionally.
  383: 
  384: =item dbi_source() zero-copy path is skipped when query-time criteria apply
  385: 
  386: When a component database implements C<dbi_source()> but the current query
  387: includes criteria for columns in that database, C<Database::Join> cannot use
  388: the zero-copy ATTACH path (doing so would require generating a C<WHERE> clause
  389: inside the attached database, which is not supported in this version).  The
  390: database is queried normally via C<selectall_arrayref> and rows are spilled
  391: into the temporary SQLite file instead.
  392: 
  393: =item Temp file directory must be writable and have free space
  394: 
  395: Each query call that uses the SQLite path creates one temporary C<.db> file in
  396: C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  397: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  398: only the directory is under your control.  If the directory is not writable,
  399: or the filesystem is full, the call will C<croak> with C<error_sqlite_connect>.
  400: Check permissions and free space if you see that error.
  401: 
  402: =back

  419:         max_array_rows   => 10_000,        # threshold for 'auto' mode

  425: =head3 DESCRIPTION
  426: 
  427: Constructs and returns a new C<Database::Join> object.
  428: 
  429: Each element of C<databases> must be an already-instantiated subclass of
  430: C<Database::Abstraction>.  The constructor calls C<columns()> on every
  431: database to build an internal column-routing table and verifies that
  432: C<join_column> (or its local alias from C<join_map>) is present in each one.
  433: 
  434: Columns listed in C<remove_columns> are hidden immediately: they do not appear
  435: in C<columns()>, C<schema()>, or any returned row hashref.  This is equivalent
  436: to calling C<remove_column> once per name after construction.
  437: 
  438: =head3 API SPECIFICATION
  439: 
  440: =head4 Input
  441: 
  442:     databases      => { type => 'arrayref', required => 1 }
  443:                       # One or more Database::Abstraction subclass objects.
  444:                       #
  445:                       # DOMAIN -- EP valid:   non-empty arrayref of blessed DA subclasses.
  446:                       # DOMAIN -- EP invalid: scalar, hashref, or absent => croak.
  447:                       # DOMAIN -- BVA size:   minimum 1 element; no documented upper bound.
  448:                       # DOMAIN -- BVA elem:   each element must pass isa('Database::Abstraction').
  449: 
  450:     join_column    => { type => 'string',   optional => 1, default => 'entry' }
  451:                       # The column name shared by all databases (the join key).
  452:                       #
  453:                       # DOMAIN -- EP valid:   any non-empty string present in every component DA.
  454:                       # DOMAIN -- EP invalid: column absent from any DA => croak join_col_missing.
  455:                       # DOMAIN -- BVA:        empty string '' is treated as a column name and
  456:                       #                       will croak if (as expected) it is absent from every DA.
  457:                       # DOMAIN -- NOTE:       matching is case-sensitive and exact.
  458: 
  459:     join_type      => { type => 'string',   optional => 1, default => 'left',
  460:                         enum => ['inner', 'left', 'outer'] }
  461:                       # Controls which keys appear in the result when not all
  462:                       # databases share the same key values.
  463:                       #
  464:                       # DOMAIN -- EP valid:   exactly 'inner', 'left', or 'outer'.
  465:                       # DOMAIN -- EP invalid: any other string including 'INNER', 'LEFT',
  466:                       #                       'OUTER' (enum check is case-sensitive), 'cross',
  467:                       #                       or '' => croak from validate_strict.
  468: 
  469:     join_map       => { type => 'hashref',  optional => 1 }
  470:                       # Zero-based database index => local column name.
  471:                       # See the join_map section for full details.
  472:                       #
  473:                       # DOMAIN -- EP valid:   hashref values must be plain strings.
  474:                       # DOMAIN -- EP invalid: reference value (hashref, arrayref, coderef, etc.)
  475:                       #                       => croak; the guard prevents heap-address leakage.
  476:                       # DOMAIN -- BVA:        out-of-range keys (beyond the databases array) are
  477:                       #                       silently ignored.
  478: 
  479:     filters        => { type => 'hashref',  optional => 1 }
  480:                       # Zero-based database index => criteria hashref.
  481:                       # Permanent row restrictions on individual databases.
  482:                       # See the filters section for full details.
  483: 
  484:     collision_prefix => { type => 'hashref', optional => 1 }
  485:                       # Zero-based database index (>0) => prefix string.
  486:                       # When a secondary database has a column that collides
  487:                       # with a column already present in the merged view, the
  488:                       # secondary column is published as "$prefix.$col" instead
  489:                       # of silently overwriting the earlier value.
  490:                       # Index 0 entries are silently ignored.
  491:                       # Omitting this parameter preserves the original
  492:                       # last-database-wins behaviour.
  493:                       # See the collision_prefix section for full details.
  494:                       #
  495:                       # DOMAIN -- EP valid:   absent or {} => last-database-wins (no change).
  496:                       # DOMAIN -- EP valid:   { N => 'prefix' } where N > 0 => colliding
  497:                       #                       columns from DB[N] published as "$prefix.$col";
  498:                       #                       non-colliding columns from the same DB added plain.
  499:                       # DOMAIN -- EP note:    index-0 entries are silently ignored.
  500:                       # DOMAIN -- Invariant:  join_column is never prefixed regardless of

  696: =head2 join_map - joining on differently-named columns
  697: 
  698: By default every component database must have a column whose name matches
  699: C<join_column>.  If a database uses a different local name for the join key,
  700: declare the mapping with C<join_map>.
  701: 
  702: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  703: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  704: B<value> is the name that B<that particular database> uses for the join key.
  705: 
  706: Databases not listed in C<join_map> are assumed to already have a column
  707: named C<join_column> and need no entry.
  708: 
  709: Throughout the merged view the join key is I<always> referred to by the name
  710: given in C<join_column>.  The local alias is never exposed in returned rows,
  711: in C<columns()>, or in C<schema()>.
  712: 
  713: B<When do you need join_map?>
  714: 
  715: You need C<join_map> when you have two tables like:
  716: 
  717:     cities table  : entry (the city name) | statecode
  718:     stnames table : entry (the state code) | state
  719: 
  720: Here you want to join cities.statecode to stnames.entry.  You choose
  721: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  722: that same concept C<entry>, so you declare:
  723: 
  724:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  725: 
  726: B<Example>
  727: 
  728:     #                        index 0     index 1
  729:     my @databases = (       $cities,    $stnames  );
  730:     #  join key column:    'statecode'  'entry'
  731:     #  join_column:        'statecode' (chosen canonical name)
  732:     #  stnames differs, so declare the alias:
  733: 
  734:     my $join = Database::Join->new(
  735:         databases   => \@databases,
  736:         join_column => 'statecode',
  737:         join_map    => { 1 => 'entry' },
  738:     );
  739: 
  740:     my $rows = $join->selectall_arrayref();
  741:     # Each $row has keys: entry (city), statecode, state
  742:     # 'entry' from stnames is never exposed directly.
  743: 
  744:     my $row = $join->fetchrow_hashref(statecode => 'CA');

  746: B<Using add_database instead>
  747: 
  748: If you build the join incrementally with C<add_database>, pass
  749: C<join_column> directly to that call instead of using C<join_map>:
  750: 
  751:     my $join = Database::Join->new(
  752:         databases   => [ $cities ],

  759: =head2 filters - permanent per-database row filters
  760: 
  761: C<filters> lets you restrict a component database to a subset of its rows
  762: permanently, without repeating the criterion on every query call.
  763: 
  764: Think of it as telling the join: "whenever you query this database, always
  765: add these extra conditions".  Callers never need to specify the restriction
  766: themselves and can never accidentally omit it.
  767: 
  768: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  769: database in the C<databases> array (same numbering as C<join_map>).  Each
  770: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  771: accepts.
  772: 
  773: B<Key-set semantics>
  774: 
  775: A filtered database always acts as an inner-join partner, regardless of the
  776: C<join_type> setting.  Any join-key value that does not pass the filter is
  777: excluded from the merged output entirely -- not just missing its secondary
  778: columns.  This ensures the filter genuinely restricts the view rather than
  779: simply hiding a few fields.
  780: 
  781: B<Criteria merging>
  782: 
  783: When a query call also passes a criterion for a column that already has a base
  784: filter, the two constraints are combined:
  785: 
  786: =over 4
  787: 
  788: =item *
  789: 
  790: When both the base filter value and the query criterion are operator hashrefs
  791: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  792: merged: I<both> constraints apply simultaneously (AND semantics).
  793: 
  794: =item *
  795: 
  796: When either value is a plain scalar, or the operators conflict, the
  797: query-time criterion wins and the base filter for that column is ignored for
  798: that one call.
  799: 
  800: =back
  801: 
  802: B<Example -- only show orders placed more than 60 days ago>
  803: 
  804:     my $join = Database::Join->new(
  805:         databases   => [ $customers, $orders ],
  806:         join_column => 'entry',
  807:         filters     => { 1 => { age_days => { '>' => 60 } } },
  808:     );

  810:     # Every query automatically sees only old orders

  813:     # Additional criteria layer on top -- gold tier AND old order
  814:     my $vip  = $join->selectall_arrayref(tier => 'gold');
  815: 
  816:     # Range intersection: age_days > 60 AND age_days < 365
  817:     my $mid  = $join->selectall_arrayref(age_days => { '<' => 365 });

  821: 
  822:     $join->add_database($orders, filter => { age_days => { '>' => 60 } });

  824: =head2 collision_prefix - preserve colliding columns from secondary databases
  825: 
  826: By default, when a column name appears in more than one database the I<last>
  827: database wins: its value silently overwrites earlier ones in merged rows.
  828: This loses data and makes the origin invisible.
  829: 
  830: C<collision_prefix> changes this for secondary databases you designate.
  831: When a secondary database at index N has a column that already exists in the
  832: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  833: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  834: visible: the original column keeps its name (from the earlier database), and
  835: the collision gets the prefixed name.
  836: 
  837: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  838: a secondary database in the C<databases> array (same numbering as C<join_map>).
  839: Each B<value> is the prefix string to prepend.  An index-0 entry is
  840: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  841: preserves the previous last-wins behaviour and changes nothing.
  842: 
  843: Non-colliding columns from a secondary database are always added as-is with
  844: no prefix, whether or not C<collision_prefix> is configured.
  845: 
  846: B<Example -- sales table and products table, both with a "product" column>

  848:     # $sales    columns: id, product, amount, date
  849:     # $products columns: sku, product, price, category
  850:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  851: 
  852:     my $join = Database::Join->new(
  853:         databases        => [$sales, $products],
  854:         join_column      => 'product',
  855:         join_map         => { 1 => 'sku' },
  856:         collision_prefix => { 1 => 'products' },
  857:     );

  866:     # $row->{price}              -- from $products, no collision, kept as-is
  867:

  869:

  871: 
  872:     my $rows = $join->selectall_arrayref('products.product' => 'widget');

  882: =head2 backend - SQLite join backend for large datasets
  883: 
  884: C<Database::Join> can merge component databases in two different ways,
  885: controlled by the C<backend> constructor parameter.
  886: 
  887: =over 4
  888: 
  889: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  890: 
  891: All matching rows are fetched from every component database into Perl hashes
  892: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
  893: is roughly three times the combined source data size (one copy per database
  894: plus one merged copy).
  895: 
  896: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a temporary file
  897: 
  898: C<Database::Join> creates a temporary SQLite database file, spills source
  899: rows into it (one table per component database), then executes a single SQL
  900: C<JOIN> statement.  Peak RAM drops to roughly one times the source data size.
  901: 
  902: A new file is created at the start of each query call
  903: (C<selectall_arrayref>, C<fetchrow_hashref>, etc.) and deleted at the end of
  904: that same call, before the method returns -- even if an error occurs.  The
  905: file has a randomly generated name in C<tmpdir> and never persists beyond
  906: the call that created it.  See I<Temporary file: name, location, and lifetime>
  907: below for details.
  908: 
  909: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
  910: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
  911: 
  912: =item C<backend =E<gt> 'auto'> (default)
  913: 
  914: C<Database::Join> counts the total rows from all component databases cheaply
  915: -- without fetching them -- and then decides:
  916: 
  917: =over 4
  918: 
  919: =item *
  920: 
  921: If the combined count is less than or equal to C<max_array_rows> (default
  922: 10,000), use the array path.
  923: 
  924: =item *
  925: 
  926: If the combined count exceeds C<max_array_rows>, use the SQLite path.
  927: 
  928: =back
  929: 
  930: For counting to work without fetching, each component database must either
  931: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
  932: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
  933: method in its own package -- not just inherit one from a parent class.  If
  934: neither is available for a particular database, C<Database::Join> plays it
  935: safe and uses the array path for the whole query without fetching any rows.

 2758: =head1 SECURITY CONSIDERATIONS
 2759: 
 2760: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 2761: generates SQL strings, never opens files, and never calls C<system()>,
 2762: C<exec()>, or C<eval()>.  The security properties described below are
 2763: architectural guarantees, not run-time checks.
 2764: 
 2765: =head2 What Database::Join guarantees
 2766: 
 2767: =over 4
 2768: 
 2769: =item Criteria partition isolation
 2770: 
 2771: Every criterion you pass to a query method is routed to I<exactly one>
 2772: component database (the one that owns that column), or to I<all> databases
 2773: when the criterion is on the join key column.  A hostile value in a criterion
 2774: for column C<name> (owned by database A) will never reach database B.
 2775: 
 2776: =item Unknown columns are rejected before reaching any database
 2777: 
 2778: If a criterion column name is not present in any component database (or has
 2779: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 2780: and silently drops the criterion.  No database receives the hostile key.
 2781: 
 2782: =item AUTOLOAD only accepts word-character column names
 2783: 
 2784: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 2785: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 2786: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 2787: C<_>) are additionally blocked with an explicit C<croak>.
 2788: 
 2789: =item No value sanitisation (by design)
 2790: 
 2791: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 2792: I<values> in criteria hashrefs.  Preventing SQL injection is the
 2793: responsibility of the underlying C<Database::Abstraction> objects (which use
 2794: parameterised queries).  Preventing XSS or header injection is the
 2795: responsibility of the CGI or web layer that renders the output.
 2796: 
 2797: =item Taint-mode compatible (array path)
 2798: 
 2799: The array merge path contains no C<system()>, C<exec()>, backtick,
 2800: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 2801: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 2802: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 2803: an I<untainted> capture, so the column name used for dispatch is clean under
 2804: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 2805: objects; those objects are responsible for handling tainted values at the SQL
 2806: parameterisation layer.
 2807: 
 2808: =item SQLite backend: column names are quoted, values are parametrised
 2809: 
 2810: When the SQLite path is active, C<Database::Join> generates SQL internally.
 2811: All column and table names are double-quoted (SQL identifier quoting) before
 2812: being embedded in statement strings.  All row values are passed to SQLite
 2813: exclusively through DBI prepared statement placeholders -- never by string
 2814: interpolation.  A hostile value in a source row therefore cannot inject SQL
 2815: into the temporary database.
 2816: 
 2817: The temporary SQLite file is created by C<File::Temp> using a securely random,
 2818: unpredictable filename.  No C<system()> or shell command is used to create or
 2819: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 2820: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 2821: in the generated SQL come from C<columns()>, which is produced by
 2822: C<Database::Abstraction> at construction time -- they are not derived from
 2823: caller-supplied criteria values.
 2824: 
 2825: =item Operator hashref broadcast copy
 2826: 
 2827: When the same join-key criterion (an operator hashref such as
 2828: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 2829: database receives its own I<shallow copy> of the hashref.  A component database
 2830: that mutates the hashref's contents at the top level cannot affect what
 2831: subsequent databases receive.
 2832: 
 2833: =item collision_prefix value type guard
 2834: 
 2835: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 2836: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 2837: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 2838: column name, C<columns()> listing, and merged row returned to the caller.  The
 2839: guard fires before any column name is constructed.
 2840: 
 2841: =item Filter deep-copy isolation
 2842: 
 2843: The C<filters> constructor parameter and the C<filter> option of
 2844: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 2845: original hashrefs are never stored; post-construction mutation of those
 2846: hashrefs cannot widen or bypass the configured row-security constraints.
 2847: 
 2848: =back
