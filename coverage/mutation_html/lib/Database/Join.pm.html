  220: =head1 DESCRIPTION
  221: 
  222: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  223: single logical, read-only view.  Each component database is queried
  224: independently through its own C<Database::Abstraction> interface.  The results
  225: are combined using a shared key column (C<join_column>).
  226: In effect, this means that you can view data from more than one database using
  227: an intuitive, non-SQL interface.
  228: 
  229: Every storage format that C<Database::Abstraction> supports works as a
  230: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  231: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  232: within the same join.
  233: 
  234: The module exposes the same read-only API as C<Database::Abstraction>:
  235: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  236: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  237: shortcut.  Callers do not need to know how many underlying databases are
  238: involved.
  239: 
  240: Think of it as a virtual database table that is assembled on demand from
  241: several real tables, one per component database.
  242: 
  243: B<Join backends>
  244: 
  245: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  246: combined source row count.  For small datasets (up to C<max_array_rows>,
  247: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  248: automatically spills source rows into a temporary SQLite database and executes
  249: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  250: size instead of three.  You can also force either path unconditionally with
  251: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  252: 
  253: =head2 Join semantics
  254: 
  255: The C<join_type> parameter controls what happens when a particular key value
  256: exists in some component databases but not all:
  257: 
  258: =over 4
  259: 
  260: =item C<left> (the default)
  261: 
  262: All rows from the I<primary> (first) database are returned.  Columns from
  263: subsequent databases are included where a matching row is found, and simply
  264: absent from the hashref where there is no match.  If you are familiar with
  265: SQL, this is a LEFT OUTER JOIN on the first table.
  266: 
  267: =item C<inner>
  268: 
  269: Only rows whose join-column value is present in I<every> component database
  270: are returned.  This is equivalent to a SQL INNER JOIN.
  271: 
  272: =item C<outer>
  273: 
  274: Every join-column value found in I<any> component database is returned.
  275: Columns from databases that do not have that key value are absent from the
  276: merged row.  This is a FULL OUTER JOIN.
  277: 
  278: =back
  279: 
  280: B<Important override rule:> whenever you pass a query criterion for a column
  281: that belongs to a secondary database, that database automatically acts as an
  282: inner-join partner for that query only -- regardless of C<join_type>.  This
  283: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  284: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  285: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  286: as a WHERE clause would exclude them).
  287: 
  288: =head2 Column ownership and routing
  289: 
  290: At construction time, C<Database::Join> calls C<columns()> on each component
  291: database and builds an internal index that maps every column name to the
  292: database that owns it.
  293: 
  294: When you pass criteria to a query method, each key-value pair is automatically
  295: routed to the right database.  You never need to say which database a column
  296: belongs to.
  297: 
  298: The C<join_column> is special: criteria on it are broadcast to I<all>
  299: databases so that each database fetches only the relevant rows before the
  300: in-memory merge.
  301: 
  302: When the same non-join column name exists in more than one database, the
  303: I<last> database in the C<databases> array wins by default: its value
  304: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  305: preserve both values under distinct names instead.
  306: 
  307: =head1 LIMITATIONS
  308: 
  309: =over 4
  310: 
  311: =item Memory usage (array backend)
  312: 
  313: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  314: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  315: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  316: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  317: 
  318: =item SQLite backend uses a persistent cache file
  319: 
  320: When the SQLite path is active, a single C<.db> file with a randomly generated
  321: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  322: first time a query runs on a given C<Database::Join> object.  Source data is
  323: spilled into that file once; subsequent queries against the same object reuse
  324: the file without re-fetching the source data.
  325: 
  326: The cache is automatically invalidated and rebuilt whenever any source
  327: database's C<updated()> timestamp changes (indicating new data), or when
  328: C<add_database()> is called.
  329: 
  330: The file is deleted when the C<Database::Join> object is destroyed (typically
  331: when it goes out of scope).  At any given moment no more than one such file
  332: exists per object.  The directory must be writable and have enough free space
  333: for the full source data (once, not per-query).
  334: 
  335: =item No chained builder or raw SQL
  336: 
  337: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  338: or C<fetchrow_hashref> instead.
  339: 
  340: =item Single-column equi-join only
  341: 
  342: Joining on more than one column simultaneously, or on expressions, is not
  343: supported.  When the join key has different names in different databases,
  344: use C<join_map> to declare each database's local column name.
  345: 
  346: =item Sort order
  347: 
  348: Results are sorted by the C<join_column> value only.  Caller-specified
  349: C<ORDER BY> is not propagated to the component databases.
  350: 
  351: =item count() fetches all rows
  352: 
  353: C<count()> executes the full join and counts the resulting rows in Perl.  It
  354: does not push a C<COUNT(*)> query down to the databases.
  355: 
  356: =back

  358: =head1 COMMON PITFALLS
  359: 
  360: =over 4
  361: 
  362: =item The join_column must exist in every component database
  363: 
  364: If even one database is missing the join key column, C<new()> (or
  365: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  366: column has a different local name in some databases.
  367: 
  368: =item Criteria on a removed column are silently dropped
  369: 
  370: If you call C<remove_column('tier')> and later query
  371: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  372: C<carp> warning) and all rows are returned.  Always pass criteria before
  373: removing columns, or restructure your code to avoid this.
  374: 
  375: =item You cannot remove the join column
  376: 
  377: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  378: is required for the merge to work.
  379: 
  380: =item Left join does not guarantee all columns are populated
  381: 
  382: Under a LEFT join, rows from the primary database that have no matching row
  383: in a secondary database will be returned with I<no keys> from that secondary
  384: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  385: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  386: than just C<$row->{score}> when the secondary match is optional.
  387: 
  388: =item Filters act as inner-join partners
  389: 
  390: Any database that has a C<filters> entry is promoted to an inner-join partner,
  391: regardless of C<join_type>.  A row whose join-key value does not appear in
  392: the filtered database's result is removed from the merged output entirely, not
  393: merely missing its secondary columns.  This is intentional but can be
  394: surprising if you expected LEFT join semantics.
  395: 
  396: =item Criteria-merging replaces scalar filters
  397: 
  398: When both a base filter and a query criterion target the same column, and both
  399: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  400: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  401: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  402: the base filter is ignored for that query.
  403: 
  404: =item AUTOLOAD sees the full merged join when filters or join_map are active
  405: 
  406: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  407: (C<< $join->columnname(...) >>) runs the full join query rather than
  408: delegating directly to the owning database.  This is necessary for correctness
  409: but means the result respects all active filters and join-key translations,
  410: which may differ from what the owning database would return on its own.
  411: 
  412: =item Duplicate column names: last database wins (unless collision_prefix is set)
  413: 
  414: When two component databases each have a column called C<notes>, the second
  415: database's value silently overwrites the first in every merged row.  Use
  416: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  417: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  418: (or C<remove_column>) to drop the unwanted duplicate entirely.
  419: 
  420: =item Mutating the filters hashref after construction has no effect
  421: 
  422: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  423: passed to C<add_database>) at the moment of construction.  The original hashref
  424: you passed in is never stored.  If you later modify it -- for example, to
  425: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  426: Construct a new C<Database::Join> object, or use a component
  427: C<Database::Abstraction> that supports dynamic filter modification.
  428: 
  429: =item auto mode may always use the array path for some DAs
  430: 
  431: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  432: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  433: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  434: from C<Database::Abstraction> is treated as uncountable, because the parent
  435: class C<count()> expects a key argument and behaves differently from a
  436: "return total row count" function.  In that case C<Database::Join>
  437: conservatively uses the array path for the whole query, even if the dataset is
  438: large.  To opt in to the SQLite path for such a DA, either add your own
  439: C<count()> override that returns the total row count, implement C<dbi_source()>,
  440: or use C<backend =E<gt> 'sqlite'> unconditionally.
  441: 
  442: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  443: 
  444: When a component database implements C<dbi_source()>, C<Database::Join> always
  445: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  446: for columns in that database>.  The criteria are translated into parameterised
  447: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  448: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  449: force a spill; that restriction has been removed.)
  450: 
  451: =item Broadcast join-column criterion does not force secondaries into inner-join
  452: 
  453: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  454: C<Database::Join> broadcasts it to all component databases so each DA can
  455: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  456: incorrectly counted as "having criteria" for secondary databases, causing
  457: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  458: join-column criterion was present.  The fix: only non-join-column criteria
  459: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  460: a secondary to inner-join status.  The broadcast itself is now a transparent
  461: key-range selector that does not affect join semantics.
  462: 
  463: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  464: 
  465: C<LIKE> and C<NOT LIKE> criteria (e.g. C<< name => { LIKE => '%ali%' } >>) are
  466: fully supported on the SQLite backend: the pattern is always passed as a bind
  467: parameter, never interpolated into SQL, so there is no injection risk.  The
  468: behaviour is identical on both the array path (where the criterion is forwarded
  469: to the component DA) and the SQLite path.
  470: 
  471: Operators that are I<not> yet in the supported set -- C<IN>, C<NOT IN>,
  472: C<IS NULL>, C<IS NOT NULL> -- are silently skipped on the SQLite path; a
  473: C<carp> warning is emitted for each one so callers are not silently misled.
  474: The array path forwards these operators to the component DA unchanged, which
  475: may or may not honour them.  If you need these operators, use
  476: C<< backend => 'array' >> to stay on the array path, or open a feature request.
  477: 
  478: =item Temp file directory must be writable and have free space
  479: 
  480: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  481: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  482: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  483: only the directory is under your control.  The file is created on the first
  484: query and kept alive until the object is destroyed; it is not re-created on
  485: every query call.  If the directory is not writable, or the filesystem is full,
  486: the call will C<croak> with C<error_sqlite_connect>.  Check permissions and
  487: free space if you see that error.

  783: =head2 join_map - joining on differently-named columns
  784: 
  785: By default every component database must have a column whose name matches
  786: C<join_column>.  If a database uses a different local name for the join key,
  787: declare the mapping with C<join_map>.
  788: 
  789: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  790: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  791: B<value> is the name that B<that particular database> uses for the join key.
  792: 
  793: Databases not listed in C<join_map> are assumed to already have a column
  794: named C<join_column> and need no entry.
  795: 
  796: Throughout the merged view the join key is I<always> referred to by the name
  797: given in C<join_column>.  The local alias is never exposed in returned rows,
  798: in C<columns()>, or in C<schema()>.
  799: 
  800: B<When do you need join_map?>
  801: 
  802: You need C<join_map> when you have two tables like:
  803: 
  804:     cities table  : entry (the city name) | statecode
  805:     stnames table : entry (the state code) | state
  806: 
  807: Here you want to join cities.statecode to stnames.entry.  You choose
  808: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  809: that same concept C<entry>, so you declare:
  810: 
  811:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  812: 
  813: B<Example>
  814: 
  815:     #                        index 0     index 1
  816:     my @databases = (       $cities,    $stnames  );
  817:     #  join key column:    'statecode'  'entry'
  818:     #  join_column:        'statecode' (chosen canonical name)
  819:     #  stnames differs, so declare the alias:
  820: 
  821:     my $join = Database::Join->new(
  822:         databases   => \@databases,
  823:         join_column => 'statecode',
  824:         join_map    => { 1 => 'entry' },
  825:     );
  826: 
  827:     my $rows = $join->selectall_arrayref();

  831:     my $row = $join->fetchrow_hashref(statecode => 'CA');

  834: 
  835: If you build the join incrementally with C<add_database>, pass
  836: C<join_column> directly to that call instead of using C<join_map>:
  837: 
  838:     my $join = Database::Join->new(

  846: =head2 filters - permanent per-database row filters
  847: 
  848: C<filters> lets you restrict a component database to a subset of its rows
  849: permanently, without repeating the criterion on every query call.
  850: 
  851: Think of it as telling the join: "whenever you query this database, always
  852: add these extra conditions".  Callers never need to specify the restriction
  853: themselves and can never accidentally omit it.
  854: 
  855: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  856: database in the C<databases> array (same numbering as C<join_map>).  Each
  857: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  858: accepts.
  859: 
  860: B<Key-set semantics>
  861: 
  862: A filtered database always acts as an inner-join partner, regardless of the
  863: C<join_type> setting.  Any join-key value that does not pass the filter is
  864: excluded from the merged output entirely -- not just missing its secondary
  865: columns.  This ensures the filter genuinely restricts the view rather than
  866: simply hiding a few fields.
  867: 
  868: B<Criteria merging>
  869: 
  870: When a query call also passes a criterion for a column that already has a base
  871: filter, the two constraints are combined:
  872: 
  873: =over 4
  874: 
  875: =item *
  876: 
  877: When both the base filter value and the query criterion are operator hashrefs
  878: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  879: merged: I<both> constraints apply simultaneously (AND semantics).
  880: 
  881: =item *
  882: 
  883: When either value is a plain scalar, or the operators conflict, the
  884: query-time criterion wins and the base filter for that column is ignored for
  885: that one call.
  886: 
  887: =back
  888: 
  889: B<Example -- only show orders placed more than 60 days ago>
  890: 
  891:     my $join = Database::Join->new(
  892:         databases   => [ $customers, $orders ],

  897:     # Every query automatically sees only old orders
  898:     my $rows = $join->selectall_arrayref();

  900:     # Additional criteria layer on top -- gold tier AND old order

  902: 
  903:     # Range intersection: age_days > 60 AND age_days < 365
  904:     my $mid  = $join->selectall_arrayref(age_days => { '<' => 365 });

  908: 
  909:     $join->add_database($orders, filter => { age_days => { '>' => 60 } });

  911: =head2 collision_prefix - preserve colliding columns from secondary databases
  912: 
  913: By default, when a column name appears in more than one database the I<last>
  914: database wins: its value silently overwrites earlier ones in merged rows.
  915: This loses data and makes the origin invisible.
  916: 
  917: C<collision_prefix> changes this for secondary databases you designate.
  918: When a secondary database at index N has a column that already exists in the
  919: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  920: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  921: visible: the original column keeps its name (from the earlier database), and
  922: the collision gets the prefixed name.
  923: 
  924: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  925: a secondary database in the C<databases> array (same numbering as C<join_map>).
  926: Each B<value> is the prefix string to prepend.  An index-0 entry is
  927: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  928: preserves the previous last-wins behaviour and changes nothing.
  929: 
  930: Non-colliding columns from a secondary database are always added as-is with
  931: no prefix, whether or not C<collision_prefix> is configured.
  932: 
  933: B<Example -- sales table and products table, both with a "product" column>
  934: 
  935:     # $sales    columns: id, product, amount, date
  936:     # $products columns: sku, product, price, category
  937:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  938: 
  939:     my $join = Database::Join->new(
  940:         databases        => [$sales, $products],
  941:         join_column      => 'product',
  942:         join_map         => { 1 => 'sku' },
  943:         collision_prefix => { 1 => 'products' },
  944:     );
  945: 
  946:     $join->columns;
  947:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  948:     #                                                               ^-- prefixed collision
  949: 
  950:     my $row = $join->fetchrow_hashref(product => 'widget');
  951:     # $row->{product}            -- value from $sales
  952:     # $row->{'products.product'} -- value from $products (different row, same column name)
  953:     # $row->{price}              -- from $products, no collision, kept as-is
  954: 
  955: B<Querying on a prefixed column>
  956: 
  957: Use the full published name as the criterion key:
  958: 
  959:     my $rows = $join->selectall_arrayref('products.product' => 'widget');
  960:     # Internally routes as: product => 'widget' to $products
  961: 
  962: B<Interaction with remove_column>
  963: 
  964: C<remove_column> operates on published names.  To suppress a prefixed
  965: collision column entirely, pass the prefixed name:
  966: 
  967:     $join->remove_column('products.product');

  969: =head2 backend - SQLite join backend for large datasets
  970: 
  971: C<Database::Join> can merge component databases in two different ways,
  972: controlled by the C<backend> constructor parameter.
  973: 
  974: =over 4
  975: 
  976: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  977: 
  978: All matching rows are fetched from every component database into Perl hashes
  979: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
  980: is roughly three times the combined source data size (one copy per database

  983: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file

 1034: B<Temporary file: name, location, and lifetime>

 2965: 
 2966: All text that passes through C<Database::Join> at the Perl layer (column names,
 2967: criteria values, merged row values) is treated as opaque strings.
 2968: C<Database::Join> does not inspect, encode, or transform string content.
 2969: 
 2970: =over 4
 2971: 
 2972: =item Column names
 2973: 
 2974: Column names are plain ASCII strings as returned by C<Database::Abstraction::columns()>.
 2975: Non-ASCII column names are accepted but not tested; behaviour depends on the
 2976: underlying DA and database driver.
 2977: 
 2978: =item Criteria values and row data
 2979: 
 2980: Values are passed verbatim between callers and component DAs.  Full UTF-8 is
 2981: safe as long as the underlying C<Database::Abstraction> objects and their
 2982: database drivers handle UTF-8 correctly.  C<Database::Join> neither encodes
 2983: nor decodes any value.
 2984: 
 2985: =item SQLite backend
 2986: 
 2987: When the SQLite path is active, values are inserted into the temporary SQLite
 2988: database via DBI placeholders (never string interpolation), so binary-safe
 2989: round-tripping depends on C<DBD::SQLite>'s character encoding settings.
 2990: By default C<DBD::SQLite> operates in UTF-8 mode, which is correct for text
 2991: data.  Binary blobs are not explicitly tested.

 2996: (if one is supplied) via a C<translate($key, @args)> call.  The translation

 3110: =head1 SECURITY CONSIDERATIONS
 3111: 
 3112: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3113: generates SQL strings, never opens files, and never calls C<system()>,
 3114: C<exec()>, or C<eval()>.  The security properties described below are
 3115: architectural guarantees, not run-time checks.
 3116: 
 3117: =head2 What Database::Join guarantees
 3118: 
 3119: =over 4
 3120: 
 3121: =item Criteria partition isolation
 3122: 
 3123: Every criterion you pass to a query method is routed to I<exactly one>
 3124: component database (the one that owns that column), or to I<all> databases
 3125: when the criterion is on the join key column.  A hostile value in a criterion
 3126: for column C<name> (owned by database A) will never reach database B.
 3127: 
 3128: =item Unknown columns are rejected before reaching any database
 3129: 
 3130: If a criterion column name is not present in any component database (or has
 3131: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3132: and silently drops the criterion.  No database receives the hostile key.
 3133: 
 3134: =item AUTOLOAD only accepts word-character column names
 3135: 
 3136: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3137: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3138: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3139: C<_>) are additionally blocked with an explicit C<croak>.
 3140: 
 3141: =item No value sanitisation (by design)
 3142: 
 3143: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3144: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3145: responsibility of the underlying C<Database::Abstraction> objects (which use
 3146: parameterised queries).  Preventing XSS or header injection is the
 3147: responsibility of the CGI or web layer that renders the output.
 3148: 
 3149: =item Taint-mode compatible (array path)
 3150: 
 3151: The array merge path contains no C<system()>, C<exec()>, backtick,
 3152: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3153: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3154: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3155: an I<untainted> capture, so the column name used for dispatch is clean under
 3156: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3157: objects; those objects are responsible for handling tainted values at the SQL
 3158: parameterisation layer.
 3159: 
 3160: =item SQLite backend: column names are quoted, values are parametrised
 3161: 
 3162: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3163: All column and table names are double-quoted (SQL identifier quoting) before
 3164: being embedded in statement strings.  All row values are passed to SQLite
 3165: exclusively through DBI prepared statement placeholders -- never by string
 3166: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3167: into the temporary database.
 3168: 
 3169: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3170: unpredictable filename.  No C<system()> or shell command is used to create or
 3171: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3172: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3173: in the generated SQL come from C<columns()>, which is produced by
 3174: C<Database::Abstraction> at construction time -- they are not derived from
 3175: caller-supplied criteria values.
 3176: 
 3177: =item Operator hashref broadcast copy
 3178: 
 3179: When the same join-key criterion (an operator hashref such as
 3180: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3181: database receives its own I<shallow copy> of the hashref.  A component database
 3182: that mutates the hashref's contents at the top level cannot affect what
 3183: subsequent databases receive.
 3184: 
 3185: =item collision_prefix value type guard
 3186: 
 3187: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3188: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3189: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3190: column name, C<columns()> listing, and merged row returned to the caller.  The
 3191: guard fires before any column name is constructed.
 3192: 
 3193: =item Filter deep-copy isolation
 3194: 
 3195: The C<filters> constructor parameter and the C<filter> option of
 3196: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3197: original hashrefs are never stored; post-construction mutation of those
 3198: hashrefs cannot widen or bypass the configured row-security constraints.
 3199: 
 3200: =back

 3203: 
 3204: =over 4
 3205: 
 3206: =item Sanitise values before building criteria
 3207: 
 3208: DJ passes criterion values verbatim to component databases.  If your
 3209: application accepts user-supplied filter values (e.g. from a CGI query
 3210: string), those values I<must> be validated or sanitised by your application
 3211: before being passed to DJ.
 3212: 
 3213: =item Restrict which columns the caller can filter on
 3214: 
 3215: Any column in C<columns()> can be used as a filter criterion.  If a column
 3216: should not be filterable by end users (e.g. an internal status flag), hide it

 3219: =item Do not expose the joined view directly to user-supplied criteria
 3220: 
 3221: DJ is not a firewall.  It faithfully routes user input to component databases.
 3222: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 3223: columns and validates their values.
 3224:

 3519: =head1 STATE DIAGRAM
 3520: 
 3521: C<Database::Join> objects follow three independent finite state machines (FSMs).
 3522: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 3523: triggers that cause transitions (arrows), and important side-effects.
 3524: 
 3525: =head2 FSM 1: Object Lifecycle
 3526: 
 3527: Governs the structural state of a C<Database::Join> instance.
 3528: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 3529: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 3530: are not shown because they do not change state.
 3531: 
 3532:     [pre-creation]
 3533:          |
 3534:          | new( databases => [...], join_column => '...' )
 3535:          |   Side-effect: _col_db routing table built;
 3536:          |                _autoload_pk cached from dbs[0]{id}
 3537:          v
 3538:     [CONSTRUCTED] <-----------------------------------------+
 3539:          |    |                                              |
 3540:          |    +--------------------------------------------+ |
 3541:          |    (query methods: no structural change)         | |
 3542:          |                                                  | |
 3543:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 3544:          |                                      |    |        |
 3545:          |   Side-effect: col removed from       |    |        |
 3546:          |   _col_db; _col_cache and             +----+        |
 3547:          |   _schema_cache cleared.              (idempotent;  |
 3548:          |   Join column cannot be removed.)      chainable)   |
 3549:          |                                                     |
 3550:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 3551:                                                 |    |
 3552:              Side-effect: new columns added;    |    | add_database( db )
 3553:              _col_db extended; SQLite cache     |    | (chainable; each
 3554:              invalidated (if any).              +----+  extends the view)
 3555: 
 3556:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 3557:     Both transitions are legal on any valid object, in any order.
 3558: 
 3559:     Illegal triggers (always croak; object state is not changed):
 3560: 
 3561:       Trigger                              Error
 3562:       -----------------------------------  ---------------------------------
 3563:       new( databases => [] )               error_no_databases
 3564:       remove_column( join_column )         error_remove_join_column
