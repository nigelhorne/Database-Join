  251: =head1 DESCRIPTION
  252: 
  253: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  254: single logical, read-only view.  Each component database is queried
  255: independently through its own C<Database::Abstraction> interface.  The results
  256: are combined using a shared key column (C<join_column>).
  257: In effect, this means that you can view data from more than one database using
  258: an intuitive, non-SQL interface.
  259: 
  260: Every storage format that C<Database::Abstraction> supports works as a
  261: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  262: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  263: within the same join.
  264: 
  265: The module exposes the same read-only API as C<Database::Abstraction>:
  266: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  267: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  268: shortcut.  Callers do not need to know how many underlying databases are
  269: involved.
  270: 
  271: Think of it as a virtual database table that is assembled on demand from
  272: several real tables, one per component database.
  273: 
  274: B<Join backends>
  275: 
  276: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  277: combined source row count.  For small datasets (up to C<max_array_rows>,
  278: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  279: automatically spills source rows into a temporary SQLite database and executes
  280: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  281: size instead of three.  You can also force either path unconditionally with
  282: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  283: 
  284: =head2 Join semantics
  285: 
  286: The C<join_type> parameter controls what happens when a particular key value
  287: exists in some component databases but not all:
  288: 
  289: =over 4
  290: 
  291: =item C<left> (the default)
  292: 
  293: All rows from the I<primary> (first) database are returned.  Columns from
  294: subsequent databases are included where a matching row is found, and simply
  295: absent from the hashref where there is no match.  If you are familiar with
  296: SQL, this is a LEFT OUTER JOIN on the first table.
  297: 
  298: =item C<inner>
  299: 
  300: Only rows whose join-column value is present in I<every> component database
  301: are returned.  This is equivalent to a SQL INNER JOIN.
  302: 
  303: =item C<outer>
  304: 
  305: Every join-column value found in I<any> component database is returned.
  306: Columns from databases that do not have that key value are absent from the
  307: merged row.  This is a FULL OUTER JOIN.
  308: 
  309: =back
  310: 
  311: B<Important override rule:> whenever you pass a query criterion for a column
  312: that belongs to a secondary database, that database automatically acts as an
  313: inner-join partner for that query only -- regardless of C<join_type>.  This
  314: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  315: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  316: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  317: as a WHERE clause would exclude them).
  318: 
  319: =head2 Column ownership and routing
  320: 
  321: At construction time, C<Database::Join> calls C<columns()> on each component
  322: database and builds an internal index that maps every column name to the
  323: database that owns it.
  324: 
  325: When you pass criteria to a query method, each key-value pair is automatically
  326: routed to the right database.  You never need to say which database a column
  327: belongs to.
  328: 
  329: The C<join_column> is special: criteria on it are broadcast to I<all>
  330: databases so that each database fetches only the relevant rows before the
  331: in-memory merge.
  332: 
  333: When the same non-join column name exists in more than one database, the
  334: I<last> database in the C<databases> array wins by default: its value
  335: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  336: preserve both values under distinct names instead.
  337: 
  338: =head1 LIMITATIONS
  339: 
  340: =over 4
  341: 
  342: =item Memory usage (array backend)
  343: 
  344: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  345: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  346: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  347: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  348: 
  349: =item SQLite backend uses a persistent cache file
  350: 
  351: When the SQLite path is active, a single C<.db> file with a randomly generated
  352: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  353: first time a query runs on a given C<Database::Join> object.  Source data is
  354: spilled into that file once; subsequent queries against the same object reuse
  355: the file without re-fetching the source data.
  356: 
  357: The cache is automatically invalidated and rebuilt whenever any source
  358: database's C<updated()> timestamp changes (indicating new data), or when
  359: C<add_database()> is called.
  360: 
  361: The file is deleted when the C<Database::Join> object is destroyed (typically
  362: when it goes out of scope).  At any given moment no more than one such file
  363: exists per object.  The directory must be writable and have enough free space
  364: for the full source data (once, not per-query).
  365: 
  366: =item No chained builder or raw SQL
  367: 
  368: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  369: or C<fetchrow_hashref> instead.
  370: 
  371: =item Single-column equi-join only
  372: 
  373: Joining on more than one column simultaneously, or on expressions, is not
  374: supported.  When the join key has different names in different databases,
  375: use C<join_map> to declare each database's local column name.
  376: 
  377: =item Sort order
  378: 
  379: Results are sorted by the C<join_column> value only.  Caller-specified
  380: C<ORDER BY> is not propagated to the component databases.
  381: 
  382: =item count() fetches all rows
  383: 
  384: C<count()> executes the full join and counts the resulting rows in Perl.  It
  385: does not push a C<COUNT(*)> query down to the databases.
  386: 
  387: =back

  389: =head1 COMMON PITFALLS
  390: 
  391: =over 4
  392: 
  393: =item The join_column must exist in every component database
  394: 
  395: If even one database is missing the join key column, C<new()> (or
  396: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  397: column has a different local name in some databases.
  398: 
  399: =item Criteria on a removed column are silently dropped
  400: 
  401: If you call C<remove_column('tier')> and later query
  402: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  403: C<carp> warning) and all rows are returned.  Always pass criteria before
  404: removing columns, or restructure your code to avoid this.
  405: 
  406: =item You cannot remove the join column
  407: 
  408: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  409: is required for the merge to work.
  410: 
  411: =item Left join does not guarantee all columns are populated
  412: 
  413: Under a LEFT join, rows from the primary database that have no matching row
  414: in a secondary database will be returned with I<no keys> from that secondary
  415: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  416: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  417: than just C<$row->{score}> when the secondary match is optional.
  418: 
  419: =item Filters act as inner-join partners
  420: 
  421: Any database that has a C<filters> entry is promoted to an inner-join partner,
  422: regardless of C<join_type>.  A row whose join-key value does not appear in
  423: the filtered database's result is removed from the merged output entirely, not
  424: merely missing its secondary columns.  This is intentional but can be
  425: surprising if you expected LEFT join semantics.
  426: 
  427: =item Criteria-merging replaces scalar filters
  428: 
  429: When both a base filter and a query criterion target the same column, and both
  430: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  431: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  432: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  433: the base filter is ignored for that query.
  434: 
  435: =item AUTOLOAD sees the full merged join when filters or join_map are active
  436: 
  437: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  438: (C<< $join->columnname(...) >>) runs the full join query rather than
  439: delegating directly to the owning database.  This is necessary for correctness
  440: but means the result respects all active filters and join-key translations,
  441: which may differ from what the owning database would return on its own.
  442: 
  443: =item Duplicate column names: last database wins (unless collision_prefix is set)
  444: 
  445: When two component databases each have a column called C<notes>, the second
  446: database's value silently overwrites the first in every merged row.  Use
  447: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  448: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  449: (or C<remove_column>) to drop the unwanted duplicate entirely.
  450: 
  451: =item Mutating the filters hashref after construction has no effect
  452: 
  453: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  454: passed to C<add_database>) at the moment of construction.  The original hashref
  455: you passed in is never stored.  If you later modify it -- for example, to
  456: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  457: Construct a new C<Database::Join> object, or use a component
  458: C<Database::Abstraction> that supports dynamic filter modification.
  459: 
  460: =item auto mode may always use the array path for some DAs
  461: 
  462: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  463: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  464: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  465: from C<Database::Abstraction> is treated as uncountable, because the parent
  466: class C<count()> expects a key argument and behaves differently from a
  467: "return total row count" function.  In that case C<Database::Join>
  468: conservatively uses the array path for the whole query, even if the dataset is
  469: large.  To opt in to the SQLite path for such a DA, either add your own
  470: C<count()> override that returns the total row count, implement C<dbi_source()>,
  471: or use C<backend =E<gt> 'sqlite'> unconditionally.
  472: 
  473: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  474: 
  475: When a component database implements C<dbi_source()>, C<Database::Join> always
  476: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  477: for columns in that database>.  The criteria are translated into parameterised
  478: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  479: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  480: force a spill; that restriction has been removed.)
  481: 
  482: =item Broadcast join-column criterion does not force secondaries into inner-join
  483: 
  484: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  485: C<Database::Join> broadcasts it to all component databases so each DA can
  486: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  487: incorrectly counted as "having criteria" for secondary databases, causing
  488: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  489: join-column criterion was present.  The fix: only non-join-column criteria
  490: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  491: a secondary to inner-join status.  The broadcast itself is now a transparent
  492: key-range selector that does not affect join semantics.
  493: 
  494: =item Temp file directory must be writable and have free space
  495: 
  496: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  497: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  498: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  499: only the directory is under your control.  The file is created on the first
  500: query and kept alive until the object is destroyed; it is not re-created on
  501: every query call.  If the directory is not writable, or the filesystem is full,
  502: the call will C<croak> with C<error_sqlite_connect>.  Check permissions and
  503: free space if you see that error.

  799: =head2 join_map - joining on differently-named columns
  800: 
  801: By default every component database must have a column whose name matches
  802: C<join_column>.  If a database uses a different local name for the join key,
  803: declare the mapping with C<join_map>.
  804: 
  805: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  806: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  807: B<value> is the name that B<that particular database> uses for the join key.
  808: 
  809: Databases not listed in C<join_map> are assumed to already have a column
  810: named C<join_column> and need no entry.
  811: 
  812: Throughout the merged view the join key is I<always> referred to by the name
  813: given in C<join_column>.  The local alias is never exposed in returned rows,
  814: in C<columns()>, or in C<schema()>.
  815: 
  816: B<When do you need join_map?>
  817: 
  818: You need C<join_map> when you have two tables like:
  819: 
  820:     cities table  : entry (the city name) | statecode
  821:     stnames table : entry (the state code) | state
  822: 
  823: Here you want to join cities.statecode to stnames.entry.  You choose
  824: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  825: that same concept C<entry>, so you declare:
  826: 
  827:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  828: 
  829: B<Example>
  830: 
  831:     #                        index 0     index 1
  832:     my @databases = (       $cities,    $stnames  );
  833:     #  join key column:    'statecode'  'entry'
  834:     #  join_column:        'statecode' (chosen canonical name)
  835:     #  stnames differs, so declare the alias:
  836: 
  837:     my $join = Database::Join->new(
  838:         databases   => \@databases,
  839:         join_column => 'statecode',
  840:         join_map    => { 1 => 'entry' },
  841:     );

  843:     my $rows = $join->selectall_arrayref();

  862: =head2 filters - permanent per-database row filters
  863: 
  864: C<filters> lets you restrict a component database to a subset of its rows
  865: permanently, without repeating the criterion on every query call.
  866: 
  867: Think of it as telling the join: "whenever you query this database, always
  868: add these extra conditions".  Callers never need to specify the restriction
  869: themselves and can never accidentally omit it.
  870: 
  871: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  872: database in the C<databases> array (same numbering as C<join_map>).  Each
  873: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  874: accepts.
  875: 
  876: B<Key-set semantics>
  877: 
  878: A filtered database always acts as an inner-join partner, regardless of the
  879: C<join_type> setting.  Any join-key value that does not pass the filter is
  880: excluded from the merged output entirely -- not just missing its secondary
  881: columns.  This ensures the filter genuinely restricts the view rather than
  882: simply hiding a few fields.
  883: 
  884: B<Criteria merging>
  885: 
  886: When a query call also passes a criterion for a column that already has a base
  887: filter, the two constraints are combined:
  888: 
  889: =over 4
  890: 
  891: =item *
  892: 
  893: When both the base filter value and the query criterion are operator hashrefs
  894: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  895: merged: I<both> constraints apply simultaneously (AND semantics).
  896: 
  897: =item *
  898: 
  899: When either value is a plain scalar, or the operators conflict, the
  900: query-time criterion wins and the base filter for that column is ignored for
  901: that one call.
  902: 
  903: =back
  904: 
  905: B<Example -- only show orders placed more than 60 days ago>
  906: 
  907:     my $join = Database::Join->new(
  908:         databases   => [ $customers, $orders ],

  927: =head2 collision_prefix - preserve colliding columns from secondary databases
  928: 
  929: By default, when a column name appears in more than one database the I<last>
  930: database wins: its value silently overwrites earlier ones in merged rows.
  931: This loses data and makes the origin invisible.
  932: 
  933: C<collision_prefix> changes this for secondary databases you designate.
  934: When a secondary database at index N has a column that already exists in the
  935: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  936: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  937: visible: the original column keeps its name (from the earlier database), and
  938: the collision gets the prefixed name.
  939: 
  940: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  941: a secondary database in the C<databases> array (same numbering as C<join_map>).
  942: Each B<value> is the prefix string to prepend.  An index-0 entry is
  943: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  944: preserves the previous last-wins behaviour and changes nothing.
  945: 
  946: Non-colliding columns from a secondary database are always added as-is with
  947: no prefix, whether or not C<collision_prefix> is configured.
  948: 
  949: B<Example -- sales table and products table, both with a "product" column>
  950: 
  951:     # $sales    columns: id, product, amount, date
  952:     # $products columns: sku, product, price, category
  953:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  954: 
  955:     my $join = Database::Join->new(
  956:         databases        => [$sales, $products],
  957:         join_column      => 'product',
  958:         join_map         => { 1 => 'sku' },
  959:         collision_prefix => { 1 => 'products' },
  960:     );
  961: 
  962:     $join->columns;
  963:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  964:     #                                                               ^-- prefixed collision
  965: 
  966:     my $row = $join->fetchrow_hashref(product => 'widget');
  967:     # $row->{product}            -- value from $sales
  968:     # $row->{'products.product'} -- value from $products (different row, same column name)
  969:     # $row->{price}              -- from $products, no collision, kept as-is
  970:

  985: =head2 backend - SQLite join backend for large datasets
  986: 
  987: C<Database::Join> can merge component databases in two different ways,
  988: controlled by the C<backend> constructor parameter.
  989: 
  990: =over 4
  991: 
  992: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  993: 
  994: All matching rows are fetched from every component database into Perl hashes
  995: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
  996: is roughly three times the combined source data size (one copy per database
  997: plus one merged copy).
  998: 
  999: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1000: 
 1001: C<Database::Join> creates a temporary SQLite database file, spills source
 1002: rows into it (one table per component database), then executes a single SQL
 1003: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1004: source data size.
 1005: 
 1006: The temporary file is created once and reused across multiple query calls on
 1007: the same object (the cache).  Only query-time criteria vary per call; they
 1008: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1009: automatically rebuilt when any source database's C<updated()> timestamp
 1010: changes.  The file is deleted when the object is destroyed (goes out of
 1011: scope).  See I<Temporary file: name, location, and lifetime> below for
 1012: details.
 1013: 
 1014: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
 1015: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
 1016: 
 1017: =item C<backend =E<gt> 'auto'> (default)
 1018: 
 1019: C<Database::Join> counts the total rows from all component databases cheaply
 1020: -- without fetching them -- and then decides:
 1021: 
 1022: =over 4
 1023: 
 1024: =item *
 1025: 
 1026: If the combined count is less than or equal to C<max_array_rows> (default
 1027: 10,000), use the array path.
 1028: 
 1029: =item *
 1030: 
 1031: If the combined count exceeds C<max_array_rows>, use the SQLite path.
 1032: 
 1033: =back
 1034: 
 1035: For counting to work without fetching, each component database must either
 1036: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
 1037: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
 1038: method in its own package -- not just inherit one from a parent class.  If
 1039: neither is available for a particular database, C<Database::Join> plays it
 1040: safe and uses the array path for the whole query without fetching any rows.
 1041: 
 1042: =back
 1043: 
 1044: B<Choosing max_array_rows>
 1045: 
 1046: The default of 10,000 is a reasonable starting point.  Adjust it to match
 1047: your hardware and typical row width.  For wide rows (many columns or long
 1048: strings) you may want a lower threshold; for narrow rows you can raise it.
 1049: 
 1050: B<Temporary file: name, location, and lifetime>
 1051: 
 1052: When the SQLite path is active, a single temporary SQLite database file acts
 1053: as the join cache for the life of the C<Database::Join> object.
 1054: 
 1055: B<Name>: the filename is randomly generated by C<File::Temp>, for example:
 1056: 
 1057:     /tmp/Cj8xK7mP2Q.db
 1058: 
 1059: The random portion (ten characters) is chosen automatically to avoid
 1060: collisions.  Only the directory is under your control; you cannot specify
 1061: the filename itself.
 1062: 
 1063: B<Location>: controlled by the C<tmpdir> constructor parameter.
 1064: If C<tmpdir> is not specified, C<File::Spec-E<gt>tmpdir()> is used (usually
 1065: C</tmp> on Unix, or the value of the C<TEMP> or C<TMP> environment variable
 1066: on Windows).
 1067: 
 1068: B<Lifetime: one file per object, deleted when the object is destroyed>: the
 1069: file is created on the first query call that uses the SQLite path and kept
 1070: alive until the C<Database::Join> object is destroyed (i.e. when it goes out
 1071: of scope or is explicitly C<undef>-d).  At most one file exists per object at
 1072: any given moment.  Calling C<selectall_arrayref()> ten times on the same
 1073: object creates and uses I<one> file, not ten.
 1074: 
 1075: B<Cache invalidation>: the cache is automatically rebuilt (the old file is
 1076: replaced with a new one) when any source database's C<updated()> return value
 1077: changes, or when C<add_database()> is called.  Base-filter criteria
 1078: (C<filters> constructor parameter) are applied once at build time for spilled
 1079: sources; query-time criteria are applied per-call as SQL C<WHERE> clauses.
 1080: 
 1081: To use a different directory -- for example a RAM-backed filesystem or a
 1082: faster local disk:
 1083: 
 1084:     my $join = Database::Join->new(
 1085:         databases      => [ $db1, $db2 ],
 1086:         join_column    => 'entry',
 1087:         backend        => 'sqlite',
 1088:         tmpdir         => '/dev/shm',     # Linux RAM disk
 1089:     );
 1090: 
 1091: B<Zero-copy ATTACH (C<dbi_source()> interface)>
 1092: 
 1093: Normally, when the SQLite path is active, rows from each component database
 1094: are fetched one by one and inserted into the temporary SQLite file.  This is
 1095: efficient but does involve INSERT overhead.
 1096: 
 1097: If a component database is itself SQLite-backed and implements a
 1098: C<dbi_source()> method, C<Database::Join> can skip the row-by-row copy
 1099: entirely and instead use C<ATTACH DATABASE> to link the source file directly

 2895: 
 2896: All text that passes through C<Database::Join> at the Perl layer (column names,
 2897: criteria values, merged row values) is treated as opaque strings.
 2898: C<Database::Join> does not inspect, encode, or transform string content.

 2901: 
 2902: =item Column names
 2903:

 2906: underlying DA and database driver.

 2911: safe as long as the underlying C<Database::Abstraction> objects and their

 2913: nor decodes any value.

 2921: data.  Binary blobs are not explicitly tested.

 3040: =head1 SECURITY CONSIDERATIONS
 3041: 
 3042: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3043: generates SQL strings, never opens files, and never calls C<system()>,
 3044: C<exec()>, or C<eval()>.  The security properties described below are
 3045: architectural guarantees, not run-time checks.
 3046: 
 3047: =head2 What Database::Join guarantees
 3048: 
 3049: =over 4
 3050: 
 3051: =item Criteria partition isolation
 3052: 
 3053: Every criterion you pass to a query method is routed to I<exactly one>
 3054: component database (the one that owns that column), or to I<all> databases
 3055: when the criterion is on the join key column.  A hostile value in a criterion
 3056: for column C<name> (owned by database A) will never reach database B.
 3057: 
 3058: =item Unknown columns are rejected before reaching any database
 3059: 
 3060: If a criterion column name is not present in any component database (or has
 3061: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3062: and silently drops the criterion.  No database receives the hostile key.
 3063: 
 3064: =item AUTOLOAD only accepts word-character column names
 3065: 
 3066: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3067: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3068: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3069: C<_>) are additionally blocked with an explicit C<croak>.
 3070: 
 3071: =item No value sanitisation (by design)
 3072: 
 3073: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3074: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3075: responsibility of the underlying C<Database::Abstraction> objects (which use
 3076: parameterised queries).  Preventing XSS or header injection is the
 3077: responsibility of the CGI or web layer that renders the output.
 3078: 
 3079: =item Taint-mode compatible (array path)
 3080: 
 3081: The array merge path contains no C<system()>, C<exec()>, backtick,
 3082: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3083: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3084: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3085: an I<untainted> capture, so the column name used for dispatch is clean under
 3086: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3087: objects; those objects are responsible for handling tainted values at the SQL
 3088: parameterisation layer.
 3089: 
 3090: =item SQLite backend: column names are quoted, values are parametrised
 3091: 
 3092: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3093: All column and table names are double-quoted (SQL identifier quoting) before
 3094: being embedded in statement strings.  All row values are passed to SQLite
 3095: exclusively through DBI prepared statement placeholders -- never by string
 3096: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3097: into the temporary database.
 3098: 
 3099: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3100: unpredictable filename.  No C<system()> or shell command is used to create or
 3101: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3102: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3103: in the generated SQL come from C<columns()>, which is produced by
 3104: C<Database::Abstraction> at construction time -- they are not derived from
 3105: caller-supplied criteria values.
 3106: 
 3107: =item Operator hashref broadcast copy
 3108: 
 3109: When the same join-key criterion (an operator hashref such as
 3110: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3111: database receives its own I<shallow copy> of the hashref.  A component database
 3112: that mutates the hashref's contents at the top level cannot affect what
 3113: subsequent databases receive.
 3114: 
 3115: =item collision_prefix value type guard
 3116: 
 3117: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3118: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3119: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3120: column name, C<columns()> listing, and merged row returned to the caller.  The
 3121: guard fires before any column name is constructed.
 3122: 
 3123: =item Filter deep-copy isolation
 3124: 
 3125: The C<filters> constructor parameter and the C<filter> option of
 3126: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3127: original hashrefs are never stored; post-construction mutation of those
 3128: hashrefs cannot widen or bypass the configured row-security constraints.
 3129: 
 3130: =back
 3131: 
 3132: =head2 What the caller is responsible for
 3133: 
 3134: =over 4
 3135: 
 3136: =item Sanitise values before building criteria
 3137: 
 3138: DJ passes criterion values verbatim to component databases.  If your
 3139: application accepts user-supplied filter values (e.g. from a CGI query
 3140: string), those values I<must> be validated or sanitised by your application
 3141: before being passed to DJ.
 3142: 
 3143: =item Restrict which columns the caller can filter on
 3144: 
 3145: Any column in C<columns()> can be used as a filter criterion.  If a column
 3146: should not be filterable by end users (e.g. an internal status flag), hide it
 3147: with C<remove_column> so that queries on it are silently dropped.
 3148: 
 3149: =item Do not expose the joined view directly to user-supplied criteria
 3150: 
 3151: DJ is not a firewall.  It faithfully routes user input to component databases.
 3152: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 3153: columns and validates their values.
 3154:

 3449: =head1 STATE DIAGRAM
 3450: 
 3451: C<Database::Join> objects follow three independent finite state machines (FSMs).
 3452: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 3453: triggers that cause transitions (arrows), and important side-effects.
 3454: 
 3455: =head2 FSM 1: Object Lifecycle
 3456: 
 3457: Governs the structural state of a C<Database::Join> instance.
 3458: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 3459: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 3460: are not shown because they do not change state.
 3461: 
 3462:     [pre-creation]
 3463:          |
 3464:          | new( databases => [...], join_column => '...' )
 3465:          |   Side-effect: _col_db routing table built;
 3466:          |                _autoload_pk cached from dbs[0]{id}
 3467:          v
 3468:     [CONSTRUCTED] <-----------------------------------------+
 3469:          |    |                                              |
 3470:          |    +--------------------------------------------+ |
 3471:          |    (query methods: no structural change)         | |
 3472:          |                                                  | |
 3473:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 3474:          |                                      |    |        |
 3475:          |   Side-effect: col removed from       |    |        |
 3476:          |   _col_db; _col_cache and             +----+        |
 3477:          |   _schema_cache cleared.              (idempotent;  |
 3478:          |   Join column cannot be removed.)      chainable)   |
 3479:          |                                                     |
 3480:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 3481:                                                 |    |
 3482:              Side-effect: new columns added;    |    | add_database( db )
 3483:              _col_db extended; SQLite cache     |    | (chainable; each
 3484:              invalidated (if any).              +----+  extends the view)
 3485: 
 3486:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 3487:     Both transitions are legal on any valid object, in any order.
 3488: 
 3489:     Illegal triggers (always croak; object state is not changed):
 3490: 
 3491:       Trigger                              Error
 3492:       -----------------------------------  ---------------------------------
 3493:       new( databases => [] )               error_no_databases
 3494:       remove_column( join_column )         error_remove_join_column
