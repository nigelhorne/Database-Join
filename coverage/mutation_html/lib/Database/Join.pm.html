  194: =head1 DESCRIPTION
  195: 
  196: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  197: single logical, read-only view.  Each component database is queried
  198: independently through its own C<Database::Abstraction> interface.  The results
  199: are combined using a shared key column (C<join_column>).
  200: In effect, this means that you can view data from more than one database using
  201: an intuitive, non-SQL interface.
  202: 
  203: Every storage format that C<Database::Abstraction> supports works as a
  204: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  205: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  206: within the same join.
  207: 
  208: The module exposes the same read-only API as C<Database::Abstraction>:
  209: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  210: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  211: shortcut.  Callers do not need to know how many underlying databases are
  212: involved.
  213: 
  214: Think of it as a virtual database table that is assembled on demand from
  215: several real tables, one per component database.
  216: 
  217: B<Join backends>
  218: 
  219: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  220: combined source row count.  For small datasets (up to C<max_array_rows>,
  221: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  222: automatically spills source rows into a temporary SQLite database and executes
  223: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  224: size instead of three.  You can also force either path unconditionally with
  225: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  226: 
  227: =head2 Join semantics
  228: 
  229: The C<join_type> parameter controls what happens when a particular key value
  230: exists in some component databases but not all:
  231: 
  232: =over 4
  233: 
  234: =item C<left> (the default)
  235: 
  236: All rows from the I<primary> (first) database are returned.  Columns from
  237: subsequent databases are included where a matching row is found, and simply
  238: absent from the hashref where there is no match.  If you are familiar with
  239: SQL, this is a LEFT OUTER JOIN on the first table.
  240: 
  241: =item C<inner>
  242: 
  243: Only rows whose join-column value is present in I<every> component database
  244: are returned.  This is equivalent to a SQL INNER JOIN.
  245: 
  246: =item C<outer>
  247: 
  248: Every join-column value found in I<any> component database is returned.
  249: Columns from databases that do not have that key value are absent from the
  250: merged row.  This is a FULL OUTER JOIN.
  251: 
  252: =back
  253: 
  254: B<Important override rule:> whenever you pass a query criterion for a column
  255: that belongs to a secondary database, that database automatically acts as an
  256: inner-join partner for that query only -- regardless of C<join_type>.  This
  257: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  258: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  259: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  260: as a WHERE clause would exclude them).
  261: 
  262: =head2 Column ownership and routing
  263: 
  264: At construction time, C<Database::Join> calls C<columns()> on each component
  265: database and builds an internal index that maps every column name to the
  266: database that owns it.
  267: 
  268: When you pass criteria to a query method, each key-value pair is automatically
  269: routed to the right database.  You never need to say which database a column
  270: belongs to.
  271: 
  272: The C<join_column> is special: criteria on it are broadcast to I<all>
  273: databases so that each database fetches only the relevant rows before the
  274: in-memory merge.
  275: 
  276: When the same non-join column name exists in more than one database, the
  277: I<last> database in the C<databases> array wins by default: its value
  278: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  279: preserve both values under distinct names instead.
  280: 
  281: =head1 LIMITATIONS
  282: 
  283: =over 4
  284: 
  285: =item Memory usage (array backend)
  286: 
  287: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  288: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  289: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  290: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  291: 
  292: =item SQLite backend uses a persistent cache file
  293: 
  294: When the SQLite path is active, a single C<.db> file with a randomly generated
  295: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  296: first time a query runs on a given C<Database::Join> object.  Source data is
  297: spilled into that file once; subsequent queries against the same object reuse
  298: the file without re-fetching the source data.
  299: 
  300: The cache is automatically invalidated and rebuilt whenever any source
  301: database's C<updated()> timestamp changes (indicating new data), or when
  302: C<add_database()> is called.
  303: 
  304: The file is deleted when the C<Database::Join> object is destroyed (typically
  305: when it goes out of scope).  At any given moment no more than one such file
  306: exists per object.  The directory must be writable and have enough free space
  307: for the full source data (once, not per-query).
  308: 
  309: =item No chained builder or raw SQL
  310: 
  311: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  312: or C<fetchrow_hashref> instead.
  313: 
  314: =item Single-column equi-join only
  315: 
  316: Joining on more than one column simultaneously, or on expressions, is not
  317: supported.  When the join key has different names in different databases,
  318: use C<join_map> to declare each database's local column name.
  319: 
  320: =item Sort order
  321: 
  322: Results are sorted ascending by C<join_column> by default.  Pass
  323: C<< sort_by => 'colname' >> (or C<< sort_by => ['colname', 'DESC'] >>)
  324: to any query method to override this.  The array path uses string comparison
  325: (C<cmp>); for accurate numeric ordering on large datasets use the SQLite
  326: backend, which sorts natively by type.
  327: 
  328: =item count() on the array backend fetches all rows
  329: 
  330: On the array backend, C<count()> executes the full in-memory join and counts
  331: the resulting rows in Perl; no C<COUNT(*)> is pushed to the component
  332: databases.  On the SQLite backend, C<count()> executes a C<SELECT COUNT(*)>
  333: SQL query against the cached join tables, avoiding a full row transfer.
  334: 
  335: =back

  337: =head1 COMMON PITFALLS
  338: 
  339: =over 4
  340: 
  341: =item The join_column must exist in every component database
  342: 
  343: If even one database is missing the join key column, C<new()> (or
  344: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  345: column has a different local name in some databases.
  346: 
  347: =item Criteria on a removed column are silently dropped
  348: 
  349: If you call C<remove_column('tier')> and later query
  350: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  351: C<carp> warning) and all rows are returned.  Always pass criteria before
  352: removing columns, or restructure your code to avoid this.
  353: 
  354: =item You cannot remove the join column
  355: 
  356: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  357: is required for the merge to work.
  358: 
  359: =item Left join does not guarantee all columns are populated
  360: 
  361: Under a LEFT join, rows from the primary database that have no matching row
  362: in a secondary database will be returned with I<no keys> from that secondary
  363: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  364: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  365: than just C<$row->{score}> when the secondary match is optional.
  366: 
  367: =item Filters act as inner-join partners
  368: 
  369: Any database that has a C<filters> entry is promoted to an inner-join partner,
  370: regardless of C<join_type>.  A row whose join-key value does not appear in
  371: the filtered database's result is removed from the merged output entirely, not
  372: merely missing its secondary columns.  This is intentional but can be
  373: surprising if you expected LEFT join semantics.
  374: 
  375: =item Criteria-merging replaces scalar filters
  376: 
  377: When both a base filter and a query criterion target the same column, and both
  378: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  379: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  380: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  381: the base filter is ignored for that query.
  382: 
  383: =item AUTOLOAD sees the full merged join when filters or join_map are active
  384: 
  385: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  386: (C<< $join->columnname(...) >>) runs the full join query rather than
  387: delegating directly to the owning database.  This is necessary for correctness
  388: but means the result respects all active filters and join-key translations,
  389: which may differ from what the owning database would return on its own.
  390: 
  391: =item Duplicate column names: last database wins (unless collision_prefix is set)
  392: 
  393: When two component databases each have a column called C<notes>, the second
  394: database's value silently overwrites the first in every merged row.  Use
  395: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  396: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  397: (or C<remove_column>) to drop the unwanted duplicate entirely.
  398: 
  399: =item Mutating the filters hashref after construction has no effect
  400: 
  401: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  402: passed to C<add_database>) at the moment of construction.  The original hashref
  403: you passed in is never stored.  If you later modify it -- for example, to
  404: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  405: Construct a new C<Database::Join> object, or use a component
  406: C<Database::Abstraction> that supports dynamic filter modification.
  407: 
  408: =item auto mode may always use the array path for some DAs
  409: 
  410: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  411: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  412: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  413: from C<Database::Abstraction> is treated as uncountable, because the parent
  414: class C<count()> expects a key argument and behaves differently from a
  415: "return total row count" function.  In that case C<Database::Join>
  416: conservatively uses the array path for the whole query, even if the dataset is
  417: large.  To opt in to the SQLite path for such a DA, either add your own
  418: C<count()> override that returns the total row count, implement C<dbi_source()>,
  419: or use C<backend =E<gt> 'sqlite'> unconditionally.
  420: 
  421: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  422: 
  423: When a component database implements C<dbi_source()>, C<Database::Join> always
  424: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  425: for columns in that database>.  The criteria are translated into parameterised
  426: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  427: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  428: force a spill; that restriction has been removed.)
  429: 
  430: =item Broadcast join-column criterion does not force secondaries into inner-join
  431: 
  432: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  433: C<Database::Join> broadcasts it to all component databases so each DA can
  434: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  435: incorrectly counted as "having criteria" for secondary databases, causing
  436: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  437: join-column criterion was present.  The fix: only non-join-column criteria
  438: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  439: a secondary to inner-join status.  The broadcast itself is now a transparent
  440: key-range selector that does not affect join semantics.
  441: 
  442: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  443: 
  444: C<LIKE>, C<NOT LIKE>, C<IN>, and C<NOT IN> are fully supported on the SQLite
  445: backend.  C<LIKE>/C<NOT LIKE> take a scalar pattern; C<IN>/C<NOT IN> take an
  446: arrayref of values.  All are injection-safe because values are passed as bind
  447: parameters, never interpolated.
  448: 
  449:     # LIKE
  450:     my $rows = $join->selectall_arrayref(name => { LIKE => 'A%' });
  451: 
  452:     # IN
  453:     my $rows = $join->selectall_arrayref(tier => { IN => ['gold', 'silver'] });
  454: 
  455:     # NOT IN
  456:     my $rows = $join->selectall_arrayref(tier => { 'NOT IN' => ['bronze'] });
  457: 
  458: C<IN> with an empty arrayref matches no rows (SQL semantics: C<IN ()> is
  459: always false).  C<NOT IN> with an empty arrayref matches all rows (no
  460: constraint added).
  461: 
  462: C<IS NULL> and C<IS NOT NULL> are supported on the SQLite backend using an
  463: explicit operator hashref:
  464: 
  465:     my $rows = $join->selectall_arrayref(score => { 'IS NULL'     => undef });
  466:     my $rows = $join->selectall_arrayref(score => { 'IS NOT NULL' => 1    });
  467: 
  468: The hashref value is ignored; only the key selects the operator.  A bare
  469: C<undef> criterion value (C<< score => undef >>) also generates C<IS NULL>
  470: on the SQLite path.  Note: on the in-memory array path, the component DA
  471: may treat an C<undef> criterion value as C<< no filter >> rather than
  472: C<IS NULL>, so use the explicit hashref form for consistent behaviour
  473: across backends.
  474: 
  475: Any operator not in the supported set is skipped on the SQLite path with a
  476: C<carp> warning.  The array path forwards all operators to the component DA
  477: unchanged, which may or may not honour them.
  478: 
  479: =item Temp file directory must be writable and have free space
  480: 
  481: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  482: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  483: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  484: only the directory is under your control.  The file is created on the first
  485: query and kept alive until the object is destroyed; it is not re-created on

  802: =head2 join_map - joining on differently-named columns
  803: 
  804: By default every component database must have a column whose name matches
  805: C<join_column>.  If a database uses a different local name for the join key,
  806: declare the mapping with C<join_map>.
  807: 
  808: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  809: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  810: B<value> is the name that B<that particular database> uses for the join key.
  811: 
  812: Databases not listed in C<join_map> are assumed to already have a column
  813: named C<join_column> and need no entry.
  814: 
  815: Throughout the merged view the join key is I<always> referred to by the name
  816: given in C<join_column>.  The local alias is never exposed in returned rows,
  817: in C<columns()>, or in C<schema()>.
  818: 
  819: B<When do you need join_map?>
  820: 
  821: You need C<join_map> when you have two tables like:
  822: 
  823:     cities table  : entry (the city name) | statecode
  824:     stnames table : entry (the state code) | state
  825: 
  826: Here you want to join cities.statecode to stnames.entry.  You choose
  827: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  828: that same concept C<entry>, so you declare:
  829: 
  830:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'

  865: =head2 filters - permanent per-database row filters
  866: 
  867: C<filters> lets you restrict a component database to a subset of its rows
  868: permanently, without repeating the criterion on every query call.
  869: 
  870: Think of it as telling the join: "whenever you query this database, always
  871: add these extra conditions".  Callers never need to specify the restriction
  872: themselves and can never accidentally omit it.
  873: 
  874: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  875: database in the C<databases> array (same numbering as C<join_map>).  Each
  876: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  877: accepts.
  878: 
  879: B<Key-set semantics>
  880: 
  881: A filtered database always acts as an inner-join partner, regardless of the
  882: C<join_type> setting.  Any join-key value that does not pass the filter is
  883: excluded from the merged output entirely -- not just missing its secondary
  884: columns.  This ensures the filter genuinely restricts the view rather than
  885: simply hiding a few fields.
  886: 
  887: B<Criteria merging>
  888: 
  889: When a query call also passes a criterion for a column that already has a base
  890: filter, the two constraints are combined:
  891: 
  892: =over 4
  893: 
  894: =item *

  896: When both the base filter value and the query criterion are operator hashrefs
  897: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  898: merged: I<both> constraints apply simultaneously (AND semantics).
  899: 
  900: =item *
  901: 
  902: When either value is a plain scalar, or the operators conflict, the
  903: query-time criterion wins and the base filter for that column is ignored for
  904: that one call.
  905: 
  906: =back

  930: =head2 collision_prefix - preserve colliding columns from secondary databases
  931: 
  932: By default, when a column name appears in more than one database the I<last>
  933: database wins: its value silently overwrites earlier ones in merged rows.
  934: This loses data and makes the origin invisible.
  935: 
  936: C<collision_prefix> changes this for secondary databases you designate.
  937: When a secondary database at index N has a column that already exists in the
  938: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  939: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  940: visible: the original column keeps its name (from the earlier database), and
  941: the collision gets the prefixed name.
  942: 
  943: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  944: a secondary database in the C<databases> array (same numbering as C<join_map>).
  945: Each B<value> is the prefix string to prepend.  An index-0 entry is
  946: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  947: preserves the previous last-wins behaviour and changes nothing.
  948: 
  949: Non-colliding columns from a secondary database are always added as-is with
  950: no prefix, whether or not C<collision_prefix> is configured.
  951: 
  952: B<Example -- sales table and products table, both with a "product" column>

  954:     # $sales    columns: id, product, amount, date
  955:     # $products columns: sku, product, price, category

  957: 
  958:     my $join = Database::Join->new(
  959:         databases        => [$sales, $products],
  960:         join_column      => 'product',
  961:         join_map         => { 1 => 'sku' },
  962:         collision_prefix => { 1 => 'products' },
  963:     );
  964: 
  965:     $join->columns;

  988: =head2 backend - SQLite join backend for large datasets
  989: 
  990: C<Database::Join> can merge component databases in two different ways,
  991: controlled by the C<backend> constructor parameter.
  992: 
  993: =over 4
  994: 
  995: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  996: 
  997: All matching rows are fetched from every component database into Perl hashes
  998: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
  999: is roughly three times the combined source data size (one copy per database
 1000: plus one merged copy).
 1001: 
 1002: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1003: 
 1004: C<Database::Join> creates a temporary SQLite database file, spills source
 1005: rows into it (one table per component database), then executes a single SQL
 1006: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1007: source data size.
 1008: 
 1009: The temporary file is created once and reused across multiple query calls on
 1010: the same object (the cache).  Only query-time criteria vary per call; they
 1011: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1012: automatically rebuilt when any source database's C<updated()> timestamp
 1013: changes.  The file is deleted when the object is destroyed (goes out of
 1014: scope).  See I<Temporary file: name, location, and lifetime> below for
 1015: details.
 1016: 
 1017: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
 1018: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
 1019: 
 1020: =item C<backend =E<gt> 'auto'> (default)
 1021: 
 1022: C<Database::Join> counts the total rows from all component databases cheaply
 1023: -- without fetching them -- and then decides:
 1024: 
 1025: =over 4
 1026: 
 1027: =item *
 1028: 
 1029: If the combined count is less than or equal to C<max_array_rows> (default
 1030: 10,000), use the array path.
 1031: 
 1032: =item *
 1033: 
 1034: If the combined count exceeds C<max_array_rows>, use the SQLite path.
 1035: 
 1036: =back
 1037: 
 1038: For counting to work without fetching, each component database must either
 1039: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
 1040: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
 1041: method in its own package -- not just inherit one from a parent class.  If
 1042: neither is available for a particular database, C<Database::Join> plays it
 1043: safe and uses the array path for the whole query without fetching any rows.
 1044: 
 1045: =back
 1046: 
 1047: B<Choosing max_array_rows>
 1048: 
 1049: The default of 10,000 is a reasonable starting point.  Adjust it to match
 1050: your hardware and typical row width.  For wide rows (many columns or long
 1051: strings) you may want a lower threshold; for narrow rows you can raise it.
 1052: 
 1053: B<Temporary file: name, location, and lifetime>
 1054: 
 1055: When the SQLite path is active, a single temporary SQLite database file acts
 1056: as the join cache for the life of the C<Database::Join> object.
 1057: 
 1058: B<Name>: the filename is randomly generated by C<File::Temp>, for example:
 1059: 
 1060:     /tmp/Cj8xK7mP2Q.db
 1061: 
 1062: The random portion (ten characters) is chosen automatically to avoid
 1063: collisions.  Only the directory is under your control; you cannot specify
 1064: the filename itself.
 1065: 
 1066: B<Location>: controlled by the C<tmpdir> constructor parameter.
 1067: If C<tmpdir> is not specified, C<File::Spec-E<gt>tmpdir()> is used (usually
 1068: C</tmp> on Unix, or the value of the C<TEMP> or C<TMP> environment variable
 1069: on Windows).
 1070: 
 1071: B<Lifetime: one file per object, deleted when the object is destroyed>: the
 1072: file is created on the first query call that uses the SQLite path and kept
 1073: alive until the C<Database::Join> object is destroyed (i.e. when it goes out
 1074: of scope or is explicitly C<undef>-d).  At most one file exists per object at
 1075: any given moment.  Calling C<selectall_arrayref()> ten times on the same
 1076: object creates and uses I<one> file, not ten.
 1077: 
 1078: B<Cache invalidation>: the cache is automatically rebuilt (the old file is
 1079: replaced with a new one) when any source database's C<updated()> return value
 1080: changes, or when C<add_database()> is called.  Base-filter criteria
 1081: (C<filters> constructor parameter) are applied once at build time for spilled
 1082: sources; query-time criteria are applied per-call as SQL C<WHERE> clauses.
 1083: 
 1084: To use a different directory -- for example a RAM-backed filesystem or a
 1085: faster local disk:
 1086: 
 1087:     my $join = Database::Join->new(
 1088:         databases      => [ $db1, $db2 ],
 1089:         join_column    => 'entry',
 1090:         backend        => 'sqlite',
 1091:         tmpdir         => '/dev/shm',     # Linux RAM disk
 1092:     );
 1093: 
 1094: B<Parallel secondary fetches (C<parallel> constructor parameter)>
 1095: 
 1096: By default, component databases are queried sequentially - the primary first,
 1097: then each secondary in order.  When the component databases are network- or
 1098: disk-backed and have non-trivial per-query latency, the sequential fetch means
 1099: total latency is the I<sum> of all per-DA latencies.
 1100: 
 1101: Setting C<< parallel => 1 >> in the constructor enables concurrent fetching
 1102: of secondary databases using Perl C<threads>.  With C<parallel => 1> and
 1103: two or more secondary databases (C<n E<gt> 2> total), secondary fetches run in
 1104: parallel after the primary fetch completes; total latency drops to
 1105: I<max(secondary latencies)> instead of I<sum(secondary latencies)>.
 1106: 
 1107:     my $join = Database::Join->new(
 1108:         databases   => [ $customers, $loyalty, $scores ],   # 3 DAs - 2 secondaries
 1109:         join_column => 'entry',
 1110:         parallel    => 1,    # loyalty and scores fetched concurrently
 1111:     );
 1112: 
 1113: Requirements and caveats:
 1114: 
 1115: =over 4
 1116: 
 1117: =item *
 1118: 
 1119: The C<threads> module must be available.  Most distributions ship it, but it
 1120: requires a Perl binary compiled with C<-Dusethreads>.  When threads are
 1121: unavailable, a C<carp> warning is emitted and fetching falls back to
 1122: sequential; the result is identical, only slower.
 1123: 
 1124: =item *
 1125: 
 1126: Parallel fetching is only active when the join has three or more total
 1127: databases (C<n E<gt> 2>).  With two databases (one secondary), the thread
 1128: creation overhead exceeds the benefit of concurrency; sequential is used
 1129: regardless of C<parallel>.
 1130: 
 1131: =item *
 1132: 
 1133: Component databases must be safe to call from Perl threads.  In-memory
 1134: databases (CSV, JSON, TSV after slurp) are safe.  DBI-backed databases
 1135: whose handles were created in the same thread may not be safe - consult your
 1136: DBD driver's thread documentation.  The array backend is recommended for
 1137: DBI-backed sources; the SQLite backend performs its join in a single SQL
 1138: statement and does not use parallel fetching.
 1139: 
 1140: =item *
 1141: 
 1142: C<parallel => 1> applies to the array backend only.  The SQLite backend
 1143: performs a single SQL JOIN after spilling source data, so per-DA parallelism
 1144: is irrelevant.
 1145: 
 1146: =back
 1147: 
 1148: B<Zero-copy ATTACH (C<dbi_source()> interface)>
 1149: 
 1150: Normally, when the SQLite path is active, rows from each component database
 1151: are fetched one by one and inserted into the temporary SQLite file.  This is
 1152: efficient but does involve INSERT overhead.
 1153: 
 1154: If a component database is itself SQLite-backed and implements a
 1155: C<dbi_source()> method, C<Database::Join> can skip the row-by-row copy
 1156: entirely and instead use C<ATTACH DATABASE> to link the source file directly
 1157: to the temporary join connection.  This is the zero-copy path and is
 1158: significantly faster for large SQLite sources.
 1159: 
 1160: The C<dbi_source()> method must return a hashref with two keys:
 1161: 
 1162: =over 4
 1163: 
 1164: =item C<dbh>
 1165: 
 1166: A connected C<DBD::SQLite> database handle (C<DBI> connection object).
 1167: 
 1168: =item C<table>
 1169: 
 1170: The name of the table in that database that holds the source rows.
 1171: 
 1172: =back
 1173: 
 1174: Example implementation:
 1175: 
 1176:     package My::SQLiteDatabase;
 1177:     use parent 'Database::Abstraction';
 1178: 
 1179:     sub dbi_source {
 1180:         my ($self) = @_;
 1181:         return {
 1182:             dbh   => $self->{_dbh},      # connected DBD::SQLite handle
 1183:             table => $self->{_table},    # table name in that database
 1184:         };
 1185:     }
 1186: 
 1187:     1;
 1188: 
 1189: The zero-copy ATTACH path is always used when a component database implements
 1190: C<dbi_source()>.  Query-time criteria are applied as parameterised SQL
 1191: C<WHERE> clauses against the ATTACHed source table, so no row-level copy is
 1192: needed even when the current call includes column filters.  (Prior to 0.005.0
 1193: any query-time criteria forced a spill; that restriction was removed in
 1194: 0.005.0.)
 1195: 
 1196: B<Result identity>
 1197: 
 1198: Both the array path and the SQLite path produce identical results for any
 1199: given query.  You can switch between them freely without changing callers.
 1200: The C<collision_prefix> column renaming, C<join_map> key translation, and all
 1201: three join types (left, inner, outer) work identically on both paths.

 3821: =head1 SECURITY CONSIDERATIONS
 3822: 
 3823: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3824: generates SQL strings, never opens files, and never calls C<system()>,
 3825: C<exec()>, or C<eval()>.  The security properties described below are
 3826: architectural guarantees, not run-time checks.
 3827: 
 3828: =head2 What Database::Join guarantees
 3829: 
 3830: =over 4
 3831: 
 3832: =item Criteria partition isolation
 3833: 
 3834: Every criterion you pass to a query method is routed to I<exactly one>
 3835: component database (the one that owns that column), or to I<all> databases
 3836: when the criterion is on the join key column.  A hostile value in a criterion
 3837: for column C<name> (owned by database A) will never reach database B.
 3838: 
 3839: =item Unknown columns are rejected before reaching any database
 3840: 
 3841: If a criterion column name is not present in any component database (or has
 3842: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3843: and silently drops the criterion.  No database receives the hostile key.
 3844: 
 3845: =item AUTOLOAD only accepts word-character column names
 3846: 
 3847: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3848: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3849: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3850: C<_>) are additionally blocked with an explicit C<croak>.
 3851: 
 3852: =item No value sanitisation (by design)
 3853: 
 3854: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3855: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3856: responsibility of the underlying C<Database::Abstraction> objects (which use
 3857: parameterised queries).  Preventing XSS or header injection is the
 3858: responsibility of the CGI or web layer that renders the output.
 3859: 
 3860: =item Taint-mode compatible (array path)
 3861: 
 3862: The array merge path contains no C<system()>, C<exec()>, backtick,
 3863: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3864: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3865: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3866: an I<untainted> capture, so the column name used for dispatch is clean under
 3867: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3868: objects; those objects are responsible for handling tainted values at the SQL
 3869: parameterisation layer.
 3870: 
 3871: =item SQLite backend: column names are quoted, values are parametrised
 3872: 
 3873: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3874: All column and table names are double-quoted (SQL identifier quoting) before
 3875: being embedded in statement strings.  All row values are passed to SQLite
 3876: exclusively through DBI prepared statement placeholders -- never by string
 3877: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3878: into the temporary database.
 3879: 
 3880: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3881: unpredictable filename.  No C<system()> or shell command is used to create or
 3882: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3883: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3884: in the generated SQL come from C<columns()>, which is produced by
 3885: C<Database::Abstraction> at construction time -- they are not derived from
 3886: caller-supplied criteria values.
 3887: 
 3888: =item Operator hashref broadcast copy
 3889: 
 3890: When the same join-key criterion (an operator hashref such as
 3891: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3892: database receives its own I<shallow copy> of the hashref.  A component database
 3893: that mutates the hashref's contents at the top level cannot affect what
 3894: subsequent databases receive.
 3895: 
 3896: =item collision_prefix value type guard
 3897: 
 3898: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3899: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3900: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3901: column name, C<columns()> listing, and merged row returned to the caller.  The
 3902: guard fires before any column name is constructed.
 3903: 
 3904: =item Filter deep-copy isolation
 3905: 
 3906: The C<filters> constructor parameter and the C<filter> option of
 3907: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3908: original hashrefs are never stored; post-construction mutation of those
 3909: hashrefs cannot widen or bypass the configured row-security constraints.
 3910: 
 3911: =back
 3912: 
 3913: =head2 What the caller is responsible for
 3914: 
 3915: =over 4
 3916: 
 3917: =item Sanitise values before building criteria
 3918: 
 3919: DJ passes criterion values verbatim to component databases.  If your
 3920: application accepts user-supplied filter values (e.g. from a CGI query
 3921: string), those values I<must> be validated or sanitised by your application
 3922: before being passed to DJ.
 3923: 
 3924: =item Restrict which columns the caller can filter on
 3925: 
 3926: Any column in C<columns()> can be used as a filter criterion.  If a column
 3927: should not be filterable by end users (e.g. an internal status flag), hide it
 3928: with C<remove_column> so that queries on it are silently dropped.
 3929: 
 3930: =item Do not expose the joined view directly to user-supplied criteria
 3931: 
 3932: DJ is not a firewall.  It faithfully routes user input to component databases.
 3933: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 3934: columns and validates their values.
 3935: 
 3936: =back

 4230: =head1 STATE DIAGRAM
 4231: 
 4232: C<Database::Join> objects follow three independent finite state machines (FSMs).
 4233: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 4234: triggers that cause transitions (arrows), and important side-effects.
 4235: 
 4236: =head2 FSM 1: Object Lifecycle
 4237: 
 4238: Governs the structural state of a C<Database::Join> instance.
 4239: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 4240: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 4241: are not shown because they do not change state.
 4242: 
 4243:     [pre-creation]
 4244:          |
 4245:          | new( databases => [...], join_column => '...' )
 4246:          |   Side-effect: _col_db routing table built;
 4247:          |                _autoload_pk cached from dbs[0]{id}
 4248:          v
 4249:     [CONSTRUCTED] <-----------------------------------------+
 4250:          |    |                                              |
 4251:          |    +--------------------------------------------+ |
 4252:          |    (query methods: no structural change)         | |
 4253:          |                                                  | |
 4254:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 4255:          |                                      |    |        |
 4256:          |   Side-effect: col removed from       |    |        |
 4257:          |   _col_db; _col_cache and             +----+        |
 4258:          |   _schema_cache cleared.              (idempotent;  |
 4259:          |   Join column cannot be removed.)      chainable)   |
 4260:          |                                                     |
 4261:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 4262:                                                 |    |
 4263:              Side-effect: new columns added;    |    | add_database( db )
 4264:              _col_db extended; SQLite cache     |    | (chainable; each
 4265:              invalidated (if any).              +----+  extends the view)
 4266: 
 4267:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 4268:     Both transitions are legal on any valid object, in any order.
