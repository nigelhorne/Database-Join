  141: =head1 DESCRIPTION
  142: 
  143: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  144: single logical, read-only view.  Each component database is queried
  145: independently through its own C<Database::Abstraction> interface.  The results
  146: are combined in Perl memory using a shared key column (C<join_column>).
  147: In effect,
  148: this means that you can view data from more than one database using an intuitive,
  149: non-SQL,
  150: interface.
  151: 
  152: The module exposes the same read-only API as C<Database::Abstraction>:
  153: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  154: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  155: shortcut.  Callers do not need to know how many underlying databases are
  156: involved.
  157: 
  158: Think of it as a virtual database table that is assembled on demand from
  159: several real tables, one per component database.
  160: 
  161: =head2 Join semantics
  162: 
  163: The C<join_type> parameter controls what happens when a particular key value
  164: exists in some component databases but not all:
  165: 
  166: =over 4
  167: 
  168: =item C<left> (the default)
  169: 
  170: All rows from the I<primary> (first) database are returned.  Columns from
  171: subsequent databases are included where a matching row is found, and simply
  172: absent from the hashref where there is no match.  If you are familiar with
  173: SQL, this is a LEFT OUTER JOIN on the first table.
  174: 
  175: =item C<inner>
  176: 
  177: Only rows whose join-column value is present in I<every> component database
  178: are returned.  This is equivalent to a SQL INNER JOIN.
  179: 
  180: =item C<outer>
  181: 
  182: Every join-column value found in I<any> component database is returned.
  183: Columns from databases that do not have that key value are absent from the
  184: merged row.  This is a FULL OUTER JOIN.
  185: 
  186: =back
  187: 
  188: B<Important override rule:> whenever you pass a query criterion for a column
  189: that belongs to a secondary database, that database automatically acts as an
  190: inner-join partner for that query only -- regardless of C<join_type>.  This
  191: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  192: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  193: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  194: as a WHERE clause would exclude them).
  195: 
  196: =head2 Column ownership and routing
  197: 
  198: At construction time, C<Database::Join> calls C<columns()> on each component
  199: database and builds an internal index that maps every column name to the
  200: database that owns it.
  201: 
  202: When you pass criteria to a query method, each key-value pair is automatically
  203: routed to the right database.  You never need to say which database a column
  204: belongs to.
  205: 
  206: The C<join_column> is special: criteria on it are broadcast to I<all>
  207: databases so that each database fetches only the relevant rows before the
  208: in-memory merge.
  209: 
  210: When the same non-join column name exists in more than one database, the
  211: I<last> database in the C<databases> array wins by default: its value
  212: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  213: preserve both values under distinct names instead.
  214: 
  215: =head1 LIMITATIONS
  216: 
  217: =over 4
  218: 
  219: =item In-memory join only
  220: 
  221: All matching rows from every component database are fetched into memory before
  222: the merge.  This is not suitable for very large result sets.
  223: 
  224: =item No chained builder or raw SQL
  225: 
  226: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  227: or C<fetchrow_hashref> instead.
  228: 
  229: =item Single-column equi-join only
  230: 
  231: Joining on more than one column simultaneously, or on expressions, is not
  232: supported.  When the join key has different names in different databases,
  233: use C<join_map> to declare each database's local column name.
  234: 
  235: =item Sort order
  236: 
  237: Results are sorted by the C<join_column> value only.  Caller-specified
  238: C<ORDER BY> is not propagated to the component databases.
  239: 
  240: =item count() fetches all rows
  241: 
  242: C<count()> executes the full join and counts the resulting rows in Perl.  It
  243: does not push a C<COUNT(*)> query down to the databases.
  244: 
  245: =back

  247: =head1 COMMON PITFALLS
  248: 
  249: =over 4
  250: 
  251: =item The join_column must exist in every component database
  252: 
  253: If even one database is missing the join key column, C<new()> (or
  254: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  255: column has a different local name in some databases.
  256: 
  257: =item Criteria on a removed column are silently dropped
  258: 
  259: If you call C<remove_column('tier')> and later query
  260: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  261: C<carp> warning) and all rows are returned.  Always pass criteria before
  262: removing columns, or restructure your code to avoid this.
  263: 
  264: =item You cannot remove the join column
  265: 
  266: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  267: is required for the merge to work.
  268: 
  269: =item Left join does not guarantee all columns are populated
  270: 
  271: Under a LEFT join, rows from the primary database that have no matching row
  272: in a secondary database will be returned with I<no keys> from that secondary
  273: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  274: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  275: than just C<$row->{score}> when the secondary match is optional.
  276: 
  277: =item Filters act as inner-join partners
  278: 
  279: Any database that has a C<filters> entry is promoted to an inner-join partner,
  280: regardless of C<join_type>.  A row whose join-key value does not appear in
  281: the filtered database's result is removed from the merged output entirely, not
  282: merely missing its secondary columns.  This is intentional but can be
  283: surprising if you expected LEFT join semantics.
  284: 
  285: =item Criteria-merging replaces scalar filters
  286: 
  287: When both a base filter and a query criterion target the same column, and both
  288: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  289: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  290: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  291: the base filter is ignored for that query.
  292: 
  293: =item AUTOLOAD sees the full merged join when filters or join_map are active
  294: 
  295: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  296: (C<< $join->columnname(...) >>) runs the full join query rather than
  297: delegating directly to the owning database.  This is necessary for correctness
  298: but means the result respects all active filters and join-key translations,
  299: which may differ from what the owning database would return on its own.
  300: 
  301: =item Duplicate column names: last database wins (unless collision_prefix is set)
  302: 
  303: When two component databases each have a column called C<notes>, the second
  304: database's value silently overwrites the first in every merged row.  Use
  305: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  306: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  307: (or C<remove_column>) to drop the unwanted duplicate entirely.
  308: 
  309: =item Mutating the filters hashref after construction has no effect
  310: 
  311: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  312: passed to C<add_database>) at the moment of construction.  The original hashref
  313: you passed in is never stored.  If you later modify it -- for example, to
  314: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  315: Construct a new C<Database::Join> object, or use a component
  316: C<Database::Abstraction> that supports dynamic filter modification.
  317: 
  318: =back

  587: =head2 join_map - joining on differently-named columns
  588: 
  589: By default every component database must have a column whose name matches
  590: C<join_column>.  If a database uses a different local name for the join key,
  591: declare the mapping with C<join_map>.
  592: 
  593: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  594: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  595: B<value> is the name that B<that particular database> uses for the join key.
  596: 
  597: Databases not listed in C<join_map> are assumed to already have a column
  598: named C<join_column> and need no entry.
  599: 
  600: Throughout the merged view the join key is I<always> referred to by the name
  601: given in C<join_column>.  The local alias is never exposed in returned rows,
  602: in C<columns()>, or in C<schema()>.
  603: 
  604: B<When do you need join_map?>
  605: 
  606: You need C<join_map> when you have two tables like:
  607: 
  608:     cities table  : entry (the city name) | statecode
  609:     stnames table : entry (the state code) | state
  610: 
  611: Here you want to join cities.statecode to stnames.entry.  You choose
  612: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  613: that same concept C<entry>, so you declare:
  614: 
  615:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  616: 
  617: B<Example>
  618: 
  619:     #                        index 0     index 1
  620:     my @databases = (       $cities,    $stnames  );
  621:     #  join key column:    'statecode'  'entry'
  622:     #  join_column:        'statecode' (chosen canonical name)
  623:     #  stnames differs, so declare the alias:
  624: 
  625:     my $join = Database::Join->new(
  626:         databases   => \@databases,
  627:         join_column => 'statecode',
  628:         join_map    => { 1 => 'entry' },
  629:     );
  630: 
  631:     my $rows = $join->selectall_arrayref();
  632:     # Each $row has keys: entry (city), statecode, state
  633:     # 'entry' from stnames is never exposed directly.
  634: 
  635:     my $row = $join->fetchrow_hashref(statecode => 'CA');

  637: B<Using add_database instead>
  638: 
  639: If you build the join incrementally with C<add_database>, pass
  640: C<join_column> directly to that call instead of using C<join_map>:
  641: 
  642:     my $join = Database::Join->new(
  643:         databases   => [ $cities ],
  644:         join_column => 'statecode',

  646:     $join->add_database($stnames, join_column => 'entry');

  650: =head2 filters - permanent per-database row filters
  651: 
  652: C<filters> lets you restrict a component database to a subset of its rows
  653: permanently, without repeating the criterion on every query call.
  654: 
  655: Think of it as telling the join: "whenever you query this database, always
  656: add these extra conditions".  Callers never need to specify the restriction
  657: themselves and can never accidentally omit it.
  658: 
  659: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  660: database in the C<databases> array (same numbering as C<join_map>).  Each
  661: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  662: accepts.
  663: 
  664: B<Key-set semantics>
  665: 
  666: A filtered database always acts as an inner-join partner, regardless of the
  667: C<join_type> setting.  Any join-key value that does not pass the filter is
  668: excluded from the merged output entirely -- not just missing its secondary
  669: columns.  This ensures the filter genuinely restricts the view rather than
  670: simply hiding a few fields.
  671: 
  672: B<Criteria merging>
  673: 
  674: When a query call also passes a criterion for a column that already has a base
  675: filter, the two constraints are combined:
  676: 
  677: =over 4
  678: 
  679: =item *
  680: 
  681: When both the base filter value and the query criterion are operator hashrefs
  682: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  683: merged: I<both> constraints apply simultaneously (AND semantics).
  684: 
  685: =item *
  686: 
  687: When either value is a plain scalar, or the operators conflict, the
  688: query-time criterion wins and the base filter for that column is ignored for
  689: that one call.
  690: 
  691: =back
  692: 
  693: B<Example -- only show orders placed more than 60 days ago>
  694: 
  695:     my $join = Database::Join->new(
  696:         databases   => [ $customers, $orders ],
  697:         join_column => 'entry',
  698:         filters     => { 1 => { age_days => { '>' => 60 } } },
  699:     );
  700: 
  701:     # Every query automatically sees only old orders
  702:     my $rows = $join->selectall_arrayref();
  703: 
  704:     # Additional criteria layer on top -- gold tier AND old order
  705:     my $vip  = $join->selectall_arrayref(tier => 'gold');
  706: 
  707:     # Range intersection: age_days > 60 AND age_days < 365

  710: When using C<add_database>, pass C<filter> (singular) to set the base
  711: criteria for the new database:
  712: 
  713:     $join->add_database($orders, filter => { age_days => { '>' => 60 } });

  715: =head2 collision_prefix - preserve colliding columns from secondary databases
  716: 
  717: By default, when a column name appears in more than one database the I<last>
  718: database wins: its value silently overwrites earlier ones in merged rows.
  719: This loses data and makes the origin invisible.
  720: 
  721: C<collision_prefix> changes this for secondary databases you designate.
  722: When a secondary database at index N has a column that already exists in the
  723: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  724: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  725: visible: the original column keeps its name (from the earlier database), and
  726: the collision gets the prefixed name.
  727: 
  728: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  729: a secondary database in the C<databases> array (same numbering as C<join_map>).
  730: Each B<value> is the prefix string to prepend.  An index-0 entry is
  731: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  732: preserves the previous last-wins behaviour and changes nothing.
  733: 
  734: Non-colliding columns from a secondary database are always added as-is with
  735: no prefix, whether or not C<collision_prefix> is configured.
  736: 
  737: B<Example -- sales table and products table, both with a "product" column>
  738: 
  739:     # $sales    columns: id, product, amount, date

  742: 
  743:     my $join = Database::Join->new(
  744:         databases        => [$sales, $products],
  745:         join_column      => 'product',
  746:         join_map         => { 1 => 'sku' },
  747:         collision_prefix => { 1 => 'products' },
  748:     );
  749: 
  750:     $join->columns;
  751:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  752:     #                                                               ^-- prefixed collision
  753: 
  754:     my $row = $join->fetchrow_hashref(product => 'widget');
  755:     # $row->{product}            -- value from $sales
  756:     # $row->{'products.product'} -- value from $products (different row, same column name)
  757:     # $row->{price}              -- from $products, no collision, kept as-is
  758: 
  759: B<Querying on a prefixed column>
  760: 
  761: Use the full published name as the criterion key:
  762: 
  763:     my $rows = $join->selectall_arrayref('products.product' => 'widget');

  767: 
  768: C<remove_column> operates on published names.  To suppress a prefixed

  770: 
  771:     $join->remove_column('products.product');

 2267: =head1 SECURITY CONSIDERATIONS
 2268: 
 2269: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 2270: generates SQL strings, never opens files, and never calls C<system()>,
 2271: C<exec()>, or C<eval()>.  The security properties described below are
 2272: architectural guarantees, not run-time checks.
 2273: 
 2274: =head2 What Database::Join guarantees
 2275: 
 2276: =over 4
 2277: 
 2278: =item Criteria partition isolation
 2279: 
 2280: Every criterion you pass to a query method is routed to I<exactly one>
 2281: component database (the one that owns that column), or to I<all> databases
 2282: when the criterion is on the join key column.  A hostile value in a criterion
 2283: for column C<name> (owned by database A) will never reach database B.
 2284: 
 2285: =item Unknown columns are rejected before reaching any database
 2286: 
 2287: If a criterion column name is not present in any component database (or has
 2288: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 2289: and silently drops the criterion.  No database receives the hostile key.
 2290: 
 2291: =item AUTOLOAD only accepts word-character column names
 2292: 
 2293: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 2294: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 2295: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 2296: C<_>) are additionally blocked with an explicit C<croak>.
 2297: 
 2298: =item No value sanitisation (by design)
 2299: 
 2300: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 2301: I<values> in criteria hashrefs.  Preventing SQL injection is the
 2302: responsibility of the underlying C<Database::Abstraction> objects (which use
 2303: parameterised queries).  Preventing XSS or header injection is the
 2304: responsibility of the CGI or web layer that renders the output.
 2305: 
 2306: =item Taint-mode compatible
 2307: 
 2308: C<Database::Join> contains no C<system()>, C<exec()>, backtick, C<open(PIPE)>,
 2309: or C<eval STRING> calls.  It neither opens files nor constructs shell commands.
 2310: The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive quantifier
 2311: (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces an I<untainted>
 2312: capture, so the column name used for dispatch is clean under C<-T>.  Criteria
 2313: values are passed verbatim to component C<Database::Abstraction> objects; those
 2314: objects are responsible for handling tainted values at the SQL parameterisation
 2315: layer.
 2316: 
 2317: =item Operator hashref broadcast copy
 2318: 
 2319: When the same join-key criterion (an operator hashref such as
 2320: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 2321: database receives its own I<shallow copy> of the hashref.  A component database
 2322: that mutates the hashref's contents at the top level cannot affect what
 2323: subsequent databases receive.
 2324: 
 2325: =item collision_prefix value type guard
 2326: 
 2327: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 2328: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 2329: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 2330: column name, C<columns()> listing, and merged row returned to the caller.  The
 2331: guard fires before any column name is constructed.
 2332: 
 2333: =item Filter deep-copy isolation
 2334: 
 2335: The C<filters> constructor parameter and the C<filter> option of
 2336: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 2337: original hashrefs are never stored; post-construction mutation of those
 2338: hashrefs cannot widen or bypass the configured row-security constraints.
 2339: 
 2340: =back
