  245: =head1 DESCRIPTION
  246: 
  247: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  248: single logical, read-only view.  Each component database is queried
  249: independently through its own C<Database::Abstraction> interface.  The results
  250: are combined using a shared key column (C<join_column>).
  251: In effect, this means that you can view data from more than one database using
  252: an intuitive, non-SQL interface.
  253: 
  254: Every storage format that C<Database::Abstraction> supports works as a
  255: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  256: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  257: within the same join.
  258: 
  259: The module exposes the same read-only API as C<Database::Abstraction>:
  260: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  261: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  262: shortcut.  Callers do not need to know how many underlying databases are
  263: involved.
  264: 
  265: Think of it as a virtual database table that is assembled on demand from
  266: several real tables, one per component database.
  267: 
  268: B<Join backends>
  269: 
  270: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  271: combined source row count.  For small datasets (up to C<max_array_rows>,
  272: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  273: automatically spills source rows into a temporary SQLite database and executes
  274: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  275: size instead of three.  You can also force either path unconditionally with
  276: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  277: 
  278: =head2 Join semantics
  279: 
  280: The C<join_type> parameter controls what happens when a particular key value
  281: exists in some component databases but not all:
  282: 
  283: =over 4
  284: 
  285: =item C<left> (the default)
  286: 
  287: All rows from the I<primary> (first) database are returned.  Columns from
  288: subsequent databases are included where a matching row is found, and simply
  289: absent from the hashref where there is no match.  If you are familiar with
  290: SQL, this is a LEFT OUTER JOIN on the first table.
  291: 
  292: =item C<inner>
  293: 
  294: Only rows whose join-column value is present in I<every> component database
  295: are returned.  This is equivalent to a SQL INNER JOIN.
  296: 
  297: =item C<outer>
  298: 
  299: Every join-column value found in I<any> component database is returned.
  300: Columns from databases that do not have that key value are absent from the
  301: merged row.  This is a FULL OUTER JOIN.
  302: 
  303: =back
  304: 
  305: B<Important override rule:> whenever you pass a query criterion for a column
  306: that belongs to a secondary database, that database automatically acts as an
  307: inner-join partner for that query only -- regardless of C<join_type>.  This
  308: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  309: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  310: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  311: as a WHERE clause would exclude them).
  312: 
  313: =head2 Column ownership and routing
  314: 
  315: At construction time, C<Database::Join> calls C<columns()> on each component
  316: database and builds an internal index that maps every column name to the
  317: database that owns it.
  318: 
  319: When you pass criteria to a query method, each key-value pair is automatically
  320: routed to the right database.  You never need to say which database a column
  321: belongs to.
  322: 
  323: The C<join_column> is special: criteria on it are broadcast to I<all>
  324: databases so that each database fetches only the relevant rows before the
  325: in-memory merge.
  326: 
  327: When the same non-join column name exists in more than one database, the
  328: I<last> database in the C<databases> array wins by default: its value
  329: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  330: preserve both values under distinct names instead.
  331: 
  332: =head1 LIMITATIONS
  333: 
  334: =over 4
  335: 
  336: =item Memory usage (array backend)
  337: 
  338: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  339: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  340: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  341: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  342: 
  343: =item SQLite backend uses a persistent cache file
  344: 
  345: When the SQLite path is active, a single C<.db> file with a randomly generated
  346: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  347: first time a query runs on a given C<Database::Join> object.  Source data is
  348: spilled into that file once; subsequent queries against the same object reuse
  349: the file without re-fetching the source data.
  350: 
  351: The cache is automatically invalidated and rebuilt whenever any source
  352: database's C<updated()> timestamp changes (indicating new data), or when
  353: C<add_database()> is called.
  354: 
  355: The file is deleted when the C<Database::Join> object is destroyed (typically
  356: when it goes out of scope).  At any given moment no more than one such file
  357: exists per object.  The directory must be writable and have enough free space
  358: for the full source data (once, not per-query).
  359: 
  360: =item No chained builder or raw SQL
  361: 
  362: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  363: or C<fetchrow_hashref> instead.
  364: 
  365: =item Single-column equi-join only
  366: 
  367: Joining on more than one column simultaneously, or on expressions, is not
  368: supported.  When the join key has different names in different databases,
  369: use C<join_map> to declare each database's local column name.
  370: 
  371: =item Sort order
  372: 
  373: Results are sorted by the C<join_column> value only.  Caller-specified
  374: C<ORDER BY> is not propagated to the component databases.
  375: 
  376: =item count() fetches all rows
  377: 
  378: C<count()> executes the full join and counts the resulting rows in Perl.  It
  379: does not push a C<COUNT(*)> query down to the databases.
  380: 
  381: =back

  383: =head1 COMMON PITFALLS
  384: 
  385: =over 4
  386: 
  387: =item The join_column must exist in every component database
  388: 
  389: If even one database is missing the join key column, C<new()> (or
  390: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  391: column has a different local name in some databases.
  392: 
  393: =item Criteria on a removed column are silently dropped
  394: 
  395: If you call C<remove_column('tier')> and later query
  396: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  397: C<carp> warning) and all rows are returned.  Always pass criteria before
  398: removing columns, or restructure your code to avoid this.
  399: 
  400: =item You cannot remove the join column
  401: 
  402: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  403: is required for the merge to work.
  404: 
  405: =item Left join does not guarantee all columns are populated
  406: 
  407: Under a LEFT join, rows from the primary database that have no matching row
  408: in a secondary database will be returned with I<no keys> from that secondary
  409: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  410: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  411: than just C<$row->{score}> when the secondary match is optional.
  412: 
  413: =item Filters act as inner-join partners
  414: 
  415: Any database that has a C<filters> entry is promoted to an inner-join partner,
  416: regardless of C<join_type>.  A row whose join-key value does not appear in
  417: the filtered database's result is removed from the merged output entirely, not
  418: merely missing its secondary columns.  This is intentional but can be
  419: surprising if you expected LEFT join semantics.
  420: 
  421: =item Criteria-merging replaces scalar filters
  422: 
  423: When both a base filter and a query criterion target the same column, and both
  424: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  425: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  426: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  427: the base filter is ignored for that query.
  428: 
  429: =item AUTOLOAD sees the full merged join when filters or join_map are active
  430: 
  431: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  432: (C<< $join->columnname(...) >>) runs the full join query rather than
  433: delegating directly to the owning database.  This is necessary for correctness
  434: but means the result respects all active filters and join-key translations,
  435: which may differ from what the owning database would return on its own.
  436: 
  437: =item Duplicate column names: last database wins (unless collision_prefix is set)
  438: 
  439: When two component databases each have a column called C<notes>, the second
  440: database's value silently overwrites the first in every merged row.  Use
  441: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  442: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  443: (or C<remove_column>) to drop the unwanted duplicate entirely.
  444: 
  445: =item Mutating the filters hashref after construction has no effect
  446: 
  447: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  448: passed to C<add_database>) at the moment of construction.  The original hashref
  449: you passed in is never stored.  If you later modify it -- for example, to
  450: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  451: Construct a new C<Database::Join> object, or use a component
  452: C<Database::Abstraction> that supports dynamic filter modification.
  453: 
  454: =item auto mode may always use the array path for some DAs
  455: 
  456: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  457: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  458: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  459: from C<Database::Abstraction> is treated as uncountable, because the parent
  460: class C<count()> expects a key argument and behaves differently from a
  461: "return total row count" function.  In that case C<Database::Join>
  462: conservatively uses the array path for the whole query, even if the dataset is
  463: large.  To opt in to the SQLite path for such a DA, either add your own
  464: C<count()> override that returns the total row count, implement C<dbi_source()>,
  465: or use C<backend =E<gt> 'sqlite'> unconditionally.
  466: 
  467: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  468: 
  469: When a component database implements C<dbi_source()>, C<Database::Join> always
  470: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  471: for columns in that database>.  The criteria are translated into parameterised
  472: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  473: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  474: force a spill; that restriction has been removed.)
  475: 
  476: =item Broadcast join-column criterion does not force secondaries into inner-join
  477: 
  478: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  479: C<Database::Join> broadcasts it to all component databases so each DA can
  480: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  481: incorrectly counted as "having criteria" for secondary databases, causing
  482: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  483: join-column criterion was present.  The fix: only non-join-column criteria
  484: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  485: a secondary to inner-join status.  The broadcast itself is now a transparent
  486: key-range selector that does not affect join semantics.
  487: 
  488: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  489: 
  490: C<LIKE> and C<NOT LIKE> criteria (e.g. C<< name => { LIKE => '%ali%' } >>) are
  491: fully supported on the SQLite backend: the pattern is always passed as a bind
  492: parameter, never interpolated into SQL, so there is no injection risk.  The
  493: behaviour is identical on both the array path (where the criterion is forwarded
  494: to the component DA) and the SQLite path.
  495: 
  496: Operators that are I<not> yet in the supported set -- C<IN>, C<NOT IN>,
  497: C<IS NULL>, C<IS NOT NULL> -- are silently skipped on the SQLite path; a
  498: C<carp> warning is emitted for each one so callers are not silently misled.
  499: The array path forwards these operators to the component DA unchanged, which
  500: may or may not honour them.  If you need these operators, use
  501: C<< backend => 'array' >> to stay on the array path, or open a feature request.
  502: 
  503: =item Temp file directory must be writable and have free space
  504: 
  505: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  506: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  507: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  508: only the directory is under your control.  The file is created on the first
  509: query and kept alive until the object is destroyed; it is not re-created on
  510: every query call.  If the directory is not writable, or the filesystem is full,
  511: the call will C<croak> with C<error_sqlite_connect>.  Check permissions and
  512: free space if you see that error.

  808: =head2 join_map - joining on differently-named columns
  809: 
  810: By default every component database must have a column whose name matches
  811: C<join_column>.  If a database uses a different local name for the join key,
  812: declare the mapping with C<join_map>.
  813: 
  814: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  815: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  816: B<value> is the name that B<that particular database> uses for the join key.
  817: 
  818: Databases not listed in C<join_map> are assumed to already have a column
  819: named C<join_column> and need no entry.
  820: 
  821: Throughout the merged view the join key is I<always> referred to by the name
  822: given in C<join_column>.  The local alias is never exposed in returned rows,
  823: in C<columns()>, or in C<schema()>.
  824: 
  825: B<When do you need join_map?>
  826: 
  827: You need C<join_map> when you have two tables like:
  828: 
  829:     cities table  : entry (the city name) | statecode
  830:     stnames table : entry (the state code) | state

  832: Here you want to join cities.statecode to stnames.entry.  You choose
  833: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  834: that same concept C<entry>, so you declare:
  835: 
  836:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'

  839:

  871: =head2 filters - permanent per-database row filters
  872: 
  873: C<filters> lets you restrict a component database to a subset of its rows
  874: permanently, without repeating the criterion on every query call.
  875: 
  876: Think of it as telling the join: "whenever you query this database, always
  877: add these extra conditions".  Callers never need to specify the restriction
  878: themselves and can never accidentally omit it.
  879: 
  880: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  881: database in the C<databases> array (same numbering as C<join_map>).  Each
  882: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  883: accepts.
  884: 
  885: B<Key-set semantics>
  886: 
  887: A filtered database always acts as an inner-join partner, regardless of the
  888: C<join_type> setting.  Any join-key value that does not pass the filter is
  889: excluded from the merged output entirely -- not just missing its secondary
  890: columns.  This ensures the filter genuinely restricts the view rather than
  891: simply hiding a few fields.
  892: 
  893: B<Criteria merging>
  894: 
  895: When a query call also passes a criterion for a column that already has a base
  896: filter, the two constraints are combined:
  897: 
  898: =over 4
  899: 
  900: =item *
  901: 
  902: When both the base filter value and the query criterion are operator hashrefs
  903: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  904: merged: I<both> constraints apply simultaneously (AND semantics).
  905: 
  906: =item *
  907: 
  908: When either value is a plain scalar, or the operators conflict, the
  909: query-time criterion wins and the base filter for that column is ignored for
  910: that one call.
  911: 
  912: =back

  936: =head2 collision_prefix - preserve colliding columns from secondary databases
  937: 
  938: By default, when a column name appears in more than one database the I<last>
  939: database wins: its value silently overwrites earlier ones in merged rows.
  940: This loses data and makes the origin invisible.
  941: 
  942: C<collision_prefix> changes this for secondary databases you designate.
  943: When a secondary database at index N has a column that already exists in the
  944: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  945: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  946: visible: the original column keeps its name (from the earlier database), and
  947: the collision gets the prefixed name.
  948: 
  949: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  950: a secondary database in the C<databases> array (same numbering as C<join_map>).
  951: Each B<value> is the prefix string to prepend.  An index-0 entry is
  952: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  953: preserves the previous last-wins behaviour and changes nothing.
  954: 
  955: Non-colliding columns from a secondary database are always added as-is with
  956: no prefix, whether or not C<collision_prefix> is configured.
  957:

  964:     my $join = Database::Join->new(
  965:         databases        => [$sales, $products],
  966:         join_column      => 'product',

  994: =head2 backend - SQLite join backend for large datasets
  995: 
  996: C<Database::Join> can merge component databases in two different ways,
  997: controlled by the C<backend> constructor parameter.
  998: 
  999: =over 4
 1000: 
 1001: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
 1002: 
 1003: All matching rows are fetched from every component database into Perl hashes
 1004: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
 1005: is roughly three times the combined source data size (one copy per database
 1006: plus one merged copy).
 1007: 
 1008: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1009: 
 1010: C<Database::Join> creates a temporary SQLite database file, spills source
 1011: rows into it (one table per component database), then executes a single SQL
 1012: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1013: source data size.
 1014: 
 1015: The temporary file is created once and reused across multiple query calls on
 1016: the same object (the cache).  Only query-time criteria vary per call; they
 1017: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1018: automatically rebuilt when any source database's C<updated()> timestamp
 1019: changes.  The file is deleted when the object is destroyed (goes out of
 1020: scope).  See I<Temporary file: name, location, and lifetime> below for
 1021: details.
 1022: 
 1023: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in

 1025: 
 1026: =item C<backend =E<gt> 'auto'> (default)
 1027: 
 1028: C<Database::Join> counts the total rows from all component databases cheaply
 1029: -- without fetching them -- and then decides:
 1030:

 1032: 
 1033: =item *
 1034: 
 1035: If the combined count is less than or equal to C<max_array_rows> (default
 1036: 10,000), use the array path.
 1037: 
 1038: =item *
 1039: 
 1040: If the combined count exceeds C<max_array_rows>, use the SQLite path.
 1041: 
 1042: =back
 1043: 
 1044: For counting to work without fetching, each component database must either

 1049: safe and uses the array path for the whole query without fetching any rows.
 1050: 
 1051: =back
 1052: 
 1053: B<Choosing max_array_rows>
 1054: 
 1055: The default of 10,000 is a reasonable starting point.  Adjust it to match
 1056: your hardware and typical row width.  For wide rows (many columns or long
 1057: strings) you may want a lower threshold; for narrow rows you can raise it.
 1058: 
 1059: B<Temporary file: name, location, and lifetime>
 1060: 
 1061: When the SQLite path is active, a single temporary SQLite database file acts
 1062: as the join cache for the life of the C<Database::Join> object.
 1063: 
 1064: B<Name>: the filename is randomly generated by C<File::Temp>, for example:
 1065: 
 1066:     /tmp/Cj8xK7mP2Q.db

 1074: C</tmp> on Unix, or the value of the C<TEMP> or C<TMP> environment variable

 2907: 
 2908: All text that passes through C<Database::Join> at the Perl layer (column names,
 2909: criteria values, merged row values) is treated as opaque strings.
 2910: C<Database::Join> does not inspect, encode, or transform string content.
 2911: 
 2912: =over 4
 2913: 
 2914: =item Column names
 2915: 
 2916: Column names are plain ASCII strings as returned by C<Database::Abstraction::columns()>.
 2917: Non-ASCII column names are accepted but not tested; behaviour depends on the
 2918: underlying DA and database driver.
 2919: 
 2920: =item Criteria values and row data
 2921: 
 2922: Values are passed verbatim between callers and component DAs.  Full UTF-8 is
 2923: safe as long as the underlying C<Database::Abstraction> objects and their
 2924: database drivers handle UTF-8 correctly.  C<Database::Join> neither encodes
 2925: nor decodes any value.
 2926: 
 2927: =item SQLite backend
 2928:

 2930: database via DBI placeholders (never string interpolation), so binary-safe
 2931: round-tripping depends on C<DBD::SQLite>'s character encoding settings.
 2932: By default C<DBD::SQLite> operates in UTF-8 mode, which is correct for text
 2933: data.  Binary blobs are not explicitly tested.

 3052: =head1 SECURITY CONSIDERATIONS
 3053: 
 3054: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3055: generates SQL strings, never opens files, and never calls C<system()>,
 3056: C<exec()>, or C<eval()>.  The security properties described below are
 3057: architectural guarantees, not run-time checks.
 3058: 
 3059: =head2 What Database::Join guarantees
 3060: 
 3061: =over 4
 3062: 
 3063: =item Criteria partition isolation
 3064: 
 3065: Every criterion you pass to a query method is routed to I<exactly one>
 3066: component database (the one that owns that column), or to I<all> databases
 3067: when the criterion is on the join key column.  A hostile value in a criterion
 3068: for column C<name> (owned by database A) will never reach database B.
 3069: 
 3070: =item Unknown columns are rejected before reaching any database
 3071: 
 3072: If a criterion column name is not present in any component database (or has
 3073: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3074: and silently drops the criterion.  No database receives the hostile key.
 3075: 
 3076: =item AUTOLOAD only accepts word-character column names
 3077: 
 3078: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3079: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3080: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3081: C<_>) are additionally blocked with an explicit C<croak>.
 3082: 
 3083: =item No value sanitisation (by design)
 3084: 
 3085: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3086: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3087: responsibility of the underlying C<Database::Abstraction> objects (which use
 3088: parameterised queries).  Preventing XSS or header injection is the
 3089: responsibility of the CGI or web layer that renders the output.
 3090: 
 3091: =item Taint-mode compatible (array path)
 3092: 
 3093: The array merge path contains no C<system()>, C<exec()>, backtick,
 3094: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3095: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3096: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3097: an I<untainted> capture, so the column name used for dispatch is clean under
 3098: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3099: objects; those objects are responsible for handling tainted values at the SQL
 3100: parameterisation layer.
 3101: 
 3102: =item SQLite backend: column names are quoted, values are parametrised
 3103: 
 3104: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3105: All column and table names are double-quoted (SQL identifier quoting) before
 3106: being embedded in statement strings.  All row values are passed to SQLite
 3107: exclusively through DBI prepared statement placeholders -- never by string
 3108: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3109: into the temporary database.
 3110: 
 3111: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3112: unpredictable filename.  No C<system()> or shell command is used to create or
 3113: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3114: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3115: in the generated SQL come from C<columns()>, which is produced by
 3116: C<Database::Abstraction> at construction time -- they are not derived from
 3117: caller-supplied criteria values.
 3118: 
 3119: =item Operator hashref broadcast copy
 3120: 
 3121: When the same join-key criterion (an operator hashref such as
 3122: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3123: database receives its own I<shallow copy> of the hashref.  A component database
 3124: that mutates the hashref's contents at the top level cannot affect what
 3125: subsequent databases receive.
 3126: 
 3127: =item collision_prefix value type guard
 3128: 
 3129: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3130: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3131: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3132: column name, C<columns()> listing, and merged row returned to the caller.  The
 3133: guard fires before any column name is constructed.
 3134: 
 3135: =item Filter deep-copy isolation
 3136: 
 3137: The C<filters> constructor parameter and the C<filter> option of
 3138: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3139: original hashrefs are never stored; post-construction mutation of those
 3140: hashrefs cannot widen or bypass the configured row-security constraints.
 3141: 
 3142: =back

 3145: 
 3146: =over 4
 3147: 
 3148: =item Sanitise values before building criteria
 3149: 
 3150: DJ passes criterion values verbatim to component databases.  If your
 3151: application accepts user-supplied filter values (e.g. from a CGI query
 3152: string), those values I<must> be validated or sanitised by your application
 3153: before being passed to DJ.
 3154: 
 3155: =item Restrict which columns the caller can filter on
 3156: 
 3157: Any column in C<columns()> can be used as a filter criterion.  If a column

 3162: 
 3163: DJ is not a firewall.  It faithfully routes user input to component databases.
 3164: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 3165: columns and validates their values.

 3461: =head1 STATE DIAGRAM
 3462: 
 3463: C<Database::Join> objects follow three independent finite state machines (FSMs).
 3464: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 3465: triggers that cause transitions (arrows), and important side-effects.
 3466: 
 3467: =head2 FSM 1: Object Lifecycle
 3468: 
 3469: Governs the structural state of a C<Database::Join> instance.
 3470: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 3471: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 3472: are not shown because they do not change state.
 3473: 
 3474:     [pre-creation]
 3475:          |
 3476:          | new( databases => [...], join_column => '...' )
 3477:          |   Side-effect: _col_db routing table built;
 3478:          |                _autoload_pk cached from dbs[0]{id}
 3479:          v
 3480:     [CONSTRUCTED] <-----------------------------------------+
 3481:          |    |                                              |
 3482:          |    +--------------------------------------------+ |
 3483:          |    (query methods: no structural change)         | |
 3484:          |                                                  | |
 3485:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 3486:          |                                      |    |        |
 3487:          |   Side-effect: col removed from       |    |        |
 3488:          |   _col_db; _col_cache and             +----+        |
 3489:          |   _schema_cache cleared.              (idempotent;  |
 3490:          |   Join column cannot be removed.)      chainable)   |
 3491:          |                                                     |
 3492:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 3493:                                                 |    |
 3494:              Side-effect: new columns added;    |    | add_database( db )
 3495:              _col_db extended; SQLite cache     |    | (chainable; each
 3496:              invalidated (if any).              +----+  extends the view)

 3499:     Both transitions are legal on any valid object, in any order.
