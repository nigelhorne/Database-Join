  169: =head1 DESCRIPTION
  170: 
  171: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  172: single logical, read-only view.  Each component database is queried
  173: independently through its own C<Database::Abstraction> interface.  The results
  174: are combined using a shared key column (C<join_column>).
  175: In effect, this means that you can view data from more than one database using
  176: an intuitive, non-SQL interface.
  177: 
  178: The module exposes the same read-only API as C<Database::Abstraction>:
  179: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  180: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  181: shortcut.  Callers do not need to know how many underlying databases are
  182: involved.
  183: 
  184: Think of it as a virtual database table that is assembled on demand from
  185: several real tables, one per component database.
  186: 
  187: B<Join backends>
  188: 
  189: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  190: combined source row count.  For small datasets (up to C<max_array_rows>,
  191: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  192: automatically spills source rows into a temporary SQLite database and executes
  193: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  194: size instead of three.  You can also force either path unconditionally with
  195: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  196: 
  197: =head2 Join semantics
  198: 
  199: The C<join_type> parameter controls what happens when a particular key value
  200: exists in some component databases but not all:
  201: 
  202: =over 4
  203: 
  204: =item C<left> (the default)
  205: 
  206: All rows from the I<primary> (first) database are returned.  Columns from
  207: subsequent databases are included where a matching row is found, and simply
  208: absent from the hashref where there is no match.  If you are familiar with
  209: SQL, this is a LEFT OUTER JOIN on the first table.
  210: 
  211: =item C<inner>
  212: 
  213: Only rows whose join-column value is present in I<every> component database
  214: are returned.  This is equivalent to a SQL INNER JOIN.
  215: 
  216: =item C<outer>
  217: 
  218: Every join-column value found in I<any> component database is returned.
  219: Columns from databases that do not have that key value are absent from the
  220: merged row.  This is a FULL OUTER JOIN.
  221: 
  222: =back
  223: 
  224: B<Important override rule:> whenever you pass a query criterion for a column
  225: that belongs to a secondary database, that database automatically acts as an
  226: inner-join partner for that query only -- regardless of C<join_type>.  This
  227: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  228: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  229: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  230: as a WHERE clause would exclude them).
  231: 
  232: =head2 Column ownership and routing
  233: 
  234: At construction time, C<Database::Join> calls C<columns()> on each component
  235: database and builds an internal index that maps every column name to the
  236: database that owns it.
  237: 
  238: When you pass criteria to a query method, each key-value pair is automatically
  239: routed to the right database.  You never need to say which database a column
  240: belongs to.
  241: 
  242: The C<join_column> is special: criteria on it are broadcast to I<all>
  243: databases so that each database fetches only the relevant rows before the
  244: in-memory merge.
  245: 
  246: When the same non-join column name exists in more than one database, the
  247: I<last> database in the C<databases> array wins by default: its value
  248: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  249: preserve both values under distinct names instead.
  250: 
  251: =head1 LIMITATIONS
  252: 
  253: =over 4
  254: 
  255: =item Memory usage (array backend)
  256: 
  257: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  258: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  259: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  260: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  261: 
  262: =item SQLite backend writes temporary files
  263: 
  264: When the SQLite path is active, a temporary C<.db> file is created in
  265: C<tmpdir> for every query call.  The file is removed when the call returns.
  266: The directory must be writable and have sufficient free space.
  267: 
  268: =item No chained builder or raw SQL
  269: 
  270: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  271: or C<fetchrow_hashref> instead.
  272: 
  273: =item Single-column equi-join only
  274: 
  275: Joining on more than one column simultaneously, or on expressions, is not
  276: supported.  When the join key has different names in different databases,
  277: use C<join_map> to declare each database's local column name.
  278: 
  279: =item Sort order
  280: 
  281: Results are sorted by the C<join_column> value only.  Caller-specified
  282: C<ORDER BY> is not propagated to the component databases.
  283: 
  284: =item count() fetches all rows
  285: 
  286: C<count()> executes the full join and counts the resulting rows in Perl.  It
  287: does not push a C<COUNT(*)> query down to the databases.
  288: 
  289: =back
  290: 
  291: =head1 COMMON PITFALLS
  292: 
  293: =over 4
  294: 
  295: =item The join_column must exist in every component database
  296: 
  297: If even one database is missing the join key column, C<new()> (or
  298: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  299: column has a different local name in some databases.
  300: 
  301: =item Criteria on a removed column are silently dropped
  302: 
  303: If you call C<remove_column('tier')> and later query
  304: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  305: C<carp> warning) and all rows are returned.  Always pass criteria before
  306: removing columns, or restructure your code to avoid this.
  307: 
  308: =item You cannot remove the join column
  309: 
  310: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  311: is required for the merge to work.
  312: 
  313: =item Left join does not guarantee all columns are populated
  314: 
  315: Under a LEFT join, rows from the primary database that have no matching row
  316: in a secondary database will be returned with I<no keys> from that secondary
  317: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  318: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  319: than just C<$row->{score}> when the secondary match is optional.
  320: 
  321: =item Filters act as inner-join partners
  322: 
  323: Any database that has a C<filters> entry is promoted to an inner-join partner,
  324: regardless of C<join_type>.  A row whose join-key value does not appear in
  325: the filtered database's result is removed from the merged output entirely, not
  326: merely missing its secondary columns.  This is intentional but can be
  327: surprising if you expected LEFT join semantics.
  328: 
  329: =item Criteria-merging replaces scalar filters
  330: 
  331: When both a base filter and a query criterion target the same column, and both
  332: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  333: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  334: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  335: the base filter is ignored for that query.
  336: 
  337: =item AUTOLOAD sees the full merged join when filters or join_map are active
  338: 
  339: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  340: (C<< $join->columnname(...) >>) runs the full join query rather than
  341: delegating directly to the owning database.  This is necessary for correctness
  342: but means the result respects all active filters and join-key translations,
  343: which may differ from what the owning database would return on its own.
  344: 
  345: =item Duplicate column names: last database wins (unless collision_prefix is set)
  346: 
  347: When two component databases each have a column called C<notes>, the second
  348: database's value silently overwrites the first in every merged row.  Use
  349: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  350: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  351: (or C<remove_column>) to drop the unwanted duplicate entirely.
  352: 
  353: =item Mutating the filters hashref after construction has no effect
  354: 
  355: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  356: passed to C<add_database>) at the moment of construction.  The original hashref
  357: you passed in is never stored.  If you later modify it -- for example, to
  358: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  359: Construct a new C<Database::Join> object, or use a component
  360: C<Database::Abstraction> that supports dynamic filter modification.
  361: 
  362: =item auto mode may always use the array path for some DAs
  363: 
  364: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  365: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  366: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  367: from C<Database::Abstraction> is treated as uncountable, because the parent
  368: class C<count()> expects a key argument and behaves differently from a
  369: "return total row count" function.  In that case C<Database::Join>
  370: conservatively uses the array path for the whole query, even if the dataset is
  371: large.  To opt in to the SQLite path for such a DA, either add your own
  372: C<count()> override that returns the total row count, implement C<dbi_source()>,
  373: or use C<backend =E<gt> 'sqlite'> unconditionally.
  374: 
  375: =item dbi_source() zero-copy path is skipped when query-time criteria apply
  376: 
  377: When a component database implements C<dbi_source()> but the current query
  378: includes criteria for columns in that database, C<Database::Join> cannot use
  379: the zero-copy ATTACH path (doing so would require generating a C<WHERE> clause
  380: inside the attached database, which is not supported in this version).  The
  381: database is queried normally via C<selectall_arrayref> and rows are spilled
  382: into the temporary SQLite file instead.
  383: 
  384: =item Temp file directory must be writable and have free space
  385: 
  386: When the SQLite path is active, a temporary C<.db> file is created in
  387: C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>) for every query call.
  388: If the directory is not writable, or the filesystem is full, the call will
  389: C<croak> with C<error_sqlite_connect>.  Check permissions and free space if
  390: you see that error.
  391: 
  392: =back

  415: =head3 DESCRIPTION
  416: 
  417: Constructs and returns a new C<Database::Join> object.
  418: 
  419: Each element of C<databases> must be an already-instantiated subclass of
  420: C<Database::Abstraction>.  The constructor calls C<columns()> on every
  421: database to build an internal column-routing table and verifies that
  422: C<join_column> (or its local alias from C<join_map>) is present in each one.
  423: 
  424: Columns listed in C<remove_columns> are hidden immediately: they do not appear
  425: in C<columns()>, C<schema()>, or any returned row hashref.  This is equivalent
  426: to calling C<remove_column> once per name after construction.
  427: 
  428: =head3 API SPECIFICATION
  429: 
  430: =head4 Input
  431: 
  432:     databases      => { type => 'arrayref', required => 1 }
  433:                       # One or more Database::Abstraction subclass objects.
  434:                       #
  435:                       # DOMAIN -- EP valid:   non-empty arrayref of blessed DA subclasses.
  436:                       # DOMAIN -- EP invalid: scalar, hashref, or absent => croak.
  437:                       # DOMAIN -- BVA size:   minimum 1 element; no documented upper bound.
  438:                       # DOMAIN -- BVA elem:   each element must pass isa('Database::Abstraction').
  439: 
  440:     join_column    => { type => 'string',   optional => 1, default => 'entry' }
  441:                       # The column name shared by all databases (the join key).
  442:                       #
  443:                       # DOMAIN -- EP valid:   any non-empty string present in every component DA.
  444:                       # DOMAIN -- EP invalid: column absent from any DA => croak join_col_missing.
  445:                       # DOMAIN -- BVA:        empty string '' is treated as a column name and
  446:                       #                       will croak if (as expected) it is absent from every DA.
  447:                       # DOMAIN -- NOTE:       matching is case-sensitive and exact.
  448: 
  449:     join_type      => { type => 'string',   optional => 1, default => 'left',
  450:                         enum => ['inner', 'left', 'outer'] }
  451:                       # Controls which keys appear in the result when not all
  452:                       # databases share the same key values.
  453:                       #
  454:                       # DOMAIN -- EP valid:   exactly 'inner', 'left', or 'outer'.
  455:                       # DOMAIN -- EP invalid: any other string including 'INNER', 'LEFT',
  456:                       #                       'OUTER' (enum check is case-sensitive), 'cross',
  457:                       #                       or '' => croak from validate_strict.
  458: 
  459:     join_map       => { type => 'hashref',  optional => 1 }
  460:                       # Zero-based database index => local column name.
  461:                       # See the join_map section for full details.
  462:                       #
  463:                       # DOMAIN -- EP valid:   hashref values must be plain strings.
  464:                       # DOMAIN -- EP invalid: reference value (hashref, arrayref, coderef, etc.)
  465:                       #                       => croak; the guard prevents heap-address leakage.
  466:                       # DOMAIN -- BVA:        out-of-range keys (beyond the databases array) are
  467:                       #                       silently ignored.
  468: 
  469:     filters        => { type => 'hashref',  optional => 1 }
  470:                       # Zero-based database index => criteria hashref.
  471:                       # Permanent row restrictions on individual databases.
  472:                       # See the filters section for full details.
  473: 
  474:     collision_prefix => { type => 'hashref', optional => 1 }
  475:                       # Zero-based database index (>0) => prefix string.
  476:                       # When a secondary database has a column that collides
  477:                       # with a column already present in the merged view, the
  478:                       # secondary column is published as "$prefix.$col" instead
  479:                       # of silently overwriting the earlier value.
  480:                       # Index 0 entries are silently ignored.
  481:                       # Omitting this parameter preserves the original
  482:                       # last-database-wins behaviour.
  483:                       # See the collision_prefix section for full details.
  484:                       #
  485:                       # DOMAIN -- EP valid:   absent or {} => last-database-wins (no change).
  486:                       # DOMAIN -- EP valid:   { N => 'prefix' } where N > 0 => colliding
  487:                       #                       columns from DB[N] published as "$prefix.$col";
  488:                       #                       non-colliding columns from the same DB added plain.
  489:                       # DOMAIN -- EP note:    index-0 entries are silently ignored.
  490:                       # DOMAIN -- Invariant:  join_column is never prefixed regardless of
  491:                       #                       collision_prefix configuration.
  492: 
  493:     remove_columns => { type => 'arrayref', optional => 1 }
  494:                       # Column names to hide from the merged view.
  495:                       #
  496:                       # DOMAIN -- EP valid:   arrayref of any strings; non-existent columns
  497:                       #                       are silently ignored (idempotent).
  498:                       # DOMAIN -- EP invalid: join_column itself => croak remove_join_col.
  499:                       # DOMAIN -- BVA:        [] empty arrayref is a safe no-op.
  500: 
  501:     backend        => { type => 'string',   optional => 1, default => 'auto',
  502:                         enum => ['array', 'sqlite', 'auto'] }

  682: =head2 join_map - joining on differently-named columns
  683: 
  684: By default every component database must have a column whose name matches
  685: C<join_column>.  If a database uses a different local name for the join key,
  686: declare the mapping with C<join_map>.
  687: 
  688: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  689: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  690: B<value> is the name that B<that particular database> uses for the join key.
  691: 
  692: Databases not listed in C<join_map> are assumed to already have a column
  693: named C<join_column> and need no entry.
  694: 
  695: Throughout the merged view the join key is I<always> referred to by the name
  696: given in C<join_column>.  The local alias is never exposed in returned rows,
  697: in C<columns()>, or in C<schema()>.
  698: 
  699: B<When do you need join_map?>
  700: 
  701: You need C<join_map> when you have two tables like:
  702: 
  703:     cities table  : entry (the city name) | statecode
  704:     stnames table : entry (the state code) | state
  705: 
  706: Here you want to join cities.statecode to stnames.entry.  You choose
  707: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  708: that same concept C<entry>, so you declare:
  709: 
  710:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  711: 
  712: B<Example>
  713: 
  714:     #                        index 0     index 1
  715:     my @databases = (       $cities,    $stnames  );
  716:     #  join key column:    'statecode'  'entry'
  717:     #  join_column:        'statecode' (chosen canonical name)
  718:     #  stnames differs, so declare the alias:
  719: 
  720:     my $join = Database::Join->new(
  721:         databases   => \@databases,
  722:         join_column => 'statecode',
  723:         join_map    => { 1 => 'entry' },
  724:     );

  745: =head2 filters - permanent per-database row filters
  746: 
  747: C<filters> lets you restrict a component database to a subset of its rows
  748: permanently, without repeating the criterion on every query call.
  749: 
  750: Think of it as telling the join: "whenever you query this database, always
  751: add these extra conditions".  Callers never need to specify the restriction
  752: themselves and can never accidentally omit it.
  753: 
  754: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  755: database in the C<databases> array (same numbering as C<join_map>).  Each
  756: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  757: accepts.
  758: 
  759: B<Key-set semantics>
  760: 
  761: A filtered database always acts as an inner-join partner, regardless of the
  762: C<join_type> setting.  Any join-key value that does not pass the filter is
  763: excluded from the merged output entirely -- not just missing its secondary
  764: columns.  This ensures the filter genuinely restricts the view rather than
  765: simply hiding a few fields.
  766: 
  767: B<Criteria merging>
  768: 
  769: When a query call also passes a criterion for a column that already has a base
  770: filter, the two constraints are combined:
  771: 
  772: =over 4
  773: 
  774: =item *
  775: 
  776: When both the base filter value and the query criterion are operator hashrefs
  777: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  778: merged: I<both> constraints apply simultaneously (AND semantics).
  779: 
  780: =item *
  781: 
  782: When either value is a plain scalar, or the operators conflict, the
  783: query-time criterion wins and the base filter for that column is ignored for
  784: that one call.
  785: 
  786: =back
  787: 
  788: B<Example -- only show orders placed more than 60 days ago>
  789: 
  790:     my $join = Database::Join->new(

  810: =head2 collision_prefix - preserve colliding columns from secondary databases
  811: 
  812: By default, when a column name appears in more than one database the I<last>
  813: database wins: its value silently overwrites earlier ones in merged rows.
  814: This loses data and makes the origin invisible.
  815: 
  816: C<collision_prefix> changes this for secondary databases you designate.
  817: When a secondary database at index N has a column that already exists in the
  818: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  819: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  820: visible: the original column keeps its name (from the earlier database), and
  821: the collision gets the prefixed name.
  822: 
  823: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  824: a secondary database in the C<databases> array (same numbering as C<join_map>).
  825: Each B<value> is the prefix string to prepend.  An index-0 entry is
  826: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  827: preserves the previous last-wins behaviour and changes nothing.
  828: 
  829: Non-colliding columns from a secondary database are always added as-is with
  830: no prefix, whether or not C<collision_prefix> is configured.
  831: 
  832: B<Example -- sales table and products table, both with a "product" column>
  833: 
  834:     # $sales    columns: id, product, amount, date
  835:     # $products columns: sku, product, price, category
  836:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  837: 
  838:     my $join = Database::Join->new(
  839:         databases        => [$sales, $products],
  840:         join_column      => 'product',
  841:         join_map         => { 1 => 'sku' },
  842:         collision_prefix => { 1 => 'products' },
  843:     );
  844: 
  845:     $join->columns;
  846:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  847:     #                                                               ^-- prefixed collision
  848: 
  849:     my $row = $join->fetchrow_hashref(product => 'widget');
  850:     # $row->{product}            -- value from $sales
  851:     # $row->{'products.product'} -- value from $products (different row, same column name)
  852:     # $row->{price}              -- from $products, no collision, kept as-is
  853: 
  854: B<Querying on a prefixed column>
  855: 
  856: Use the full published name as the criterion key:
  857: 
  858:     my $rows = $join->selectall_arrayref('products.product' => 'widget');

  865: 
  866:     $join->remove_column('products.product');

  868: =head2 backend - SQLite join backend for large datasets
  869: 
  870: C<Database::Join> can merge component databases in two different ways,
  871: controlled by the C<backend> constructor parameter.
  872: 
  873: =over 4
  874: 
  875: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  876: 
  877: All matching rows are fetched from every component database into Perl hashes
  878: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
  879: is roughly three times the combined source data size (one copy per database
  880: plus one merged copy).
  881: 
  882: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a temporary file
  883: 
  884: C<Database::Join> creates a temporary SQLite database file, spills source
  885: rows into it (one table per component database), then executes a single SQL
  886: C<JOIN> statement.  Peak RAM drops to roughly one times the source data size.
  887: The temporary file is created securely by C<File::Temp> and removed
  888: automatically when the query call returns, even if an error occurs.
  889: 
  890: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
  891: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
  892: 
  893: =item C<backend =E<gt> 'auto'> (default)
  894: 
  895: C<Database::Join> counts the total rows from all component databases cheaply
  896: -- without fetching them -- and then decides:
  897: 
  898: =over 4
  899: 
  900: =item *
  901: 
  902: If the combined count is less than or equal to C<max_array_rows> (default
  903: 10,000), use the array path.
  904: 
  905: =item *
  906: 
  907: If the combined count exceeds C<max_array_rows>, use the SQLite path.
  908: 
  909: =back
  910: 
  911: For counting to work without fetching, each component database must either
  912: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
  913: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
  914: method in its own package -- not just inherit one from a parent class.  If
  915: neither is available for a particular database, C<Database::Join> plays it
  916: safe and uses the array path for the whole query without fetching any rows.
  917: 
  918: =back
  919: 
  920: B<Choosing max_array_rows>
  921: 
  922: The default of 10,000 is a reasonable starting point.  Adjust it to match
  923: your hardware and typical row width.  For wide rows (many columns or long
  924: strings) you may want a lower threshold; for narrow rows you can raise it.
  925: 
  926: B<Temporary file location (tmpdir)>
  927: 
  928: When the SQLite path is active, the temporary C<.db> file is created in the
  929: directory given by C<tmpdir>.  If C<tmpdir> is not specified,
  930: C<File::Spec-E<gt>tmpdir()> is used (usually C</tmp> on Unix, or the value of
  931: the C<TEMP> or C<TMP> environment variable on Windows).
  932: 
  933: To use a different directory -- for example a RAM-backed filesystem or a
  934: faster local disk:
  935: 
  936:     my $join = Database::Join->new(
  937:         databases      => [ $db1, $db2 ],
  938:         join_column    => 'entry',
  939:         backend        => 'sqlite',
  940:         tmpdir         => '/dev/shm',     # Linux RAM disk
  941:     );
  942: 
  943: B<Zero-copy ATTACH (C<dbi_source()> interface)>
  944: 
  945: Normally, when the SQLite path is active, rows from each component database
  946: are fetched one by one and inserted into the temporary SQLite file.  This is
  947: efficient but does involve INSERT overhead.
  948: 
  949: If a component database is itself SQLite-backed and implements a
  950: C<dbi_source()> method, C<Database::Join> can skip the row-by-row copy
  951: entirely and instead use C<ATTACH DATABASE> to link the source file directly
  952: to the temporary join connection.  This is the zero-copy path and is
  953: significantly faster for large SQLite sources.
  954: 
  955: The C<dbi_source()> method must return a hashref with two keys:
  956: 
  957: =over 4
  958: 
  959: =item C<dbh>
  960: 
  961: A connected C<DBD::SQLite> database handle (C<DBI> connection object).
  962: 
  963: =item C<table>
  964: 
  965: The name of the table in that database that holds the source rows.
  966: 
  967: =back
  968: 
  969: Example implementation:
  970: 
  971:     package My::SQLiteDatabase;

  987: into the temporary file.

  991: Both the array path and the SQLite path produce identical results for any

 2590: safe as long as the underlying C<Database::Abstraction> objects and their

 2719: =head1 SECURITY CONSIDERATIONS
 2720: 
 2721: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 2722: generates SQL strings, never opens files, and never calls C<system()>,
 2723: C<exec()>, or C<eval()>.  The security properties described below are
 2724: architectural guarantees, not run-time checks.
 2725: 
 2726: =head2 What Database::Join guarantees
 2727: 
 2728: =over 4
 2729: 
 2730: =item Criteria partition isolation
 2731: 
 2732: Every criterion you pass to a query method is routed to I<exactly one>
 2733: component database (the one that owns that column), or to I<all> databases
 2734: when the criterion is on the join key column.  A hostile value in a criterion
 2735: for column C<name> (owned by database A) will never reach database B.
 2736: 
 2737: =item Unknown columns are rejected before reaching any database
 2738: 
 2739: If a criterion column name is not present in any component database (or has
 2740: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 2741: and silently drops the criterion.  No database receives the hostile key.
 2742: 
 2743: =item AUTOLOAD only accepts word-character column names
 2744: 
 2745: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 2746: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 2747: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 2748: C<_>) are additionally blocked with an explicit C<croak>.
 2749: 
 2750: =item No value sanitisation (by design)
 2751: 
 2752: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 2753: I<values> in criteria hashrefs.  Preventing SQL injection is the
 2754: responsibility of the underlying C<Database::Abstraction> objects (which use
 2755: parameterised queries).  Preventing XSS or header injection is the
 2756: responsibility of the CGI or web layer that renders the output.
 2757: 
 2758: =item Taint-mode compatible (array path)
 2759: 
 2760: The array merge path contains no C<system()>, C<exec()>, backtick,
 2761: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 2762: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 2763: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 2764: an I<untainted> capture, so the column name used for dispatch is clean under
 2765: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 2766: objects; those objects are responsible for handling tainted values at the SQL
 2767: parameterisation layer.
 2768: 
 2769: =item SQLite backend: column names are quoted, values are parametrised
 2770: 
 2771: When the SQLite path is active, C<Database::Join> generates SQL internally.
 2772: All column and table names are double-quoted (SQL identifier quoting) before
 2773: being embedded in statement strings.  All row values are passed to SQLite
 2774: exclusively through DBI prepared statement placeholders -- never by string
 2775: interpolation.  A hostile value in a source row therefore cannot inject SQL
 2776: into the temporary database.
 2777: 
 2778: The temporary SQLite file is created by C<File::Temp> using a securely random,
 2779: unpredictable filename.  No C<system()> or shell command is used to create or
 2780: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 2781: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 2782: in the generated SQL come from C<columns()>, which is produced by
 2783: C<Database::Abstraction> at construction time -- they are not derived from
 2784: caller-supplied criteria values.
 2785: 
 2786: =item Operator hashref broadcast copy
 2787: 
 2788: When the same join-key criterion (an operator hashref such as
 2789: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 2790: database receives its own I<shallow copy> of the hashref.  A component database
 2791: that mutates the hashref's contents at the top level cannot affect what
 2792: subsequent databases receive.
 2793: 
 2794: =item collision_prefix value type guard
 2795: 
 2796: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 2797: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 2798: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 2799: column name, C<columns()> listing, and merged row returned to the caller.  The
 2800: guard fires before any column name is constructed.
 2801: 
 2802: =item Filter deep-copy isolation
 2803: 
 2804: The C<filters> constructor parameter and the C<filter> option of
 2805: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 2806: original hashrefs are never stored; post-construction mutation of those
 2807: hashrefs cannot widen or bypass the configured row-security constraints.
 2808: 
 2809: =back
