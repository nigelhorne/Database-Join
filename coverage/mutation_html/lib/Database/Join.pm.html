  251: =head1 DESCRIPTION
  252: 
  253: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  254: single logical, read-only view.  Each component database is queried
  255: independently through its own C<Database::Abstraction> interface.  The results
  256: are combined using a shared key column (C<join_column>).
  257: In effect, this means that you can view data from more than one database using
  258: an intuitive, non-SQL interface.
  259: 
  260: The module exposes the same read-only API as C<Database::Abstraction>:
  261: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  262: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  263: shortcut.  Callers do not need to know how many underlying databases are
  264: involved.
  265: 
  266: Think of it as a virtual database table that is assembled on demand from
  267: several real tables, one per component database.
  268: 
  269: B<Join backends>
  270: 
  271: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  272: combined source row count.  For small datasets (up to C<max_array_rows>,
  273: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  274: automatically spills source rows into a temporary SQLite database and executes
  275: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  276: size instead of three.  You can also force either path unconditionally with
  277: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  278: 
  279: =head2 Join semantics
  280: 
  281: The C<join_type> parameter controls what happens when a particular key value
  282: exists in some component databases but not all:
  283: 
  284: =over 4
  285: 
  286: =item C<left> (the default)
  287: 
  288: All rows from the I<primary> (first) database are returned.  Columns from
  289: subsequent databases are included where a matching row is found, and simply
  290: absent from the hashref where there is no match.  If you are familiar with
  291: SQL, this is a LEFT OUTER JOIN on the first table.
  292: 
  293: =item C<inner>
  294: 
  295: Only rows whose join-column value is present in I<every> component database
  296: are returned.  This is equivalent to a SQL INNER JOIN.
  297: 
  298: =item C<outer>
  299: 
  300: Every join-column value found in I<any> component database is returned.
  301: Columns from databases that do not have that key value are absent from the
  302: merged row.  This is a FULL OUTER JOIN.
  303: 
  304: =back
  305: 
  306: B<Important override rule:> whenever you pass a query criterion for a column
  307: that belongs to a secondary database, that database automatically acts as an
  308: inner-join partner for that query only -- regardless of C<join_type>.  This
  309: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  310: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  311: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  312: as a WHERE clause would exclude them).
  313: 
  314: =head2 Column ownership and routing
  315: 
  316: At construction time, C<Database::Join> calls C<columns()> on each component
  317: database and builds an internal index that maps every column name to the
  318: database that owns it.
  319: 
  320: When you pass criteria to a query method, each key-value pair is automatically
  321: routed to the right database.  You never need to say which database a column
  322: belongs to.
  323: 
  324: The C<join_column> is special: criteria on it are broadcast to I<all>
  325: databases so that each database fetches only the relevant rows before the
  326: in-memory merge.
  327: 
  328: When the same non-join column name exists in more than one database, the
  329: I<last> database in the C<databases> array wins by default: its value
  330: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  331: preserve both values under distinct names instead.
  332: 
  333: =head1 LIMITATIONS
  334: 
  335: =over 4
  336: 
  337: =item Memory usage (array backend)
  338: 
  339: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  340: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  341: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  342: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  343: 
  344: =item SQLite backend uses a persistent cache file
  345: 
  346: When the SQLite path is active, a single C<.db> file with a randomly generated
  347: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  348: first time a query runs on a given C<Database::Join> object.  Source data is
  349: spilled into that file once; subsequent queries against the same object reuse
  350: the file without re-fetching the source data.
  351: 
  352: The cache is automatically invalidated and rebuilt whenever any source
  353: database's C<updated()> timestamp changes (indicating new data), or when
  354: C<add_database()> is called.
  355: 
  356: The file is deleted when the C<Database::Join> object is destroyed (typically
  357: when it goes out of scope).  At any given moment no more than one such file
  358: exists per object.  The directory must be writable and have enough free space
  359: for the full source data (once, not per-query).
  360: 
  361: =item No chained builder or raw SQL
  362: 
  363: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  364: or C<fetchrow_hashref> instead.
  365: 
  366: =item Single-column equi-join only
  367: 
  368: Joining on more than one column simultaneously, or on expressions, is not
  369: supported.  When the join key has different names in different databases,
  370: use C<join_map> to declare each database's local column name.
  371: 
  372: =item Sort order
  373: 
  374: Results are sorted by the C<join_column> value only.  Caller-specified
  375: C<ORDER BY> is not propagated to the component databases.
  376: 
  377: =item count() fetches all rows
  378: 
  379: C<count()> executes the full join and counts the resulting rows in Perl.  It
  380: does not push a C<COUNT(*)> query down to the databases.
  381: 
  382: =back

  384: =head1 COMMON PITFALLS
  385: 
  386: =over 4
  387: 
  388: =item The join_column must exist in every component database
  389: 
  390: If even one database is missing the join key column, C<new()> (or
  391: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  392: column has a different local name in some databases.
  393: 
  394: =item Criteria on a removed column are silently dropped
  395: 
  396: If you call C<remove_column('tier')> and later query
  397: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  398: C<carp> warning) and all rows are returned.  Always pass criteria before
  399: removing columns, or restructure your code to avoid this.
  400: 
  401: =item You cannot remove the join column
  402: 
  403: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  404: is required for the merge to work.
  405: 
  406: =item Left join does not guarantee all columns are populated
  407: 
  408: Under a LEFT join, rows from the primary database that have no matching row
  409: in a secondary database will be returned with I<no keys> from that secondary
  410: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  411: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  412: than just C<$row->{score}> when the secondary match is optional.
  413: 
  414: =item Filters act as inner-join partners
  415: 
  416: Any database that has a C<filters> entry is promoted to an inner-join partner,
  417: regardless of C<join_type>.  A row whose join-key value does not appear in
  418: the filtered database's result is removed from the merged output entirely, not
  419: merely missing its secondary columns.  This is intentional but can be
  420: surprising if you expected LEFT join semantics.
  421: 
  422: =item Criteria-merging replaces scalar filters
  423: 
  424: When both a base filter and a query criterion target the same column, and both
  425: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  426: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  427: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  428: the base filter is ignored for that query.
  429: 
  430: =item AUTOLOAD sees the full merged join when filters or join_map are active
  431: 
  432: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  433: (C<< $join->columnname(...) >>) runs the full join query rather than
  434: delegating directly to the owning database.  This is necessary for correctness
  435: but means the result respects all active filters and join-key translations,
  436: which may differ from what the owning database would return on its own.
  437: 
  438: =item Duplicate column names: last database wins (unless collision_prefix is set)
  439: 
  440: When two component databases each have a column called C<notes>, the second
  441: database's value silently overwrites the first in every merged row.  Use
  442: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  443: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  444: (or C<remove_column>) to drop the unwanted duplicate entirely.
  445: 
  446: =item Mutating the filters hashref after construction has no effect
  447: 
  448: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  449: passed to C<add_database>) at the moment of construction.  The original hashref
  450: you passed in is never stored.  If you later modify it -- for example, to
  451: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  452: Construct a new C<Database::Join> object, or use a component
  453: C<Database::Abstraction> that supports dynamic filter modification.
  454: 
  455: =item auto mode may always use the array path for some DAs
  456: 
  457: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  458: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  459: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  460: from C<Database::Abstraction> is treated as uncountable, because the parent
  461: class C<count()> expects a key argument and behaves differently from a
  462: "return total row count" function.  In that case C<Database::Join>
  463: conservatively uses the array path for the whole query, even if the dataset is
  464: large.  To opt in to the SQLite path for such a DA, either add your own
  465: C<count()> override that returns the total row count, implement C<dbi_source()>,
  466: or use C<backend =E<gt> 'sqlite'> unconditionally.
  467: 
  468: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  469: 
  470: When a component database implements C<dbi_source()>, C<Database::Join> always
  471: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  472: for columns in that database>.  The criteria are translated into parameterised
  473: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  474: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  475: force a spill; that restriction has been removed.)
  476: 
  477: =item Temp file directory must be writable and have free space
  478: 
  479: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  480: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  481: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  482: only the directory is under your control.  The file is created on the first
  483: query and kept alive until the object is destroyed; it is not re-created on
  484: every query call.  If the directory is not writable, or the filesystem is full,
  485: the call will C<croak> with C<error_sqlite_connect>.  Check permissions and
  486: free space if you see that error.
  487:

  782: =head2 join_map - joining on differently-named columns
  783: 
  784: By default every component database must have a column whose name matches
  785: C<join_column>.  If a database uses a different local name for the join key,
  786: declare the mapping with C<join_map>.
  787: 
  788: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  789: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  790: B<value> is the name that B<that particular database> uses for the join key.
  791: 
  792: Databases not listed in C<join_map> are assumed to already have a column
  793: named C<join_column> and need no entry.
  794: 
  795: Throughout the merged view the join key is I<always> referred to by the name
  796: given in C<join_column>.  The local alias is never exposed in returned rows,
  797: in C<columns()>, or in C<schema()>.
  798: 
  799: B<When do you need join_map?>
  800: 
  801: You need C<join_map> when you have two tables like:
  802: 
  803:     cities table  : entry (the city name) | statecode
  804:     stnames table : entry (the state code) | state
  805: 
  806: Here you want to join cities.statecode to stnames.entry.  You choose
  807: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  808: that same concept C<entry>, so you declare:
  809: 
  810:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  811: 
  812: B<Example>
  813: 
  814:     #                        index 0     index 1
  815:     my @databases = (       $cities,    $stnames  );
  816:     #  join key column:    'statecode'  'entry'
  817:     #  join_column:        'statecode' (chosen canonical name)
  818:     #  stnames differs, so declare the alias:
  819: 
  820:     my $join = Database::Join->new(
  821:         databases   => \@databases,
  822:         join_column => 'statecode',

  845: =head2 filters - permanent per-database row filters
  846: 
  847: C<filters> lets you restrict a component database to a subset of its rows
  848: permanently, without repeating the criterion on every query call.
  849: 
  850: Think of it as telling the join: "whenever you query this database, always
  851: add these extra conditions".  Callers never need to specify the restriction
  852: themselves and can never accidentally omit it.
  853: 
  854: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  855: database in the C<databases> array (same numbering as C<join_map>).  Each
  856: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  857: accepts.
  858: 
  859: B<Key-set semantics>
  860: 
  861: A filtered database always acts as an inner-join partner, regardless of the
  862: C<join_type> setting.  Any join-key value that does not pass the filter is
  863: excluded from the merged output entirely -- not just missing its secondary
  864: columns.  This ensures the filter genuinely restricts the view rather than
  865: simply hiding a few fields.
  866: 
  867: B<Criteria merging>
  868: 
  869: When a query call also passes a criterion for a column that already has a base
  870: filter, the two constraints are combined:

  872: =over 4
  873: 
  874: =item *

  876: When both the base filter value and the query criterion are operator hashrefs
  877: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  878: merged: I<both> constraints apply simultaneously (AND semantics).
  879: 
  880: =item *
  881: 
  882: When either value is a plain scalar, or the operators conflict, the
  883: query-time criterion wins and the base filter for that column is ignored for
  884: that one call.
  885: 
  886: =back
  887:

  910: =head2 collision_prefix - preserve colliding columns from secondary databases
  911: 
  912: By default, when a column name appears in more than one database the I<last>
  913: database wins: its value silently overwrites earlier ones in merged rows.
  914: This loses data and makes the origin invisible.
  915: 
  916: C<collision_prefix> changes this for secondary databases you designate.
  917: When a secondary database at index N has a column that already exists in the
  918: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  919: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  920: visible: the original column keeps its name (from the earlier database), and
  921: the collision gets the prefixed name.
  922: 
  923: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  924: a secondary database in the C<databases> array (same numbering as C<join_map>).
  925: Each B<value> is the prefix string to prepend.  An index-0 entry is
  926: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  927: preserves the previous last-wins behaviour and changes nothing.
  928: 
  929: Non-colliding columns from a secondary database are always added as-is with
  930: no prefix, whether or not C<collision_prefix> is configured.
  931: 
  932: B<Example -- sales table and products table, both with a "product" column>
  933: 
  934:     # $sales    columns: id, product, amount, date
  935:     # $products columns: sku, product, price, category

  937: 
  938:     my $join = Database::Join->new(
  939:         databases        => [$sales, $products],
  940:         join_column      => 'product',
  941:         join_map         => { 1 => 'sku' },
  942:         collision_prefix => { 1 => 'products' },
  943:     );
  944: 
  945:     $join->columns;
  946:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']

  948: 
  949:     my $row = $join->fetchrow_hashref(product => 'widget');

  951:     # $row->{'products.product'} -- value from $products (different row, same column name)
  952:     # $row->{price}              -- from $products, no collision, kept as-is
  953: 
  954: B<Querying on a prefixed column>
  955: 
  956: Use the full published name as the criterion key:
  957: 
  958:     my $rows = $join->selectall_arrayref('products.product' => 'widget');
  959:     # Internally routes as: product => 'widget' to $products
  960: 
  961: B<Interaction with remove_column>
  962: 
  963: C<remove_column> operates on published names.  To suppress a prefixed
  964: collision column entirely, pass the prefixed name:
  965: 
  966:     $join->remove_column('products.product');

  968: =head2 backend - SQLite join backend for large datasets

  982: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
  983: 
  984: C<Database::Join> creates a temporary SQLite database file, spills source
  985: rows into it (one table per component database), then executes a single SQL
  986: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
  987: source data size.
  988: 
  989: The temporary file is created once and reused across multiple query calls on
  990: the same object (the cache).  Only query-time criteria vary per call; they
  991: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
  992: automatically rebuilt when any source database's C<updated()> timestamp
  993: changes.  The file is deleted when the object is destroyed (goes out of
  994: scope).  See I<Temporary file: name, location, and lifetime> below for
  995: details.
  996: 
  997: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
  998: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).

 1002: C<Database::Join> counts the total rows from all component databases cheaply

 1005: =over 4

 1007: =item *
 1008:

 1010: 10,000), use the array path.
 1011: 
 1012: =item *
 1013: 
 1014: If the combined count exceeds C<max_array_rows>, use the SQLite path.
 1015:

 1023: safe and uses the array path for the whole query without fetching any rows.
 1024: 
 1025: =back
 1026: 
 1027: B<Choosing max_array_rows>

 1030: your hardware and typical row width.  For wide rows (many columns or long

 1032: 
 1033: B<Temporary file: name, location, and lifetime>
 1034: 
 1035: When the SQLite path is active, a single temporary SQLite database file acts
 1036: as the join cache for the life of the C<Database::Join> object.
 1037: 
 1038: B<Name>: the filename is randomly generated by C<File::Temp>, for example:
 1039: 
 1040:     /tmp/Cj8xK7mP2Q.db
 1041:

 1043: collisions.  Only the directory is under your control; you cannot specify

 1061: (C<filters> constructor parameter) are applied once at build time for spilled

 1074: B<Zero-copy ATTACH (C<dbi_source()> interface)>
 1075: 
 1076: Normally, when the SQLite path is active, rows from each component database

 1078: efficient but does involve INSERT overhead.

 3000: =head1 SECURITY CONSIDERATIONS
 3001: 
 3002: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3003: generates SQL strings, never opens files, and never calls C<system()>,
 3004: C<exec()>, or C<eval()>.  The security properties described below are
 3005: architectural guarantees, not run-time checks.
 3006: 
 3007: =head2 What Database::Join guarantees
 3008: 
 3009: =over 4
 3010: 
 3011: =item Criteria partition isolation
 3012: 
 3013: Every criterion you pass to a query method is routed to I<exactly one>
 3014: component database (the one that owns that column), or to I<all> databases
 3015: when the criterion is on the join key column.  A hostile value in a criterion
 3016: for column C<name> (owned by database A) will never reach database B.
 3017: 
 3018: =item Unknown columns are rejected before reaching any database
 3019: 
 3020: If a criterion column name is not present in any component database (or has
 3021: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3022: and silently drops the criterion.  No database receives the hostile key.
 3023: 
 3024: =item AUTOLOAD only accepts word-character column names
 3025: 
 3026: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3027: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3028: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3029: C<_>) are additionally blocked with an explicit C<croak>.
 3030: 
 3031: =item No value sanitisation (by design)
 3032: 
 3033: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3034: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3035: responsibility of the underlying C<Database::Abstraction> objects (which use
 3036: parameterised queries).  Preventing XSS or header injection is the
 3037: responsibility of the CGI or web layer that renders the output.
 3038: 
 3039: =item Taint-mode compatible (array path)
 3040: 
 3041: The array merge path contains no C<system()>, C<exec()>, backtick,
 3042: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3043: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3044: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3045: an I<untainted> capture, so the column name used for dispatch is clean under
 3046: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3047: objects; those objects are responsible for handling tainted values at the SQL
 3048: parameterisation layer.
 3049: 
 3050: =item SQLite backend: column names are quoted, values are parametrised
 3051: 
 3052: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3053: All column and table names are double-quoted (SQL identifier quoting) before
 3054: being embedded in statement strings.  All row values are passed to SQLite
 3055: exclusively through DBI prepared statement placeholders -- never by string
 3056: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3057: into the temporary database.
 3058: 
 3059: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3060: unpredictable filename.  No C<system()> or shell command is used to create or
 3061: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3062: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3063: in the generated SQL come from C<columns()>, which is produced by
 3064: C<Database::Abstraction> at construction time -- they are not derived from
 3065: caller-supplied criteria values.
 3066: 
 3067: =item Operator hashref broadcast copy
 3068: 
 3069: When the same join-key criterion (an operator hashref such as
 3070: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3071: database receives its own I<shallow copy> of the hashref.  A component database
 3072: that mutates the hashref's contents at the top level cannot affect what
 3073: subsequent databases receive.
 3074: 
 3075: =item collision_prefix value type guard
 3076: 
 3077: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3078: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3079: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3080: column name, C<columns()> listing, and merged row returned to the caller.  The
 3081: guard fires before any column name is constructed.
 3082: 
 3083: =item Filter deep-copy isolation
 3084: 
 3085: The C<filters> constructor parameter and the C<filter> option of
 3086: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3087: original hashrefs are never stored; post-construction mutation of those
 3088: hashrefs cannot widen or bypass the configured row-security constraints.
 3089: 
 3090: =back
 3091: 
 3092: =head2 What the caller is responsible for
 3093: 
 3094: =over 4
 3095: 
 3096: =item Sanitise values before building criteria
 3097: 
 3098: DJ passes criterion values verbatim to component databases.  If your
 3099: application accepts user-supplied filter values (e.g. from a CGI query
 3100: string), those values I<must> be validated or sanitised by your application
 3101: before being passed to DJ.
 3102: 
 3103: =item Restrict which columns the caller can filter on
 3104: 
 3105: Any column in C<columns()> can be used as a filter criterion.  If a column
 3106: should not be filterable by end users (e.g. an internal status flag), hide it
 3107: with C<remove_column> so that queries on it are silently dropped.
 3108: 
 3109: =item Do not expose the joined view directly to user-supplied criteria
 3110: 
 3111: DJ is not a firewall.  It faithfully routes user input to component databases.
 3112: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 3113: columns and validates their values.
 3114: 
 3115: =back

 3409: =head1 STATE DIAGRAM
 3410: 
 3411: C<Database::Join> objects follow three independent finite state machines (FSMs).
 3412: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 3413: triggers that cause transitions (arrows), and important side-effects.
 3414: 
 3415: =head2 FSM 1: Object Lifecycle
 3416: 
 3417: Governs the structural state of a C<Database::Join> instance.
 3418: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 3419: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 3420: are not shown because they do not change state.
 3421: 
 3422:     [pre-creation]
 3423:          |
 3424:          | new( databases => [...], join_column => '...' )
 3425:          |   Side-effect: _col_db routing table built;
 3426:          |                _autoload_pk cached from dbs[0]{id}
 3427:          v
 3428:     [CONSTRUCTED] <-----------------------------------------+
 3429:          |    |                                              |
 3430:          |    +--------------------------------------------+ |
 3431:          |    (query methods: no structural change)         | |
 3432:          |                                                  | |
 3433:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 3434:          |                                      |    |        |
 3435:          |   Side-effect: col removed from       |    |        |
 3436:          |   _col_db; _col_cache and             +----+        |
 3437:          |   _schema_cache cleared.              (idempotent;  |
 3438:          |   Join column cannot be removed.)      chainable)   |
 3439:          |                                                     |
 3440:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 3441:                                                 |    |
 3442:              Side-effect: new columns added;    |    | add_database( db )
 3443:              _col_db extended; SQLite cache     |    | (chainable; each
 3444:              invalidated (if any).              +----+  extends the view)
 3445: 
 3446:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 3447:     Both transitions are legal on any valid object, in any order.
