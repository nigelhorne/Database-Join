  141: =head1 DESCRIPTION
  142: 
  143: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  144: single logical, read-only view.  Each component database is queried
  145: independently through its own C<Database::Abstraction> interface.  The results
  146: are combined in Perl memory using a shared key column (C<join_column>).
  147: In effect,
  148: this means that you can view data from more than one database using an intuitive,
  149: non-SQL,
  150: interface.
  151: 
  152: The module exposes the same read-only API as C<Database::Abstraction>:
  153: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  154: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  155: shortcut.  Callers do not need to know how many underlying databases are
  156: involved.
  157: 
  158: Think of it as a virtual database table that is assembled on demand from
  159: several real tables, one per component database.
  160: 
  161: =head2 Join semantics
  162: 
  163: The C<join_type> parameter controls what happens when a particular key value
  164: exists in some component databases but not all:
  165: 
  166: =over 4
  167: 
  168: =item C<left> (the default)
  169: 
  170: All rows from the I<primary> (first) database are returned.  Columns from
  171: subsequent databases are included where a matching row is found, and simply
  172: absent from the hashref where there is no match.  If you are familiar with
  173: SQL, this is a LEFT OUTER JOIN on the first table.
  174: 
  175: =item C<inner>
  176: 
  177: Only rows whose join-column value is present in I<every> component database
  178: are returned.  This is equivalent to a SQL INNER JOIN.
  179: 
  180: =item C<outer>
  181: 
  182: Every join-column value found in I<any> component database is returned.
  183: Columns from databases that do not have that key value are absent from the
  184: merged row.  This is a FULL OUTER JOIN.
  185: 
  186: =back
  187: 
  188: B<Important override rule:> whenever you pass a query criterion for a column
  189: that belongs to a secondary database, that database automatically acts as an
  190: inner-join partner for that query only -- regardless of C<join_type>.  This
  191: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  192: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  193: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  194: as a WHERE clause would exclude them).
  195: 
  196: =head2 Column ownership and routing
  197: 
  198: At construction time, C<Database::Join> calls C<columns()> on each component
  199: database and builds an internal index that maps every column name to the
  200: database that owns it.
  201: 
  202: When you pass criteria to a query method, each key-value pair is automatically
  203: routed to the right database.  You never need to say which database a column
  204: belongs to.
  205: 
  206: The C<join_column> is special: criteria on it are broadcast to I<all>
  207: databases so that each database fetches only the relevant rows before the
  208: in-memory merge.
  209: 
  210: When the same non-join column name exists in more than one database, the
  211: I<last> database in the C<databases> array wins by default: its value
  212: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  213: preserve both values under distinct names instead.
  214: 
  215: =head1 LIMITATIONS
  216: 
  217: =over 4
  218: 
  219: =item In-memory join only
  220: 
  221: All matching rows from every component database are fetched into memory before
  222: the merge.  This is not suitable for very large result sets.
  223: 
  224: =item No chained builder or raw SQL
  225: 
  226: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  227: or C<fetchrow_hashref> instead.
  228: 
  229: =item Single-column equi-join only
  230: 
  231: Joining on more than one column simultaneously, or on expressions, is not
  232: supported.  When the join key has different names in different databases,
  233: use C<join_map> to declare each database's local column name.
  234: 
  235: =item Sort order
  236: 
  237: Results are sorted by the C<join_column> value only.  Caller-specified
  238: C<ORDER BY> is not propagated to the component databases.
  239: 
  240: =item count() fetches all rows
  241: 
  242: C<count()> executes the full join and counts the resulting rows in Perl.  It
  243: does not push a C<COUNT(*)> query down to the databases.
  244: 
  245: =back
  246: 
  247: =head1 COMMON PITFALLS
  248: 
  249: =over 4
  250: 
  251: =item The join_column must exist in every component database
  252: 
  253: If even one database is missing the join key column, C<new()> (or
  254: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  255: column has a different local name in some databases.
  256: 
  257: =item Criteria on a removed column are silently dropped
  258: 
  259: If you call C<remove_column('tier')> and later query
  260: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  261: C<carp> warning) and all rows are returned.  Always pass criteria before
  262: removing columns, or restructure your code to avoid this.
  263: 
  264: =item You cannot remove the join column
  265: 
  266: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  267: is required for the merge to work.
  268: 
  269: =item Left join does not guarantee all columns are populated
  270: 
  271: Under a LEFT join, rows from the primary database that have no matching row
  272: in a secondary database will be returned with I<no keys> from that secondary
  273: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  274: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  275: than just C<$row->{score}> when the secondary match is optional.
  276: 
  277: =item Filters act as inner-join partners
  278: 
  279: Any database that has a C<filters> entry is promoted to an inner-join partner,
  280: regardless of C<join_type>.  A row whose join-key value does not appear in
  281: the filtered database's result is removed from the merged output entirely, not
  282: merely missing its secondary columns.  This is intentional but can be
  283: surprising if you expected LEFT join semantics.
  284: 
  285: =item Criteria-merging replaces scalar filters
  286: 
  287: When both a base filter and a query criterion target the same column, and both
  288: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  289: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  290: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  291: the base filter is ignored for that query.
  292: 
  293: =item AUTOLOAD sees the full merged join when filters or join_map are active
  294: 
  295: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  296: (C<< $join->columnname(...) >>) runs the full join query rather than
  297: delegating directly to the owning database.  This is necessary for correctness
  298: but means the result respects all active filters and join-key translations,
  299: which may differ from what the owning database would return on its own.
  300: 
  301: =item Duplicate column names: last database wins (unless collision_prefix is set)
  302: 
  303: When two component databases each have a column called C<notes>, the second
  304: database's value silently overwrites the first in every merged row.  Use
  305: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  306: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  307: (or C<remove_column>) to drop the unwanted duplicate entirely.
  308: 
  309: =back

  558: =head2 join_map - joining on differently-named columns
  559: 
  560: By default every component database must have a column whose name matches
  561: C<join_column>.  If a database uses a different local name for the join key,
  562: declare the mapping with C<join_map>.
  563: 
  564: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  565: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  566: B<value> is the name that B<that particular database> uses for the join key.
  567: 
  568: Databases not listed in C<join_map> are assumed to already have a column
  569: named C<join_column> and need no entry.
  570: 
  571: Throughout the merged view the join key is I<always> referred to by the name
  572: given in C<join_column>.  The local alias is never exposed in returned rows,
  573: in C<columns()>, or in C<schema()>.

  575: B<When do you need join_map?>
  576: 
  577: You need C<join_map> when you have two tables like:

  579:     cities table  : entry (the city name) | statecode
  580:     stnames table : entry (the state code) | state

  582: Here you want to join cities.statecode to stnames.entry.  You choose
  583: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  584: that same concept C<entry>, so you declare:

  586:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'

  589: 
  590:     #                        index 0     index 1
  591:     my @databases = (       $cities,    $stnames  );

  621: =head2 filters - permanent per-database row filters
  622: 
  623: C<filters> lets you restrict a component database to a subset of its rows
  624: permanently, without repeating the criterion on every query call.
  625: 
  626: Think of it as telling the join: "whenever you query this database, always
  627: add these extra conditions".  Callers never need to specify the restriction
  628: themselves and can never accidentally omit it.
  629: 
  630: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  631: database in the C<databases> array (same numbering as C<join_map>).  Each
  632: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  633: accepts.
  634: 
  635: B<Key-set semantics>
  636: 
  637: A filtered database always acts as an inner-join partner, regardless of the
  638: C<join_type> setting.  Any join-key value that does not pass the filter is
  639: excluded from the merged output entirely -- not just missing its secondary
  640: columns.  This ensures the filter genuinely restricts the view rather than
  641: simply hiding a few fields.
  642: 
  643: B<Criteria merging>
  644: 
  645: When a query call also passes a criterion for a column that already has a base

  648: =over 4
  649: 
  650: =item *

  653: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are

  656: =item *

  658: When either value is a plain scalar, or the operators conflict, the

  662: =back

  664: B<Example -- only show orders placed more than 60 days ago>
  665: 
  666:     my $join = Database::Join->new(

  686: =head2 collision_prefix - preserve colliding columns from secondary databases
  687: 
  688: By default, when a column name appears in more than one database the I<last>
  689: database wins: its value silently overwrites earlier ones in merged rows.

  702: meaningless and silently ignored.  Omitting C<collision_prefix> entirely

 2123: =head1 SECURITY CONSIDERATIONS
 2124: 
 2125: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 2126: generates SQL strings, never opens files, and never calls C<system()>,
 2127: C<exec()>, or C<eval()>.  The security properties described below are
 2128: architectural guarantees, not run-time checks.
 2129: 
 2130: =head2 What Database::Join guarantees
 2131: 
 2132: =over 4
 2133: 
 2134: =item Criteria partition isolation
 2135: 
 2136: Every criterion you pass to a query method is routed to I<exactly one>
 2137: component database (the one that owns that column), or to I<all> databases
 2138: when the criterion is on the join key column.  A hostile value in a criterion
 2139: for column C<name> (owned by database A) will never reach database B.
 2140: 
 2141: =item Unknown columns are rejected before reaching any database
 2142: 
 2143: If a criterion column name is not present in any component database (or has
 2144: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 2145: and silently drops the criterion.  No database receives the hostile key.
 2146: 
 2147: =item AUTOLOAD only accepts word-character column names
 2148: 
 2149: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 2150: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 2151: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 2152: C<_>) are additionally blocked with an explicit C<croak>.
 2153: 
 2154: =item No value sanitisation (by design)
 2155: 
 2156: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 2157: I<values> in criteria hashrefs.  Preventing SQL injection is the
 2158: responsibility of the underlying C<Database::Abstraction> objects (which use
 2159: parameterised queries).  Preventing XSS or header injection is the
 2160: responsibility of the CGI or web layer that renders the output.
 2161: 
 2162: =item Taint-mode compatible
 2163: 
 2164: C<Database::Join> contains no C<system()>, C<exec()>, backtick, C<open(PIPE)>,
 2165: or C<eval STRING> calls.  It neither opens files nor constructs shell commands.
 2166: The AUTOLOAD regex C</::(\w+)$/>  produces an I<untainted> capture, so the
 2167: column name used for dispatch is clean under C<-T>.  Criteria values are
 2168: passed verbatim to component C<Database::Abstraction> objects; those objects
 2169: are responsible for handling tainted values at the SQL parameterisation layer.
 2170: 
 2171: =item Operator hashref aliasing
 2172: 
 2173: When the same join-key criterion (an operator hashref such as
 2174: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, all of
 2175: them receive a reference to the I<same> hashref.  A malicious component
 2176: database that mutates the hashref's contents could affect what subsequent
 2177: databases receive.  Component databases are assumed to be trusted.
 2178: 
 2179: =back
 2180: 
 2181: =head2 What the caller is responsible for
 2182: 
 2183: =over 4
 2184: 
 2185: =item Sanitise values before building criteria
 2186: 
 2187: DJ passes criterion values verbatim to component databases.  If your
 2188: application accepts user-supplied filter values (e.g. from a CGI query
 2189: string), those values I<must> be validated or sanitised by your application
 2190: before being passed to DJ.
 2191: 
 2192: =item Restrict which columns the caller can filter on
 2193: 
 2194: Any column in C<columns()> can be used as a filter criterion.  If a column
 2195: should not be filterable by end users (e.g. an internal status flag), hide it
 2196: with C<remove_column> so that queries on it are silently dropped.
 2197: 
 2198: =item Do not expose the joined view directly to user-supplied criteria
 2199: 
 2200: DJ is not a firewall.  It faithfully routes user input to component databases.
 2201: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 2202: columns and validates their values.
 2203: 
 2204: =back
