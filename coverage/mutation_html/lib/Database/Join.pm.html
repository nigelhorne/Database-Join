  140: =head1 DESCRIPTION
  141: 
  142: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  143: single logical, read-only view.  Each component database is queried
  144: independently through its own C<Database::Abstraction> interface.  The results
  145: are combined in Perl memory using a shared key column (C<join_column>).
  146: 
  147: The module exposes the same read-only API as C<Database::Abstraction>:
  148: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  149: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  150: shortcut.  Callers do not need to know how many underlying databases are
  151: involved.
  152: 
  153: Think of it as a virtual database table that is assembled on demand from
  154: several real tables, one per component database.
  155: 
  156: =head2 Join semantics
  157: 
  158: The C<join_type> parameter controls what happens when a particular key value
  159: exists in some component databases but not all:
  160: 
  161: =over 4
  162: 
  163: =item C<left> (the default)
  164: 
  165: All rows from the I<primary> (first) database are returned.  Columns from
  166: subsequent databases are included where a matching row is found, and simply
  167: absent from the hashref where there is no match.  If you are familiar with
  168: SQL, this is a LEFT OUTER JOIN on the first table.
  169: 
  170: =item C<inner>
  171: 
  172: Only rows whose join-column value is present in I<every> component database
  173: are returned.  This is equivalent to a SQL INNER JOIN.
  174: 
  175: =item C<outer>
  176: 
  177: Every join-column value found in I<any> component database is returned.
  178: Columns from databases that do not have that key value are absent from the
  179: merged row.  This is a FULL OUTER JOIN.
  180: 
  181: =back
  182: 
  183: B<Important override rule:> whenever you pass a query criterion for a column
  184: that belongs to a secondary database, that database automatically acts as an
  185: inner-join partner for that query only -- regardless of C<join_type>.  This
  186: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  187: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  188: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  189: as a WHERE clause would exclude them).
  190: 
  191: =head2 Column ownership and routing
  192: 
  193: At construction time, C<Database::Join> calls C<columns()> on each component
  194: database and builds an internal index that maps every column name to the
  195: database that owns it.
  196: 
  197: When you pass criteria to a query method, each key-value pair is automatically
  198: routed to the right database.  You never need to say which database a column
  199: belongs to.
  200: 
  201: The C<join_column> is special: criteria on it are broadcast to I<all>
  202: databases so that each database fetches only the relevant rows before the
  203: in-memory merge.
  204: 
  205: When the same non-join column name exists in more than one database, the
  206: I<last> database in the C<databases> array wins by default: its value
  207: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  208: preserve both values under distinct names instead.
  209: 
  210: =head1 LIMITATIONS
  211: 
  212: =over 4
  213: 
  214: =item In-memory join only
  215: 
  216: All matching rows from every component database are fetched into memory before
  217: the merge.  This is not suitable for very large result sets.
  218: 
  219: =item No chained builder or raw SQL
  220: 
  221: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  222: or C<fetchrow_hashref> instead.
  223: 
  224: =item Single-column equi-join only
  225: 
  226: Joining on more than one column simultaneously, or on expressions, is not
  227: supported.  When the join key has different names in different databases,
  228: use C<join_map> to declare each database's local column name.
  229: 
  230: =item Sort order
  231: 
  232: Results are sorted by the C<join_column> value only.  Caller-specified
  233: C<ORDER BY> is not propagated to the component databases.
  234: 
  235: =item count() fetches all rows
  236: 
  237: C<count()> executes the full join and counts the resulting rows in Perl.  It
  238: does not push a C<COUNT(*)> query down to the databases.
  239: 
  240: =back

  242: =head1 COMMON PITFALLS
  243: 
  244: =over 4
  245: 
  246: =item The join_column must exist in every component database
  247: 
  248: If even one database is missing the join key column, C<new()> (or
  249: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  250: column has a different local name in some databases.
  251: 
  252: =item Criteria on a removed column are silently dropped
  253: 
  254: If you call C<remove_column('tier')> and later query
  255: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  256: C<carp> warning) and all rows are returned.  Always pass criteria before
  257: removing columns, or restructure your code to avoid this.
  258: 
  259: =item You cannot remove the join column
  260: 
  261: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  262: is required for the merge to work.
  263: 
  264: =item Left join does not guarantee all columns are populated
  265: 
  266: Under a LEFT join, rows from the primary database that have no matching row
  267: in a secondary database will be returned with I<no keys> from that secondary
  268: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  269: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  270: than just C<$row->{score}> when the secondary match is optional.
  271: 
  272: =item Filters act as inner-join partners
  273: 
  274: Any database that has a C<filters> entry is promoted to an inner-join partner,
  275: regardless of C<join_type>.  A row whose join-key value does not appear in
  276: the filtered database's result is removed from the merged output entirely, not
  277: merely missing its secondary columns.  This is intentional but can be
  278: surprising if you expected LEFT join semantics.
  279: 
  280: =item Criteria-merging replaces scalar filters
  281: 
  282: When both a base filter and a query criterion target the same column, and both
  283: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  284: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  285: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  286: the base filter is ignored for that query.
  287: 
  288: =item AUTOLOAD sees the full merged join when filters or join_map are active
  289: 
  290: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  291: (C<< $join->columnname(...) >>) runs the full join query rather than
  292: delegating directly to the owning database.  This is necessary for correctness
  293: but means the result respects all active filters and join-key translations,
  294: which may differ from what the owning database would return on its own.
  295: 
  296: =item Duplicate column names: last database wins (unless collision_prefix is set)
  297: 
  298: When two component databases each have a column called C<notes>, the second
  299: database's value silently overwrites the first in every merged row.  Use
  300: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  301: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  302: (or C<remove_column>) to drop the unwanted duplicate entirely.
  303: 
  304: =back

  547: =head2 join_map - joining on differently-named columns
  548: 
  549: By default every component database must have a column whose name matches
  550: C<join_column>.  If a database uses a different local name for the join key,
  551: declare the mapping with C<join_map>.
  552: 
  553: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  554: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  555: B<value> is the name that B<that particular database> uses for the join key.
  556: 
  557: Databases not listed in C<join_map> are assumed to already have a column
  558: named C<join_column> and need no entry.
  559: 
  560: Throughout the merged view the join key is I<always> referred to by the name
  561: given in C<join_column>.  The local alias is never exposed in returned rows,
  562: in C<columns()>, or in C<schema()>.

  564: B<When do you need join_map?>
  565: 
  566: You need C<join_map> when you have two tables like:

  568:     cities table  : entry (the city name) | statecode
  569:     stnames table : entry (the state code) | state

  571: Here you want to join cities.statecode to stnames.entry.  You choose
  572: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  573: that same concept C<entry>, so you declare:

  575:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'

  578: 
  579:     #                        index 0     index 1
  580:     my @databases = (       $cities,    $stnames  );
  581:     #  join key column:    'statecode'  'entry'

  583:     #  stnames differs, so declare the alias:
  584: 
  585:     my $join = Database::Join->new(

  610: =head2 filters - permanent per-database row filters
  611: 
  612: C<filters> lets you restrict a component database to a subset of its rows
  613: permanently, without repeating the criterion on every query call.
  614: 
  615: Think of it as telling the join: "whenever you query this database, always
  616: add these extra conditions".  Callers never need to specify the restriction
  617: themselves and can never accidentally omit it.
  618: 
  619: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  620: database in the C<databases> array (same numbering as C<join_map>).  Each
  621: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  622: accepts.
  623: 
  624: B<Key-set semantics>
  625: 
  626: A filtered database always acts as an inner-join partner, regardless of the
  627: C<join_type> setting.  Any join-key value that does not pass the filter is
  628: excluded from the merged output entirely -- not just missing its secondary
  629: columns.  This ensures the filter genuinely restricts the view rather than
  630: simply hiding a few fields.
  631: 
  632: B<Criteria merging>
  633: 
  634: When a query call also passes a criterion for a column that already has a base
  635: filter, the two constraints are combined:
  636: 
  637: =over 4
  638: 
  639: =item *

  641: When both the base filter value and the query criterion are operator hashrefs
  642: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  643: merged: I<both> constraints apply simultaneously (AND semantics).
  644: 
  645: =item *
  646: 
  647: When either value is a plain scalar, or the operators conflict, the
  648: query-time criterion wins and the base filter for that column is ignored for
  649: that one call.
  650: 
  651: =back
  652: 
  653: B<Example -- only show orders placed more than 60 days ago>
  654: 
  655:     my $join = Database::Join->new(

  675: =head2 collision_prefix - preserve colliding columns from secondary databases
  676: 
  677: By default, when a column name appears in more than one database the I<last>
  678: database wins: its value silently overwrites earlier ones in merged rows.
  679: This loses data and makes the origin invisible.
  680: 
  681: C<collision_prefix> changes this for secondary databases you designate.
  682: When a secondary database at index N has a column that already exists in the

  684: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  685: visible: the original column keeps its name (from the earlier database), and

  687: 
  688: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of

  691: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  692: preserves the previous last-wins behaviour and changes nothing.
  693: 
  694: Non-colliding columns from a secondary database are always added as-is with

 2048: =head1 SECURITY CONSIDERATIONS
 2049: 
 2050: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 2051: generates SQL strings, never opens files, and never calls C<system()>,
 2052: C<exec()>, or C<eval()>.  The security properties described below are
 2053: architectural guarantees, not run-time checks.
 2054: 
 2055: =head2 What Database::Join guarantees
 2056: 
 2057: =over 4
 2058: 
 2059: =item Criteria partition isolation
 2060: 
 2061: Every criterion you pass to a query method is routed to I<exactly one>
 2062: component database (the one that owns that column), or to I<all> databases
 2063: when the criterion is on the join key column.  A hostile value in a criterion
 2064: for column C<name> (owned by database A) will never reach database B.
 2065: 
 2066: =item Unknown columns are rejected before reaching any database
 2067: 
 2068: If a criterion column name is not present in any component database (or has
 2069: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 2070: and silently drops the criterion.  No database receives the hostile key.
 2071: 
 2072: =item AUTOLOAD only accepts word-character column names
 2073: 
 2074: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 2075: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 2076: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 2077: C<_>) are additionally blocked with an explicit C<croak>.
 2078: 
 2079: =item No value sanitisation (by design)
 2080: 
 2081: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 2082: I<values> in criteria hashrefs.  Preventing SQL injection is the
 2083: responsibility of the underlying C<Database::Abstraction> objects (which use
 2084: parameterised queries).  Preventing XSS or header injection is the
 2085: responsibility of the CGI or web layer that renders the output.
 2086: 
 2087: =item Taint-mode compatible
 2088: 
 2089: C<Database::Join> contains no C<system()>, C<exec()>, backtick, C<open(PIPE)>,
 2090: or C<eval STRING> calls.  It neither opens files nor constructs shell commands.
 2091: The AUTOLOAD regex C</::(\w+)$/>  produces an I<untainted> capture, so the
 2092: column name used for dispatch is clean under C<-T>.  Criteria values are
 2093: passed verbatim to component C<Database::Abstraction> objects; those objects
 2094: are responsible for handling tainted values at the SQL parameterisation layer.
 2095: 
 2096: =item Operator hashref aliasing
 2097: 
 2098: When the same join-key criterion (an operator hashref such as
 2099: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, all of
 2100: them receive a reference to the I<same> hashref.  A malicious component
 2101: database that mutates the hashref's contents could affect what subsequent
 2102: databases receive.  Component databases are assumed to be trusted.
 2103: 
 2104: =back
 2105: 
 2106: =head2 What the caller is responsible for
 2107: 
 2108: =over 4
 2109: 
 2110: =item Sanitise values before building criteria
 2111: 
 2112: DJ passes criterion values verbatim to component databases.  If your
 2113: application accepts user-supplied filter values (e.g. from a CGI query
 2114: string), those values I<must> be validated or sanitised by your application
 2115: before being passed to DJ.
 2116: 
 2117: =item Restrict which columns the caller can filter on
 2118: 
 2119: Any column in C<columns()> can be used as a filter criterion.  If a column
 2120: should not be filterable by end users (e.g. an internal status flag), hide it
 2121: with C<remove_column> so that queries on it are silently dropped.
 2122: 
 2123: =item Do not expose the joined view directly to user-supplied criteria
 2124: 
 2125: DJ is not a firewall.  It faithfully routes user input to component databases.
 2126: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 2127: columns and validates their values.
 2128: 
 2129: =back
