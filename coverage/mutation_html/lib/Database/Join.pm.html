  214: =head1 DESCRIPTION
  215: 
  216: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  217: single logical, read-only view.  Each component database is queried
  218: independently through its own C<Database::Abstraction> interface.  The results
  219: are combined using a shared key column (C<join_column>).
  220: In effect, this means that you can view data from more than one database using
  221: an intuitive, non-SQL interface.
  222: 
  223: Every storage format that C<Database::Abstraction> supports works as a
  224: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  225: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  226: within the same join.
  227: 
  228: The module exposes the same read-only API as C<Database::Abstraction>:
  229: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  230: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  231: shortcut.  Callers do not need to know how many underlying databases are
  232: involved.
  233: 
  234: Think of it as a virtual database table that is assembled on demand from
  235: several real tables, one per component database.
  236: 
  237: B<Join backends>
  238: 
  239: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  240: combined source row count.  For small datasets (up to C<max_array_rows>,
  241: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  242: automatically spills source rows into a temporary SQLite database and executes
  243: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  244: size instead of three.  You can also force either path unconditionally with
  245: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  246: 
  247: =head2 Join semantics
  248: 
  249: The C<join_type> parameter controls what happens when a particular key value
  250: exists in some component databases but not all:
  251: 
  252: =over 4
  253: 
  254: =item C<left> (the default)
  255: 
  256: All rows from the I<primary> (first) database are returned.  Columns from
  257: subsequent databases are included where a matching row is found, and simply
  258: absent from the hashref where there is no match.  If you are familiar with
  259: SQL, this is a LEFT OUTER JOIN on the first table.
  260: 
  261: =item C<inner>
  262: 
  263: Only rows whose join-column value is present in I<every> component database
  264: are returned.  This is equivalent to a SQL INNER JOIN.
  265: 
  266: =item C<outer>
  267: 
  268: Every join-column value found in I<any> component database is returned.
  269: Columns from databases that do not have that key value are absent from the
  270: merged row.  This is a FULL OUTER JOIN.
  271: 
  272: =back
  273: 
  274: B<Important override rule:> whenever you pass a query criterion for a column
  275: that belongs to a secondary database, that database automatically acts as an
  276: inner-join partner for that query only -- regardless of C<join_type>.  This
  277: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  278: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  279: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  280: as a WHERE clause would exclude them).
  281: 
  282: =head2 Column ownership and routing
  283: 
  284: At construction time, C<Database::Join> calls C<columns()> on each component
  285: database and builds an internal index that maps every column name to the
  286: database that owns it.
  287: 
  288: When you pass criteria to a query method, each key-value pair is automatically
  289: routed to the right database.  You never need to say which database a column
  290: belongs to.
  291: 
  292: The C<join_column> is special: criteria on it are broadcast to I<all>
  293: databases so that each database fetches only the relevant rows before the
  294: in-memory merge.
  295: 
  296: When the same non-join column name exists in more than one database, the
  297: I<last> database in the C<databases> array wins by default: its value
  298: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  299: preserve both values under distinct names instead.
  300: 
  301: =head1 LIMITATIONS
  302: 
  303: =over 4
  304: 
  305: =item Memory usage (array backend)
  306: 
  307: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  308: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  309: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  310: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  311: 
  312: =item SQLite backend uses a persistent cache file
  313: 
  314: When the SQLite path is active, a single C<.db> file with a randomly generated
  315: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  316: first time a query runs on a given C<Database::Join> object.  Source data is
  317: spilled into that file once; subsequent queries against the same object reuse
  318: the file without re-fetching the source data.
  319: 
  320: The cache is automatically invalidated and rebuilt whenever any source
  321: database's C<updated()> timestamp changes (indicating new data), or when
  322: C<add_database()> is called.
  323: 
  324: The file is deleted when the C<Database::Join> object is destroyed (typically
  325: when it goes out of scope).  At any given moment no more than one such file
  326: exists per object.  The directory must be writable and have enough free space
  327: for the full source data (once, not per-query).
  328: 
  329: =item No chained builder or raw SQL
  330: 
  331: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  332: or C<fetchrow_hashref> instead.
  333: 
  334: =item Single-column equi-join only
  335: 
  336: Joining on more than one column simultaneously, or on expressions, is not
  337: supported.  When the join key has different names in different databases,
  338: use C<join_map> to declare each database's local column name.
  339: 
  340: =item Sort order
  341: 
  342: Results are sorted ascending by C<join_column> by default.  Pass
  343: C<< order_by => 'colname' >> (or C<< order_by => ['colname', 'DESC'] >>)
  344: to any query method to override this.  The array path uses string comparison
  345: (C<cmp>); for accurate numeric ordering on large datasets use the SQLite
  346: backend, which sorts natively by type.
  347: 
  348: =item count() fetches all rows
  349: 
  350: C<count()> executes the full join and counts the resulting rows in Perl.  It
  351: does not push a C<COUNT(*)> query down to the databases.
  352: 
  353: =back
  354: 
  355: =head1 COMMON PITFALLS
  356: 
  357: =over 4
  358: 
  359: =item The join_column must exist in every component database
  360: 
  361: If even one database is missing the join key column, C<new()> (or
  362: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  363: column has a different local name in some databases.
  364: 
  365: =item Criteria on a removed column are silently dropped
  366: 
  367: If you call C<remove_column('tier')> and later query
  368: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  369: C<carp> warning) and all rows are returned.  Always pass criteria before
  370: removing columns, or restructure your code to avoid this.
  371: 
  372: =item You cannot remove the join column
  373: 
  374: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  375: is required for the merge to work.
  376: 
  377: =item Left join does not guarantee all columns are populated
  378: 
  379: Under a LEFT join, rows from the primary database that have no matching row
  380: in a secondary database will be returned with I<no keys> from that secondary
  381: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  382: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  383: than just C<$row->{score}> when the secondary match is optional.
  384: 
  385: =item Filters act as inner-join partners
  386: 
  387: Any database that has a C<filters> entry is promoted to an inner-join partner,
  388: regardless of C<join_type>.  A row whose join-key value does not appear in
  389: the filtered database's result is removed from the merged output entirely, not
  390: merely missing its secondary columns.  This is intentional but can be
  391: surprising if you expected LEFT join semantics.
  392: 
  393: =item Criteria-merging replaces scalar filters
  394: 
  395: When both a base filter and a query criterion target the same column, and both
  396: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  397: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  398: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  399: the base filter is ignored for that query.
  400: 
  401: =item AUTOLOAD sees the full merged join when filters or join_map are active
  402: 
  403: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  404: (C<< $join->columnname(...) >>) runs the full join query rather than
  405: delegating directly to the owning database.  This is necessary for correctness
  406: but means the result respects all active filters and join-key translations,
  407: which may differ from what the owning database would return on its own.
  408: 
  409: =item Duplicate column names: last database wins (unless collision_prefix is set)
  410: 
  411: When two component databases each have a column called C<notes>, the second
  412: database's value silently overwrites the first in every merged row.  Use
  413: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  414: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  415: (or C<remove_column>) to drop the unwanted duplicate entirely.
  416: 
  417: =item Mutating the filters hashref after construction has no effect
  418: 
  419: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  420: passed to C<add_database>) at the moment of construction.  The original hashref
  421: you passed in is never stored.  If you later modify it -- for example, to
  422: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  423: Construct a new C<Database::Join> object, or use a component
  424: C<Database::Abstraction> that supports dynamic filter modification.
  425: 
  426: =item auto mode may always use the array path for some DAs
  427: 
  428: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  429: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  430: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  431: from C<Database::Abstraction> is treated as uncountable, because the parent
  432: class C<count()> expects a key argument and behaves differently from a
  433: "return total row count" function.  In that case C<Database::Join>
  434: conservatively uses the array path for the whole query, even if the dataset is
  435: large.  To opt in to the SQLite path for such a DA, either add your own
  436: C<count()> override that returns the total row count, implement C<dbi_source()>,
  437: or use C<backend =E<gt> 'sqlite'> unconditionally.
  438: 
  439: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  440: 
  441: When a component database implements C<dbi_source()>, C<Database::Join> always
  442: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  443: for columns in that database>.  The criteria are translated into parameterised
  444: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  445: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  446: force a spill; that restriction has been removed.)
  447: 
  448: =item Broadcast join-column criterion does not force secondaries into inner-join
  449: 
  450: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  451: C<Database::Join> broadcasts it to all component databases so each DA can
  452: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  453: incorrectly counted as "having criteria" for secondary databases, causing
  454: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  455: join-column criterion was present.  The fix: only non-join-column criteria
  456: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  457: a secondary to inner-join status.  The broadcast itself is now a transparent
  458: key-range selector that does not affect join semantics.
  459: 
  460: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  461: 
  462: C<LIKE>, C<NOT LIKE>, C<IN>, and C<NOT IN> are fully supported on the SQLite
  463: backend.  C<LIKE>/C<NOT LIKE> take a scalar pattern; C<IN>/C<NOT IN> take an
  464: arrayref of values.  All are injection-safe because values are passed as bind
  465: parameters, never interpolated.
  466: 
  467:     # LIKE
  468:     my $rows = $join->selectall_arrayref(name => { LIKE => 'A%' });
  469: 
  470:     # IN
  471:     my $rows = $join->selectall_arrayref(tier => { IN => ['gold', 'silver'] });
  472: 
  473:     # NOT IN
  474:     my $rows = $join->selectall_arrayref(tier => { 'NOT IN' => ['bronze'] });
  475: 
  476: C<IN> with an empty arrayref matches no rows (SQL semantics: C<IN ()> is
  477: always false).  C<NOT IN> with an empty arrayref matches all rows (no
  478: constraint added).
  479: 
  480: C<IS NULL> and C<IS NOT NULL> are supported on the SQLite backend using an
  481: explicit operator hashref:
  482: 
  483:     my $rows = $join->selectall_arrayref(score => { 'IS NULL'     => undef });
  484:     my $rows = $join->selectall_arrayref(score => { 'IS NOT NULL' => 1    });
  485: 
  486: The hashref value is ignored; only the key selects the operator.  A bare
  487: C<undef> criterion value (C<< score => undef >>) also generates C<IS NULL>
  488: on the SQLite path.  Note: on the in-memory array path, the component DA
  489: may treat an C<undef> criterion value as C<< no filter >> rather than
  490: C<IS NULL>, so use the explicit hashref form for consistent behaviour
  491: across backends.
  492: 
  493: Any operator not in the supported set is skipped on the SQLite path with a

  802: =head2 join_map - joining on differently-named columns
  803: 
  804: By default every component database must have a column whose name matches
  805: C<join_column>.  If a database uses a different local name for the join key,
  806: declare the mapping with C<join_map>.
  807: 
  808: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  809: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  810: B<value> is the name that B<that particular database> uses for the join key.
  811: 
  812: Databases not listed in C<join_map> are assumed to already have a column
  813: named C<join_column> and need no entry.
  814: 
  815: Throughout the merged view the join key is I<always> referred to by the name
  816: given in C<join_column>.  The local alias is never exposed in returned rows,
  817: in C<columns()>, or in C<schema()>.
  818: 
  819: B<When do you need join_map?>
  820: 
  821: You need C<join_map> when you have two tables like:
  822: 
  823:     cities table  : entry (the city name) | statecode
  824:     stnames table : entry (the state code) | state
  825: 
  826: Here you want to join cities.statecode to stnames.entry.  You choose
  827: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  828: that same concept C<entry>, so you declare:
  829: 
  830:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  831: 
  832: B<Example>
  833: 
  834:     #                        index 0     index 1
  835:     my @databases = (       $cities,    $stnames  );
  836:     #  join key column:    'statecode'  'entry'
  837:     #  join_column:        'statecode' (chosen canonical name)
  838:     #  stnames differs, so declare the alias:
  839: 
  840:     my $join = Database::Join->new(
  841:         databases   => \@databases,
  842:         join_column => 'statecode',
  843:         join_map    => { 1 => 'entry' },

  865: =head2 filters - permanent per-database row filters
  866: 
  867: C<filters> lets you restrict a component database to a subset of its rows
  868: permanently, without repeating the criterion on every query call.
  869: 
  870: Think of it as telling the join: "whenever you query this database, always
  871: add these extra conditions".  Callers never need to specify the restriction
  872: themselves and can never accidentally omit it.
  873: 
  874: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  875: database in the C<databases> array (same numbering as C<join_map>).  Each
  876: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  877: accepts.
  878: 
  879: B<Key-set semantics>
  880: 
  881: A filtered database always acts as an inner-join partner, regardless of the
  882: C<join_type> setting.  Any join-key value that does not pass the filter is
  883: excluded from the merged output entirely -- not just missing its secondary
  884: columns.  This ensures the filter genuinely restricts the view rather than
  885: simply hiding a few fields.
  886: 
  887: B<Criteria merging>
  888: 
  889: When a query call also passes a criterion for a column that already has a base
  890: filter, the two constraints are combined:
  891: 
  892: =over 4
  893: 
  894: =item *
  895: 
  896: When both the base filter value and the query criterion are operator hashrefs
  897: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  898: merged: I<both> constraints apply simultaneously (AND semantics).
  899: 
  900: =item *
  901: 
  902: When either value is a plain scalar, or the operators conflict, the
  903: query-time criterion wins and the base filter for that column is ignored for
  904: that one call.
  905: 
  906: =back
  907:

  909: 
  910:     my $join = Database::Join->new(

  930: =head2 collision_prefix - preserve colliding columns from secondary databases
  931: 
  932: By default, when a column name appears in more than one database the I<last>
  933: database wins: its value silently overwrites earlier ones in merged rows.
  934: This loses data and makes the origin invisible.
  935: 
  936: C<collision_prefix> changes this for secondary databases you designate.
  937: When a secondary database at index N has a column that already exists in the
  938: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  939: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  940: visible: the original column keeps its name (from the earlier database), and
  941: the collision gets the prefixed name.
  942: 
  943: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  944: a secondary database in the C<databases> array (same numbering as C<join_map>).
  945: Each B<value> is the prefix string to prepend.  An index-0 entry is
  946: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  947: preserves the previous last-wins behaviour and changes nothing.
  948: 
  949: Non-colliding columns from a secondary database are always added as-is with
  950: no prefix, whether or not C<collision_prefix> is configured.
  951: 
  952: B<Example -- sales table and products table, both with a "product" column>
  953: 
  954:     # $sales    columns: id, product, amount, date
  955:     # $products columns: sku, product, price, category
  956:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  957: 
  958:     my $join = Database::Join->new(
  959:         databases        => [$sales, $products],
  960:         join_column      => 'product',
  961:         join_map         => { 1 => 'sku' },
  962:         collision_prefix => { 1 => 'products' },
  963:     );
  964: 
  965:     $join->columns;
  966:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  967:     #                                                               ^-- prefixed collision
  968: 
  969:     my $row = $join->fetchrow_hashref(product => 'widget');
  970:     # $row->{product}            -- value from $sales
  971:     # $row->{'products.product'} -- value from $products (different row, same column name)
  972:     # $row->{price}              -- from $products, no collision, kept as-is
  973: 
  974: B<Querying on a prefixed column>
  975: 
  976: Use the full published name as the criterion key:

  988: =head2 backend - SQLite join backend for large datasets
  989: 
  990: C<Database::Join> can merge component databases in two different ways,
  991: controlled by the C<backend> constructor parameter.
  992: 
  993: =over 4
  994: 
  995: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  996: 
  997: All matching rows are fetched from every component database into Perl hashes
  998: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
  999: is roughly three times the combined source data size (one copy per database
 1000: plus one merged copy).
 1001: 
 1002: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1003: 
 1004: C<Database::Join> creates a temporary SQLite database file, spills source
 1005: rows into it (one table per component database), then executes a single SQL
 1006: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1007: source data size.
 1008: 
 1009: The temporary file is created once and reused across multiple query calls on
 1010: the same object (the cache).  Only query-time criteria vary per call; they
 1011: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1012: automatically rebuilt when any source database's C<updated()> timestamp
 1013: changes.  The file is deleted when the object is destroyed (goes out of
 1014: scope).  See I<Temporary file: name, location, and lifetime> below for
 1015: details.
 1016: 
 1017: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
 1018: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
 1019: 
 1020: =item C<backend =E<gt> 'auto'> (default)
 1021: 
 1022: C<Database::Join> counts the total rows from all component databases cheaply
 1023: -- without fetching them -- and then decides:

 1025: =over 4
 1026: 
 1027: =item *
 1028: 
 1029: If the combined count is less than or equal to C<max_array_rows> (default
 1030: 10,000), use the array path.
 1031: 
 1032: =item *
 1033: 
 1034: If the combined count exceeds C<max_array_rows>, use the SQLite path.
 1035: 
 1036: =back
 1037: 
 1038: For counting to work without fetching, each component database must either
 1039: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
 1040: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
 1041: method in its own package -- not just inherit one from a parent class.  If
 1042: neither is available for a particular database, C<Database::Join> plays it
 1043: safe and uses the array path for the whole query without fetching any rows.
 1044: 
 1045: =back
 1046: 
 1047: B<Choosing max_array_rows>
 1048: 
 1049: The default of 10,000 is a reasonable starting point.  Adjust it to match
 1050: your hardware and typical row width.  For wide rows (many columns or long
 1051: strings) you may want a lower threshold; for narrow rows you can raise it.
 1052: 
 1053: B<Temporary file: name, location, and lifetime>
 1054: 
 1055: When the SQLite path is active, a single temporary SQLite database file acts
 1056: as the join cache for the life of the C<Database::Join> object.
 1057: 
 1058: B<Name>: the filename is randomly generated by C<File::Temp>, for example:
 1059: 
 1060:     /tmp/Cj8xK7mP2Q.db
 1061:

 1063: collisions.  Only the directory is under your control; you cannot specify
 1064: the filename itself.

 1068: C</tmp> on Unix, or the value of the C<TEMP> or C<TMP> environment variable

 1070: 
 1071: B<Lifetime: one file per object, deleted when the object is destroyed>: the
 1072: file is created on the first query call that uses the SQLite path and kept

 1094: B<Zero-copy ATTACH (C<dbi_source()> interface)>
 1095:

 3226: =head1 SECURITY CONSIDERATIONS
 3227: 
 3228: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3229: generates SQL strings, never opens files, and never calls C<system()>,
 3230: C<exec()>, or C<eval()>.  The security properties described below are
 3231: architectural guarantees, not run-time checks.
 3232: 
 3233: =head2 What Database::Join guarantees
 3234: 
 3235: =over 4
 3236: 
 3237: =item Criteria partition isolation
 3238: 
 3239: Every criterion you pass to a query method is routed to I<exactly one>
 3240: component database (the one that owns that column), or to I<all> databases
 3241: when the criterion is on the join key column.  A hostile value in a criterion
 3242: for column C<name> (owned by database A) will never reach database B.
 3243: 
 3244: =item Unknown columns are rejected before reaching any database
 3245: 
 3246: If a criterion column name is not present in any component database (or has
 3247: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3248: and silently drops the criterion.  No database receives the hostile key.
 3249: 
 3250: =item AUTOLOAD only accepts word-character column names
 3251: 
 3252: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3253: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3254: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3255: C<_>) are additionally blocked with an explicit C<croak>.
 3256: 
 3257: =item No value sanitisation (by design)
 3258: 
 3259: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3260: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3261: responsibility of the underlying C<Database::Abstraction> objects (which use
 3262: parameterised queries).  Preventing XSS or header injection is the
 3263: responsibility of the CGI or web layer that renders the output.
 3264: 
 3265: =item Taint-mode compatible (array path)
 3266: 
 3267: The array merge path contains no C<system()>, C<exec()>, backtick,
 3268: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3269: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3270: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3271: an I<untainted> capture, so the column name used for dispatch is clean under
 3272: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3273: objects; those objects are responsible for handling tainted values at the SQL
 3274: parameterisation layer.
 3275: 
 3276: =item SQLite backend: column names are quoted, values are parametrised
 3277: 
 3278: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3279: All column and table names are double-quoted (SQL identifier quoting) before
 3280: being embedded in statement strings.  All row values are passed to SQLite
 3281: exclusively through DBI prepared statement placeholders -- never by string
 3282: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3283: into the temporary database.
 3284: 
 3285: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3286: unpredictable filename.  No C<system()> or shell command is used to create or
 3287: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3288: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3289: in the generated SQL come from C<columns()>, which is produced by
 3290: C<Database::Abstraction> at construction time -- they are not derived from
 3291: caller-supplied criteria values.
 3292: 
 3293: =item Operator hashref broadcast copy
 3294: 
 3295: When the same join-key criterion (an operator hashref such as
 3296: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3297: database receives its own I<shallow copy> of the hashref.  A component database
 3298: that mutates the hashref's contents at the top level cannot affect what
 3299: subsequent databases receive.
 3300: 
 3301: =item collision_prefix value type guard
 3302: 
 3303: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3304: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3305: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3306: column name, C<columns()> listing, and merged row returned to the caller.  The
 3307: guard fires before any column name is constructed.
 3308: 
 3309: =item Filter deep-copy isolation
 3310: 
 3311: The C<filters> constructor parameter and the C<filter> option of
 3312: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3313: original hashrefs are never stored; post-construction mutation of those
 3314: hashrefs cannot widen or bypass the configured row-security constraints.
 3315: 
 3316: =back

 3638: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 3639: triggers that cause transitions (arrows), and important side-effects.
 3640: 
 3641: =head2 FSM 1: Object Lifecycle
 3642: 
 3643: Governs the structural state of a C<Database::Join> instance.
 3644: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 3645: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 3646: are not shown because they do not change state.
 3647: 
 3648:     [pre-creation]
 3649:          |
 3650:          | new( databases => [...], join_column => '...' )
 3651:          |   Side-effect: _col_db routing table built;
 3652:          |                _autoload_pk cached from dbs[0]{id}
 3653:          v
 3654:     [CONSTRUCTED] <-----------------------------------------+
 3655:          |    |                                              |
 3656:          |    +--------------------------------------------+ |
 3657:          |    (query methods: no structural change)         | |
 3658:          |                                                  | |
 3659:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 3660:          |                                      |    |        |
 3661:          |   Side-effect: col removed from       |    |        |
 3662:          |   _col_db; _col_cache and             +----+        |
 3663:          |   _schema_cache cleared.              (idempotent;  |
 3664:          |   Join column cannot be removed.)      chainable)   |
 3665:          |                                                     |
 3666:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 3667:                                                 |    |
 3668:              Side-effect: new columns added;    |    | add_database( db )
 3669:              _col_db extended; SQLite cache     |    | (chainable; each
 3670:              invalidated (if any).              +----+  extends the view)
 3671: 
 3672:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 3673:     Both transitions are legal on any valid object, in any order.
 3674: 
 3675:     Illegal triggers (always croak; object state is not changed):
 3676: 
 3677:       Trigger                              Error
 3678:       -----------------------------------  ---------------------------------
 3679:       new( databases => [] )               error_no_databases
 3680:       remove_column( join_column )         error_remove_join_column
 3681:       add_database( non-reference )        error_invalid_database
 3682:       new() with join_col absent from DB   error_join_col_absent

 3684: =head2 FSM 2: SQLite Cache Lifecycle
 3685: 
 3686: Governs the temporary SQLite cache used by the C<backend='sqlite'> and
 3687: C<backend='auto'> join paths.  The cache does not exist until the first
 3688: query on the SQLite path.
 3689: 
 3690:     [ABSENT] <----- add_database( db )
 3691:        |                  |
 3692:        |  (no temp file)  | Side-effect: old DBI handle disconnected;
 3693:        |                  |   _sqlite_cache deleted.
 3694:        |                  |
 3695:        |                  +<-------------------------------------------+
 3696:        |                                                               |
 3697:        | first query on SQLite path                                    |
 3698:        | Side-effect: File::Temp db created in tmpdir;                 |
 3699:        |   DBI connected; sources ATTACHed or spilled;                 |
 3700:        |   _sqlite_cache = { dbh, tmpfile, n, updated, ... }           |
 3701:        v                                                               |
 3702:     [FRESH] <--+                                                       |
 3703:        |        |                                                      |
 3704:        |        | subsequent queries                                   |
 3705:        |        | (cache reused; refaddr of _sqlite_cache unchanged)   |
 3706:        +--------+                                                      |
 3707:        |                                                               |
 3708:        | updated() timestamp of any source DA changes                  |
 3709:        | -- OR -- source row count changes                             |
 3710:        | Side-effect: none yet (_cache_fresh returns false)            |
 3711:        v                                                               |
 3712:     [STALE]                                                            |
 3713:        |                                                               |
 3714:        | next query                                                    |
 3715:        | Side-effect: old DBI handle disconnected; old temp file       |
 3716:        |   unlinked; new temp file built from current source data.     |
 3717:        +---------------------------------------------------------------+
 3718:        (transitions to FRESH)
 3719: 
 3720:     On object DESTROY:
 3721:       FRESH/STALE:  DBI handle disconnected; File::Temp object released
 3722:                     (temp file unlinked by File::Temp DESTROY).
 3723:       ABSENT:       No temp file exists; no-op.

 3725: =head2 FSM 3: Column Visibility (per column)
 3726: 
 3727: Each column in the logical view independently follows a two-state machine.
 3728: Transition from VISIBLE to REMOVED is one-way: C<add_database> never
 3729: restores a column that is in C<_removed_cols>.
 3730: 
 3731:     [VISIBLE] <-- initial state for every column at construction
 3732:          |    |
 3733:          |    | query / columns() / schema()
 3734:          |    | (column present in results; no state change)
 3735:          +----+
 3736:          |
 3737:          | remove_column( col )
 3738:          | Side-effect: col deleted from _col_db;
 3739:          |   _col_cache and _schema_cache cleared.
 3740:          v
 3741:     [REMOVED] <---+
 3742:          |         |
 3743:          |         | remove_column( col ) again
 3744:          |         | (idempotent; no error; no second side-effect)
 3745:          +---------+
 3746: 
 3747:     One-way invariant:
 3748:       If col is in _removed_cols, then add_database( db_that_has_col )
 3749:       does NOT re-add it.  Formal: col_db' = col_db âŠ• { c | c in
 3750:       ran(db.columns) \ {local_jc} \ removed }.
