  225: =head1 DESCRIPTION
  226: 
  227: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  228: single logical, read-only view.  Each component database is queried
  229: independently through its own C<Database::Abstraction> interface.  The results
  230: are combined using a shared key column (C<join_column>).
  231: In effect, this means that you can view data from more than one database using
  232: an intuitive, non-SQL interface.
  233: 
  234: Every storage format that C<Database::Abstraction> supports works as a
  235: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  236: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  237: within the same join.
  238: 
  239: The module exposes the same read-only API as C<Database::Abstraction>:
  240: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  241: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  242: shortcut.  Callers do not need to know how many underlying databases are
  243: involved.
  244: 
  245: Think of it as a virtual database table that is assembled on demand from
  246: several real tables, one per component database.
  247: 
  248: B<Join backends>
  249: 
  250: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  251: combined source row count.  For small datasets (up to C<max_array_rows>,
  252: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  253: automatically spills source rows into a temporary SQLite database and executes
  254: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  255: size instead of three.  You can also force either path unconditionally with
  256: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  257: 
  258: =head2 Join semantics
  259: 
  260: The C<join_type> parameter controls what happens when a particular key value
  261: exists in some component databases but not all:
  262: 
  263: =over 4
  264: 
  265: =item C<left> (the default)
  266: 
  267: All rows from the I<primary> (first) database are returned.  Columns from
  268: subsequent databases are included where a matching row is found, and simply
  269: absent from the hashref where there is no match.  If you are familiar with
  270: SQL, this is a LEFT OUTER JOIN on the first table.
  271: 
  272: =item C<inner>
  273: 
  274: Only rows whose join-column value is present in I<every> component database
  275: are returned.  This is equivalent to a SQL INNER JOIN.
  276: 
  277: =item C<outer>
  278: 
  279: Every join-column value found in I<any> component database is returned.
  280: Columns from databases that do not have that key value are absent from the
  281: merged row.  This is a FULL OUTER JOIN.
  282: 
  283: =back
  284: 
  285: B<Important override rule:> whenever you pass a query criterion for a column
  286: that belongs to a secondary database, that database automatically acts as an
  287: inner-join partner for that query only -- regardless of C<join_type>.  This
  288: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  289: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  290: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  291: as a WHERE clause would exclude them).
  292: 
  293: =head2 Column ownership and routing
  294: 
  295: At construction time, C<Database::Join> calls C<columns()> on each component
  296: database and builds an internal index that maps every column name to the
  297: database that owns it.
  298: 
  299: When you pass criteria to a query method, each key-value pair is automatically
  300: routed to the right database.  You never need to say which database a column
  301: belongs to.
  302: 
  303: The C<join_column> is special: criteria on it are broadcast to I<all>
  304: databases so that each database fetches only the relevant rows before the
  305: in-memory merge.
  306: 
  307: When the same non-join column name exists in more than one database, the
  308: I<last> database in the C<databases> array wins by default: its value
  309: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  310: preserve both values under distinct names instead.
  311: 
  312: =head1 LIMITATIONS
  313: 
  314: =over 4
  315: 
  316: =item Memory usage (array backend)
  317: 
  318: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  319: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  320: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  321: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  322: 
  323: =item SQLite backend uses a persistent cache file
  324: 
  325: When the SQLite path is active, a single C<.db> file with a randomly generated
  326: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  327: first time a query runs on a given C<Database::Join> object.  Source data is
  328: spilled into that file once; subsequent queries against the same object reuse
  329: the file without re-fetching the source data.
  330: 
  331: The cache is automatically invalidated and rebuilt whenever any source
  332: database's C<updated()> timestamp changes (indicating new data), or when
  333: C<add_database()> is called.
  334: 
  335: The file is deleted when the C<Database::Join> object is destroyed (typically
  336: when it goes out of scope).  At any given moment no more than one such file
  337: exists per object.  The directory must be writable and have enough free space
  338: for the full source data (once, not per-query).
  339: 
  340: =item No chained builder or raw SQL
  341: 
  342: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  343: or C<fetchrow_hashref> instead.
  344: 
  345: =item Single-column equi-join only
  346: 
  347: Joining on more than one column simultaneously, or on expressions, is not
  348: supported.  When the join key has different names in different databases,
  349: use C<join_map> to declare each database's local column name.
  350: 
  351: =item Sort order
  352: 
  353: Results are sorted by the C<join_column> value only.  Caller-specified
  354: C<ORDER BY> is not propagated to the component databases.
  355: 
  356: =item count() fetches all rows
  357: 
  358: C<count()> executes the full join and counts the resulting rows in Perl.  It
  359: does not push a C<COUNT(*)> query down to the databases.
  360: 
  361: =back
  362: 
  363: =head1 COMMON PITFALLS
  364: 
  365: =over 4
  366: 
  367: =item The join_column must exist in every component database
  368: 
  369: If even one database is missing the join key column, C<new()> (or
  370: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  371: column has a different local name in some databases.
  372: 
  373: =item Criteria on a removed column are silently dropped
  374: 
  375: If you call C<remove_column('tier')> and later query
  376: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  377: C<carp> warning) and all rows are returned.  Always pass criteria before
  378: removing columns, or restructure your code to avoid this.
  379: 
  380: =item You cannot remove the join column
  381: 
  382: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  383: is required for the merge to work.
  384: 
  385: =item Left join does not guarantee all columns are populated
  386: 
  387: Under a LEFT join, rows from the primary database that have no matching row
  388: in a secondary database will be returned with I<no keys> from that secondary
  389: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  390: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  391: than just C<$row->{score}> when the secondary match is optional.
  392: 
  393: =item Filters act as inner-join partners
  394: 
  395: Any database that has a C<filters> entry is promoted to an inner-join partner,
  396: regardless of C<join_type>.  A row whose join-key value does not appear in
  397: the filtered database's result is removed from the merged output entirely, not
  398: merely missing its secondary columns.  This is intentional but can be
  399: surprising if you expected LEFT join semantics.
  400: 
  401: =item Criteria-merging replaces scalar filters
  402: 
  403: When both a base filter and a query criterion target the same column, and both
  404: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  405: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  406: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  407: the base filter is ignored for that query.
  408: 
  409: =item AUTOLOAD sees the full merged join when filters or join_map are active
  410: 
  411: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  412: (C<< $join->columnname(...) >>) runs the full join query rather than
  413: delegating directly to the owning database.  This is necessary for correctness
  414: but means the result respects all active filters and join-key translations,
  415: which may differ from what the owning database would return on its own.
  416: 
  417: =item Duplicate column names: last database wins (unless collision_prefix is set)
  418: 
  419: When two component databases each have a column called C<notes>, the second
  420: database's value silently overwrites the first in every merged row.  Use
  421: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  422: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  423: (or C<remove_column>) to drop the unwanted duplicate entirely.
  424: 
  425: =item Mutating the filters hashref after construction has no effect
  426: 
  427: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  428: passed to C<add_database>) at the moment of construction.  The original hashref
  429: you passed in is never stored.  If you later modify it -- for example, to
  430: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  431: Construct a new C<Database::Join> object, or use a component
  432: C<Database::Abstraction> that supports dynamic filter modification.
  433: 
  434: =item auto mode may always use the array path for some DAs
  435: 
  436: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  437: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  438: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  439: from C<Database::Abstraction> is treated as uncountable, because the parent
  440: class C<count()> expects a key argument and behaves differently from a
  441: "return total row count" function.  In that case C<Database::Join>
  442: conservatively uses the array path for the whole query, even if the dataset is
  443: large.  To opt in to the SQLite path for such a DA, either add your own
  444: C<count()> override that returns the total row count, implement C<dbi_source()>,
  445: or use C<backend =E<gt> 'sqlite'> unconditionally.
  446: 
  447: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  448: 
  449: When a component database implements C<dbi_source()>, C<Database::Join> always
  450: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  451: for columns in that database>.  The criteria are translated into parameterised
  452: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  453: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  454: force a spill; that restriction has been removed.)
  455: 
  456: =item Broadcast join-column criterion does not force secondaries into inner-join
  457: 
  458: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  459: C<Database::Join> broadcasts it to all component databases so each DA can
  460: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  461: incorrectly counted as "having criteria" for secondary databases, causing
  462: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  463: join-column criterion was present.  The fix: only non-join-column criteria
  464: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  465: a secondary to inner-join status.  The broadcast itself is now a transparent
  466: key-range selector that does not affect join semantics.
  467: 
  468: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  469: 
  470: C<LIKE> and C<NOT LIKE> criteria (e.g. C<< name => { LIKE => '%ali%' } >>) are
  471: fully supported on the SQLite backend: the pattern is always passed as a bind
  472: parameter, never interpolated into SQL, so there is no injection risk.  The
  473: behaviour is identical on both the array path (where the criterion is forwarded
  474: to the component DA) and the SQLite path.
  475: 
  476: Operators that are I<not> yet in the supported set -- C<IN>, C<NOT IN>,
  477: C<IS NULL>, C<IS NOT NULL> -- are silently skipped on the SQLite path; a
  478: C<carp> warning is emitted for each one so callers are not silently misled.
  479: The array path forwards these operators to the component DA unchanged, which
  480: may or may not honour them.  If you need these operators, use
  481: C<< backend => 'array' >> to stay on the array path, or open a feature request.
  482: 
  483: =item Temp file directory must be writable and have free space
  484: 
  485: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  486: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  487: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  488: only the directory is under your control.  The file is created on the first
  489: query and kept alive until the object is destroyed; it is not re-created on

  788: =head2 join_map - joining on differently-named columns
  789: 
  790: By default every component database must have a column whose name matches
  791: C<join_column>.  If a database uses a different local name for the join key,
  792: declare the mapping with C<join_map>.
  793: 
  794: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  795: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  796: B<value> is the name that B<that particular database> uses for the join key.
  797: 
  798: Databases not listed in C<join_map> are assumed to already have a column
  799: named C<join_column> and need no entry.
  800: 
  801: Throughout the merged view the join key is I<always> referred to by the name
  802: given in C<join_column>.  The local alias is never exposed in returned rows,
  803: in C<columns()>, or in C<schema()>.
  804: 
  805: B<When do you need join_map?>
  806: 
  807: You need C<join_map> when you have two tables like:
  808: 
  809:     cities table  : entry (the city name) | statecode
  810:     stnames table : entry (the state code) | state
  811: 
  812: Here you want to join cities.statecode to stnames.entry.  You choose
  813: C<< join_column => 'statecode' >> as the canonical name, but stnames calls
  814: that same concept C<entry>, so you declare:
  815: 
  816:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'
  817: 
  818: B<Example>
  819: 
  820:     #                        index 0     index 1
  821:     my @databases = (       $cities,    $stnames  );
  822:     #  join key column:    'statecode'  'entry'
  823:     #  join_column:        'statecode' (chosen canonical name)
  824:     #  stnames differs, so declare the alias:
  825: 
  826:     my $join = Database::Join->new(
  827:         databases   => \@databases,
  828:         join_column => 'statecode',
  829:         join_map    => { 1 => 'entry' },
  830:     );
  831: 
  832:     my $rows = $join->selectall_arrayref();
  833:     # Each $row has keys: entry (city), statecode, state
  834:     # 'entry' from stnames is never exposed directly.
  835: 
  836:     my $row = $join->fetchrow_hashref(statecode => 'CA');

  838: B<Using add_database instead>
  839: 
  840: If you build the join incrementally with C<add_database>, pass
  841: C<join_column> directly to that call instead of using C<join_map>:
  842: 
  843:     my $join = Database::Join->new(

  851: =head2 filters - permanent per-database row filters
  852: 
  853: C<filters> lets you restrict a component database to a subset of its rows
  854: permanently, without repeating the criterion on every query call.
  855: 
  856: Think of it as telling the join: "whenever you query this database, always
  857: add these extra conditions".  Callers never need to specify the restriction
  858: themselves and can never accidentally omit it.
  859: 
  860: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  861: database in the C<databases> array (same numbering as C<join_map>).  Each
  862: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  863: accepts.
  864: 
  865: B<Key-set semantics>
  866: 
  867: A filtered database always acts as an inner-join partner, regardless of the
  868: C<join_type> setting.  Any join-key value that does not pass the filter is
  869: excluded from the merged output entirely -- not just missing its secondary
  870: columns.  This ensures the filter genuinely restricts the view rather than
  871: simply hiding a few fields.
  872: 
  873: B<Criteria merging>
  874: 
  875: When a query call also passes a criterion for a column that already has a base
  876: filter, the two constraints are combined:
  877: 
  878: =over 4
  879: 
  880: =item *
  881: 
  882: When both the base filter value and the query criterion are operator hashrefs
  883: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are
  884: merged: I<both> constraints apply simultaneously (AND semantics).
  885: 
  886: =item *
  887: 
  888: When either value is a plain scalar, or the operators conflict, the
  889: query-time criterion wins and the base filter for that column is ignored for
  890: that one call.
  891: 
  892: =back
  893:

  895: 
  896:     my $join = Database::Join->new(

  916: =head2 collision_prefix - preserve colliding columns from secondary databases
  917: 
  918: By default, when a column name appears in more than one database the I<last>
  919: database wins: its value silently overwrites earlier ones in merged rows.
  920: This loses data and makes the origin invisible.
  921: 
  922: C<collision_prefix> changes this for secondary databases you designate.
  923: When a secondary database at index N has a column that already exists in the
  924: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  925: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  926: visible: the original column keeps its name (from the earlier database), and
  927: the collision gets the prefixed name.
  928: 
  929: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  930: a secondary database in the C<databases> array (same numbering as C<join_map>).
  931: Each B<value> is the prefix string to prepend.  An index-0 entry is
  932: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  933: preserves the previous last-wins behaviour and changes nothing.
  934: 
  935: Non-colliding columns from a secondary database are always added as-is with
  936: no prefix, whether or not C<collision_prefix> is configured.
  937: 
  938: B<Example -- sales table and products table, both with a "product" column>
  939: 
  940:     # $sales    columns: id, product, amount, date
  941:     # $products columns: sku, product, price, category
  942:     # join on 'product' (left key) matched against 'sku' (right key via join_map)
  943: 
  944:     my $join = Database::Join->new(
  945:         databases        => [$sales, $products],
  946:         join_column      => 'product',
  947:         join_map         => { 1 => 'sku' },
  948:         collision_prefix => { 1 => 'products' },
  949:     );
  950: 
  951:     $join->columns;
  952:     # => ['amount', 'category', 'date', 'id', 'price', 'product', 'products.product']
  953:     #                                                               ^-- prefixed collision
  954: 
  955:     my $row = $join->fetchrow_hashref(product => 'widget');
  956:     # $row->{product}            -- value from $sales
  957:     # $row->{'products.product'} -- value from $products (different row, same column name)
  958:     # $row->{price}              -- from $products, no collision, kept as-is
  959: 
  960: B<Querying on a prefixed column>
  961: 
  962: Use the full published name as the criterion key:
  963: 
  964:     my $rows = $join->selectall_arrayref('products.product' => 'widget');
  965:     # Internally routes as: product => 'widget' to $products
  966: 
  967: B<Interaction with remove_column>
  968: 
  969: C<remove_column> operates on published names.  To suppress a prefixed
  970: collision column entirely, pass the prefixed name:
  971: 
  972:     $join->remove_column('products.product');

  981: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  982:

  988: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file

  992: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
  993: source data size.

  997: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
  998: automatically rebuilt when any source database's C<updated()> timestamp

 1001: details.

 2950: =head1 ENCODING
 2951: 
 2952: All text that passes through C<Database::Join> at the Perl layer (column names,
 2953: criteria values, merged row values) is treated as opaque strings.
 2954: C<Database::Join> does not inspect, encode, or transform string content.
 2955: 
 2956: =over 4
 2957: 
 2958: =item Column names
 2959: 
 2960: Column names are plain ASCII strings as returned by C<Database::Abstraction::columns()>.
 2961: Non-ASCII column names are accepted but not tested; behaviour depends on the
 2962: underlying DA and database driver.
 2963: 
 2964: =item Criteria values and row data
 2965: 
 2966: Values are passed verbatim between callers and component DAs.  Full UTF-8 is
 2967: safe as long as the underlying C<Database::Abstraction> objects and their
 2968: database drivers handle UTF-8 correctly.  C<Database::Join> neither encodes
 2969: nor decodes any value.
 2970: 
 2971: =item SQLite backend
 2972: 
 2973: When the SQLite path is active, values are inserted into the temporary SQLite
 2974: database via DBI placeholders (never string interpolation), so binary-safe
 2975: round-tripping depends on C<DBD::SQLite>'s character encoding settings.
 2976: By default C<DBD::SQLite> operates in UTF-8 mode, which is correct for text
 2977: data.  Binary blobs are not explicitly tested.
 2978: 
 2979: =item i18n messages
 2980: 
 2981: All internal error and warning messages route through the C<i18n> object
 2982: (if one is supplied) via a C<translate($key, @args)> call.  The translation
 2983: dictionary controls the final encoding of those strings.

 3096: =head1 SECURITY CONSIDERATIONS
 3097: 
 3098: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3099: generates SQL strings, never opens files, and never calls C<system()>,
 3100: C<exec()>, or C<eval()>.  The security properties described below are
 3101: architectural guarantees, not run-time checks.
 3102: 
 3103: =head2 What Database::Join guarantees
 3104: 
 3105: =over 4
 3106: 
 3107: =item Criteria partition isolation
 3108: 
 3109: Every criterion you pass to a query method is routed to I<exactly one>
 3110: component database (the one that owns that column), or to I<all> databases
 3111: when the criterion is on the join key column.  A hostile value in a criterion
 3112: for column C<name> (owned by database A) will never reach database B.
 3113: 
 3114: =item Unknown columns are rejected before reaching any database
 3115: 
 3116: If a criterion column name is not present in any component database (or has
 3117: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3118: and silently drops the criterion.  No database receives the hostile key.
 3119: 
 3120: =item AUTOLOAD only accepts word-character column names
 3121: 
 3122: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3123: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3124: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3125: C<_>) are additionally blocked with an explicit C<croak>.
 3126: 
 3127: =item No value sanitisation (by design)
 3128: 
 3129: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3130: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3131: responsibility of the underlying C<Database::Abstraction> objects (which use
 3132: parameterised queries).  Preventing XSS or header injection is the
 3133: responsibility of the CGI or web layer that renders the output.
 3134: 
 3135: =item Taint-mode compatible (array path)
 3136: 
 3137: The array merge path contains no C<system()>, C<exec()>, backtick,
 3138: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3139: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3140: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3141: an I<untainted> capture, so the column name used for dispatch is clean under
 3142: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3143: objects; those objects are responsible for handling tainted values at the SQL
 3144: parameterisation layer.
 3145: 
 3146: =item SQLite backend: column names are quoted, values are parametrised
 3147: 
 3148: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3149: All column and table names are double-quoted (SQL identifier quoting) before
 3150: being embedded in statement strings.  All row values are passed to SQLite
 3151: exclusively through DBI prepared statement placeholders -- never by string
 3152: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3153: into the temporary database.
 3154: 
 3155: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3156: unpredictable filename.  No C<system()> or shell command is used to create or
 3157: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3158: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3159: in the generated SQL come from C<columns()>, which is produced by
 3160: C<Database::Abstraction> at construction time -- they are not derived from
 3161: caller-supplied criteria values.
 3162: 
 3163: =item Operator hashref broadcast copy
 3164: 
 3165: When the same join-key criterion (an operator hashref such as
 3166: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3167: database receives its own I<shallow copy> of the hashref.  A component database
 3168: that mutates the hashref's contents at the top level cannot affect what
 3169: subsequent databases receive.
 3170: 
 3171: =item collision_prefix value type guard
 3172: 
 3173: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3174: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3175: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3176: column name, C<columns()> listing, and merged row returned to the caller.  The
 3177: guard fires before any column name is constructed.
 3178: 
 3179: =item Filter deep-copy isolation
 3180: 
 3181: The C<filters> constructor parameter and the C<filter> option of
 3182: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3183: original hashrefs are never stored; post-construction mutation of those
 3184: hashrefs cannot widen or bypass the configured row-security constraints.
 3185: 
 3186: =back

 3189: 
 3190: =over 4
 3191: 
 3192: =item Sanitise values before building criteria
 3193: 
 3194: DJ passes criterion values verbatim to component databases.  If your

 3208: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
 3209: columns and validates their values.

 3505: =head1 STATE DIAGRAM
 3506: 
 3507: C<Database::Join> objects follow three independent finite state machines (FSMs).
 3508: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 3509: triggers that cause transitions (arrows), and important side-effects.
 3510: 
 3511: =head2 FSM 1: Object Lifecycle
 3512: 
 3513: Governs the structural state of a C<Database::Join> instance.
 3514: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 3515: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 3516: are not shown because they do not change state.
 3517: 
 3518:     [pre-creation]
 3519:          |
 3520:          | new( databases => [...], join_column => '...' )
 3521:          |   Side-effect: _col_db routing table built;
 3522:          |                _autoload_pk cached from dbs[0]{id}
 3523:          v
 3524:     [CONSTRUCTED] <-----------------------------------------+
 3525:          |    |                                              |
 3526:          |    +--------------------------------------------+ |
 3527:          |    (query methods: no structural change)         | |
 3528:          |                                                  | |
 3529:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 3530:          |                                      |    |        |
 3531:          |   Side-effect: col removed from       |    |        |
 3532:          |   _col_db; _col_cache and             +----+        |
 3533:          |   _schema_cache cleared.              (idempotent;  |
 3534:          |   Join column cannot be removed.)      chainable)   |
 3535:          |                                                     |
 3536:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 3537:                                                 |    |
 3538:              Side-effect: new columns added;    |    | add_database( db )
 3539:              _col_db extended; SQLite cache     |    | (chainable; each
 3540:              invalidated (if any).              +----+  extends the view)
 3541: 
 3542:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 3543:     Both transitions are legal on any valid object, in any order.
 3544: 
 3545:     Illegal triggers (always croak; object state is not changed):
 3546: 
 3547:       Trigger                              Error
 3548:       -----------------------------------  ---------------------------------
 3549:       new( databases => [] )               error_no_databases
 3550:       remove_column( join_column )         error_remove_join_column
 3551:       add_database( non-reference )        error_invalid_database
 3552:       new() with join_col absent from DB   error_join_col_absent
