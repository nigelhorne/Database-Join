  142: =head1 DESCRIPTION
  143: 
  144: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  145: single logical, read-only view.  Each component database is queried
  146: independently through its own C<Database::Abstraction> interface.  The results
  147: are combined in Perl memory using a shared key column (C<join_column>).
  148: 
  149: The module exposes the same read-only API as C<Database::Abstraction>:
  150: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  151: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  152: shortcut.  Callers do not need to know how many underlying databases are
  153: involved.
  154: 
  155: Think of it as a virtual database table that is assembled on demand from
  156: several real tables, one per component database.
  157: 
  158: =head2 Join semantics
  159: 
  160: The C<join_type> parameter controls what happens when a particular key value
  161: exists in some component databases but not all:
  162: 
  163: =over 4
  164: 
  165: =item C<left> (the default)
  166: 
  167: All rows from the I<primary> (first) database are returned.  Columns from
  168: subsequent databases are included where a matching row is found, and simply
  169: absent from the hashref where there is no match.  If you are familiar with
  170: SQL, this is a LEFT OUTER JOIN on the first table.
  171: 
  172: =item C<inner>
  173: 
  174: Only rows whose join-column value is present in I<every> component database
  175: are returned.  This is equivalent to a SQL INNER JOIN.
  176: 
  177: =item C<outer>
  178: 
  179: Every join-column value found in I<any> component database is returned.
  180: Columns from databases that do not have that key value are absent from the
  181: merged row.  This is a FULL OUTER JOIN.
  182: 
  183: =back
  184: 
  185: B<Important override rule:> whenever you pass a query criterion for a column
  186: that belongs to a secondary database, that database automatically acts as an
  187: inner-join partner for that query only -- regardless of C<join_type>.  This
  188: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  189: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  190: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  191: as a WHERE clause would exclude them).
  192: 
  193: =head2 Column ownership and routing
  194: 
  195: At construction time, C<Database::Join> calls C<columns()> on each component
  196: database and builds an internal index that maps every column name to the
  197: database that owns it.
  198: 
  199: When you pass criteria to a query method, each key-value pair is automatically
  200: routed to the right database.  You never need to say which database a column
  201: belongs to.
  202: 
  203: The C<join_column> is special: criteria on it are broadcast to I<all>
  204: databases so that each database fetches only the relevant rows before the
  205: in-memory merge.
  206: 
  207: When the same non-join column name exists in more than one database, the
  208: I<last> database in the C<databases> array wins: its value overwrites earlier
  209: ones in merged rows.
  210: 
  211: =head1 LIMITATIONS
  212: 
  213: =over 4
  214: 
  215: =item In-memory join only
  216: 
  217: All matching rows from every component database are fetched into memory before
  218: the merge.  This is not suitable for very large result sets.
  219: 
  220: =item No chained builder or raw SQL
  221: 
  222: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  223: or C<fetchrow_hashref> instead.
  224: 
  225: =item Single-column equi-join only
  226: 
  227: Joining on more than one column simultaneously, or on expressions, is not
  228: supported.  When the join key has different names in different databases,
  229: use C<join_map> to declare each database's local column name.
  230: 
  231: =item Sort order
  232: 
  233: Results are sorted by the C<join_column> value only.  Caller-specified
  234: C<ORDER BY> is not propagated to the component databases.
  235: 
  236: =item count() fetches all rows
  237: 
  238: C<count()> executes the full join and counts the resulting rows in Perl.  It
  239: does not push a C<COUNT(*)> query down to the databases.
  240: 
  241: =back

  243: =head1 COMMON PITFALLS
  244: 
  245: =over 4
  246: 
  247: =item The join_column must exist in every component database
  248: 
  249: If even one database is missing the join key column, C<new()> (or
  250: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  251: column has a different local name in some databases.
  252: 
  253: =item Criteria on a removed column are silently dropped
  254: 
  255: If you call C<remove_column('tier')> and later query
  256: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  257: C<carp> warning) and all rows are returned.  Always pass criteria before
  258: removing columns, or restructure your code to avoid this.
  259: 
  260: =item You cannot remove the join column
  261: 
  262: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  263: is required for the merge to work.
  264: 
  265: =item Left join does not guarantee all columns are populated
  266: 
  267: Under a LEFT join, rows from the primary database that have no matching row
  268: in a secondary database will be returned with I<no keys> from that secondary
  269: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  270: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  271: than just C<$row->{score}> when the secondary match is optional.
  272: 
  273: =item Filters act as inner-join partners
  274: 
  275: Any database that has a C<filters> entry is promoted to an inner-join partner,
  276: regardless of C<join_type>.  A row whose join-key value does not appear in
  277: the filtered database's result is removed from the merged output entirely, not
  278: merely missing its secondary columns.  This is intentional but can be
  279: surprising if you expected LEFT join semantics.
  280: 
  281: =item Criteria-merging replaces scalar filters
  282: 
  283: When both a base filter and a query criterion target the same column, and both
  284: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  285: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  286: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  287: the base filter is ignored for that query.
  288: 
  289: =item AUTOLOAD sees the full merged join when filters or join_map are active
  290: 
  291: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  292: (C<< $join->columnname(...) >>) runs the full join query rather than
  293: delegating directly to the owning database.  This is necessary for correctness
  294: but means the result respects all active filters and join-key translations,
  295: which may differ from what the owning database would return on its own.
  296: 
  297: =item Duplicate column names: last database wins
  298: 
  299: When two component databases each have a column called C<notes>, the second
  300: database's value silently overwrites the first in every merged row.  Use
  301: C<remove_columns> (or C<remove_column>) to drop the unwanted duplicate.
  302: 
  303: =back

  305: =head1 SECURITY CONSIDERATIONS
  306: 
  307: C<Database::Join> is a pure in-memory routing and merge layer.  It never
  308: generates SQL strings, never opens files, and never calls C<system()>,
  309: C<exec()>, or C<eval()>.  The security properties described below are
  310: architectural guarantees, not run-time checks.
  311: 
  312: =head2 What Database::Join guarantees
  313: 
  314: =over 4
  315: 
  316: =item Criteria partition isolation
  317: 
  318: Every criterion you pass to a query method is routed to I<exactly one>
  319: component database (the one that owns that column), or to I<all> databases
  320: when the criterion is on the join key column.  A hostile value in a criterion
  321: for column C<name> (owned by database A) will never reach database B.
  322: 
  323: =item Unknown columns are rejected before reaching any database
  324: 
  325: If a criterion column name is not present in any component database (or has
  326: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
  327: and silently drops the criterion.  No database receives the hostile key.
  328: 
  329: =item AUTOLOAD only accepts word-character column names
  330: 
  331: Perl's method dispatch extracts the column name via C<\w+>, which matches only
  332: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
  333: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
  334: C<_>) are additionally blocked with an explicit C<croak>.
  335: 
  336: =item No value sanitisation (by design)
  337: 
  338: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
  339: I<values> in criteria hashrefs.  Preventing SQL injection is the
  340: responsibility of the underlying C<Database::Abstraction> objects (which use
  341: parameterised queries).  Preventing XSS or header injection is the
  342: responsibility of the CGI or web layer that renders the output.
  343: 
  344: =item Taint-mode compatible
  345: 
  346: C<Database::Join> contains no C<system()>, C<exec()>, backtick, C<open(PIPE)>,
  347: or C<eval STRING> calls.  It neither opens files nor constructs shell commands.
  348: The AUTOLOAD regex C</::(\w+)$/>  produces an I<untainted> capture, so the
  349: column name used for dispatch is clean under C<-T>.  Criteria values are
  350: passed verbatim to component C<Database::Abstraction> objects; those objects
  351: are responsible for handling tainted values at the SQL parameterisation layer.
  352: 
  353: =item Operator hashref aliasing
  354: 
  355: When the same join-key criterion (an operator hashref such as
  356: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, all of
  357: them receive a reference to the I<same> hashref.  A malicious component
  358: database that mutates the hashref's contents could affect what subsequent
  359: databases receive.  Component databases are assumed to be trusted.
  360: 
  361: =back
  362: 
  363: =head2 What the caller is responsible for
  364: 
  365: =over 4
  366: 
  367: =item Sanitise values before building criteria
  368: 
  369: DJ passes criterion values verbatim to component databases.  If your
  370: application accepts user-supplied filter values (e.g. from a CGI query
  371: string), those values I<must> be validated or sanitised by your application
  372: before being passed to DJ.
  373: 
  374: =item Restrict which columns the caller can filter on
  375: 
  376: Any column in C<columns()> can be used as a filter criterion.  If a column
  377: should not be filterable by end users (e.g. an internal status flag), hide it
  378: with C<remove_column> so that queries on it are silently dropped.
  379: 
  380: =item Do not expose the joined view directly to user-supplied criteria
  381: 
  382: DJ is not a firewall.  It faithfully routes user input to component databases.
  383: Wrap DJ calls in a thin service layer that whitelists the permitted criterion
  384: columns and validates their values.
  385: 
  386: =back

  641: =head2 filters - permanent per-database row filters
  642: 
  643: C<filters> lets you restrict a component database to a subset of its rows
  644: permanently, without repeating the criterion on every query call.
  645: 
  646: Think of it as telling the join: "whenever you query this database, always
  647: add these extra conditions".  Callers never need to specify the restriction
  648: themselves and can never accidentally omit it.
  649: 
  650: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  651: database in the C<databases> array (same numbering as C<join_map>).  Each
  652: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  653: accepts.
  654: 
  655: B<Key-set semantics>
  656: 
  657: A filtered database always acts as an inner-join partner, regardless of the
  658: C<join_type> setting.  Any join-key value that does not pass the filter is
  659: excluded from the merged output entirely -- not just missing its secondary
  660: columns.  This ensures the filter genuinely restricts the view rather than
  661: simply hiding a few fields.
  662: 
  663: B<Criteria merging>
  664: 
  665: When a query call also passes a criterion for a column that already has a base
  666: filter, the two constraints are combined:

  668: =over 4
  669: 
  670: =item *

  673: (e.g. C<< { '>' => 60 } >> and C<< { '<' => 365 } >>), their operators are

  676: =item *

  678: When either value is a plain scalar, or the operators conflict, the
  679: query-time criterion wins and the base filter for that column is ignored for

  681: 
  682: =back

  684: B<Example -- only show orders placed more than 60 days ago>

  686:     my $join = Database::Join->new(
