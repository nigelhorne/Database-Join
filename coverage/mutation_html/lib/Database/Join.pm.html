  193: =head1 DESCRIPTION
  194: 
  195: C<Database::Join> merges two or more L<Database::Abstraction> objects into a
  196: single logical, read-only view.  Each component database is queried
  197: independently through its own C<Database::Abstraction> interface.  The results
  198: are combined using a shared key column (C<join_column>).
  199: In effect, this means that you can view data from more than one database using
  200: an intuitive, non-SQL interface.
  201: 
  202: Every storage format that C<Database::Abstraction> supports works as a
  203: component database: CSV, PSV, TSV, SQLite, JSON, XML, XLSX, BerkeleyDB, HTML
  204: URL, JSON URL, or any custom subclass.  Component databases may mix formats
  205: within the same join.
  206: 
  207: The module exposes the same read-only API as C<Database::Abstraction>:
  208: C<selectall_arrayref>, C<selectall_array>, C<fetchrow_hashref>, C<count>,
  209: C<columns>, C<schema>, C<updated>, C<set_logger>, and the AUTOLOAD column
  210: shortcut.  Callers do not need to know how many underlying databases are
  211: involved.
  212: 
  213: Think of it as a virtual database table that is assembled on demand from
  214: several real tables, one per component database.
  215: 
  216: B<Join backends>
  217: 
  218: By default (C<backend =E<gt> 'auto'>), C<Database::Join> first checks the
  219: combined source row count.  For small datasets (up to C<max_array_rows>,
  220: default 10,000 rows) it merges entirely in Perl memory.  For larger datasets it
  221: automatically spills source rows into a temporary SQLite database and executes
  222: a single SQL JOIN there, keeping peak RAM to roughly one times the source data
  223: size instead of three.  You can also force either path unconditionally with
  224: C<backend =E<gt> 'sqlite'> or C<backend =E<gt> 'array'>.
  225: 
  226: =head2 Join semantics
  227: 
  228: The C<join_type> parameter controls what happens when a particular key value
  229: exists in some component databases but not all:
  230: 
  231: =over 4
  232: 
  233: =item C<left> (the default)
  234: 
  235: All rows from the I<primary> (first) database are returned.  Columns from
  236: subsequent databases are included where a matching row is found, and simply
  237: absent from the hashref where there is no match.  If you are familiar with
  238: SQL, this is a LEFT OUTER JOIN on the first table.
  239: 
  240: =item C<inner>
  241: 
  242: Only rows whose join-column value is present in I<every> component database
  243: are returned.  This is equivalent to a SQL INNER JOIN.
  244: 
  245: =item C<outer>
  246: 
  247: Every join-column value found in I<any> component database is returned.
  248: Columns from databases that do not have that key value are absent from the
  249: merged row.  This is a FULL OUTER JOIN.
  250: 
  251: =back
  252: 
  253: B<Important override rule:> whenever you pass a query criterion for a column
  254: that belongs to a secondary database, that database automatically acts as an
  255: inner-join partner for that query only -- regardless of C<join_type>.  This
  256: gives WHERE-clause semantics.  For example, if you have a LEFT join but query
  257: C<< tier => 'gold' >> on a secondary database, only rows whose secondary entry
  258: has tier = 'gold' are returned (rows with no secondary entry are excluded, just
  259: as a WHERE clause would exclude them).
  260: 
  261: =head2 Column ownership and routing
  262: 
  263: At construction time, C<Database::Join> calls C<columns()> on each component
  264: database and builds an internal index that maps every column name to the
  265: database that owns it.
  266: 
  267: When you pass criteria to a query method, each key-value pair is automatically
  268: routed to the right database.  You never need to say which database a column
  269: belongs to.
  270: 
  271: The C<join_column> is special: criteria on it are broadcast to I<all>
  272: databases so that each database fetches only the relevant rows before the
  273: in-memory merge.
  274: 
  275: When the same non-join column name exists in more than one database, the
  276: I<last> database in the C<databases> array wins by default: its value
  277: overwrites earlier ones in merged rows.  Use C<collision_prefix> to
  278: preserve both values under distinct names instead.
  279: 
  280: =head1 LIMITATIONS
  281: 
  282: =over 4
  283: 
  284: =item Memory usage (array backend)
  285: 
  286: When C<backend> is C<'array'> (or C<'auto'> and the dataset is small), all
  287: matching rows are fetched into Perl memory.  Peak RAM is roughly three times
  288: the source data size.  For large datasets use C<backend =E<gt> 'sqlite'>, or
  289: leave C<backend =E<gt> 'auto'> and set C<max_array_rows> appropriately.
  290: 
  291: =item SQLite backend uses a persistent cache file
  292: 
  293: When the SQLite path is active, a single C<.db> file with a randomly generated
  294: name (chosen by C<File::Temp> to avoid collisions) is created in C<tmpdir> the
  295: first time a query runs on a given C<Database::Join> object.  Source data is
  296: spilled into that file once; subsequent queries against the same object reuse
  297: the file without re-fetching the source data.
  298: 
  299: The cache is automatically invalidated and rebuilt whenever any source
  300: database's C<updated()> timestamp changes (indicating new data), or when
  301: C<add_database()> is called.
  302: 
  303: The file is deleted when the C<Database::Join> object is destroyed (typically
  304: when it goes out of scope).  At any given moment no more than one such file
  305: exists per object.  The directory must be writable and have enough free space
  306: for the full source data (once, not per-query).
  307: 
  308: =item No chained builder or raw SQL
  309: 
  310: C<query()> and C<execute()> are not implemented.  Use C<selectall_arrayref>
  311: or C<fetchrow_hashref> instead.
  312: 
  313: =item Single-column equi-join only
  314: 
  315: Joining on more than one column simultaneously, or on expressions, is not
  316: supported.  When the join key has different names in different databases,
  317: use C<join_map> to declare each database's local column name.
  318: 
  319: =item Sort order
  320: 
  321: Results are sorted ascending by C<join_column> by default.  Pass
  322: C<< order_by => 'colname' >> (or C<< order_by => ['colname', 'DESC'] >>)
  323: to any query method to override this.  The array path uses string comparison
  324: (C<cmp>); for accurate numeric ordering on large datasets use the SQLite
  325: backend, which sorts natively by type.
  326: 
  327: =item count() on the array backend fetches all rows
  328: 
  329: On the array backend, C<count()> executes the full in-memory join and counts
  330: the resulting rows in Perl; no C<COUNT(*)> is pushed to the component
  331: databases.  On the SQLite backend, C<count()> executes a C<SELECT COUNT(*)>
  332: SQL query against the cached join tables, avoiding a full row transfer.
  333: 
  334: =back

  336: =head1 COMMON PITFALLS
  337: 
  338: =over 4
  339: 
  340: =item The join_column must exist in every component database
  341: 
  342: If even one database is missing the join key column, C<new()> (or
  343: C<add_database()>) will C<croak> immediately.  Use C<join_map> when the
  344: column has a different local name in some databases.
  345: 
  346: =item Criteria on a removed column are silently dropped
  347: 
  348: If you call C<remove_column('tier')> and later query
  349: C<< selectall_arrayref(tier => 'gold') >>, the criterion is ignored (with a
  350: C<carp> warning) and all rows are returned.  Always pass criteria before
  351: removing columns, or restructure your code to avoid this.
  352: 
  353: =item You cannot remove the join column
  354: 
  355: C<< $join->remove_column($join->join_column) >> will C<croak>.  The join key
  356: is required for the merge to work.
  357: 
  358: =item Left join does not guarantee all columns are populated
  359: 
  360: Under a LEFT join, rows from the primary database that have no matching row
  361: in a secondary database will be returned with I<no keys> from that secondary
  362: database.  Accessing C<< $row->{score} >> on such a row returns C<undef> --
  363: not zero, not an empty string.  Always test C<defined $row->{score}> rather
  364: than just C<$row->{score}> when the secondary match is optional.
  365: 
  366: =item Filters act as inner-join partners
  367: 
  368: Any database that has a C<filters> entry is promoted to an inner-join partner,
  369: regardless of C<join_type>.  A row whose join-key value does not appear in
  370: the filtered database's result is removed from the merged output entirely, not
  371: merely missing its secondary columns.  This is intentional but can be
  372: surprising if you expected LEFT join semantics.
  373: 
  374: =item Criteria-merging replaces scalar filters
  375: 
  376: When both a base filter and a query criterion target the same column, and both
  377: are operator hashrefs (e.g. C<< { '>' => 60 } >>), the operators are combined
  378: (AND semantics).  But if the query criterion is a plain scalar (e.g.
  379: C<< score => 75 >>), it I<replaces> the base filter for that column entirely --
  380: the base filter is ignored for that query.
  381: 
  382: =item AUTOLOAD sees the full merged join when filters or join_map are active
  383: 
  384: When either C<filters> or C<join_map> is in effect, the AUTOLOAD shortcut
  385: (C<< $join->columnname(...) >>) runs the full join query rather than
  386: delegating directly to the owning database.  This is necessary for correctness
  387: but means the result respects all active filters and join-key translations,
  388: which may differ from what the owning database would return on its own.
  389: 
  390: =item Duplicate column names: last database wins (unless collision_prefix is set)
  391: 
  392: When two component databases each have a column called C<notes>, the second
  393: database's value silently overwrites the first in every merged row.  Use
  394: C<collision_prefix => { 1 => 'right' }> to publish the second database's
  395: C<notes> as C<right.notes> so both values survive, or use C<remove_columns>
  396: (or C<remove_column>) to drop the unwanted duplicate entirely.
  397: 
  398: =item Mutating the filters hashref after construction has no effect
  399: 
  400: C<Database::Join> deep-copies the C<filters> hashref (and any C<filter>
  401: passed to C<add_database>) at the moment of construction.  The original hashref
  402: you passed in is never stored.  If you later modify it -- for example, to
  403: tighten or loosen a filter criterion -- the joined view is I<not> affected.
  404: Construct a new C<Database::Join> object, or use a component
  405: C<Database::Abstraction> that supports dynamic filter modification.
  406: 
  407: =item auto mode may always use the array path for some DAs
  408: 
  409: C<backend =E<gt> 'auto'> counts rows cheaply only when each component database
  410: either implements C<dbi_source()> (SQLite-backed) or directly defines a
  411: C<count()> method in its own package.  A DA that merely I<inherits> C<count()>
  412: from C<Database::Abstraction> is treated as uncountable, because the parent
  413: class C<count()> expects a key argument and behaves differently from a
  414: "return total row count" function.  In that case C<Database::Join>
  415: conservatively uses the array path for the whole query, even if the dataset is
  416: large.  To opt in to the SQLite path for such a DA, either add your own
  417: C<count()> override that returns the total row count, implement C<dbi_source()>,
  418: or use C<backend =E<gt> 'sqlite'> unconditionally.
  419: 
  420: =item dbi_source() ATTACH is unconditional - query-time criteria go into WHERE
  421: 
  422: When a component database implements C<dbi_source()>, C<Database::Join> always
  423: uses the zero-copy ATTACH path, I<even when the current query includes criteria
  424: for columns in that database>.  The criteria are translated into parameterised
  425: SQL C<WHERE> clauses applied against the ATTACHed table; no row-level copy is
  426: performed.  (Prior to 0.005.0 the presence of any query-time criteria would
  427: force a spill; that restriction has been removed.)
  428: 
  429: =item Broadcast join-column criterion does not force secondaries into inner-join
  430: 
  431: When a caller passes a join-column criterion (e.g. C<entry =E<gt> 'k1'>),
  432: C<Database::Join> broadcasts it to all component databases so each DA can
  433: filter its fetch to the requested key.  Prior to 0.006.0 this broadcast was
  434: incorrectly counted as "having criteria" for secondary databases, causing
  435: C<left> and C<outer> joins to silently behave as C<inner> joins when a
  436: join-column criterion was present.  The fix: only non-join-column criteria
  437: (e.g. column filters from the caller or base C<filters =E<gt> {...}>) promote
  438: a secondary to inner-join status.  The broadcast itself is now a transparent
  439: key-range selector that does not affect join semantics.
  440: 
  441: =item LIKE and NOT LIKE work on the SQLite path; other pattern operators do not yet
  442: 
  443: C<LIKE>, C<NOT LIKE>, C<IN>, and C<NOT IN> are fully supported on the SQLite
  444: backend.  C<LIKE>/C<NOT LIKE> take a scalar pattern; C<IN>/C<NOT IN> take an
  445: arrayref of values.  All are injection-safe because values are passed as bind
  446: parameters, never interpolated.
  447: 
  448:     # LIKE
  449:     my $rows = $join->selectall_arrayref(name => { LIKE => 'A%' });
  450: 
  451:     # IN
  452:     my $rows = $join->selectall_arrayref(tier => { IN => ['gold', 'silver'] });
  453: 
  454:     # NOT IN
  455:     my $rows = $join->selectall_arrayref(tier => { 'NOT IN' => ['bronze'] });
  456: 
  457: C<IN> with an empty arrayref matches no rows (SQL semantics: C<IN ()> is
  458: always false).  C<NOT IN> with an empty arrayref matches all rows (no
  459: constraint added).
  460: 
  461: C<IS NULL> and C<IS NOT NULL> are supported on the SQLite backend using an
  462: explicit operator hashref:
  463: 
  464:     my $rows = $join->selectall_arrayref(score => { 'IS NULL'     => undef });
  465:     my $rows = $join->selectall_arrayref(score => { 'IS NOT NULL' => 1    });
  466: 
  467: The hashref value is ignored; only the key selects the operator.  A bare
  468: C<undef> criterion value (C<< score => undef >>) also generates C<IS NULL>
  469: on the SQLite path.  Note: on the in-memory array path, the component DA
  470: may treat an C<undef> criterion value as C<< no filter >> rather than
  471: C<IS NULL>, so use the explicit hashref form for consistent behaviour
  472: across backends.
  473: 
  474: Any operator not in the supported set is skipped on the SQLite path with a
  475: C<carp> warning.  The array path forwards all operators to the component DA
  476: unchanged, which may or may not honour them.
  477: 
  478: =item Temp file directory must be writable and have free space
  479: 
  480: The SQLite path creates one temporary C<.db> file per C<Database::Join> object
  481: in C<tmpdir> (default: C<File::Spec-E<gt>tmpdir()>, usually C</tmp> on Unix).
  482: The filename is randomly generated by C<File::Temp> -- you cannot predict it,
  483: only the directory is under your control.  The file is created on the first
  484: query and kept alive until the object is destroyed; it is not re-created on
  485: every query call.  If the directory is not writable, or the filesystem is full,
  486: the call will C<croak> with C<error_sqlite_connect>.  Check permissions and
  487: free space if you see that error.

  801: =head2 join_map - joining on differently-named columns
  802: 
  803: By default every component database must have a column whose name matches
  804: C<join_column>.  If a database uses a different local name for the join key,
  805: declare the mapping with C<join_map>.
  806: 
  807: C<join_map> is a hashref.  Each B<key> is the B<zero-based position> of a
  808: database in the C<databases> array (0 = first, 1 = second, and so on).  Each
  809: B<value> is the name that B<that particular database> uses for the join key.
  810: 
  811: Databases not listed in C<join_map> are assumed to already have a column
  812: named C<join_column> and need no entry.
  813: 
  814: Throughout the merged view the join key is I<always> referred to by the name
  815: given in C<join_column>.  The local alias is never exposed in returned rows,
  816: in C<columns()>, or in C<schema()>.

  818: B<When do you need join_map?>
  819: 
  820: You need C<join_map> when you have two tables like:

  827: that same concept C<entry>, so you declare:

  829:     join_map => { 1 => 'entry' }  # stnames (index 1) calls it 'entry'

  864: =head2 filters - permanent per-database row filters
  865: 
  866: C<filters> lets you restrict a component database to a subset of its rows
  867: permanently, without repeating the criterion on every query call.
  868: 
  869: Think of it as telling the join: "whenever you query this database, always
  870: add these extra conditions".  Callers never need to specify the restriction
  871: themselves and can never accidentally omit it.
  872: 
  873: C<filters> is a hashref.  Each B<key> is the B<zero-based position> of a
  874: database in the C<databases> array (same numbering as C<join_map>).  Each
  875: B<value> is a criteria hashref in the same format as C<selectall_arrayref>
  876: accepts.
  877: 
  878: B<Key-set semantics>
  879: 
  880: A filtered database always acts as an inner-join partner, regardless of the
  881: C<join_type> setting.  Any join-key value that does not pass the filter is
  882: excluded from the merged output entirely -- not just missing its secondary
  883: columns.  This ensures the filter genuinely restricts the view rather than
  884: simply hiding a few fields.
  885: 
  886: B<Criteria merging>
  887: 
  888: When a query call also passes a criterion for a column that already has a base
  889: filter, the two constraints are combined:

  891: =over 4
  892: 
  893: =item *

  897: merged: I<both> constraints apply simultaneously (AND semantics).
  898: 
  899: =item *
  900: 
  901: When either value is a plain scalar, or the operators conflict, the
  902: query-time criterion wins and the base filter for that column is ignored for
  903: that one call.

  905: =back

  929: =head2 collision_prefix - preserve colliding columns from secondary databases
  930: 
  931: By default, when a column name appears in more than one database the I<last>
  932: database wins: its value silently overwrites earlier ones in merged rows.
  933: This loses data and makes the origin invisible.
  934: 
  935: C<collision_prefix> changes this for secondary databases you designate.
  936: When a secondary database at index N has a column that already exists in the
  937: merged view, and C<collision_prefix-E<gt>{N}> is set, the colliding column is
  938: published as C<"$prefix.$col"> instead of overwriting.  Both values are then
  939: visible: the original column keeps its name (from the earlier database), and
  940: the collision gets the prefixed name.
  941: 
  942: C<collision_prefix> is a hashref.  Each B<key> is the B<zero-based index> of
  943: a secondary database in the C<databases> array (same numbering as C<join_map>).
  944: Each B<value> is the prefix string to prepend.  An index-0 entry is
  945: meaningless and silently ignored.  Omitting C<collision_prefix> entirely
  946: preserves the previous last-wins behaviour and changes nothing.
  947: 
  948: Non-colliding columns from a secondary database are always added as-is with
  949: no prefix, whether or not C<collision_prefix> is configured.
  950:

  957:     my $join = Database::Join->new(
  958:         databases        => [$sales, $products],
  959:         join_column      => 'product',
  960:         join_map         => { 1 => 'sku' },
  961:         collision_prefix => { 1 => 'products' },

  987: =head2 backend - SQLite join backend for large datasets
  988: 
  989: C<Database::Join> can merge component databases in two different ways,
  990: controlled by the C<backend> constructor parameter.
  991: 
  992: =over 4
  993: 
  994: =item C<backend =E<gt> 'array'> -- in-memory merge (original behaviour)
  995: 
  996: All matching rows are fetched from every component database into Perl hashes
  997: and merged there.  Simple and fast for small and medium datasets.  Peak RAM
  998: is roughly three times the combined source data size (one copy per database
  999: plus one merged copy).
 1000: 
 1001: =item C<backend =E<gt> 'sqlite'> -- SQL JOIN via a cached temporary file
 1002: 
 1003: C<Database::Join> creates a temporary SQLite database file, spills source
 1004: rows into it (one table per component database), then executes a single SQL
 1005: C<JOIN> statement per query call.  Peak RAM drops to roughly one times the
 1006: source data size.
 1007: 
 1008: The temporary file is created once and reused across multiple query calls on
 1009: the same object (the cache).  Only query-time criteria vary per call; they
 1010: are applied as SQL C<WHERE> clauses against the cached data.  The cache is
 1011: automatically rebuilt when any source database's C<updated()> timestamp
 1012: changes.  The file is deleted when the object is destroyed (goes out of
 1013: scope).  See I<Temporary file: name, location, and lifetime> below for
 1014: details.
 1015: 
 1016: Requires C<DBD::SQLite E<gt>= 1.70> (C<FULL OUTER JOIN> support was added in
 1017: SQLite 3.39.0; DBD::SQLite 1.70 ships SQLite 3.39.2).
 1018: 
 1019: =item C<backend =E<gt> 'auto'> (default)
 1020: 
 1021: C<Database::Join> counts the total rows from all component databases cheaply
 1022: -- without fetching them -- and then decides:
 1023: 
 1024: =over 4
 1025: 
 1026: =item *
 1027: 
 1028: If the combined count is less than or equal to C<max_array_rows> (default
 1029: 10,000), use the array path.
 1030: 
 1031: =item *
 1032: 
 1033: If the combined count exceeds C<max_array_rows>, use the SQLite path.
 1034: 
 1035: =back
 1036: 
 1037: For counting to work without fetching, each component database must either
 1038: implement the C<dbi_source()> interface (for SQLite-backed sources, where a
 1039: C<COUNT(*)> SQL query is issued directly), or directly define a C<count()>
 1040: method in its own package -- not just inherit one from a parent class.  If
 1041: neither is available for a particular database, C<Database::Join> plays it
 1042: safe and uses the array path for the whole query without fetching any rows.
 1043: 
 1044: =back
 1045: 
 1046: B<Choosing max_array_rows>
 1047: 
 1048: The default of 10,000 is a reasonable starting point.  Adjust it to match
 1049: your hardware and typical row width.  For wide rows (many columns or long
 1050: strings) you may want a lower threshold; for narrow rows you can raise it.
 1051: 
 1052: B<Temporary file: name, location, and lifetime>
 1053: 
 1054: When the SQLite path is active, a single temporary SQLite database file acts
 1055: as the join cache for the life of the C<Database::Join> object.
 1056: 
 1057: B<Name>: the filename is randomly generated by C<File::Temp>, for example:
 1058: 
 1059:     /tmp/Cj8xK7mP2Q.db
 1060: 
 1061: The random portion (ten characters) is chosen automatically to avoid
 1062: collisions.  Only the directory is under your control; you cannot specify
 1063: the filename itself.
 1064: 
 1065: B<Location>: controlled by the C<tmpdir> constructor parameter.
 1066: If C<tmpdir> is not specified, C<File::Spec-E<gt>tmpdir()> is used (usually
 1067: C</tmp> on Unix, or the value of the C<TEMP> or C<TMP> environment variable
 1068: on Windows).
 1069: 
 1070: B<Lifetime: one file per object, deleted when the object is destroyed>: the
 1071: file is created on the first query call that uses the SQLite path and kept
 1072: alive until the C<Database::Join> object is destroyed (i.e. when it goes out
 1073: of scope or is explicitly C<undef>-d).  At most one file exists per object at
 1074: any given moment.  Calling C<selectall_arrayref()> ten times on the same
 1075: object creates and uses I<one> file, not ten.
 1076: 
 1077: B<Cache invalidation>: the cache is automatically rebuilt (the old file is
 1078: replaced with a new one) when any source database's C<updated()> return value
 1079: changes, or when C<add_database()> is called.  Base-filter criteria
 1080: (C<filters> constructor parameter) are applied once at build time for spilled
 1081: sources; query-time criteria are applied per-call as SQL C<WHERE> clauses.
 1082: 
 1083: To use a different directory -- for example a RAM-backed filesystem or a
 1084: faster local disk:
 1085: 
 1086:     my $join = Database::Join->new(
 1087:         databases      => [ $db1, $db2 ],
 1088:         join_column    => 'entry',
 1089:         backend        => 'sqlite',
 1090:         tmpdir         => '/dev/shm',     # Linux RAM disk
 1091:     );
 1092: 
 1093: B<Parallel secondary fetches (C<parallel> constructor parameter)>
 1094: 
 1095: By default, component databases are queried sequentially - the primary first,
 1096: then each secondary in order.  When the component databases are network- or
 1097: disk-backed and have non-trivial per-query latency, the sequential fetch means
 1098: total latency is the I<sum> of all per-DA latencies.
 1099: 
 1100: Setting C<< parallel => 1 >> in the constructor enables concurrent fetching
 1101: of secondary databases using Perl C<threads>.  With C<parallel => 1> and
 1102: two or more secondary databases (C<n E<gt> 2> total), secondary fetches run in
 1103: parallel after the primary fetch completes; total latency drops to
 1104: I<max(secondary latencies)> instead of I<sum(secondary latencies)>.
 1105: 
 1106:     my $join = Database::Join->new(
 1107:         databases   => [ $customers, $loyalty, $scores ],   # 3 DAs - 2 secondaries
 1108:         join_column => 'entry',
 1109:         parallel    => 1,    # loyalty and scores fetched concurrently
 1110:     );
 1111: 
 1112: Requirements and caveats:
 1113: 
 1114: =over 4
 1115: 
 1116: =item *
 1117: 
 1118: The C<threads> module must be available.  Most distributions ship it, but it
 1119: requires a Perl binary compiled with C<-Dusethreads>.  When threads are
 1120: unavailable, a C<carp> warning is emitted and fetching falls back to
 1121: sequential; the result is identical, only slower.
 1122: 
 1123: =item *
 1124: 
 1125: Parallel fetching is only active when the join has three or more total
 1126: databases (C<n E<gt> 2>).  With two databases (one secondary), the thread
 1127: creation overhead exceeds the benefit of concurrency; sequential is used
 1128: regardless of C<parallel>.
 1129: 
 1130: =item *
 1131: 
 1132: Component databases must be safe to call from Perl threads.  In-memory
 1133: databases (CSV, JSON, TSV after slurp) are safe.  DBI-backed databases
 1134: whose handles were created in the same thread may not be safe - consult your
 1135: DBD driver's thread documentation.  The array backend is recommended for
 1136: DBI-backed sources; the SQLite backend performs its join in a single SQL
 1137: statement and does not use parallel fetching.
 1138: 
 1139: =item *
 1140: 
 1141: C<parallel => 1> applies to the array backend only.  The SQLite backend
 1142: performs a single SQL JOIN after spilling source data, so per-DA parallelism
 1143: is irrelevant.
 1144: 
 1145: =back
 1146: 
 1147: B<Zero-copy ATTACH (C<dbi_source()> interface)>
 1148: 
 1149: Normally, when the SQLite path is active, rows from each component database
 1150: are fetched one by one and inserted into the temporary SQLite file.  This is
 1151: efficient but does involve INSERT overhead.
 1152: 
 1153: If a component database is itself SQLite-backed and implements a
 1154: C<dbi_source()> method, C<Database::Join> can skip the row-by-row copy
 1155: entirely and instead use C<ATTACH DATABASE> to link the source file directly
 1156: to the temporary join connection.  This is the zero-copy path and is
 1157: significantly faster for large SQLite sources.
 1158: 
 1159: The C<dbi_source()> method must return a hashref with two keys:
 1160: 
 1161: =over 4
 1162: 
 1163: =item C<dbh>
 1164: 
 1165: A connected C<DBD::SQLite> database handle (C<DBI> connection object).
 1166: 
 1167: =item C<table>
 1168: 
 1169: The name of the table in that database that holds the source rows.
 1170: 
 1171: =back
 1172: 
 1173: Example implementation:
 1174: 
 1175:     package My::SQLiteDatabase;
 1176:     use parent 'Database::Abstraction';
 1177: 
 1178:     sub dbi_source {
 1179:         my ($self) = @_;
 1180:         return {
 1181:             dbh   => $self->{_dbh},      # connected DBD::SQLite handle
 1182:             table => $self->{_table},    # table name in that database
 1183:         };
 1184:     }
 1185: 
 1186:     1;
 1187: 
 1188: The zero-copy ATTACH path is always used when a component database implements
 1189: C<dbi_source()>.  Query-time criteria are applied as parameterised SQL
 1190: C<WHERE> clauses against the ATTACHed source table, so no row-level copy is
 1191: needed even when the current call includes column filters.  (Prior to 0.005.0
 1192: any query-time criteria forced a spill; that restriction was removed in
 1193: 0.005.0.)
 1194: 
 1195: B<Result identity>
 1196: 
 1197: Both the array path and the SQLite path produce identical results for any
 1198: given query.  You can switch between them freely without changing callers.
 1199: The C<collision_prefix> column renaming, C<join_map> key translation, and all
 1200: three join types (left, inner, outer) work identically on both paths.

 3697: =head1 SECURITY CONSIDERATIONS
 3698: 
 3699: C<Database::Join> is a pure in-memory routing and merge layer.  It never
 3700: generates SQL strings, never opens files, and never calls C<system()>,
 3701: C<exec()>, or C<eval()>.  The security properties described below are
 3702: architectural guarantees, not run-time checks.
 3703: 
 3704: =head2 What Database::Join guarantees
 3705: 
 3706: =over 4
 3707: 
 3708: =item Criteria partition isolation
 3709: 
 3710: Every criterion you pass to a query method is routed to I<exactly one>
 3711: component database (the one that owns that column), or to I<all> databases
 3712: when the criterion is on the join key column.  A hostile value in a criterion
 3713: for column C<name> (owned by database A) will never reach database B.
 3714: 
 3715: =item Unknown columns are rejected before reaching any database
 3716: 
 3717: If a criterion column name is not present in any component database (or has
 3718: been hidden with C<remove_column>), C<Database::Join> logs a C<carp> warning
 3719: and silently drops the criterion.  No database receives the hostile key.
 3720: 
 3721: =item AUTOLOAD only accepts word-character column names
 3722: 
 3723: Perl's method dispatch extracts the column name via C<\w+>, which matches only
 3724: C<[A-Za-z0-9_]>.  Hostile method names with shell metacharacters, quotes, or
 3725: spaces cannot reach the AUTOLOAD dispatch path.  Private names (starting with
 3726: C<_>) are additionally blocked with an explicit C<croak>.
 3727: 
 3728: =item No value sanitisation (by design)
 3729: 
 3730: C<Database::Join> does I<not> sanitise, HTML-encode, or validate the
 3731: I<values> in criteria hashrefs.  Preventing SQL injection is the
 3732: responsibility of the underlying C<Database::Abstraction> objects (which use
 3733: parameterised queries).  Preventing XSS or header injection is the
 3734: responsibility of the CGI or web layer that renders the output.
 3735: 
 3736: =item Taint-mode compatible (array path)
 3737: 
 3738: The array merge path contains no C<system()>, C<exec()>, backtick,
 3739: C<open(PIPE)>, or C<eval STRING> calls.  It neither opens files nor constructs
 3740: shell commands.  The AUTOLOAD regex C</ :: (\w++) \z /x> uses a possessive
 3741: quantifier (C<\w++>) and a strict end-of-string anchor (C<\z>) and produces
 3742: an I<untainted> capture, so the column name used for dispatch is clean under
 3743: C<-T>.  Criteria values are passed verbatim to component C<Database::Abstraction>
 3744: objects; those objects are responsible for handling tainted values at the SQL
 3745: parameterisation layer.
 3746: 
 3747: =item SQLite backend: column names are quoted, values are parametrised
 3748: 
 3749: When the SQLite path is active, C<Database::Join> generates SQL internally.
 3750: All column and table names are double-quoted (SQL identifier quoting) before
 3751: being embedded in statement strings.  All row values are passed to SQLite
 3752: exclusively through DBI prepared statement placeholders -- never by string
 3753: interpolation.  A hostile value in a source row therefore cannot inject SQL
 3754: into the temporary database.
 3755: 
 3756: The temporary SQLite file is created by C<File::Temp> using a securely random,
 3757: unpredictable filename.  No C<system()> or shell command is used to create or
 3758: remove it.  The connection is made with C<DBI-E<gt>connect(..., { RaiseError =E<gt> 1,
 3759: PrintError =E<gt> 0 })> and is closed before the method returns.  Column names
 3760: in the generated SQL come from C<columns()>, which is produced by
 3761: C<Database::Abstraction> at construction time -- they are not derived from
 3762: caller-supplied criteria values.
 3763: 
 3764: =item Operator hashref broadcast copy
 3765: 
 3766: When the same join-key criterion (an operator hashref such as
 3767: C<< { '>' => 'A' } >>) is broadcast to multiple component databases, each
 3768: database receives its own I<shallow copy> of the hashref.  A component database
 3769: that mutates the hashref's contents at the top level cannot affect what
 3770: subsequent databases receive.
 3771: 
 3772: =item collision_prefix value type guard
 3773: 
 3774: C<_build_col_index> rejects any C<collision_prefix> value that is a reference
 3775: (hashref, arrayref, coderef, etc.) with an immediate C<croak>.  A reference
 3776: value would stringify to C<"HASH(0x...)">, leaking a heap address into every
 3777: column name, C<columns()> listing, and merged row returned to the caller.  The
 3778: guard fires before any column name is constructed.
 3779: 
 3780: =item Filter deep-copy isolation
 3781: 
 3782: The C<filters> constructor parameter and the C<filter> option of
 3783: C<add_database()> are I<deep-copied> at the point of use.  The caller's
 3784: original hashrefs are never stored; post-construction mutation of those
 3785: hashrefs cannot widen or bypass the configured row-security constraints.
 3786: 
 3787: =back

 3791: =over 4
 3792:

 4106: =head1 STATE DIAGRAM
 4107: 
 4108: C<Database::Join> objects follow three independent finite state machines (FSMs).
 4109: Each FSM is described with an ASCII diagram showing valid states (boxes), the
 4110: triggers that cause transitions (arrows), and important side-effects.
 4111: 
 4112: =head2 FSM 1: Object Lifecycle
 4113: 
 4114: Governs the structural state of a C<Database::Join> instance.
 4115: Query methods (C<selectall_arrayref>, C<fetchrow_hashref>, C<count>,
 4116: C<columns>, C<schema>, C<updated>) are schema-preserving (Xi-transitions) and
 4117: are not shown because they do not change state.
 4118: 
 4119:     [pre-creation]
 4120:          |
 4121:          | new( databases => [...], join_column => '...' )
 4122:          |   Side-effect: _col_db routing table built;
 4123:          |                _autoload_pk cached from dbs[0]{id}
 4124:          v
 4125:     [CONSTRUCTED] <-----------------------------------------+
 4126:          |    |                                              |
 4127:          |    +--------------------------------------------+ |
 4128:          |    (query methods: no structural change)         | |
 4129:          |                                                  | |
 4130:          |-- remove_column( col ) -------> [COL_REMOVED] <--+ |
 4131:          |                                      |    |        |
 4132:          |   Side-effect: col removed from       |    |        |
 4133:          |   _col_db; _col_cache and             +----+        |
 4134:          |   _schema_cache cleared.              (idempotent;  |
 4135:          |   Join column cannot be removed.)      chainable)   |
 4136:          |                                                     |
 4137:          +-- add_database( db ) ----------> [DB_ADDED] <------+
 4138:                                                 |    |
 4139:              Side-effect: new columns added;    |    | add_database( db )
 4140:              _col_db extended; SQLite cache     |    | (chainable; each
 4141:              invalidated (if any).              +----+  extends the view)
 4142: 
 4143:     Note: COL_REMOVED and DB_ADDED are not mutually exclusive.
 4144:     Both transitions are legal on any valid object, in any order.

 4156: 
 4157: Governs the temporary SQLite cache used by the C<backend='sqlite'> and

 4159: query on the SQLite path.

 4161:     [ABSENT] <----- add_database( db )
